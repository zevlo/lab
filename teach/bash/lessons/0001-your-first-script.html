Bash for DevOps · Lesson 0001

From Commands to a Script

≈ 12 minutes · one win: a script you built, ran, and checked · glossary · cheatsheet

Why this matters

Your mission is to automate DevOps work. Automation starts at one moment: commands you type by hand become a file you can run, share, and put in a pipeline. That file is a script. Make one today, and every later lesson improves it.

The one idea

A script is a text file of commands, run from top to bottom. That is the whole magic. There is no second language hiding inside bash — the commands you already know (date, df, echo) are the same ones inside a script. [1]

Build your first script

We will build a small but genuinely useful tool: a quick server health check. Follow the steps in your terminal. Type them; do not paste the whole block blindly.

  1. Make a practice folder and enter it: 
    mkdir -p ~/lab
cd ~/lab
  2. Create the file with any editor you like (nano healthcheck.sh works everywhere) and give it exactly these lines: 
    #!/usr/bin/env bash
# healthcheck.sh — quick server vitals
echo "=== health check ==="
date
df -h /
echo "=== done ==="

    Line by line:

    LineJob
    #!/usr/bin/env bashThe shebang. It names the program that runs this file: bash. [1]
    # healthcheck.sh …A comment, for humans. Bash ignores everything after #.
    echo, date, df Commands you already know, one per line, run in order.
  3. Grant execute permission: 
    chmod +x healthcheck.sh

    A new file is just text. This marks it as a runnable program.

  4. Run it: 
    ./healthcheck.sh

    Expected output looks like this (your values will differ):

    === health check ===
Wed Sep 10 09:14:03 CEST 2026
Filesystem      Size   Used  Avail Capacity  Mounted on
/dev/disk3s1s1  460Gi  189Gi  258Gi    43%     /
=== done ===

Prove it worked. Run:

./healthcheck.sh && echo "PASS"

You should see PASS. Every command leaves behind an exit status — 0 for success. && runs the next command only when the first one succeeded. CI pipelines are built on this idea.

The two ways to run a script

You typeWhat happens
./healthcheck.shThe system runs the file as a program. The shebang picks bash. Needs chmod +x.
bash healthcheck.shYou start bash yourself and hand it the file. Runs even without chmod +x.

Why the ./? The shell finds bare names like ls only by searching the folders listed in PATH. Your ~/lab folder is not on that list, so ./ shows the shell exactly where the file is. [1]

Error you will seeCauseFix
command not foundYou typed healthcheck.sh without ./ Type ./healthcheck.sh
Permission deniedNo execute permission chmod +x healthcheck.sh

Check yourself

Answer from memory — this is practice for recalling it at work, not recognition. Wrong answers are fine; try again.

1 · What does the shebang line do?

2 · ./deploy.sh prints “Permission denied”. What fixes it?

3 · Why does the shell find ls without a path, but not healthcheck.sh?

4 · bash healthcheck.sh runs even without execute permission. Why?

Practice on your own work

  1. Extend it: add uptime as a new line inside healthcheck.sh, anywhere between the two echo lines. Run it again. Your feedback: the output must contain load average (on Linux: load average appears at the end; on macOS it prints three load numbers).
  2. Break it on purpose: remove the shebang line, run it, then put it back. What still works, and what changed? (Hint: try it both with ./ and with bash.)
  3. Get your script checked: paste it into shellcheck.net — or install it with brew install shellcheck and run shellcheck healthcheck.sh. The goal now is simply to have met your checker; it will start mattering from the next lesson on.
