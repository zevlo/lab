Bash for DevOps · Lesson 0003

Scripts That Take Orders

≈ 14 minutes · one win: ./diskcheck.sh /any/path — no editing, plus a guard that fails loudly and correctly · ← lesson 0002 · glossary

Why this matters

Your diskcheck.sh works, but changing the target means editing the file. Real tools do not work that way — you never edit ls to list a different folder; you hand it an argument. Today your script becomes a tool: it takes orders at run time, and it refuses to run blind when it gets none. That refusal — a usage message and a failing exit status — is the habit that separates trusted DevOps scripts from dangerous ones.

The one idea

Words after the script name are handed to the script, numbered from 1. Bash stores them for you:

You runInside the script
./diskcheck.sh /var /tmp $1 is /var · $2 is /tmp · $# is 2 · $0 is ./diskcheck.sh

Bash calls $1, $2, … positional parameters; $0 is the script's own name; $# counts the arguments [1]. One familiar rule applies unchanged from last lesson: quote them — "$1" — because arguments are text, and text can contain spaces.

Take an argument

  1. Replace the hardcoded line. In ~/lab/diskcheck.sh, change one line — target="/" becomes: 
    target="$1"
    Nothing else changes. Your script now reads: 
    #!/usr/bin/env bash
# diskcheck.sh — check free space on a path you give
target="$1"
echo "=== disk check: $target ==="
df -h "$target"
  2. Run it with orders: 
    ./diskcheck.sh /
./diskcheck.sh "$HOME/lab"
    Two different checks, zero edits. The script is now a tool.
  3. Now break it: run ./diskcheck.sh with no argument: 
    df: : No such file or directory
    A confusing error with nothing pointing at the real cause. Worse: whoever runs this in a pipeline sees it fail for a mystery reason. A good tool refuses to run blind — and says why.

The guard: your first if

Add these four lines above target="$1" — you already know why above: the script runs top to bottom, and a guard only protects if it runs first:

if [ $# -eq 0 ]; then
  echo "usage: $0 /path/to/check" >&2
  exit 1
fi

Reading it piece by piece:

PartJob
if [ $# -eq 0 ] A condition: is the argument count zero? [ … ] is a test command; -eq means "equal". Full test syntax is next lesson — this one pattern is enough today.
echo … >&2 Send the message to stderr, the error channel, where pipelines and logs expect problems to appear [2].
exit 1 Stop immediately, leaving exit status 1 — failure. Anything that called your script (CI, another script, &&) sees the failure and reacts. Success would be exit 0.
$0 The script's own name in the message — it stays correct even if the file gets renamed.

Prove the guard with your own hands:

./diskcheck.sh
usage: ./diskcheck.sh /path/to/check
echo $?
1   ← the failure was reported honestly
./diskcheck.sh /
=== disk check: / === …
echo $?
0   ← and so was the success

That number is how your script will talk to CI pipelines, cron jobs, and other scripts for the rest of your career.

Practice on your own work

  1. Guard and verify. Add the guard to diskcheck.sh, then run the four commands in the callout above. Your feedback: echo $? prints exactly 1 after the empty run and 0 after the good run.
  2. Use it like a tool. Check three different paths without opening the file: /, "$HOME/lab", and any other folder you care about at work.
  3. Transfer the pattern. From scratch, write peek.sh — shows the last 15 lines of any file: the shebang, the same guard, then tail -n 15 "$1". Test it on ./peek.sh /etc/hosts. Same skeleton, new tool — that skeleton is the shape of thousands of real DevOps scripts.
