Variables and Quoting

≈ 14 minutes · one win: a reusable script — and you personally witness the bug that breaks most beginner scripts · ← lesson 0001 · glossary

Why this matters

Last time you turned commands into a script. Today the script stops being hardcoded: one variable, and the same file checks any disk on any server. But variables come with a trap — quoting — and it is the single most common bug in bash. You will trigger it, see it fail, and fix it. After today, you will spot it in every script you read.

The one idea

name=value stores text; $name pastes it back. Two rules make assignments work:

RuleRightWrong — what bash does instead
No spaces around = target="/var/log" target = "/var/log" — bash runs a command named target [1]
No $ when storing target="/var/log" $target=/var/log — bash reads an old value first [1]

Read the value back with a dollar sign — bash calls this expansion:

# try it right in your terminal
target="/var/log"
echo "checking: $target"

Make your script reusable

  1. Create diskcheck.sh in ~/lab: 
    #!/usr/bin/env bash
# diskcheck.sh — check free space on one path
target="/"
echo "=== disk check: $target ==="
df -h "$target"
  2. Run it: chmod +x diskcheck.sh once, then ./diskcheck.sh.
  3. Reuse it: change the one line to target="$HOME/lab" and run again. Same script, different job. This is the whole point of a variable: store once, point anywhere.

The trap: watch the spaces disappear

Unquoted expansions get re-split into words; quoted ones stay whole. Run this in your terminal and look carefully:

note="backup   plan   v2"
echo $note
backup plan v2          ← extra spaces: gone
echo "$note"
backup   plan   v2      ← exactly as stored

What happened? Bash pasted the value into the command, then — because there were no quotes — cut it into words at the spaces. That cut is called word splitting. With "$note" the value arrives as one piece, untouched.

Missing spaces look harmless. Missing files are worse. Run this:

touch "my notes.txt"
file="my notes.txt"
ls $file
ls: my: No such file or directory
ls: notes.txt: No such file or directory
ls "$file"
my notes.txt

One pair of quotes is the difference between a bug report and a working script. ShellCheck has a warning code for exactly this — SC2086, the most common warning in all of bash [2]. From today, your habit: quote every expansion: "$name" [3].

Two kinds of quotes

You writeBash printsWhy
echo "disk full on $target" disk full on / Double quotes: variables expand
echo 'disk full on $target' disk full on $target Single quotes: everything is literal [4]

Rule of thumb: double quotes let variables in; single quotes keep text exactly as typed. One more form you will meet in real scripts: braces ${target} — the explicit way to write an expansion, needed when gluing text onto a name, as in "${target}_report.txt". Braces are not quotes — you still need the double quotes around them.

Practice on your own work

  1. Trigger the bug on purpose. Edit diskcheck.sh: remove the quotes around "$target" on the df line. Create a path with a space in it — mkdir -p "$HOME/lab/my stuff" — set target="$HOME/lab/my stuff", and run. Watch it fail. Put the quotes back; watch it pass. You have now personally met SC2086.
  2. Run the checker. Paste the broken version into shellcheck.net (or shellcheck diskcheck.sh). Find SC2086 in its output and read its explanation. Fix until ShellCheck is silent — make that your definition of “done” from now on.
  3. Stretch (optional): add a second variable to healthcheck.sh from last lesson — label="web server 1" — and print it in the header: echo "=== health check: $label ===".
