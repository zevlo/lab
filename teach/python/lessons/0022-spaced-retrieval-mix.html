The four pieces on the bench

Same idea as the assembly lesson, but the pieces are older. Each one is something you have already milled:

  1. Lists + loops — for x in things: iteration, line.split() returning a list, indexing into it.
  2. Dictionaries — {} literal, .get(key, default) for safe lookup, .items() for iterating pairs.
  3. Reading files — with open(...) as f:, for line in f:, .strip(), .split().
  4. Capstone shape — try: around the open, specific except FileNotFoundError:, exit nonzero on failure.

No piece here is new. The lesson is just seeing them next to each other in one file, mixed.

Read the mixed file

Here is the whole script. Each line is tagged with the piece it exercises — the same labels from the bench above:

counts = {}                                              # — (2) dict literal

try:                                                     # — (4) capstone guard
    with open("app.log") as f:                           # — (3) files
        for line in f:                                   # — (1) loop over iterable
            level = line.split()[0]                      # — (1) list index after split
            counts[level] = counts.get(level, 0) + 1     # — (2) safe increment
except FileNotFoundError:
    print("error: app.log not found")
    raise SystemExit(1)

for level, n in counts.items():                          # — (1) + (2) loop over pairs
    print(f"{level}: {n}")

Read it top to bottom. counts starts empty. The try wraps the whole file operation so a missing file does not crash the script with a traceback — the same shape you used in your count_errors.py and the capstone. Inside the loop, line.split()[0] grabs the first word of each line (the log level). The line counts[level] = counts.get(level, 0) + 1 is the idiomatic Python increment-or-insert: read the current count as 0 if missing, add one, write it back. After the file is done, a second loop prints each level and its count. Two loops, two roles — one builds, one reports.

Why two loops instead of one

You might be tempted to print inside the first loop. Resist it. Splitting count from report is the small but real interview discipline that lets you:

  • sort the output before printing (for level, n in sorted(counts.items()):);
  • print only levels above a threshold (if n > 2);
  • reuse counts somewhere else later in the script.

The tally loop answers how many. The report loop answers what to show the human. Keeping them separate is a habit worth having.

Build the data first. Print the data second. Two loops, two jobs.

The one trap to remember

Two weeks cold is exactly long enough for this gotcha to bite again: writing counts[level] on the left of an assignment when the key is not yet in the dict. Compare:

counts[level] = counts.get(level, 0) + 1     # ok: .get() supplies 0 if missing
counts[level] = counts[level] + 1             # KeyError on first sight of `level`

The left-hand counts[level] = is fine — assignment creates the key. The right-hand counts[level] lookup is the one that explodes on a missing key. Use .get() on the right side whenever a missing key is expected, not exceptional. Same rule as Lesson 3.

Now type it for real

From memory, create tally_log.py in exercises/. Use the mixed file above as your guide, then close it and type your own. The data file app.log already exists in exercises/ — do not modify it. Required shape:

  1. Start with an empty dict: counts = {}.
  2. Wrap a with open("app.log") as f: block in a try: / except FileNotFoundError:. In the except, print error: app.log not found and raise SystemExit(1).
  3. Inside the with block, loop over lines. For each line, take level = line.split()[0] and update the dict with counts[level] = counts.get(level, 0) + 1.
  4. After the try/except, loop for level, n in counts.items(): and print(f"{level}: {n}").
  5. Run it from exercises/:
python3 tally_log.py

Expected output (the file has 3 INFO lines and 2 ERROR lines; dict insertion order puts INFO first because it appears first in the file):

INFO: 3
ERROR: 2

Then — the failure-path check — temporarily rename app.log to app.log.bak, re-run python3 tally_log.py, and confirm you see exactly error: app.log not found and a nonzero exit (echo $? right after should print 1). Rename the file back. That is the capstone guard doing its job.
