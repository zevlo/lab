Dictionaries

The data structure behind every config file, API response, and inventory you'll ever script against.

Recall first

From memory, before reading on: how do you get the number of items in a list called servers? And what does servers[-1] give you? Answer both, then check the reference if unsure.

The one idea

A list answers "what's item number 3?" A dictionary answers "what's the value for this name?" It stores key: value pairs — hostname to status, config key to setting, container to image. Most real DevOps data is shaped like this, which is why JSON (coming in a later lesson) maps directly onto dicts.

status = {"web01": "up", "web02": "up", "db01": "down"}

status["web01"]        # "up"    — look up by key
status["db01"] = "up"  # overwrite an existing value
status["cache01"] = "up"   # same syntax adds a NEW key
len(status)            # 4 pairs now
"web02" in status      # True — checks keys, not values

Two things to notice. Curly braces and colons build it. And lookup uses square brackets like lists do — but with a name inside instead of a position.

The missing-key problem

Look up a key that isn't there and Python raises a KeyError — the dict cousin of the TypeError you met in Lesson 1:

status["web09"]                  # 💥 KeyError: 'web09'
status.get("web09")              # None — no crash
status.get("web09", "unknown")   # "unknown" — your chosen fallback

Rule of thumb: use [...] when the key must exist (a missing key is a real bug and should crash loudly), and .get() when absence is normal — like an optional setting in a config.

Looping over a dict

The .items() method hands you each pair, and the for loop takes two variables — one for the key, one for the value:

for host, state in status.items():
    print(f"{host}: {state}")
web01: up
web02: up
db01: down

Need only one side? status.keys() and status.values() exist, and a plain for h in status: loops over keys.
