Assemble a Host Check Tool

The four parts on the bench

Think of these as four blocks you have already milled. Today you stack them:

  1. The class — a Host blueprint with __init__ (stores data) and summary (reads that data).
  2. The argv guard — check len(sys.argv) before indexing; exit cleanly if missing.
  3. The main() function — wires argv to the class, then prints.
  4. The entry guard — if __name__ == "__main__": so importing the file does not run the CLI.

No piece here is new. The lesson is just seeing them next to each other in one file.

Read the assembled file

Here is the whole script. Each block is tagged with the piece it is — the same labels from the bench above:

import sys                                              # stdlib: argv

class Host:                                             # — (1) the class
    def __init__(self, name, status):
        self.name = name
        self.status = status

    def summary(self):
        return f"{self.name}: {self.status}"

def main():                                             # — (3) main()
    if len(sys.argv) < 3:                               # — (2) argv guard
        print("usage: host_check.py <name> <status>")
        raise SystemExit(1)
    host = Host(sys.argv[1], sys.argv[2])
    print(host.summary())

if __name__ == "__main__":                              # — (4) entry guard
    main()

Read it top to bottom. The class lives at the top so main() (defined below it) can use it. The entry guard sits at the very bottom — the last line of the file — because its only job is to call main() when the file is run directly. Official note on this layout: the Python tutorial puts the if __name__ == "__main__" block at the end of the module so importable definitions sit above it (__main__ — Top-level code environment).

Why the pieces stay separate

Splitting the file this way pays off the moment someone imports it:

from host_check import Host
print(Host("db-01", "down").summary())   # db-01: down

The class is reusable on its own. The usage: message and the exit only fire when you run the file — never when you import it. That is the whole point of the entry guard.

Same file, two modes: run it as a CLI, or import it as a library. The guard is the switch.

The one trap to remember

Last lesson you hit a small snag: calling a method without parentheses. It is worth seeing the difference side by side one more time, because it bites everyone:

host = Host("web-01", "up")

print(host.summary())   # web-01: up   ← the RETURNED string
print(host.summary)     # <bound method ...>  ← the method OBJECT

Add the parentheses to call the method. Leave them off and you are just reading the method as a value — like pointing at a function instead of running it. The rule is the same one you already know for print itself: print is the function, print() calls it.

Now type it for real

From memory, create host_check.py in exercises/. Use the assembled file above as your guide, then close it and type your own. Required shape:

  1. import sys.
  2. Define class Host with __init__(self, name, status) storing self.name and self.status, plus a summary(self) method that returns f"{self.name}: {self.status}".
  3. Define main(): if len(sys.argv) < 3, print usage: host_check.py <name> <status> and raise SystemExit(1); otherwise build host = Host(sys.argv[1], sys.argv[2]) and print(host.summary()).
  4. End the file with the entry guard calling main().
  5. Run these three checks from exercises/:
python3 host_check.py
python3 host_check.py web-01 up
python3 -c "from host_check import Host; print(Host('db-01', 'down').summary())"

Expected output:

usage: host_check.py <name> <status>
web-01: up
db-01: down

Then — the gotcha check — add one more line to main() before the existing print: print(host.summary) (no parentheses). Re-run python3 host_check.py web-01 up and confirm the first line is a <bound method Host.summary of ...> object, then web-01: up. Once you have seen it, delete that line. That visual is the vaccine against the call-vs-reference bug.
