Troubleshooting Workflow

Quick reference — SCOPE → STATUS → EVENTS → LOGS → RELATED.

The funnel

When something breaks, run the same five steps every time. Do not skip to logs until you know whether a container ever started.

SCOPE   → Am I looking at the right cluster and namespace?
STATUS  → What does kubectl get say? (pods, deploy, endpoints)
EVENTS  → kubectl describe … → Events section (bottom)
LOGS    → kubectl logs … (add --previous if it crashed)
RELATED → Upstream/downstream: PVC, Service selector, Ingress, quota

Scope commands

kubectl config current-context
kubectl get ns
kubectl get pods -n <ns>
kubectl get pods -A | grep <name>

Core commands

kubectl get pods -o wide
kubectl describe pod <pod>
kubectl logs <pod> [-c <container>] [--previous]
kubectl get endpointslice -l kubernetes.io/service-name=<svc>
# get endpoints <svc> — deprecated v1.33+; still works with warning
kubectl get events --sort-by='.lastTimestamp'
kubectl rollout status deployment/<name>
kubectl get rs

Deploy incidents (after apply/upgrade)

kubectl rollout status deployment/<name>   # stuck or progressing?
kubectl get rs                              # old vs new ReplicaSet
kubectl describe pod <failing-pod>        # then logs if CrashLoopBackOff

rollout undo recovers fast; production durable fix is usually revert the manifest in Git and apply.

Golden rule: if the container never started, there are no application logs — answer is in describe Events. If it started then crashed, describe shows exit code; logs on the crashing pod shows error text.
