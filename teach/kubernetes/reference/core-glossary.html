Kubernetes Core Glossary

Reference — the working vocabulary for this workspace. Definitions track the official glossary.

Terms are grouped the way the system is layered: the machinery first, then the objects you declare, then the words used to talk about both.

The Machinery

Cluster
A set of worker machines (nodes) running containerized applications, managed by a control plane. Every cluster has at least one node. [glossary]
Node
A worker machine (VM or physical) in the cluster. Runs the kubelet and a container runtime, and hosts Pods. [docs]
Control plane
The container-orchestration layer that exposes the API and makes global decisions about the cluster. Comprises the API server, etcd, the scheduler, and controller managers. [docs]
API server (kube-apiserver)
The front door. Every read and write of cluster state — from you, from controllers, from kubelets — goes through it. Nothing talks to etcd directly except the API server. [docs]
etcd
Consistent, highly-available key-value store holding all cluster data — including every object's desired state. The cluster's memory. [docs]
Scheduler (kube-scheduler)
Watches for newly created Pods with no assigned node, and picks a node for each based on resources, constraints, and policies. It assigns; the kubelet runs. [docs]
Controller
A control loop that watches the shared state through the API server and makes changes attempting to move current state toward desired state. The central mechanism of Kubernetes. [docs]
kubelet
The agent on each node. Ensures the containers described in PodSpecs assigned to its node are running and healthy. [docs]

The Objects You Declare

Pod
The smallest deployable unit: one or more containers sharing network and storage, always scheduled together onto one node. Pods are ephemeral — they are replaced, not healed. [docs]
Deployment
Declares a desired state for a set of identical Pods (image, replica count, update strategy). The Deployment controller manages a ReplicaSet to make it so, including rolling updates. [docs]
ReplicaSet
Maintains a stable set of replica Pods running at any given time. Usually owned by a Deployment — you rarely create one directly. [docs]
Service
A stable network endpoint (name + virtual IP) for a set of Pods selected by labels. Pods come and go; the Service name endures. [docs]
Namespace
A scope boundary inside one cluster. Most workload objects (Pod, Deployment, Service, ConfigMap, Secret) live in a namespace; names are unique within it, not cluster-wide. Cluster-scoped objects (Node, StorageClass, Namespace itself) have no namespace. Services resolve by short DNS name only within the same namespace — cross-namespace needs FQDN (<svc>.<ns>.svc.cluster.local). [docs] · [patterns]
Context
A named entry in kubeconfig binding a cluster, user credentials, and optional default namespace. kubectl uses the current context when you omit -n. Switch with kubectl config use-context; set default namespace with kubectl config set-context --current --namespace=…. [docs] · [patterns]
kubeconfig
The client configuration file (usually ~/.kube/config) listing clusters, users, and contexts. Not necessarily named "kubeconfig" — any file can serve. OrbStack ships kubectl and merges cluster config into your kubeconfig. [docs]

Rollouts

Rollout
What happens when you change a Deployment's pod template (image, env, etc.): the controller creates a new ReplicaSet and gradually shifts replica counts from old to new. Driven by the same reconciliation as everything else. [docs]
Revision
A rollout checkpoint you can return to. Under the hood it is simply an old ReplicaSet kept at zero replicas — kubectl rollout undo just scales it back up. [docs]
RollingUpdate / maxSurge / maxUnavailable
The default update strategy and its two knobs: maxSurge — how many extra pods may exist above the desired count during the update; maxUnavailable — how many may be missing. Both default to 25%. Together they guarantee capacity during a rollout. [docs]
ImagePullBackOff
Pod status meaning the kubelet cannot pull the container image (bad tag, missing registry credentials, network) and is retrying with increasing delays. Container never started — no logs. Diagnose with kubectl describe pod → Events. [docs] · [workflow]
CrashLoopBackOff
Pod status meaning the container started, exited with an error, and the kubelet is restarting it with increasing backoff. RESTARTS climbs. Diagnose with kubectl logs <pod> --previous for the crash output; describe for probe failures or OOMKilled. [docs] · [workflow]
CreateContainerConfigError
Pod status meaning the kubelet cannot create the container because configuration is invalid or missing — e.g. configMapKeyRef / secretKeyRef pointing at a non-existent object, or a volume mount the node cannot satisfy. Container never started. Diagnose with kubectl describe pod → Events naming the missing ref. [docs] · [workflow]

Troubleshooting

Troubleshooting workflow (SCOPE → STATUS → EVENTS → LOGS → RELATED)
Repeatable incident funnel: confirm cluster/namespace (SCOPE), read kubectl get STATUS columns (STATUS), inspect Events via describe (EVENTS), read container output only if a container ran (LOGS), then check bindings — PVC, endpoints, Ingress, quota (RELATED). Golden rule: no container start → no logs; answer is in Events. [reference] · [docs]

Configuration

ConfigMap
Stores non-confidential configuration as key-value pairs (or multi-line file content). Pods consume via env vars or volume mounts. Decouples settings from container images. Not for secrets — no encryption. [docs] · [patterns]
Secret
Like a ConfigMap but intended for confidential data (passwords, tokens, keys). Same consumption patterns. Values are base64-encoded in etcd by default — not encrypted unless encryption at rest is enabled. RBAC and external secret stores are production essentials. [docs] · [patterns]
Env var vs volume mount
Env vars (configMapKeyRef, secretKeyRef, envFrom) are frozen at container start — config changes require pod restart. Volume mounts update files in place on the kubelet sync cycle (except subPath mounts). Choose based on whether the app needs live reload. [docs]

Health & Probes

Readiness probe
Asks: "can this pod take traffic right now?" While failing, the pod is removed from its Services' EndpointSlices — quarantined, not restarted. Also gates rollouts: a new pod that never becomes Ready stalls the rollout. May legitimately check dependencies (DB, cache). [docs]
Liveness probe
Asks: "is this container beyond saving?" While failing past the threshold, the kubelet restarts the container. Must test only the container itself — never dependencies — or an external outage becomes a cluster-wide restart storm. [docs]
Startup probe
Protects slow-starting containers: liveness and readiness checks are suspended until the startup probe first succeeds. Use instead of long initialDelaySeconds. [docs]
Probe mechanics
Three check types: httpGet (2xx/3xx = pass), tcpSocket (connect = pass), exec (exit 0 = pass). Timing knobs: periodSeconds (how often), failureThreshold (consecutive failures before acting), initialDelaySeconds (grace before first check). [docs]

Resources

Resource request
The amount of CPU or memory a container asks to reserve when scheduled. The scheduler sums requests across pods on a node and only places a new pod where allocatable − allocated ≥ this pod's requests. Does not throttle runtime usage by itself. [docs] · [patterns]
Resource limit
The maximum CPU or memory a container may consume at runtime, enforced by the kubelet via cgroups. CPU over limit → throttled (compressible). Memory over limit → OOMKilled (incompressible). [docs] · [patterns]
QoS class
Quality of Service tier assigned automatically from requests/limits: Guaranteed (limit = request for all containers' CPU and memory), Burstable (some resources set), BestEffort (none set). Influences eviction order under node memory pressure. [docs]
OOMKilled
Container terminated because it exceeded its memory limit (or the node ran out of memory). Exit code 137. Diagnose with kubectl describe pod → Last State: Terminated, Reason: OOMKilled. Not the same as a liveness restart — the cgroup hard-stopped the process. [docs]
Allocatable
Resources on a node available for pods after the system reserves CPU/memory for OS and Kubernetes daemons. What the scheduler compares against when honoring requests. kubectl describe node → Allocatable and Allocated resources. [docs]
ResourceQuota
Namespace-level cap on aggregate resource consumption — the sum of pod requests/limits (and optionally object counts) across the namespace. Enforced at admission; exceeding spec.hard rejects new pods with 403 Forbidden or leaves ReplicaSets in FailedCreate. Does not change already-running pods. When quota covers cpu or memory, new pods must declare requests or limits for that resource (use LimitRange defaults). [docs] · [patterns]
LimitRange
Namespace policy constraining each pod or container: default / defaultRequest injected when resources are omitted; min / max reject out-of-range values at admission. Pairs with ResourceQuota so teams need not set resources on every manifest. Does not retroactively change running pods. [docs] · [patterns]

Scaling

Horizontal Pod Autoscaler (HPA)
Controller that adjusts a workload's spec.replicas from metrics — typically CPU or memory utilization via metrics-server. Targets a scale reference (usually a Deployment). CPU utilization = usage ÷ CPU request; pods without CPU requests produce <unknown> metrics. Bounded by minReplicas / maxReplicas; does not bypass ResourceQuota or node allocatable. Reconciles over manual kubectl scale. [docs] · [patterns]
metrics-server
Cluster add-on that aggregates resource usage from kubelets and exposes the metrics.k8s.io API. Powers kubectl top and resource-based HPA. Not a long-term metrics store — for dashboards use Prometheus or similar. On OrbStack you may need to install it and enable the PodAndContainerStatsFromCRI kubelet feature gate. [project] · [patterns]

Service Networking

ClusterIP
The default Service type: a stable virtual IP reachable only from inside the cluster. The workhorse for service-to-service traffic. [docs]
NodePort
A Service type that additionally opens a fixed port (default range 30000–32767) on every node, forwarding to the Service. A blunt but simple way in from outside. [docs]
LoadBalancer
A Service type that asks the environment for an external load balancer (cloud LB in the cloud; on OrbStack, services are reachable at *.k8s.orb.local from your Mac). Builds on NodePort. [docs]
EndpointSlice
The live, system-maintained list of pod IPs currently backing a Service — the answer to the selector's query, updated as pods come and go. [docs]
kube-proxy
Runs on each node and programs the packet rules that make a Service's virtual IP actually route to a backend pod. You never talk to it; it makes ClusterIPs work. [docs]
Cluster DNS (CoreDNS)
An in-cluster DNS server that gives every Service a name: <service> within the same namespace, <service>.<namespace>.svc.cluster.local in full. Pods use names, not IPs. [docs]
port / targetPort / nodePort
Three different ports in a Service spec: port — what the Service exposes to clients; targetPort — what the container actually listens on; nodePort — the per-node port (NodePort/LoadBalancer types only). [docs]
Ingress
An API object holding HTTP(S) routing rules — "requests for this host/path go to that Service." Pure data: it does nothing without an Ingress controller to act on it. [docs]
Ingress controller
The reverse proxy that watches Ingress objects and configures itself to enforce them — the control loop applied to HTTP routing. Must be installed separately on most clusters, including OrbStack (e.g. Traefik via Helm). [docs]
IngressClass / ingressClassName
Names which controller should handle a given Ingress (a cluster can run several). On OrbStack: traefik. [docs]
Ingress TLS / TLS termination
HTTPS at the Ingress controller: client→controller is encrypted; controller→Service→Pod is typically plaintext. Cert stored in a kubernetes.io/tls Secret (tls.crt, tls.key), referenced by spec.tls.secretName. tls.hosts must match rules.host for SNI. Secret must be in the same namespace as the Ingress. [docs] · [patterns]
NetworkPolicy
Namespace-scoped firewall rules for pod network traffic. spec.podSelector chooses which pods are protected; ingress[].from / egress[].to declare allowed peers. Default is permit-all until a policy selects a pod for a direction — then only explicit allows pass. Orthogonal to Services (routing vs permission). Enforced by the CNI / policy controller (kube-router on OrbStack/k3s). [docs] · [patterns]

The Vocabulary

Desired state
What you have told the cluster you want, recorded in each object's spec. Kubernetes works continuously — not once — to make reality match it. [docs]
spec / status
Two halves of nearly every object. spec: the state you want (you write it). status: the state it actually has (the system writes it). The gap between them is what controllers exist to close. [docs]
Manifest
A YAML (or JSON) file specifying the desired state of one or more objects. Applying a manifest = declaring intent. [glossary]
Declarative vs imperative
Declarative: state what you want (kubectl apply -f app.yaml) and let controllers figure out how. Imperative: issue direct commands (kubectl run, kubectl scale). Production work is declarative. [docs]
Label / selector
Labels are key/value pairs attached to objects; selectors query them. This is how Deployments find their Pods and Services find their backends — loose coupling by query, not by reference. [docs]
Reconciliation
The act of a controller comparing desired state with observed state and taking action to close the gap. Endless, automatic, level-triggered. [docs]
kubectl
The command-line client for the Kubernetes API. Everything it does is an API call to the API server. [quick reference]
Dry-run (--dry-run=client / server)
Simulate an operation without persisting (or, for client, without contacting the server at all). --dry-run=client -o yaml scaffolds manifest structure locally; apply --dry-run=server validates against API admission without writing. [docs] · [patterns]
kubectl diff
Compares a manifest file's desired spec against live cluster state and prints a unified diff. Safe preview before apply; also surfaces what would change on upgrade. Works with rendered Kustomize output via kubectl diff -k. [docs] · [patterns]

Manifest Tooling

Kustomize
Built-in manifest customization: a base directory of resources plus overlay directories that patch or transform them (namespace, namePrefix, replicas, images, strategic-merge patches). No template language — output is plain YAML applied with kubectl apply -k. Patch targets use base resource names before transforms. [docs] · [patterns]
Kustomize base
The shared manifest skeleton (base/kustomization.yaml + resource YAML). Environment-agnostic — holds the canonical Deployment, Service, etc. Overlays reference it rather than duplicating files. [patterns]
Kustomize overlay
An environment-specific kustomization.yaml that lists resources: [../../base] plus transformers and patches. Example: staging gets lower replicas and a different image tag; production references the same base with different deltas. [patterns]
Helm
Kubernetes package manager: installs charts as named releases, tracks revision history, supports rollback. Renders Go templates with values.yaml overrides, then applies manifests to the API — same declarative end state as kubectl apply. [docs] · [patterns]
Helm chart
A package of Kubernetes templates (templates/), default values (values.yaml), and metadata (Chart.yaml). Can be a local directory, a tarball, or fetched from a chart repository. One chart can be installed many times as separate releases. [docs] · [patterns]
Helm release
A named, installed instance of a chart in a cluster (e.g. release metrics-server from chart metrics-server/metrics-server). Each install, upgrade, or rollback increments the release revision. Removed with helm uninstall. [docs] · [patterns]
Helm values (values.yaml)
Default parameters for a chart, overridden at install/upgrade via -f files or --set. Templates reference them as {{ .Values.field }}. Inspect live values with helm get values RELEASE. [docs] · [patterns]

Storage

PersistentVolume (PV)
Cluster-scoped representation of a storage resource — a chunk of NFS, a cloud disk, a hostPath directory. Created manually or dynamically by a provisioner. Bound to exactly one PVC at a time. [docs] · [patterns]
PersistentVolumeClaim (PVC)
Namespace-scoped request for storage: size, access mode, optional StorageClass. Pods mount PVCs via volumes.persistentVolumeClaim. Survives pod deletion — new pods reattach the same claim. [docs] · [patterns]
StorageClass
Cluster-scoped template for dynamic provisioning — names a provisioner (e.g. rancher.io/local-path), reclaim policy (Delete/Retain), and volume binding mode (Immediate or WaitForFirstConsumer). PVCs reference it via storageClassName. [docs] · [patterns]
Access mode (RWO / ROX / RWX)
How many nodes may mount a volume simultaneously. ReadWriteOnce (RWO) — one node read/write, typical for databases. PVC access mode must match the bound PV. [docs] · [patterns]
emptyDir
Ephemeral pod volume — created when the pod is scheduled, deleted when the pod is removed. Good for scratch space; not durable storage. Contrast with PVC. [docs] · [patterns]

Stateful Workloads

StatefulSet
Controller for stateful apps: stable pod names (app-0, app-1), ordered scale-up/down, and volumeClaimTemplates that provision one PVC per ordinal. Requires a headless Service matching spec.serviceName. Deleting pod app-0 recreates app-0 with the same PVC — unlike a Deployment. [docs] · [patterns]
Headless Service
A Service with clusterIP: None — no virtual IP, DNS returns individual pod A records. Enables stable per-pod hostnames like db-0.db.namespace.svc.cluster.local for StatefulSet members. [docs] · [patterns]
volumeClaimTemplate
A PVC spec embedded in a StatefulSet. The controller creates claims named <templateName>-<statefulsetName>-<ordinal> (e.g. data-db-0). Each pod mounts only its own claim. [docs] · [patterns]
