Resource Requests & Limits

Quick reference — scheduling promises vs runtime ceilings.

Two numbers, two jobs

FieldWho reads itEffect
requestsSchedulerMinimum reserved for placement — pod lands only on a node with enough allocatable after subtracting other pods' requests
limitskubelet / cgroupHard ceiling at runtime — enforced on the container process

Manifest shape

containers:
- name: app
  image: nginx:1.29
  resources:
    requests:
      cpu: "100m"      # 0.1 core
      memory: "128Mi"
    limits:
      cpu: "500m"
      memory: "256Mi"

Units

ResourceUnitExample
CPUCores or millicores1 = one core, 100m = 0.1 core, 500m = half a core
MemoryBinary SI (powers of 1024)128Mi, 1Gi — not MB/GB

CPU vs memory when exceeded

ResourceOver limit?Symptom
CPUThrottled (compressible)Slower; rarely killed. kubectl top may still show usage near limit
MemoryOOMKilled (incompressible)Container exit 137; pod may CrashLoopBackOff. describe pod → Reason: OOMKilled

QoS classes

ClassConditionEviction order (roughly)
GuaranteedEvery container: limit = request for CPU and memory (both set)Last evicted under memory pressure
BurstableAt least one request or limit set; not all GuaranteedMiddle
BestEffortNo requests or limits on any containerFirst evicted

See kubectl get pod -o jsonpath='{.status.qosClass}'.

Diagnostics

SymptomLikely causeCheck
Pending + Insufficient cpu/memoryRequests exceed node allocatablekubectl describe pod Events; kubectl describe node Allocated resources
OOMKilled / exit 137Memory limit too low for workloadkubectl describe pod Last State; raise limit or fix leak
Slow under load, not crashingCPU throttling at limitkubectl top pod; compare to limits.cpu
Node healthy, pod never schedulesImpossible request (e.g. 999 CPU on one node)Events on pod; sum requests vs node capacity

Useful commands

kubectl describe node                          # Allocatable + Allocated resources
kubectl describe pod <name>                    # OOMKilled, FailedScheduling events
kubectl top pod                                # needs metrics-server
kubectl get pod -o wide                        # STATUS, RESTARTS
Homelab note: on a single-node OrbStack cluster, one pod with huge requests blocks itself — there is nowhere else to schedule. At work, the same manifest might land on a bigger node; the diagnostic flow is identical.
