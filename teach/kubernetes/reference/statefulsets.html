StatefulSets

Quick reference — stable names, ordered rollout, PVC per pod.

What it is

A StatefulSet manages pods that need stable identity and stable storage. Pod names are predictable (web-0, web-1); each ordinal gets its own PVC from volumeClaimTemplates. Contrast with a Deployment, which treats pods as interchangeable.

Deployment vs StatefulSet

DeploymentStatefulSet
Pod namesRandom suffix (web-7d4f9-abc12)Stable ordinal (web-0, web-1)
StorageUsually shared PVC or nonevolumeClaimTemplates → one PVC per pod
Scale orderParallelSequential (0, then 1, then 2…)
DNSService load-balances to any podHeadless Service → per-pod DNS
Typical useStateless APIsDatabases, queues, clustered apps

Required pieces

Headless Service          StatefulSet
clusterIP: None     +     serviceName: <same name>
                          volumeClaimTemplates: …

Headless Service

apiVersion: v1
kind: Service
metadata:
  name: db
spec:
  clusterIP: None          # required for per-pod DNS
  selector:
    app: db
  ports:
  - port: 80

DNS: db-0.db.ss-lab.svc.cluster.local resolves to pod db-0's IP.

volumeClaimTemplates

Template name data + StatefulSet name db + ordinal 0 → PVC data-db-0. Scale to 2 → auto-creates data-db-1.

volumeClaimTemplates:
- metadata:
    name: data
  spec:
    accessModes: [ReadWriteOnce]
    storageClassName: local-path
    resources:
      requests:
        storage: 1Gi

Commands

kubectl get statefulset,pod,pvc -n NS
kubectl delete pod db-0 -n NS          # controller recreates db-0, same PVC
kubectl scale statefulset/db --replicas=2 -n NS
kubectl delete statefulset db -n NS     # pods go; PVCs often remain

Rule of thumb: if the app cares which pod it is or which disk it owns, use a StatefulSet — not a Deployment with a shared PVC.
