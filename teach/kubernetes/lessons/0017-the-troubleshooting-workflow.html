The Troubleshooting Workflow

One repeatable funnel for every incident — pod, service, or rollout.

Sixteen lessons taught you what objects do. At work and in the homelab, the real skill is diagnosing why reality diverged from the manifest — under pressure, often at 2am. This lesson formalizes the workflow scattered across prior labs into a single reflex: SCOPE → STATUS → EVENTS → LOGS → RELATED. The next few lessons in this arc drill each layer deeper.

The Idea

The official debugging guide starts with triage: what kind of problem is this? [debug pods] Pods, Services, and rollouts each have different failure modes — but the inspection order is the same.

SCOPE   → right cluster? right namespace?
STATUS  → kubectl get — what does the STATUS column say?
EVENTS  → kubectl describe → Events (bottom of output)
LOGS    → kubectl logs (only if a container actually ran)
RELATED → check the binding: PVC, endpoints, Ingress, quota

Most junior mistakes come from skipping steps or using the wrong tool:

MistakeWhy it fails
kubectl logs on a Pending podContainer never started — no logs exist
describe the Service when pods are ImagePullBackOffService is fine; the pod is broken
Restarting pods when endpoints are emptySelector typo — new pods won't help
Debugging in default when the app is in stagingWrong scope — lesson 0007
Golden rule: read the STATUS column before choosing a tool. ImagePullBackOff and Pending → Events in describe. CrashLoopBackOff → container ran and died → describe shows exit code; logs on the crashing pod shows the error text.

Status vocabulary

These appear in kubectl get pods. They tell you where in the lifecycle things broke [docs]:

STATUSMeaningFirst move
PendingNot scheduled yet (or waiting on volumes)describe pod → scheduler / PVC events
ImagePullBackOffCannot pull imagedescribe pod → tag typo, registry auth
CreateContainerConfigErrorMissing Secret/ConfigMap or bad mountdescribe pod → which ref is missing
CrashLoopBackOffStarted, crashed, kubelet backing offdescribe → exit code; logs on crashing pod
Running but no trafficContainer alive; app or routing wronglogs, then EndpointSlice / endpoints check

Lab — Four breaks, one workflow (~25 min)

OrbStack, context orbstack. Lab files in yaml/debug-lab/:

cd ~/projects/teach/kubernetes/yaml/debug-lab
ls

Expect web.yaml, web-bad-image.yaml, web-bad-config.yaml, web-crash.yaml, web-bad-selector.yaml. For each break: run the funnel yourself before reading the fix.

0

SCOPE — confirm cluster, then pin namespace.

kubectl config current-context
kubectl get nodes
kubectl apply -f web.yaml
kubectl config set-context --current --namespace=debug-lab

Expect orbstack. Namespace created; all following commands omit -n because the context default is debug-lab.

1

Verify healthy app.

kubectl get pods,svc
kubectl port-forward svc/web 8080:80 &
curl -s localhost:8080 | head -n 3

Expect pod Running, 1/1 Ready. curl returns nginx HTML. Kill port-forward when done (fg then Ctrl-C, or kill %1).

2

Break A — bad image tag. Break via manifest (production-shaped):

kubectl apply -f web-bad-image.yaml
kubectl get pods -w

Expect STATUS → ImagePullBackOff or ErrImagePull. Your turn: run describe, read Events — bad tag or "not found".

kubectl describe pod -l app=web | tail -n 15

Fix — restore working manifest:

kubectl apply -f web.yaml
3

Break B — missing ConfigMap.

kubectl apply -f web-bad-config.yaml
kubectl get pods

Expect CreateContainerConfigError or ContainerCreating stuck. describe Events should name missing-config. No useful logs — container never started.

kubectl describe pod -l app=web | grep -A2 -i configmap

Fix:

kubectl apply -f web.yaml
4

Break C — crash on startup. Changing the Deployment starts a rollout (lesson 0004):

kubectl apply -f web-crash.yaml
kubectl get pods

Expect a pod in CrashLoopBackOff, RESTARTS climbing. You may briefly see two pods — old healthy + new crashing — while the rollout stalls. Triage:

kubectl rollout status deployment/web
kubectl get rs

describe on the crashing pod — Last State: Terminated, Exit Code: 1. That is that it died; not the error message.

kubectl describe pod -l app=web | grep -A5 "Last State:"

Logs — copy the NAME of the pod in CrashLoopBackOff from get pods, then:

kubectl logs web-XXXXXXXXXX-XXXXX

Expect boom if logs are available. On OrbStack, --previous may fail on fast exits — plain logs on the crashing pod is fine. If two pods exist, do not use logs deployment/web — it may pick the healthy one.

Fix:

kubectl apply -f web.yaml
5

Break D — Running pods, no traffic. Break via manifest — wrong Service selector (lesson 0010):

kubectl apply -f web-bad-selector.yaml
kubectl get pods
kubectl get endpointslice -l kubernetes.io/service-name=web

Red flag: pods are Running 1/1 but the EndpointSlice has no ready addresses (empty endpoints list). That mismatch — healthy pods, dead routing — means look at the Service selector vs pod labels, not the pods themselves. (kubectl get endpoints web still works but prints a deprecation warning on Kubernetes v1.33+; EndpointSlice is the replacement.)

kubectl get svc web -o yaml | grep -A3 selector
kubectl get pods --show-labels

Selector says app: web-broken; pod labels say app: web — no match, so no backends.

Fix — restore selector in web.yaml (or re-apply it):

kubectl apply -f web.yaml

EndpointSlice repopulates with the pod IP; port-forward + curl works again.

6

Clean up.

kubectl delete namespace debug-lab
kubectl config set-context --current --namespace=default
DevOps habit: write the STATUS column in your incident notes before touching anything. It picks the tool. "Restarted pod three times" without checking STATUS is how you burn an hour on a selector typo.

Quiz

1. Pod STATUS is Pending for five minutes. Teammate suggests kubectl logs. Best response?

2. STATUS ImagePullBackOff. Where is the root cause most likely written?

3. All pods Running 1/1; Service curl fails. First RELATED-layer check?

4. STATUS CrashLoopBackOff, RESTARTS at six. Most useful next command?

5. You run kubectl get pods — empty. Teammate sees Running pods. SCOPE step?
