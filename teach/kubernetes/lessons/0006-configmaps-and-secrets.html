Lesson 0006 · Kubernetes Fundamentals

ConfigMaps & Secrets: Configuration Separate from Images

Same image everywhere; different config per environment.

Lessons 0004–0005 taught you to ship and heal code. But if your database URL lives in the Dockerfile, every environment change means a rebuild — and every secret in git is a resume-generating event. At work, ConfigMaps and Secrets are how dev, staging, and prod run the same image tag with different settings. In the homelab, they're how you tweak a service at midnight without rebuilding a container.

Quick re-anchor from lesson 0005: readiness controls membership (am I in the Service?), liveness controls existence (do I get restarted?) — quarantine vs. defibrillator. Liveness must never check dependencies.

The Idea

Two API objects hold configuration outside your container image [ConfigMap docs] [Secret docs]:

ObjectHoldsNot for
ConfigMapNon-confidential settings — log levels, config files, HTML templatesPasswords or tokens (use Secret)
SecretConfidential data — API keys, passwords, TLS keysReplacing real encryption (base64 ≠ secure)

Pods consume them two main ways, and the choice matters because updates behave differently:

MechanismHowWhen ConfigMap/Secret changes…
Environment variableenv[].valueFrom.configMapKeyRef or secretKeyRefValue is frozen at pod start. Need a restart (kubectl rollout restart) or new pods.
Volume mountvolumes[].configMap + volumeMountsFiles update in place on the kubelet's sync cycle — no restart. (Exception: subPath mounts do not update.)

Mechanically, both are just key-value objects in etcd. A ConfigMap has a data: map; a Secret has data: (base64) or stringData: (plain text at apply time). The Pod spec references them — same loose-coupling pattern as label selectors.

The mental model in one line: ConfigMaps and Secrets are configuration objects pods point at — not baked into the image — and how you point (env vs volume) decides whether changes propagate live.

Changing a ConfigMap alone does not trigger a Deployment rollout — only changes inside spec.template do (lesson 0004). That's a feature for volume-mounted config files; it's a footgun for env vars.

Lab — Configure, Break, Fix (~25 min)

Against OrbStack. You'll build on the nginx web workload from lesson 0005, externalizing its homepage and a banner env var.

1

Create web-config.yaml — four documents in one file:

apiVersion: v1
kind: ConfigMap
metadata:
  name: web-content
data:
  index.html: |
    <!DOCTYPE html><html><body>
    <h1>Lesson 0006 — ConfigMap mount</h1>
    </body></html>
  SITE_BANNER: "v1-banner"
---
apiVersion: v1
kind: Secret
metadata:
  name: web-secret
type: Opaque
stringData:
  MAINT_TOKEN: homelab-secret-token
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.29
        env:
        - name: SITE_BANNER
          valueFrom:
            configMapKeyRef:
              name: web-content
              key: SITE_BANNER
        - name: MAINT_TOKEN
          valueFrom:
            secretKeyRef:
              name: web-secret
              key: MAINT_TOKEN
        readinessProbe:
          httpGet: { path: /, port: 80 }
          periodSeconds: 2
        volumeMounts:
        - name: html
          mountPath: /usr/share/nginx/html
          readOnly: true
      volumes:
      - name: html
        configMap:
          name: web-content
          items:
          - key: index.html
            path: index.html
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
  - port: 80

Apply and verify the ConfigMap drove the page content:

kubectl config use-context orbstack
kubectl apply -f web-config.yaml
kubectl get pods
kubectl port-forward svc/web 8080:80   # terminal 2

In a browser or with curl: curl -s localhost:8080. Also peek inside a pod:

kubectl exec deploy/web -- printenv SITE_BANNER MAINT_TOKEN
kubectl exec deploy/web -- cat /usr/share/nginx/html/index.html

Expect: custom HTML (not nginx default welcome page), SITE_BANNER=v1-banner, and the secret token visible as plain text in the env — Secrets hide values from casual kubectl get, not from anyone who can exec into the pod.

2

Live config via volume. Edit the ConfigMap — change the heading text in index.html — and apply:

kubectl apply -f web-config.yaml

Without restarting anything, re-read the file and re-curl (may take up to ~60 seconds for the kubelet to sync):

kubectl exec deploy/web -- cat /usr/share/nginx/html/index.html
curl -s localhost:8080

Expect: file content and HTTP response update without a rollout. Pod names unchanged. This is why apps read config from mounted files when they need hot reload.

3

Frozen config via env var. Change SITE_BANNER in the ConfigMap to v2-banner and apply again. Check the env var:

kubectl exec deploy/web -- printenv SITE_BANNER

Expect: still v1-banner. Env vars are captured at container start. Now restart:

kubectl rollout restart deployment/web
kubectl rollout status deployment/web
kubectl exec deploy/web -- printenv SITE_BANNER

Expect: v2-banner. A config-only change didn't trigger this — you had to ask for new pods explicitly.

4

Break it. First, start watching pods in terminal 2 — you'll need this view, not the browser:

kubectl get pods -l app=web -w

Now edit web-config.yaml. In the Deployment only — inside the SITE_BANNER env var's configMapKeyRef block — change key: SITE_BANNER to key: SITE_BANNERR. Do not rename SITE_BANNER in the ConfigMap data: section; leave that as-is.

kubectl apply -f web-config.yaml

Now check three layers — pods, rollout, and (optionally) HTTP:

kubectl get pods -l app=web
kubectl get rs -l app=web
curl -s localhost:8080 | head -3   # optional — may still work!

Pick the pod in CreateContainerConfigError (name will differ from the healthy ones) and read its events:

kubectl describe pod <broken-pod-name>

If curl still works, the break still worked. That's containment — same pattern as lesson 0004's bad image tag. Old pods keep serving while new ones never start: expect one or more pods in CreateContainerConfigError, events like couldn't find key SITE_BANNERR in ConfigMap web-content, kubectl rollout status deployment/web hanging, and a new ReplicaSet stuck at 0 ready while the previous RS still holds healthy replicas. The failure is in pod status, not in the HTTP response.

5

Fix it. Restore key: SITE_BANNER, apply, and confirm recovery:

kubectl apply -f web-config.yaml
kubectl rollout status deployment/web
kubectl get pods

Expect: all pods 1/1 Running again. Also inspect how "secret" the Secret really is:

kubectl get secret web-secret -o yaml

Expect: MAINT_TOKEN shown as base64 in data: — encoding, not encryption. Anyone with namespace read access can decode it.

6

Clean up:

kubectl delete -f web-config.yaml
Production habits this lab doesn't cover yet: RBAC limiting who reads Secrets, encryption at rest in etcd, external secret managers (Vault, AWS Secrets Manager), and marking ConfigMaps immutable: true to prevent accidental edits. Know they exist; we'll touch RBAC and namespaces soon.
