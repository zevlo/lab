Services & the Networking Model

How traffic finds pods that won't sit still.

In lesson 0001 you killed a pod and the control loop replaced it — with a different name and a different IP. That creates the problem this lesson solves: if backends are constantly replaced, what do you point your app (or your browser, in the homelab) at? Get this layer right and you can wire any set of workloads together — at work or on your own cluster.

The Idea

A Service is a stable address for an unstable set of pods [docs]. It has three moving parts:

  • A label selector — a live query, not a list. The Service doesn't know pod names; it asks, continuously, "which pods currently carry the label app=hello?" The system keeps the answer in an EndpointSlice, updated as pods come and go. This is the control loop again, applied to networking.
  • A stable virtual IP (the ClusterIP) — allocated once, never changes for the life of the Service. kube-proxy programs every node so traffic to that IP gets routed to one of the current backend pods.
  • A DNS name — cluster DNS gives every Service a name. From the same namespace, plain hello works; the full form is hello.default.svc.cluster.local [docs]. In practice, apps talk to names and never see an IP at all.

Two ports matter in every Service spec, and confusing them is the classic beginner bug [docs]:

FieldMeaning
portWhat the Service exposes — what clients connect to.
targetPortWhat the container actually listens on. The Service forwards here.

Finally, Services come in types, each building on the last [docs]:

TypeReachable fromUse for
ClusterIPInside the cluster onlyService-to-service traffic (the default, and most Services)
NodePortAny node's IP, on a high port (30000–32767)Quick external access without extra machinery
LoadBalancerAn external IP from the environmentReal external traffic. In the cloud: a cloud LB. On OrbStack: services are reachable at *.k8s.orb.local from your Mac — which is exactly what your lab uses below.
The mental model in one line: pods are found by query (labels), reached by name (DNS), and the system maintains the plumbing in between — continuously, like everything else in Kubernetes.

Lab — Wire It Up and Break It (~15 min)

Against your OrbStack cluster, two terminals again.

1

Confirm the cluster, then recreate our deployment:

kubectl config use-context orbstack
kubectl create deployment hello --image=nginx --replicas=3
2

See the problem first-hand. List pod IPs, then kill one:

kubectl get pods -o wide          # note each pod's IP column
kubectl delete pod <one-of-them>
kubectl get pods -o wide          # the replacement has a NEW ip

Expect: the new pod has a different name and a different IP. Anything hardcoding that old IP is now broken. This is the problem Services exist to solve.

3

Create a Service for the deployment and inspect what got built:

kubectl expose deployment hello --port=80
kubectl get service hello                  # note the CLUSTER-IP
kubectl get endpointslices -l kubernetes.io/service-name=hello -o wide

Expect: a stable ClusterIP, and an EndpointSlice listing three pod IPs — the current answer to the selector's query. (kubectl expose copied the selector from the deployment's labels.)

4

Prove the DNS name works. Launch a throwaway client pod inside the cluster:

kubectl run client --rm -it --image=busybox -- sh
# now inside the pod:
wget -qO- http://hello | head -n 4
nslookup hello
exit

Expect: the nginx welcome HTML, fetched by the bare name hello — no IP anywhere. nslookup shows the name resolving to the ClusterIP you saw in step 3.

5

Watch the selector behave as a live query. In terminal 2:

kubectl get endpointslices -l kubernetes.io/service-name=hello -o wide -w

In terminal 1, change the world:

kubectl scale deployment hello --replicas=5
kubectl delete pod <any-hello-pod>

Expect: the EndpointSlice updates within moments each time — IPs added on scale-up, a dead pod's IP swapped for its replacement. The Service never changed; only the query's answer did. (Ctrl-C the watch when done.)

6

Now reach it from your Mac — the homelab move. Ask for a LoadBalancer:

kubectl expose deployment hello --name=hello-lb --type=LoadBalancer --port=8080 --target-port=80
kubectl get service hello-lb

Expect: EXTERNAL-IP populates (OrbStack assigns a reachable address via *.k8s.orb.local — in the cloud this would be a real load balancer). Note the port mapping: clients use 8080, the container listens on 80 — port vs targetPort, live.

Then, in your Mac's browser or terminal:

curl -s http://hello-lb.k8s.orb.local:8080 | head -n 4

Expect: nginx HTML, served from a pod inside the cluster, reached from macOS via OrbStack's wildcard DNS. No kubectl port-forward needed.

7

Clean up:

kubectl delete deployment hello
kubectl delete service hello hello-lb
