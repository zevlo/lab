Kustomize: Base & Overlays

One app definition, many environments — still plain YAML at the end.

Lesson 0010 taught scaffold → edit → apply. That works until you maintain app-dev.yaml, app-staging.yaml, and app-prod.yaml that differ in three fields. At work, teams use Kustomize or Helm to stop copy-pasting. Kustomize keeps everything as YAML patches — no template language — and ships inside kubectl. In the homelab, a base/ plus overlays/staging/ is how you deploy the same app to different namespaces with different replica counts and image tags without maintaining three full manifests.

The Idea

Kustomize reads a kustomization.yaml entrypoint, loads listed resources, applies transformers (prefix, namespace, image tag, replicas, patches), and emits final manifests [docs]:

app/
├── base/                    # shared skeleton
│   ├── kustomization.yaml
│   ├── deployment.yaml
│   └── service.yaml
└── overlays/
    └── staging/             # env-specific deltas
        ├── kustomization.yaml
        └── resources-patch.yaml
ConceptRole
BaseCanonical app — Deployment + Service. Checked into git once.
OverlayReferences the base via resources: [../../base] and adds only what differs.
TransformersBuilt-in fields in overlay kustomization.yaml — replicas, images, namePrefix, namespace, etc.
PatchesSmall YAML fragments merged onto base objects — e.g. tighter resources in staging.

Two commands matter:

kubectl kustomize overlays/staging    # preview rendered YAML
kubectl apply -k overlays/staging     # build + apply in one step

The output is normal Kubernetes objects — same declarative apply from lesson 0010. Kustomize is not a runtime component; it is a build step in front of the API.

Patch targets use the resource's base name (api), not the transformed name after namePrefix (stg-api). The replicas and images fields work the same way — reference api and nginx, not stg-api or nginx:1.29.

The mental model in one line: base is truth; overlay is a recipe of diffs; always preview with kubectl kustomize before apply -k.

Kustomize vs Helm: Helm uses Go templates and packaged charts — good when you need conditionals and packaged releases. Kustomize uses patches on plain YAML — good when diffs between environments are small and you want everything readable in git without {{ }}. Many repos use both; start with Kustomize when the problem is "same app, three namespaces."

Lab — Base, Staging Overlay, Break a Patch (~30 min)

OrbStack. You'll build a small Kustomize tree, preview it, apply staging, then break the Service selector with a patch — the lesson 0010 selector bug, reproduced through overlays. Reference copies live in yaml/kustomize-lab/ in this repo.

1

Orient.

kubectl config use-context orbstack
kubectl cluster-info

Expect control plane at https://127.0.0.1:26443. Create a working directory, e.g. mkdir -p ~/kustomize-lab/{base,overlays/staging}.

2

Write the base. Three files under base/:

# base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- deployment.yaml
- service.yaml
# base/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  labels:
    app: api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
      - name: nginx
        image: nginx:1.29
        ports:
        - containerPort: 80
        readinessProbe:
          httpGet:
            path: /
            port: 80
          periodSeconds: 2
# base/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  ports:
  - port: 80
    targetPort: 80
  selector:
    app: api

Preview the base alone:

kubectl kustomize base/

Expect: two documents (Deployment + Service), names unchanged, image nginx:1.29, replicas 2.

3

Write the staging overlay. Under overlays/staging/:

# overlays/staging/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

namespace: kustomize-lab
namePrefix: stg-

resources:
- ../../base

replicas:
- name: api
  count: 1

images:
- name: nginx
  newTag: "1.27"

patches:
- path: resources-patch.yaml
# overlays/staging/resources-patch.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  template:
    spec:
      containers:
      - name: nginx
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 200m
            memory: 128Mi

Preview the full render — read this output carefully before applying. This command prints YAML only; nothing reaches the cluster until step 4.

kubectl kustomize overlays/staging | grep -E '^(  )?(kind:|  name:|namespace:|  replicas:|    image:|    app:)'

Expect: namespace kustomize-lab; Deployment/Service named stg-api; replicas 1; image nginx:1.27; pod labels and Service selector both still app: api. If kubectl get deploy -n kustomize-lab is empty here, that is normal — you have not applied yet.

4

Apply staging. This is the step that actually creates objects — kustomize alone does not:

kubectl apply -k overlays/staging
kubectl rollout status deployment/stg-api -n kustomize-lab
kubectl get pods,svc,endpoints -n kustomize-lab

Expect: apply prints deployment.apps/stg-api created and service/stg-api created (or configured on re-run). Then one Running/Ready pod; Service stg-api; endpoints list a pod IP. You do not need to create namespace manually — the overlay's namespace: field handles it.

kubectl port-forward -n kustomize-lab svc/stg-api 8080:80
curl -s localhost:8080 | head -n 1

Expect: nginx HTML.

5

Break — bad selector patch. Create overlays/staging/break-selector-patch.yaml:

apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app: api-typo

Add it to the overlay patches list in kustomization.yaml, then re-apply:

kubectl apply -k overlays/staging
kubectl get endpoints stg-api -n kustomize-lab
curl -s --connect-timeout 2 localhost:8080 | head -n 1

Expect: apply succeeds — no error. Endpoints empty (<none>). Curl fails or hangs. Pods still Running — the bug is in rendered wiring, not pod health. Preview catches it:

kubectl kustomize overlays/staging | grep -A2 'kind: Service' -m1
kubectl kustomize overlays/staging | grep -E 'selector:|app:'

Expect: Service selector app: api-typo, pod template labels app: api — mismatch visible in rendered output before apply, if you look.

6

Fix and clean up. Remove the break patch from kustomization.yaml (or fix selector to app: api). Diff, re-apply, verify endpoints:

kubectl diff -k overlays/staging
kubectl apply -k overlays/staging
kubectl get endpoints stg-api -n kustomize-lab
kubectl delete -k overlays/staging

Expect: diff shows selector change; endpoints repopulated; delete removes all overlay resources and namespace.

Two preview habits: step 3 — inspect rendered names, tags, and replicas before apply. step 5 — a patch can break selectors while pods stay healthy; kubectl kustomize shows the wiring, get endpoints confirms it on the cluster. Same lesson as 0010, different tool.

Quiz

1. Staging needs one replica; production keeps two. Where do you declare that?

2. Overlay has namePrefix: stg-. Strategic-merge patch metadata.name should be?

3. Container image is nginx:1.29. Overlay should retag to 1.27 only in staging. Correct images entry?

4. After kubectl apply -k overlays/staging, pods Ready but Service unreachable. First check?
