Lesson 0014 · Kubernetes Fundamentals

Helm: Charts & Releases

Package, parameterize, install — with revision history and rollback.

Lesson 0013 layered plain YAML with Kustomize patches. You have already run Helm for Traefik (0003) and metrics-server (0012) — but those were one-liners against someone else's chart. At work, Helm is how you install Postgres, Redis, or a vendor monitoring stack without hand-writing every object. In the homelab, it is the fastest path from "I need this add-on" to a tracked, upgradable release you can roll back when an upgrade goes wrong.

The Idea

Helm is a package manager for Kubernetes. Three nouns cover almost everything [Helm docs]:

TermWhat it is
ChartA directory (or tarball) of templates/ plus default values.yaml — the package, like a Homebrew formula.
ReleaseA named instance of a chart running in the cluster. Install the same chart twice → two releases (e.g. postgres-app-a and postgres-app-b).
ValuesParameters fed into Go templates as {{ .Values.replicaCount }}. Override via values.yaml, -f, or --set.

A minimal chart layout (from helm create):

helm-lab/
├── Chart.yaml          # chart metadata (name, version)
├── values.yaml         # defaults — edit these, not templates, when possible
└── templates/
    ├── deployment.yaml # {{ .Values.image.repository }} …
    ├── service.yaml
    └── _helpers.tpl    # shared label/selector snippets

Helm renders templates + values into plain manifests, then sends them to the API — same declarative end state as kubectl apply. The difference from Kustomize is how you customize: Go templates and packaged charts instead of YAML patches.

Commands that mirror lesson 0013's preview/deploy split:

helm template lab ./helm-lab -n helm-lab    # preview rendered YAML — nothing in cluster
helm install lab ./helm-lab -n helm-lab --create-namespace   # deploy release "lab"
helm upgrade lab ./helm-lab -n helm-lab    # new revision on config change
helm rollback lab 1 -n helm-lab           # revert to revision 1
helm uninstall lab -n helm-lab            # remove release + its objects

For charts you did not author: add a repo, inspect defaults, install with overrides — exactly what you did for Traefik and metrics-server:

helm repo add metrics-server https://kubernetes-sigs.github.io/metrics-server/
helm show values metrics-server/metrics-server   # read defaults before overriding
helm upgrade --install metrics-server metrics-server/metrics-server \
  -n kube-system --set args="{--kubelet-insecure-tls}"

upgrade --install is idempotent: create the release if missing, upgrade if present — the usual pattern for cluster add-ons.

The mental model in one line: chart is the recipe; values are the knobs; release is the named dinner you actually served — and Helm remembers every revision.

Helm vs Kustomize (revisited): Kustomize patches your YAML — best when env diffs are small and you want zero {{ }}. Helm templates and packages charts — best when installing third-party software, you need conditionals/loops, or you want helm rollback. Many teams use Kustomize for in-house apps and Helm for dependencies. Both end in Kubernetes objects managed by the same control loops.

Lab — Scaffold, Template, Install, Break, Rollback (~30 min)

OrbStack. You will scaffold a chart with helm create, preview with helm template, install a release, break a Service selector in a template (the lesson 0010/0013 wiring bug, via Helm), then roll back. Working directory e.g. ~/helm-lab/.

1

Orient.

kubectl config use-context orbstack
helm version
kubectl cluster-info

Expect Helm v3+ (or v4) and control plane at https://127.0.0.1:26443. If connection refused, you are on a stale context — switch to orbstack, not rancher-desktop.

2

Scaffold a chart.

mkdir -p ~/helm-lab && cd ~/helm-lab
helm create helm-lab
ls helm-lab/

Expect Chart.yaml, values.yaml, templates/. Open values.yaml — note replicaCount, image.repository, service.port. These are the knobs; templates reference them with {{ .Values.… }}.

Edit values.yaml — pin a known nginx tag:

# under image:
  tag: "1.27"
3

Preview — template only. Same habit as kubectl kustomize in lesson 0013: render before deploy. This prints YAML only; nothing reaches the cluster until step 4.

helm template lab ./helm-lab -n helm-lab --create-namespace \
  | grep -E '^(kind:|  name:|  replicas:|    image:|    app\.kubernetes\.io/name:)'

Expect Deployment and Service named lab-helm-lab (release name + chart name); replicas 1; image nginx:1.27. If kubectl get deploy -n helm-lab is empty here, that is normal — you have not installed yet.

4

Install the release. This is the step that actually creates objects:

helm install lab ./helm-lab -n helm-lab --create-namespace
kubectl rollout status deployment/lab-helm-lab -n helm-lab
kubectl get pods,svc,endpoints -n helm-lab
helm list -n helm-lab

Expect STATUS: deployed, REVISION: 1. One Running/Ready pod; Service lab-helm-lab; endpoints list a pod IP. helm list shows release lab.

kubectl port-forward -n helm-lab svc/lab-helm-lab 8080:80
curl -s localhost:8080 | head -n 1

Expect nginx HTML.

5

Break — bad selector in template. Edit helm-lab/templates/service.yaml. Replace the selector: block (the lines using selectorLabels) with a hard-coded typo:

  selector:
    app.kubernetes.io/name: typo

Upgrade the release — Helm applies the new render:

helm upgrade lab ./helm-lab -n helm-lab
helm history lab -n helm-lab
kubectl get endpoints lab-helm-lab -n helm-lab
curl -s --connect-timeout 2 localhost:8080 | head -n 1

Expect: upgrade succeeds — revision 2. Endpoints empty (<none>). Curl fails or hangs. Pods still Running — wiring bug, not pod health. Preview catches it:

helm template lab ./helm-lab -n helm-lab | grep -E 'selector:|app\.kubernetes\.io/name:'

Expect: Service selector typo, pod labels still helm-lab — mismatch visible in rendered output before upgrade, if you look.

6

Rollback and clean up. Restore the template selector (put back the selectorLabels helper), or roll back without editing:

helm rollback lab 1 -n helm-lab
kubectl get endpoints lab-helm-lab -n helm-lab
curl -s localhost:8080 | head -n 1

Expect: revision 3 (rollback counts as a new revision); endpoints repopulated; curl works. Inspect history:

helm history lab -n helm-lab

Expect three rows — deploy, broken upgrade, rollback. Remove everything:

helm uninstall lab -n helm-lab
kubectl get all -n helm-lab

Expect namespace empty (or only leftover resources if any). Optional: kubectl delete namespace helm-lab.

Two preview habits: step 3 — helm template before helm install (same trap as previewing Kustomize without apply -k). step 5 — a template edit can break selectors while pods stay healthy; rendered output shows the wiring, get endpoints confirms it on the cluster. helm rollback is the safety net Kustomize does not give you out of the box.
