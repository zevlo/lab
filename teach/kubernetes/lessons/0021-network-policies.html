NetworkPolicies: Who May Talk to Whom

Services route traffic. NetworkPolicies permit or deny it.

Lessons 0002 and 0019 taught how traffic finds pods — Services, EndpointSlices, Ingress. By default, every pod in a cluster can reach every other pod. That is fine for learning; it is not fine for production. A NetworkPolicy is a firewall rule at the pod network layer: which sources may connect to which destinations, on which ports. At work, this is how you keep the database tier reachable only from the API tier. In the homelab, it is how you practice zero-trust segmentation before a real multi-team cluster.

The Idea

NetworkPolicies are opt-in restrictions enforced by the CNI / network-policy controller. OrbStack's Kubernetes (k3s) includes kube-router's policy controller — no extra install [k3s docs].

Default (no policies)After a policy selects a pod
All pod-to-pod traffic allowedFor each declared direction (Ingress / Egress), only explicitly allowed traffic is permitted
Services still route normallyA working Service does not override a deny — if policy blocks the flow, packets never arrive

Read a policy in two halves [docs]:

spec:
  podSelector:          # WHO is protected (which pods this policy applies TO)
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  ingress:
  - from:               # WHO may connect (sources allowed IN)
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 80

The trap: spec.podSelector is not "the pods allowed to connect." It is "the pods being isolated." Sources live under ingress[].from or egress[].to.

Orthogonal to Services. A Service answers "which pod IPs should receive traffic for backend?" A NetworkPolicy answers "is this packet allowed to reach that pod at all?" Lesson 0019 debugging still applies — but when policy is the break, pods and EndpointSlices look healthy while connections time out.

Common selectors in from / to:

FieldMatches
podSelectorPods in the same namespace with these labels
namespaceSelectorAll pods in namespaces matching these labels
ipBlockCIDR ranges outside the cluster (less common in fundamentals)

Egress policies bite twice: blocking port 80 to your app and forgetting port 53 to kube-dns in kube-system means DNS resolution fails before TCP ever starts — curl http://backend hangs or reports "Could not resolve host" even when the backend pod is fine.

Lab — Three breaks, permit/deny (~25 min)

OrbStack, context orbstack. Lab files in yaml/networkpolicy-lab/:

cd ~/projects/teach/kubernetes/yaml/networkpolicy-lab
ls

Expect namespace.yaml, stack.yaml, policy-ingress-restrict.yaml, policy-ingress-broken.yaml, policy-egress-broken.yaml, policy-egress-fixed.yaml. Three workloads: frontend, backend, client (curl pod).

0

SCOPE — confirm cluster, pin namespace.

kubectl config current-context
kubectl apply -f namespace.yaml
kubectl config set-context --current --namespace=networkpolicy-lab

Expect orbstack. Namespace created; following commands omit -n.

1

Baseline — open cluster, all paths work.

kubectl apply -f stack.yaml
kubectl rollout status deployment/frontend deployment/backend deployment/client --timeout=90s
kubectl get pods,svc,networkpolicy

Expect three Running pods, two Services, no NetworkPolicies yet.

kubectl exec deploy/client -- curl -s -o /dev/null -w "client→backend: %{http_code}\n" --connect-timeout 3 http://backend
kubectl exec deploy/frontend -- wget -qO- --timeout=3 http://backend 2>/dev/null | head -n 1

Expect HTTP 200 from client and nginx HTML from frontend. Both can reach backend.

2

Break A — ingress restricted: only frontend may reach backend.

kubectl apply -f policy-ingress-restrict.yaml
kubectl get networkpolicy

Policy backend-ingress exists. Re-test paths:

kubectl exec deploy/client -- curl -s -o /dev/null -w "client→backend: %{http_code}\n" --connect-timeout 3 http://backend
kubectl exec deploy/frontend -- wget -qO- --timeout=3 http://backend 2>/dev/null | head -n 1

Client: 000, timeout, or connection failed (exact message varies). Frontend: still returns nginx HTML. Pods and EndpointSlice unchanged — this is policy, not Service wiring.

Your turn: read the policy before moving on.

kubectl describe networkpolicy backend-ingress
kubectl get pod -l app=backend --show-labels

podSelector: app=backend isolates backend pods. from: app=frontend is the only ingress source allowed on port 80.

3

Break B — policy exists but selects the wrong pods.

kubectl delete networkpolicy backend-ingress
kubectl apply -f policy-ingress-broken.yaml
kubectl get networkpolicy

Policy still listed — looks like protection is on. Test client again:

kubectl exec deploy/client -- curl -s -o /dev/null -w "client→backend: %{http_code}\n" --connect-timeout 3 http://backend

Client returns 200 again — restriction gone. Diagnose:

kubectl get networkpolicy backend-ingress -o yaml | grep -A3 podSelector
kubectl get pod -l app=backend --show-labels

Policy podSelector says app: backend-typo; backend pods have app: backend. The policy applies to zero pods — backend stays on default-allow. Same class of bug as lesson 0019's Service selector typo, different layer.

Fix:

kubectl apply -f policy-ingress-restrict.yaml
kubectl exec deploy/client -- curl -s -o /dev/null -w "client→backend: %{http_code}\n" --connect-timeout 3 http://backend

Client blocked again (000 / timeout).

4

Break C — egress policy blocks DNS. Remove ingress policy first; restrict client egress only.

kubectl delete networkpolicy backend-ingress
kubectl apply -f policy-egress-broken.yaml
kubectl exec deploy/client -- curl -s -o /dev/null -w "client→backend: %{http_code}\n" --connect-timeout 5 http://backend

Fails or times out — but backend pod is Running and Service endpoints are populated. The policy allows egress to backend:80 only; DNS to kube-dns on port 53 is missing. Optional confirm:

kubectl get networkpolicy client-egress -o yaml | grep -A20 egress:
kubectl get svc -n kube-system -l k8s-app=kube-dns

Egress rules list backend only — no UDP/TCP 53 to kube-system. Cluster DNS Service exists in kube-system.

Fix — allow DNS, then backend:

kubectl apply -f policy-egress-fixed.yaml
kubectl exec deploy/client -- curl -s -o /dev/null -w "client→backend: %{http_code}\n" --connect-timeout 5 http://backend

HTTP 200 returns.

5

Clean up.

kubectl delete namespace networkpolicy-lab
kubectl config set-context --current --namespace=default
Debugging policy breaks: pods Ready + endpoints populated + connection timeout → think NetworkPolicy (RELATED layer), not rollout or selector. Read get networkpolicy and verify spec.podSelector matches the protected pods. For egress, remember DNS before app ports.

Quiz

1. Fresh cluster, zero NetworkPolicy objects. Pod A in namespace dev curls Pod B in namespace prod. Result?

2. NetworkPolicy has podSelector: app: backend and one ingress rule from podSelector: app: frontend. What does the top-level podSelector identify?

3. After a correct ingress policy, client cannot reach backend but frontend can. Pods and EndpointSlice healthy. Root cause?

4. Egress policy on client allows TCP 80 to backend only. curl http://backend fails; backend pod Running. Most likely missing rule?

5. Teammate says "Service and NetworkPolicy do the same thing — both control who hits the backend." Best correction?
