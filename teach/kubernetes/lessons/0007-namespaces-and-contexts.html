Namespaces & Contexts: Knowing Where You Are

Scope on the cluster; aim on the terminal.

Every lesson so far landed in default. That was fine while you were learning mechanics — but a homelab with media, monitoring, and experiments in one undifferentiated bucket becomes a debugging nightmare, and at work "I deployed it" without "to where" is how you overwrite a teammate's service. Namespaces carve the cluster into isolated scopes; contexts tell kubectl which cluster — and which default namespace — you're talking to.

The Idea

A namespace is a scope boundary inside one cluster [docs]. Most objects you've met — Pods, Deployments, Services, ConfigMaps, Secrets — are namespaced: their names must be unique within a namespace, but two namespaces can each have a Deployment called web without conflict.

Namespaces are not hard security walls by themselves (RBAC does that — later). They are how you organize workloads, avoid naming collisions, and attach policy per team or environment. The official docs recommend not running production in default — for your homelab, think homelab, media, monitoring instead.

Some objects are cluster-scoped — they have no namespace. You've interacted with Nodes implicitly; StorageClasses and PersistentVolumes are others. Quick check anytime:

kubectl api-resources --namespaced=true   # Pod, Deployment, Service, …
kubectl api-resources --namespaced=false  # Node, Namespace, StorageClass, …

This ties back to lesson 0002: cluster DNS gives a Service the short name web within its own namespace. From elsewhere you need the FQDN: web.homelab.svc.cluster.local [docs]. Same config file, different namespaces — that's how dev/staging/prod patterns work.

And lesson 0006: ConfigMaps and Secrets are namespace-scoped too. A Pod can only reference a ConfigMap in the same namespace.

A context is a triple: cluster + credentials + default namespace [docs]. Stored in your kubeconfig (~/.kube/config; OrbStack also writes cluster config under ~/.orbstack/k8s/). Right now you likely have one cluster (orbstack) but you still have a current context — and its default namespace is probably default.

The mental model in one line: namespaces are where on the cluster; context (and -n) is where kubectl is looking right now.

Lab — Scope, Aim, Mis-aim (~25 min)

Against OrbStack. You'll create a homelab namespace, prove isolation, cross a namespace boundary with DNS, then trigger the classic "I deployed it but can't see it" mistake.

1

Orient. Before touching anything, know your aim:

kubectl config use-context orbstack
kubectl config current-context
kubectl config view --minify
kubectl get namespaces

Expect: context orbstack, default namespace likely default (or empty, which means default). Four built-in namespaces: default, kube-system, kube-public, kube-node-lease.

2

Create homelab.yaml — a namespace, a Deployment, and a Service, all scoped to homelab:

apiVersion: v1
kind: Namespace
metadata:
  name: homelab
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: homelab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.29
---
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: homelab
spec:
  selector:
    app: web
  ports:
  - port: 80
kubectl apply -f homelab.yaml
kubectl get pods
kubectl get pods -n homelab
kubectl get pods -A | grep web

Expect: plain kubectl get pods shows nothing new (you're still aimed at default). -n homelab shows two Running pods. -A shows them with the homelab column — your first move when pods "vanish."

3

Set your default aim. Pin the current context to homelab so you can drop -n for this session:

kubectl config set-context --current --namespace=homelab
kubectl config view --minify | grep namespace:
kubectl get pods

Expect: two web pods without typing -n. This is a preference in your kubeconfig — not a cluster change.

4

Cross-namespace DNS. Create a second namespace and a probe pod that tries to reach web:

kubectl create namespace sandbox
kubectl run probe -n sandbox --image=curlimages/curl --restart=Never --command -- sleep 3600
kubectl wait -n sandbox --for=condition=Ready pod/probe --timeout=60s

Short name (resolves inside sandbox only — there is no web Service here):

kubectl exec -n sandbox probe -- curl -s -o /dev/null -w "%{http_code}" --connect-timeout 2 http://web/ || echo " failed"

FQDN (reaches homelab's Service):

kubectl exec -n sandbox probe -- curl -s -o /dev/null -w "%{http_code}" http://web.homelab.svc.cluster.local/

Expect: short name fails or times out; FQDN returns 200. Same Service name, different scope — DNS needs the namespace in the path when you cross the boundary.

5

Break it — the invisible deploy. Reset your context aim to default:

kubectl config set-context --current --namespace=default

Create api.yaml — a Deployment named api with no metadata.namespace field:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 1
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
      - name: nginx
        image: nginx:1.29

You intend this for homelab. Apply, then look where you expect it:

kubectl apply -f api.yaml
kubectl get pods -n homelab
kubectl get deploy -n homelab

Expect: nothing named api in homelab. The deploy succeeded — just not where you were looking. Find it:

kubectl get deploy -A | grep api
kubectl get pods -A | grep api

Expect: api landed in default because both your context default namespace and the YAML omitted an explicit scope. The cluster did exactly what you asked. This is the #1 namespace bug in the wild.

6

Fix it. Delete the stray deploy and re-create it in the right scope — pick one style and stick to it in your homelab:

kubectl delete -f api.yaml

# Option A: namespace in YAML

Add namespace: homelab under metadata in api.yaml, then:

kubectl apply -f api.yaml
kubectl get deploy -n homelab

Or Option B: keep context aimed at homelab (kubectl config set-context --current --namespace=homelab) and always verify with kubectl config view --minify before applying.

Expect: api visible in homelab. Best practice: set metadata.namespace in the manifest and know your current context — belt and suspenders.

7

Clean up. Deleting a namespace deletes everything inside it:

kubectl delete -f api.yaml
kubectl delete -f homelab.yaml
kubectl delete namespace sandbox
kubectl config set-context --current --namespace=default
Containment check: if a co-worker says "the site still works" while a deploy looks missing, you may be looking at the wrong namespace — same class of illusion as lesson 0006 step 4. Run kubectl get pods -A before assuming failure.
