Resource Requests & Limits: Promises and Ceilings

What the scheduler reserves vs what the kubelet enforces.

Lesson 0001 introduced the scheduler picking a node for each pod. Lesson 0005 showed the kubelet enforcing health. Resource requests and limits are the third leg: you declare how much CPU and memory a container needs, and two different components act on those numbers. At work, missing limits let one runaway pod starve everything on a node. In the homelab, a single OrbStack node makes that pain immediate — there is nowhere else to hide.

The Idea

Every container can declare two numbers per resource (CPU, memory) inside resources [docs]:

FieldWho uses itWhat it means
requestsScheduler"I need at least this much to run here." The scheduler subtracts all pods' requests from a node's allocatable capacity before placing yours.
limitskubelet (cgroups)"Never let me use more than this." Enforced on the running process.
resources:
  requests:
    cpu: "100m"       # 0.1 core — scheduling promise
    memory: "128Mi"
  limits:
    cpu: "500m"       # ceiling — runtime enforcement
    memory: "256Mi"

The asymmetry that bites people in production:

ResourceOver the limitTypical symptom
CPUThrottled (compressible)Slower; rarely killed
MemoryOOMKilled (incompressible)Exit 137; CrashLoopBackOff if the process keeps allocating

Three more pieces worth knowing now (details in the reference):

  • Units. CPU: cores or millicores (100m = 0.1 core). Memory: binary (Mi, Gi) — not MB/GB.
  • QoS class. Kubernetes assigns Guaranteed / Burstable / BestEffort from how requests and limits relate — affects eviction order under memory pressure [docs].
  • Pending vs crashing. Impossible requests → pod stays Pending (Insufficient cpu in Events). Memory limit too tight → pod runs, then gets OOMKilled. Different fields, different failure modes — watch the right signal.
The mental model in one line: requests are a scheduling promise ("fit me on a node with room"); limits are a runtime ceiling ("kill or throttle me if I exceed this").

Lab — Reserve, OOM, and Pending (~25 min)

Against OrbStack. Namespace homelab. You'll deploy a memory stressor twice — once broken, once fixed — then trigger a scheduling failure.

1

Orient. See what your single node actually has to give:

kubectl config use-context orbstack
kubectl create namespace homelab --dry-run=client -o yaml | kubectl apply -f -
kubectl config set-context --current --namespace=homelab
kubectl get nodes
kubectl describe node | grep -A6 Allocatable
kubectl describe node | grep -A12 "Allocated resources"

Expect: one node (e.g. orbstack). Allocatable shows CPU (often ~4–8 cores) and memory (often several Gi). Allocated resources sums existing pods' requests — mostly system pods so far.

2

Create stress.yaml — a pod that allocates memory on purpose, with a tight limit:

apiVersion: v1
kind: Pod
metadata:
  name: mem-stress
spec:
  restartPolicy: Never
  containers:
  - name: stress
    image: polinux/stress
    command: ["stress"]
    args: ["--vm", "1", "--vm-bytes", "200M", "--vm-hang", "1"]
    resources:
      requests:
        memory: "64Mi"
        cpu: "100m"
      limits:
        memory: "64Mi"   # intentionally too small for 200M allocation
kubectl apply -f stress.yaml
kubectl get pod mem-stress -w   # Ctrl+C once STATUS settles

Expect: pod reaches Error or OOMKilled quickly — not Running for long. The container asked for 200M; the cgroup cap is 64Mi.

3

Diagnose the OOM. Watch the container termination reason, not probe state:

kubectl describe pod mem-stress | tail -20
kubectl get pod mem-stress -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}{"\n"}'

Expect: Reason: OOMKilled, exit code 137. Events may mention memory limit. This is the kubelet enforcing limits.memory — not a liveness restart, not a scheduling problem.

4

Fix it. Raise the memory limit (and request) above what stress allocates — e.g. 256Mi — and re-apply. Because restartPolicy: Never, delete first:

kubectl delete pod mem-stress
# edit stress.yaml: memory request and limit → 256Mi
kubectl apply -f stress.yaml
kubectl get pod mem-stress -w

Expect: Running then Completed (stress exits cleanly after hanging). Optional — if metrics-server is installed: kubectl top pod mem-stress while Running.

5

Break scheduling. Create greedy.yaml — same image, impossible CPU request:

apiVersion: v1
kind: Pod
metadata:
  name: greedy
spec:
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.9
    resources:
      requests:
        cpu: "999"   # more cores than any single node has
kubectl apply -f greedy.yaml
kubectl get pod greedy
kubectl describe pod greedy | tail -12

Expect: Pending indefinitely. Events: FailedScheduling / Insufficient cpu. The scheduler cannot find a node whose allocatable minus existing requests fits 999 CPU. No OOM — the pod never started.

6

Fix and clean up. Delete the impossible pod; remove lab objects:

kubectl delete -f greedy.yaml
kubectl delete -f stress.yaml
kubectl delete namespace homelab
kubectl config set-context --current --namespace=default
Don't confuse the two breaks: step 3 — pod ran, then OOMKilled (limit too low). step 5 — pod never runs, stays Pending (request too high). Same resources block, different fields, different components.
