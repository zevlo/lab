Rollout and Helm Revision Debugging

After the deploy breaks — triage the rollout, not the homepage.

Lesson 0004 taught rollouts and rollout undo. Lesson 0014 taught helm rollback. Lessons 0017–0019 drilled pod and networking failures. This lesson closes the troubleshooting arc: deploy incidents — when someone runs kubectl apply or helm upgrade and traffic degrades. At work, the first question is not "is the site down?" but "is the rollout stuck, and which ReplicaSet is failing?" In the homelab, the same funnel saves you from deleting a healthy Deployment while one bad pod blocks progress.

The Idea

A deploy changes the pod template. The Deployment controller spins up a new ReplicaSet and slides replicas. When something goes wrong, you get a stuck rollout — old pods may still serve while new ones never become Ready [failed deployment].

The deploy-incident funnel (after confirming SCOPE — right cluster and namespace):

STATUS  → kubectl rollout status deployment/<name>   # stuck or progressing?
RELATED → kubectl get rs                              # old RS still has replicas?
STATUS  → kubectl get pods                            # which pod is the new one?
EVENTS  → kubectl describe pod <failing-pod>          # ImagePullBackOff? probe failure?
RECOVER → rollout undo OR fix manifest + apply        # stop bleeding vs durable fix
What you seeLikely causeOld pods still serving?First move
Rollout stuck; new pod ImagePullBackOffBad image tag / registryUsually yes (maxUnavailable)describe pod Events → fix image in manifest
Rollout stuck; new pod Running 0/1Readiness probe never passesUsually yesdescribe pod → Conditions / probe path or port
helm upgrade succeeded; app brokenBad values rendered into manifestDepends on rollouthelm history → same pod funnel → helm rollback
Containment vs diagnosis. kubectl rollout undo and helm rollback are recovery — they stop the bleeding fast. At work, the durable fix is usually revert the bad commit in Git and apply again. Diagnose first so you know what to revert.

During a stuck rollout with two replicas, you may see three pods — two old Ready pods plus one new failing pod. That is maxSurge at work (lesson 0004). Do not assume total pod count equals replica count.

Helm adds one layer: each upgrade is a numbered revision. helm history RELEASE maps revision numbers to cluster state; helm rollback RELEASE N re-applies revision N's rendered manifests — the Helm equivalent of scaling the old ReplicaSet back up.

Lab — Three deploy breaks, one funnel (~30 min)

OrbStack, context orbstack. Lab files in yaml/deploy-incident-lab/:

cd ~/projects/teach/kubernetes/yaml/deploy-incident-lab
ls

Expect namespace.yaml, baseline.yaml, image-bad.yaml, image-fixed.yaml, probe-bad.yaml, probe-fixed.yaml, and chart/ (minimal Helm chart). Two terminals help for Break A — watch ReplicaSets in terminal 2.

0

SCOPE — confirm cluster, pin namespace.

kubectl config current-context
kubectl apply -f namespace.yaml
kubectl config set-context --current --namespace=deploy-incident-lab

Expect orbstack. Namespace created; following commands omit -n.

1

Baseline — healthy Deployment with readiness probe.

kubectl apply -f baseline.yaml
kubectl rollout status deployment/api --timeout=60s
kubectl get pods,rs
kubectl port-forward svc/api 8080:80 &
curl -s localhost:8080 | head -n 1
kill %1

Expect two Ready pods, one ReplicaSet at 2/2. Port-forward returns nginx HTML.

2

Break A — bad image tag; rollout contained. (Lesson 0004, now inside the funnel.)

In terminal 2: kubectl get rs -w

kubectl apply -f image-bad.yaml
kubectl rollout status deployment/api

rollout status hangs — Ctrl-C. Terminal 2: second ReplicaSet appears; new pod stuck; old RS still at 2. Your turn — do not open fix files yet:

kubectl get pods
kubectl get rs
kubectl describe pod -l pod-template-hash=<new-hash> | tail -n 15

Tip: kubectl get rs shows two ReplicaSets — the one with DESIRED 2 and READY 2 is the old good revision; the one with a failing pod is new. New pod: ErrImagePull / ImagePullBackOff. Old pods still Running 1/1 — outage contained.

Recover — stop the bleeding, then apply the fixed manifest (production pattern):

kubectl rollout undo deployment/api
kubectl rollout status deployment/api
kubectl apply -f image-fixed.yaml
kubectl get rs

rollout undo drains the bad ReplicaSet. image-fixed.yaml restores the correct image declaratively — what you would commit in Git.

3

Break B — readiness probe on wrong port; quiet failure. (Lesson 0004's caveat — app "starts" but never becomes Ready.)

kubectl apply -f probe-bad.yaml
kubectl rollout status deployment/api

Rollout stuck again. This time the new pod may show Running 0/1 — not ImagePullBackOff. Diagnose:

kubectl get pods
kubectl describe pod -l pod-template-hash=<new-hash> | grep -A8 "Readiness:"
kubectl describe pod -l pod-template-hash=<new-hash> | grep -A4 "Conditions:"

Readiness probe hits port 8080; nginx listens on 80. Conditions: Ready=False. Old pods still serve traffic.

Fix — correct probe in manifest:

kubectl apply -f probe-fixed.yaml
kubectl rollout status deployment/api
kubectl get pods

Rollout completes; all pods 1/1.

4

Break C — Helm upgrade with bad image tag. (Lesson 0014 revision history.)

helm install sidecar ./chart
kubectl rollout status deployment/sidecar-sidecar --timeout=60s
helm list

Release sidecar, revision 1, one Ready pod.

helm upgrade sidecar ./chart -f chart/values-bad.yaml
helm history sidecar
kubectl rollout status deployment/sidecar-sidecar

Upgrade "succeeds" — revision 2 — but rollout stuck. Same pod funnel:

kubectl get pods
kubectl describe pod -l app.kubernetes.io/instance=sidecar | tail -n 12

ImagePullBackOff on image nginx:1.27-broken. Revision 1's ReplicaSet may still have the good pod at zero or one depending on timing.

Recover:

helm rollback sidecar 1
helm history sidecar
kubectl rollout status deployment/sidecar-sidecar
kubectl get pods

History shows revision 3 (rollback counts as new). Pod back to nginx:1.27-alpine, Ready.

5

Clean up.

helm uninstall sidecar
kubectl delete namespace deploy-incident-lab
kubectl config set-context --current --namespace=default
Do not curl first. During a stuck rollout, HTTP may still work on old pods while the deploy is broken. Watch rollout status and ReplicaSet counts — the same containment lesson from lesson 0004, now as incident triage. Networking breaks (lesson 0019) come after you confirm the rollout finished.

Quiz

1. After kubectl apply, site still works but rollout status is stuck. Two ReplicaSets exist; new pod is ImagePullBackOff. Best first move?

2. Rollout stuck; new pod Running 0/1; old pods Ready. describe shows readiness probe failing on port 8080; container listens on 80. Root cause?

3. Production incident: bad deploy 10 minutes ago; you need to restore service immediately while a teammate reverts Git. Fastest cluster-side recovery for a kubectl-managed Deployment?

4. helm upgrade reports success; revision 2; app broken. Pods show ImagePullBackOff. After diagnosing the image tag, what maps to rollout undo for Helm?

5. Two-replica Deployment; stuck rollout; get pods shows three pods — two Ready, one failing. Why three?
