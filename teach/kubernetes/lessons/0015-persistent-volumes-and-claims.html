Lesson 0015 · Kubernetes Fundamentals

Persistent Volumes & Claims

Pods come and go — PVCs keep the data.

Lesson 0001 taught that pods are ephemeral — replaced, not healed. Lesson 0006 mounted ConfigMaps as volumes, but those hold configuration, not durable app data. When you helm install Postgres in the homelab (0014), the chart creates a PersistentVolumeClaim. At work, any database, upload store, or queue that must survive a pod restart depends on this layer. This lesson is the storage half of "stateful workloads."

The Idea

Three objects, one binding dance [PV docs]:

ObjectScopeRole
PersistentVolume (PV)ClusterThe actual storage — a disk, NFS export, or host directory.
PersistentVolumeClaim (PVC)NamespaceYour app's request: "I need 1 Gi, RWO, from storage class X."
StorageClassClusterProvisioner template — creates PVs automatically when PVCs arrive.
Pod spec
  volumes[].persistentVolumeClaim.claimName: data
       ↓ mounts
PVC "data"  ──binds──▶  PV (actual bytes on disk)
       ↑
StorageClass "local-path" provisions the PV

A pod wires storage the same way it mounts a ConfigMap — volumes + volumeMounts — but the backing object is a PVC, not a ConfigMap:

spec:
  containers:
  - name: app
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: data

Delete the pod → PVC and PV remain. A replacement pod mounting the same claim sees the same files. That is the whole point.

Not the same as emptyDir: emptyDir is scratch space tied to the pod lifecycle — gone when the pod is deleted. ConfigMap volumes hold settings that can update live (0006). PVCs hold application state that must outlive any single pod.

The mental model in one line: PVC is the contract; PV is the disk; the pod is temporary — mount the claim, never bake state into the container layer.

Access modes matter when binding: ReadWriteOnce (RWO) — one node at a time, typical for databases. ReadWriteMany (RWX) — shared read/write, needs a shared filesystem (NFS, EFS). PVC and PV must agree on mode and size.

WaitForFirstConsumer: many local StorageClasses (including OrbStack's local-path) defer provisioning until a pod that uses the PVC is scheduled. A lone PVC may sit Pending — that is normal until you apply the pod.

Lab — Provision, Persist, Break, Fix (~30 min)

OrbStack. You'll install a local provisioner if needed, bind a PVC, prove data survives pod replacement, then break binding with a wrong StorageClass name. Working directory e.g. ~/storage-lab/.

1

Orient — StorageClass.

kubectl config use-context orbstack
kubectl get storageclass

If the list is empty, install the local-path provisioner once:

kubectl apply -f https://raw.githubusercontent.com/rancher/local-path-provisioner/v0.0.30/deploy/local-path-storage.yaml
kubectl get storageclass

Expect StorageClass local-path with provisioner rancher.io/local-path. If OrbStack K8s is stopped, run orb start k8s first.

2

Create namespace and PVC. Save as storage-lab.yaml:

apiVersion: v1
kind: Namespace
metadata:
  name: storage-lab
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
  namespace: storage-lab
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: local-path
  resources:
    requests:
      storage: 64Mi
kubectl apply -f storage-lab.yaml
kubectl get pvc -n storage-lab

Expect PVC data with status Pending — normal for WaitForFirstConsumer. No pod yet, so nothing to bind to.

3

Write data — pod mounts PVC. Append to the same file (or save as writer-pod.yaml):

---
apiVersion: v1
kind: Pod
metadata:
  name: writer
  namespace: storage-lab
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["/bin/sh", "-c", "echo persisted-$(date +%s) > /data/message.txt && sleep 3600"]
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: data
kubectl apply -f storage-lab.yaml   # or writer-pod.yaml if split
kubectl get pvc,pod -n storage-lab
kubectl exec -n storage-lab writer -- cat /data/message.txt

Expect PVC Bound once the pod schedules; pod Running; message file like persisted-1718822400. Note the timestamp — you will need it in step 4.

4

Prove persistence — kill the pod, not the claim.

kubectl delete pod writer -n storage-lab
kubectl get pvc -n storage-lab

Expect pod gone; PVC data still Bound. Create a reader pod (append to your yaml or apply inline):

apiVersion: v1
kind: Pod
metadata:
  name: reader
  namespace: storage-lab
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["/bin/sh", "-c", "cat /data/message.txt && sleep 3600"]
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: data
kubectl apply -f reader-pod.yaml
kubectl exec -n storage-lab reader -- cat /data/message.txt

Expect the same message from step 3 — identical timestamp. Data lived on the PV, not in the pod.

5

Break — wrong StorageClass. Create a PVC the cluster cannot provision:

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: bad-data
  namespace: storage-lab
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: typo-path
  resources:
    requests:
      storage: 64Mi

And a pod that needs it:

apiVersion: v1
kind: Pod
metadata:
  name: broken
  namespace: storage-lab
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: bad-data
kubectl apply -f bad-pvc.yaml -f broken-pod.yaml
kubectl get pvc bad-data -n storage-lab
kubectl get pod broken -n storage-lab
kubectl describe pvc bad-data -n storage-lab | tail -n 8

Expect PVC stuck Pending (events mention missing StorageClass or no provisioner). Pod stuck Pending with reason like unbound immediate PersistentVolumeClaims. The good PVC data and reader pod are unaffected — watch which object you diagnose.

6

Fix and clean up.

kubectl delete pod broken -n storage-lab
kubectl delete pvc bad-data -n storage-lab
kubectl delete namespace storage-lab

Expect namespace and all PVCs removed. On OrbStack, local-path data may linger on disk until cluster restart — a known local-path quirk, not a lesson failure.

Two diagnostic habits: PVC Pending → describe pvc events first (wrong StorageClass? waiting for a pod?). Pod Pending with volumes → check whether every PVC is Bound. Same pattern as endpoints for Services — find the binding gap, not the symptom on the wrong object.

Quiz

1. Writer pod deleted; PVC data still Bound. New pod mounts same claim. What happens to /data/message.txt?

2. PVC Pending on OrbStack; StorageClass local-path exists; no pod mounts it yet. Most likely cause?

3. Helm Postgres chart pod Pending; kubectl get pvc shows claim Pending. First diagnostic step?

4. App needs scratch space cleared when the pod exits; no sharing across pods. Best volume type?

5. PVC storageClassName: fast-ssd but kubectl get storageclass lists only local-path. Expected PVC status?
