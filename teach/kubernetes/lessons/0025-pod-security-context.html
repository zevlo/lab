Lesson 0025 · Ops hardening · Runtime privileges

Configure a Pod security context

RBAC is the API. A security context is the Linux process.

Lesson 0024 covered who a Pod is to the Kubernetes API: a ServiceAccount plus RBAC. That identity does not limit what the process can do on the node. A container that runs as user ID (UID) 0 can still affect the node if the runtime allows it.

This lesson covers the other half. A security context sets the process user, Linux capabilities, and related flags. Pod Security Admission can enforce the Pod Security Standards on a namespace. At work, this is how you stop an app from running as root on a node. In the homelab, you use the same fields at a smaller scale.

Security context and Pod Security Standards

A security context defines privilege and access-control settings for a Pod or a container. Settings include user and group IDs, privileged mode, Linux capabilities, seccomp, and allowPrivilegeEscalation. For more information, see Configure a Security Context for a Pod or Container.

Pod-level fields apply to every container unless a container sets the same field. Container fields override overlapping Pod fields. privileged, capabilities, and allowPrivilegeEscalation exist only on the container.

If you omit securityContext, and the image has no USER instruction, the process runs as UID 0.

spec:
  securityContext:                    # Pod: UID, seccomp, fsGroup
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    securityContext:                  # Container: overrides + Linux flags
      allowPrivilegeEscalation: false
      capabilities:
        drop: ["ALL"]

The Pod Security Standards define three cumulative profiles:

ProfileMeaning
privilegedNo restrictions. Typical for some system components.
baselineBlocks known privilege escalations. Allows a default Pod spec.
restrictedCurrent hardening: non-root, drop ALL capabilities, explicit seccomp, allowPrivilegeEscalation: false.

For more information, see Pod Security Standards.

Pod Security Admission applies those profiles per namespace with labels. Modes are enforce (reject the Pod), warn, and audit. On OrbStack (k3s), the admission plugin is on. Namespaces are not restricted until you set the labels.

Enforce applies to Pods, not to the Deployment object. kubectl apply on a Deployment can succeed. The ReplicaSet then fails to create Pods. warn and audit do apply to workload objects. For more information, see Pod Security Admission.

Lab: observe, restrict, and recover

OrbStack, context orbstack. Lab files are in yaml/secctx-lab/ in this teaching workspace.

cd yaml/secctx-lab
ls

Expect namespace.yaml, namespace-restricted.yaml, stack.yaml, and the deploy break and fix files.

0

Set the lab namespace on the current context.

kubectl config use-context orbstack
kubectl apply -f namespace.yaml
kubectl config set-context --current --namespace=secctx-lab
1

If you have not set a security context, the process is root. Apply the baseline Deployment and wait until it is Ready.

kubectl apply -f stack.yaml
kubectl rollout status deployment/sleeper --timeout=90s
kubectl exec deploy/sleeper -- id

Output similar to uid=0(root) gid=0(root) groups=0(root). Version-dependent user names can differ; the UID is 0.

2

To match the restricted profile, apply the hardened spec.

kubectl apply -f deploy-restricted.yaml
kubectl rollout status deployment/sleeper --timeout=90s
kubectl exec deploy/sleeper -- id

UID 1000, not 0. Confirm the fields:

kubectl get pod -l app=sleeper -o yaml | grep -A8 securityContext

runAsNonRoot: true, runAsUser: 1000, drop: ALL.

3

Break A — runAsNonRoot: true with runAsUser: 0.

kubectl apply -f deploy-root-conflict.yaml
kubectl get pods -l app=sleeper
kubectl describe pod -l app=sleeper | tail -n 25

The new Pod is not Ready. Events mention runAsNonRoot and UID 0. The kubelet refuses to start the container. This is not an RBAC Forbidden.

Fix:

kubectl apply -f deploy-fixed.yaml
kubectl rollout status deployment/sleeper --timeout=90s

Ready again. kubectl exec deploy/sleeper -- id shows UID 1000.

4

Break B — privileged: true. Privileged mode disables most container isolation.

kubectl apply -f deploy-privileged.yaml
kubectl rollout status deployment/sleeper --timeout=90s
kubectl exec deploy/sleeper -- id
kubectl exec deploy/sleeper -- grep CapPrm /proc/1/status

UID 0 again. CapPrm is a large hex value, not all zeros. Contrast with the restricted Pod: drop ALL clears that mask. Your admin kubeconfig is unchanged. This is the process on the node, not API access from lesson 0024.

Fix:

kubectl apply -f deploy-fixed.yaml
kubectl rollout status deployment/sleeper --timeout=90s
5

Break C — enforce restricted on the namespace, then apply the root Deployment.

kubectl apply -f namespace-restricted.yaml
kubectl apply -f stack.yaml
kubectl get deploy,rs,pods -l app=sleeper
kubectl get events --field-selector reason=FailedCreate --sort-by=.lastTimestamp | tail -n 8

The Deployment object is stored. New Pods are rejected. Events mention PodSecurity restricted (non-root, drop ALL, seccomp, or allowPrivilegeEscalation). Old Ready replicas may keep running during the failed rollout. For more information, see Enforce Pod Security Standards with Namespace Labels.

Your turn: read the FailedCreate message. List the controls the profile required.

Fix:

kubectl apply -f deploy-fixed.yaml
kubectl rollout status deployment/sleeper --timeout=90s
kubectl exec deploy/sleeper -- id

Rollout succeeds under enforce=restricted. UID 1000.

6

Clean up.

kubectl delete namespace secctx-lab
kubectl config set-context --current --namespace=default
Production: set a restricted-style securityContext in the workload, and label the namespace to enforce it. Pin enforce-version to a Kubernetes minor version. latest is fine on a local cluster. Prefer a Role plus RoleBinding in the app namespace (lesson 0024) together with a non-root security context. Neither replaces the other.

Quiz

1. A Pod has no securityContext. The image has no USER instruction. Which UID does the container process use?

2. Pod securityContext sets runAsUser: 1000. The container sets runAsUser: 2000. Which UID runs?

3. runAsNonRoot: true and runAsUser: 0 are both set. What happens?

4. The namespace has enforce=restricted. You apply a Deployment whose template is privileged. What happens?

5. A RoleBinding is correct, but the container runs as UID 0 with privileged: true. What is still true?
