Desired State & the Control Loop

The one idea everything else in Kubernetes hangs off.

Your homelab node loses power at 3 a.m. and reboots. At work, a deploy gets killed mid-rollout. In both cases, minutes later, everything is running again — and nobody typed a command. This lesson is about why. If you internalize this one mechanism, most Kubernetes behavior stops being magic and becomes predictable.

The Idea

You don't give Kubernetes commands. You give it a desired state — a description of the world you want — and the cluster works continuously and forever to make reality match it.

Every object you create carries two halves [docs]:

  • spec — the state you want. You write this.
  • status — the state it actually has. The system writes this.

The gap between the two is closed by controllers: loops that watch state through the API server, compare desired with actual, and act to close the difference [docs]. The docs use a thermostat analogy: you set the temperature (desired state); the thermostat works whenever needed to hold it (current state). It never "finishes."

Why pods come back from the dead: when you declare a Deployment with replicas: 3, that's recorded in etcd as desired state. Kill a pod and the count of actual pods (2) no longer matches desired (3) — so the controller creates a replacement. It isn't healing your pod; it's reconciling a number. The old pod is gone forever. Pods are cattle, not pets.

One consequence worth saying out loud: kubectl never "does" anything to your containers. It writes desired state to the API server, and the machinery — controllers, the scheduler, the kubelet on each node — takes it from there. That's also why a node reboot is survivable: the desired state never lived on the node. It lives in etcd, and reconciliation resumes the moment the machinery can act again.

Lab — Watch Reconciliation Happen (~10 min)

Run this against your local OrbStack cluster. Open two terminals.

1

Make sure OrbStack is running with Kubernetes enabled (OrbStack app → Kubernetes, or orb start k8s), then point kubectl at it and confirm the node is up:

kubectl config use-context orbstack
kubectl get nodes

Expect: one node named orbstack with status Ready — OrbStack runs your whole cluster inside a single lightweight VM on your Mac. That one machine plays both control plane and worker node.

Now declare a desired state — 3 replicas of nginx:

kubectl create deployment hello --image=nginx --replicas=3
2

In terminal 2, watch pods continuously (leave this running for the whole lab):

kubectl get pods -w

Expect: three pods named hello-<hash>-<hash> progressing to Running.

3

Back in terminal 1 — be the 3 a.m. power cut. Kill a pod (copy a real name from the watch):

kubectl delete pod hello-xxxxxxxxx-xxxxx

Watch terminal 2: the pod goes Terminating, and a new pod with a different name appears almost instantly. You deleted; the controller reconciled. Note that nothing was "restarted" — it was replaced.

4

Now look at the two halves of the Deployment object directly:

kubectl get deployment hello -o yaml | grep -A4 "^spec:" 
kubectl get deployment hello -o yaml | grep -A6 "^status:"

Find replicas: 3 under spec (what you asked for) and readyReplicas: 3 under status (what exists). Those two numbers disagreeing, briefly, is what you just watched in step 3.

5

Change desired state and watch the loop chase it:

kubectl scale deployment hello --replicas=5   # gap: 3 actual vs 5 desired
kubectl scale deployment hello --replicas=1   # gap: 5 actual vs 1 desired

Terminal 2 shows pods created, then four terminated. Same mechanism in both directions — you never said "create" or "delete," you only changed a number.

6

Clean up:

kubectl delete deployment hello

All pods terminate — the desired state is now "no deployment," and the loop reconciles to that too.
