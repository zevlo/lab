Lesson 0003 · Kubernetes Fundamentals

Ingress: One Door, Many Services

HTTP routing as desired state — and your first hand-written manifest.

In lesson 0002 you exposed one app with one LoadBalancer on one port. Now scale that thought to your homelab: a dashboard, a media server, a wiki, a Grafana… one LoadBalancer each, every one on its own port you have to remember? In the cloud, each one is a billable load balancer. The grown-up answer is one door with a routing table — and that's Ingress.

The Idea

An Ingress is an API object that holds HTTP routing rules: requests for this hostname (or path) go to that Service [docs]. Two things to hold onto:

  • An Ingress is pure data. By itself it routes nothing — exactly like a Deployment is "pure data" until controllers act on it. The acting part is an Ingress controller: a reverse proxy running in the cluster that watches Ingress objects and reconfigures itself to match [docs]. You already know this shape — it's the control loop, applied to HTTP routing. Desired state: your rules. Actual state: the proxy's live config.
  • Ingress routes to Services, not pods. Each rule's backend names a Service and a port. The Ingress controller gets traffic to the Service; the Service's selector (lesson 0002) takes it from there. Each layer solves one problem.

Most clusters make you install a controller. OrbStack does not ship one — you'll install Traefik once via Helm (skip if you already have it from a prior lesson). After install, it gets a LoadBalancer Service reachable at *.k8s.orb.local from your Mac [OrbStack docs].

The mental model in one line: Ingress is a routing table stored as desired state; a controller (Traefik) is the thermostat that keeps a real reverse proxy matching it.

Lab — One Door, Two Apps (~20 min)

Against OrbStack. This lab includes your first hand-written manifest and a deliberately broken stage — you've earned it.

0

One-time setup — install Traefik if you don't already have an Ingress controller:

helm repo add traefik https://traefik.github.io/charts
helm repo update
helm install traefik traefik/traefik

Expect: release traefik deployed. kubectl get svc traefik shows type LoadBalancer with ports 80 and 443.

1

Confirm Traefik is alive and holding the door:

kubectl config use-context orbstack
kubectl get pods -l app.kubernetes.io/name=traefik
kubectl get svc traefik

Expect: a running traefik-… pod, and a Service of type LoadBalancer with ports 80 and 443. That's the one door.

2

Deploy two different apps, each with a plain ClusterIP Service — no LoadBalancers this time:

kubectl create deployment hello --image=nginx --replicas=2
kubectl expose deployment hello --port=80

kubectl create deployment whoami --image=traefik/whoami --replicas=2
kubectl expose deployment whoami --port=80

whoami is a tiny server that echoes back which pod served you — perfect for watching routing and load-balancing happen.

3

Now write your first manifest. Create a file called ingress.yaml (anywhere, e.g. your workspace) with exactly this:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: front-door
spec:
  ingressClassName: traefik
  rules:
  - host: hello.k8s.orb.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: hello
            port:
              number: 80
  - host: whoami.k8s.orb.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: whoami
            port:
              number: 80

Read it before applying — per the mission, you should be able to predict what the cluster will do. Two rules, two hostnames, two Service backends. ingressClassName says which controller handles it. Then declare it:

kubectl apply -f ingress.yaml
kubectl get ingress

Expect: front-door with hosts hello.k8s.orb.local,whoami.k8s.orb.local.

4

Knock on the door. Same port, different hostnames, different apps:

curl -s http://hello.k8s.orb.local | head -n 4
curl -s http://whoami.k8s.orb.local
curl -s http://whoami.k8s.orb.local   # run it a few times

Expect: nginx HTML from the first; from whoami, a report including Hostname: whoami-… — and across repeated calls, the hostname alternates between the two pods. You're watching Service-level load balancing through the Ingress. OrbStack resolves *.k8s.orb.local on your Mac automatically — http://hello.k8s.orb.local and http://whoami.k8s.orb.local work in a browser too.

If hello.k8s.orb.local doesn't answer: confirm Traefik is running (kubectl get svc traefik), the Ingress exists (kubectl get ingress), and OrbStack Kubernetes is started (orb start k8s). Hostnames must match your Ingress rules exactly — *.k8s.orb.local, not *.localhost.
5

Diagnose and fix. Break it on purpose: in ingress.yaml, change the whoami backend's port number: 80 to number: 8080, then re-apply and probe:

kubectl apply -f ingress.yaml
curl -s http://whoami.k8s.orb.local

Expect: an error from Traefik instead of a pod report. Before reading on — diagnose it yourself with:

kubectl describe ingress front-door

Look at the Backends column: the whoami rule now points at whoami:8080. Depending on your kubectl version it may or may not flag an explicit error — the reliable tell is the mismatch itself. Cross-check with kubectl get svc whoami: the Service exposes no port 8080, so the controller has nowhere to send traffic. The route is only as good as the Service behind it. Fix the port back to 80, re-apply, confirm the curl works again. This exact mismatch — Ingress port vs Service port vs container port — is one of the most common real-world Kubernetes tickets.

6

Clean up (note the symmetry: you declared with a file, you delete with the same file):

kubectl delete -f ingress.yaml
kubectl delete deployment hello whoami
kubectl delete service hello whoami
