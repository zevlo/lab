Lesson 0011 · Kubernetes Fundamentals

LimitRange & ResourceQuota: Namespace Guardrails

Caps for the whole namespace; defaults and ceilings per pod.

Lesson 0009 taught per-container requests and limits. Lesson 0007 taught namespaces as scope boundaries. At work, platform teams cap each team's namespace so one deploy cannot starve everyone else. In the homelab, the same objects keep your experiments from accidentally scheduling fifty nginx pods on a single OrbStack node. Two policies, one namespace — this lesson teaches you to read both.

The Idea

Think in three layers [quota docs] [limit docs]:

LayerWhatQuestion
Container specresources.requests / limitsHow much does this container promise and may use?
LimitRangeNamespace policy on each pod/containerWhat defaults apply when omitted? What min/max per container?
ResourceQuotaNamespace aggregate capWhat is the sum of all pods allowed to consume?

ResourceQuota tracks totals — e.g. requests.cpu: "500m" means the sum of CPU requests across all non-terminal pods in that namespace cannot exceed 500m. Exceed it and new pods are rejected. A Deployment apply may still succeed while its ReplicaSet cannot create pods — watch ReplicaSet Events, not just Deployment status.

LimitRange acts at admission on individual objects: injects defaultRequest / default when a container omits resources; rejects pods above max or below min. Critical pairing: when a namespace has a ResourceQuota on CPU or memory, every new pod must declare requests or limits for that resource — otherwise admission rejects it. LimitRange defaults are how teams avoid typing resources on every manifest.

The mental model in one line: ResourceQuota caps the namespace total; LimitRange shapes each pod (defaults + min/max). Per-pod requests/limits from lesson 0009 still drive scheduling — quotas just add up those promises.

One more rule that saves debugging time: neither policy retrofits running pods. Tighten a quota and existing pods keep running; only new creates fail. Same as lesson 0001 — admission is the gate, not a retroactive sweep.

Lab — Quota, Defaults, and Two Breaks (~25 min)

OrbStack, namespace homelab. You'll install policies, hit quota twice (admission + scale), then break LimitRange max.

1

Orient.

kubectl config use-context orbstack
kubectl create namespace homelab --dry-run=client -o yaml | kubectl apply -f -
kubectl config set-context --current --namespace=homelab
2

Install a tight ResourceQuota. Create quota.yaml:

apiVersion: v1
kind: ResourceQuota
metadata:
  name: homelab-quota
spec:
  hard:
    requests.cpu: "300m"
    requests.memory: 512Mi
    pods: "6"
kubectl apply -f quota.yaml
kubectl describe resourcequota homelab-quota

Expect: Hard shows your caps; Used is mostly zero (system may show small usage depending on version — focus on your workloads below).

3

Break — deploy without resources. Quota is active; LimitRange is not yet. Create a Deployment with no resources block:

kubectl create deployment web --image=nginx:1.29 --replicas=2
kubectl get pods -l app=web
kubectl describe rs -l app=web | tail -15

Expect: Deployment exists but pods do not become Ready — often zero running pods. ReplicaSet Events mention quota and that pods must specify requests or limits for cpu/memory. The Deployment looks fine at a glance; the ReplicaSet tells the truth.

4

Add LimitRange defaults. Create limits.yaml:

apiVersion: v1
kind: LimitRange
metadata:
  name: homelab-limits
spec:
  limits:
  - type: Container
    default:
      cpu: 100m
      memory: 128Mi
    defaultRequest:
      cpu: 50m
      memory: 64Mi
    max:
      cpu: 200m
      memory: 256Mi
kubectl apply -f limits.yaml
kubectl delete deployment web
kubectl create deployment web --image=nginx:1.29 --replicas=2
kubectl rollout status deployment/web
kubectl get pod -l app=web -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[0].resources.requests.cpu}{"\n"}{end}'

Expect: two Running pods. Requests show 50m — injected by LimitRange, not in your imperative command. describe resourcequota now shows requests.cpu Used around 100m (2 × 50m).

5

Break — exceed namespace total. Scale past the 300m CPU request cap (6 replicas × 50m = 300m is the ceiling):

kubectl scale deployment web --replicas=7
kubectl get pods -l app=web
kubectl describe rs -l app=web | tail -12
kubectl describe resourcequota homelab-quota | grep -A6 Used

Expect: at most six Running pods; seventh not created. ReplicaSet Events: FailedCreate / exceeded quota. Quota Used at the Hard limit. Deployment desired replicas = 7, actual < 7 — another case where apply or scale succeeding ≠ full health.

6

Break — exceed LimitRange max. Create greedy.yaml — one pod asking above the 200m per-container max:

apiVersion: v1
kind: Pod
metadata:
  name: greedy
spec:
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.9
    resources:
      requests:
        cpu: 500m
      limits:
        cpu: 500m
kubectl apply -f greedy.yaml

Expect: Error from server (Forbidden) — admission rejects at the API, before scheduling. Message references maximum CPU on LimitRange. Different from step 5 (quota aggregate) and lesson 0009 Pending (node allocatable).

7

Fix and clean up. Scale back, delete lab objects:

kubectl scale deployment web --replicas=2
kubectl delete -f greedy.yaml 2>/dev/null; true
kubectl delete deployment web
kubectl delete -f limits.yaml -f quota.yaml
kubectl delete namespace homelab
kubectl config set-context --current --namespace=default
Three different "blocked" signals: step 3 — no resources declared under quota (must specify requests). step 5 — namespace total exceeded (ReplicaSet FailedCreate). step 6 — single pod over LimitRange max (403 Forbidden on apply). Match the symptom to the policy layer.
