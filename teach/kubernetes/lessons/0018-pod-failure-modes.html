Pod Failure Modes: Pending, OOM, and Scheduling

Same STATUS column — three different components blocking progress.

Lesson 0017 gave you the funnel. Lesson 0009 introduced requests vs limits; lesson 0015 introduced PVC binding. This lesson connects all three under pressure: a pod that looks broken in kubectl get may be failing for completely different reasons — scheduler, kubelet, or volume binder — and each reason wants a different next command. At work, misreading CrashLoopBackOff as "bad code" when the real reason is OOMKilled sends you down the wrong rabbit hole. In the homelab, a single OrbStack node makes scheduling failures immediate: there is no bigger node to absorb an impossible request.

The Idea

Three families of pod failure that share a STATUS but differ in who is blocking and what to read [failure reasons]:

What you seeWho blockedContainer started?First move
Pending + FailedSchedulingSchedulerNodescribe pod Events → compare requests to node allocatable
Pending + unbound PVCVolume binder / provisionerNoget pvc → describe pvc (RELATED object)
CrashLoopBackOff + OOMKilledkubelet (cgroups)Yes, then killeddescribe pod → Last State: OOMKilled (exit 137 on many clusters) — not app logs first

The trap from lesson 0017 still applies: CrashLoopBackOff is a symptom, not a diagnosis. Exit code 1 with boom in logs (lesson 0017 Break C) is an application crash. Reason: OOMKilled with exit 137 is the memory limit — fix the manifest's limits.memory (or the leak), not the startup command.

Pending has sub-types. Always read Events before picking a tool. Insufficient cpu → scheduling (lesson 0009). unbound PersistentVolumeClaims → storage (lesson 0015). exceeded quota → namespace policy (lesson 0011). Same STATUS, different RELATED object.

When scheduling is the suspect, one more command earns its place:

kubectl describe node | grep -A12 "Allocated resources"

That shows how much of the node's allocatable capacity is already promised by other pods' requests. On a one-node homelab cluster, a pod asking for 999 CPU cannot land anywhere — the Events say so explicitly.

Lab — Three breaks, one funnel (~25 min)

OrbStack, context orbstack. Lab files in yaml/pod-failure-lab/:

cd ~/projects/teach/kubernetes/yaml/pod-failure-lab
ls

Expect namespace.yaml, oom-bad.yaml, oom-fixed.yaml, greedy-bad.yaml, greedy-fixed.yaml, volume-bad.yaml, volume-fixed.yaml. For each break: STATUS → Events → RELATED before reading the fix file.

0

SCOPE — confirm cluster, pin namespace.

kubectl config current-context
kubectl apply -f namespace.yaml
kubectl config set-context --current --namespace=pod-failure-lab

Expect orbstack. Namespace pod-failure-lab created; all following commands omit -n.

1

Orient — what can this node spare?

kubectl get nodes
kubectl describe node | grep -A6 Allocatable
kubectl describe node | grep -A12 "Allocated resources"

Expect one node. Note allocatable CPU and memory — you'll compare against impossible requests in Break B.

2

Break A — OOMKilled disguised as CrashLoopBackOff.

kubectl apply -f oom-bad.yaml
kubectl get pods -w

Expect STATUS CrashLoopBackOff, RESTARTS climbing. The Deployment keeps restarting a container that allocates 200M inside a 64Mi cgroup cap.

Your turn: run the funnel. Do not open oom-fixed.yaml yet.

kubectl describe pod -l app=mem-stress | grep -A6 "Last State:"
kubectl describe pod -l app=mem-stress | tail -n 12

Expect Reason: OOMKilled (exit code is often 137; OrbStack may show 1 — trust Reason). Events may mention memory limit. Application logs are often empty or unhelpful here — the kubelet killed the process before it could print much.

Fix — raise memory request and limit in the manifest:

kubectl apply -f oom-fixed.yaml
kubectl get pods -w

Expect Running then Completed (stress exits after hanging). Delete the Deployment before the next break:

kubectl delete -f oom-fixed.yaml
3

Break B — scheduler cannot place the pod.

kubectl apply -f greedy-bad.yaml
kubectl get pod greedy
kubectl describe pod greedy | tail -n 15

Expect Pending indefinitely. Events: FailedScheduling / Insufficient cpu. No OOM — the container never started. Optional cross-check:

kubectl describe node | grep -A12 "Allocated resources"

Even with a mostly idle node, 999 CPU requests cannot fit on one OrbStack node. This is lesson 0009's scheduling break, now inside the troubleshooting funnel.

Fix:

kubectl delete pod greedy
kubectl apply -f greedy-fixed.yaml
kubectl get pod greedy

Expect Running within a few seconds.

4

Break C — Pending while a PVC never binds. RELATED layer from lesson 0015:

kubectl apply -f volume-bad.yaml
kubectl get pods,pvc
kubectl describe pod volume-wait | tail -n 15

Expect pod Pending (may show ContainerCreating briefly). PVC app-data stays Pending. Pod Events mention unbound PersistentVolumeClaims or waiting on volumes. Diagnose the binding object, not the scheduler:

kubectl describe pvc app-data | tail -n 12

Events mention missing StorageClass typo-path or no provisioner. The pod is innocent — the claim cannot bind.

Fix — PVC storageClassName is immutable; delete and recreate with the correct class:

kubectl delete pod volume-wait
kubectl delete pvc app-data
kubectl apply -f volume-fixed.yaml
kubectl get pods,pvc -w

PVC Bound (OrbStack local-path may wait until the pod exists — WaitForFirstConsumer). Pod reaches Running.

5

Clean up.

kubectl delete namespace pod-failure-lab
kubectl config set-context --current --namespace=default
Three different Pending stories: Break B — scheduler Events (Insufficient cpu). Break C — PVC Events (wrong StorageClass). Lesson 0011 adds a fourth — exceeded quota at admission. Write which one you see in incident notes before editing YAML.

Quiz

1. Pod CrashLoopBackOff; describe shows Reason: OOMKilled, exit 137. Teammate opens application logs first. Best response?

2. Pod Pending five minutes; Events say FailedScheduling: Insufficient cpu. Most useful next check?

3. Pod Pending; Events mention unbound PersistentVolumeClaims. First RELATED object to inspect?

4. Container exceeds limits.memory while running. Which component enforces that, and what exit code?

5. Homelab pod Pending; Events say exceeded quota: cpu. Which prior lesson object is blocking, and where do you read it?
