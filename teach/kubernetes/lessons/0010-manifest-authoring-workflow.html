Lesson 0010 · Kubernetes Fundamentals

Manifest Authoring: Scaffold, Strip, Apply

How engineers actually produce the YAML they commit.

Nine lessons in, you've written plenty of YAML by hand. At work you'll mostly edit manifests someone else wrote. Starting a homelab service from scratch, the usual move is different: scaffold with kubectl, edit the spec, validate, apply — the same declarative control loop from lesson 0001, with a repeatable pipeline in front of it. This lesson makes that pipeline muscle memory.

The Idea

Three sources, in order of how often they appear in production [docs]:

SourceTypical use
Copy / editDefault at work — fork a sibling service, tweak image, probes, resources
--dry-run=client -o yamlScaffold a kind you rarely write; greenfield homelab services
MemorySmall edits to patterns you know — Deployment skeleton, where probes live — not every field

The homelab pipeline (what you'll lab today):

# 1. Scaffold structure (client-side — no cluster write)
kubectl create deployment api --image=nginx:1.29 --replicas=2 \
  --dry-run=client -o yaml > deploy.yaml

# 2. Edit spec by hand — probes, resources, labels

# 3. Validate before committing / applying
kubectl apply --dry-run=server -f app.yaml
kubectl diff -f app.yaml

# 4. Declare desired state
kubectl apply -f app.yaml

Two dry-run modes — confusing names, different jobs:

ModeWhere it runsPurpose
--dry-run=clientYour machineGenerate YAML; no API call
--dry-run=serverAPI serverValidate schema + admission; still no persist

If you export live objects (kubectl get deploy api -o yaml), you get server cruft — status, resourceVersion, managedFields. Strip those before git; you write spec, the system writes status [glossary]. Client dry-run output is usually clean already.

kubectl diff shows the gap between your file and the cluster — a preview of what apply would change [docs]. Critical habit: apply succeeding does not mean the app works — a typo in a Service selector is valid YAML and a successful apply, but endpoints stay empty (lesson 0002 bites again).

The mental model in one line: dry-run scaffolds shape; you own the spec; server dry-run + diff gate the apply; describe/get diagnose when behavior surprises you.

Later at scale: Helm and Kustomize generate the same YAML with less copy-paste — see lesson 0013 (Kustomize) and lesson 0014 (Helm); same apply at the end.

Lab — From Zero to app.yaml (~25 min)

OrbStack, namespace homelab. You'll build one committed manifest the way an engineer would — not typed from a blank editor.

1

Orient.

kubectl config use-context orbstack
kubectl create namespace homelab --dry-run=client -o yaml | kubectl apply -f -
kubectl config set-context --current --namespace=homelab
2

Scaffold. Generate Deployment and Service skeletons — nothing hits the cluster yet:

kubectl create deployment api --image=nginx:1.29 --replicas=2 \
  --dry-run=client -o yaml > deploy.yaml

kubectl create service clusterip api --tcp=80:80 \
  --dry-run=client -o yaml > svc.yaml

cat deploy.yaml svc.yaml

kubectl expose deployment looks up the Deployment in the cluster — it fails if you haven't applied yet, even with --dry-run=client. create service clusterip scaffolds locally; kubectl sets selector: app: api to match the Deployment above.

Expect: valid apiVersion, kind, spec blocks. Client dry-run may include an empty status: on the Service — drop it when merging. Pod labels (app: api) should match the Service selector.

3

Edit. Merge into app.yaml (one file, two documents, --- separator — same pattern as lesson 0005). Under the container, add a readiness probe and resources from lessons 0005 and 0009:

readinessProbe:
  httpGet:
    path: /
    port: 80
  periodSeconds: 2
resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "256Mi"

Delete the scratch deploy.yaml and svc.yaml once merged. This edit step is what dry-run cannot do for you.

4

Validate, then apply.

kubectl apply --dry-run=server -f app.yaml
kubectl diff -f app.yaml
kubectl apply -f app.yaml
kubectl rollout status deployment/api
kubectl get pods,endpoints

Expect: server dry-run prints object names, no error. First diff shows all resources as new (nothing live yet). After apply: pods Running/Ready; endpoints/api lists pod IPs.

kubectl port-forward svc/api 8080:80   # terminal 2
curl -s localhost:8080 | head -n 1

Expect: nginx HTML.

5

See what not to commit. Export the live Deployment — notice server-owned fields:

kubectl get deployment api -o yaml | grep -E '^(  )?(status|resourceVersion|managedFields|uid):'

Expect: lines for status:, resourceVersion:, etc. Your app.yaml should have none of these. If you ever "copy from cluster," strip them first.

6

Break it. In app.yaml, typo the Service selector — change app: api to app: apii under spec.selector only (leave Deployment pod labels as app: api). Apply:

kubectl apply -f app.yaml
kubectl get endpoints api
kubectl port-forward svc/api 8081:80
curl -s --connect-timeout 2 localhost:8081 | head -n 1

Expect: apply reports service/api configured — no error. But endpoints/api shows <none> or empty addresses. Port-forward may hang or connection refused — no backends. Valid manifest, broken wiring. Diagnose:

kubectl describe service api | grep -A3 Selector
kubectl get pods --show-labels

Expect: selector app=apii, pod labels app=api — mismatch.

7

Fix it. Restore selector app: api. Use diff before re-applying:

kubectl diff -f app.yaml
kubectl apply -f app.yaml
kubectl get endpoints api
curl -s localhost:8081 | head -n 1

Clean up:

kubectl delete -f app.yaml
kubectl delete namespace homelab
kubectl config set-context --current --namespace=default
Two different "dry-run" lessons: step 2 generates YAML locally. step 4 validates against the server. step 6 proves apply success ≠ working service — watch endpoints, not just apply output.
