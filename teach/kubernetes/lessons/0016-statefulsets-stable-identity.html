Lesson 0016 · Kubernetes Fundamentals

StatefulSets: Stable Identity

Predictable pod names, one disk each, ordered scaling.

Lesson 0015 wired a PVC into a bare Pod. That works for a demo — but a Postgres Helm chart does not create loose Pods. It creates a StatefulSet: pod postgres-0 always maps to PVC data-postgres-0, and if the pod dies, the replacement is still postgres-0 on the same disk. At work, any clustered database, Kafka broker, or etcd member uses this pattern. In the homelab, it is what separates "I mounted a volume once" from "I can run a real database."

The Idea

A Deployment treats pods as interchangeable — random suffixes, parallel rollouts, any pod can serve traffic. A StatefulSet gives each replica a stable identity [docs]:

PropertyDeploymentStatefulSet
Pod nameweb-6d4b8c-x7k2m (random)web-0, web-1 (ordinal)
StorageYou wire PVCs manually; often shared or nonevolumeClaimTemplates → PVC per ordinal
Scale-upAll replicas at onceOrdered: 0 Ready, then 1, then 2…
Network identityService load-balances to any podHeadless Service → DNS per pod

Two objects work together:

Headless Service (clusterIP: None)
       +
StatefulSet (serviceName: matches Service name)
  ├── pod db-0  ──▶  PVC data-db-0
  └── pod db-1  ──▶  PVC data-db-1   (when replicas: 2)

volumeClaimTemplates is the StatefulSet superpower from lesson 0015: instead of creating PVCs yourself, the controller creates <templateName>-<statefulsetName>-<ordinal> — e.g. template data + StatefulSet db + pod db-0 → PVC data-db-0.

Delete pod db-0 → the StatefulSet controller recreates db-0 (not db-0-xyz), remounting data-db-0. Delete a Deployment pod → replacement gets a new random name; unless you wired storage carefully, it may not remount the same claim.

The mental model in one line: Deployment = cattle; StatefulSet = pets with name tags and their own hard drives.

Per-pod DNS (via the headless Service): db-0.db.ss-lab.svc.cluster.local resolves to pod db-0's IP — peers can find each other by hostname in clustered apps.

Lab — Headless Service, StatefulSet, Break a PVC (~30 min)

OrbStack. Needs StorageClass local-path from lesson 0015. You'll deploy a one-replica StatefulSet, prove stable identity + persistence, scale to two, then break by deleting a PVC. Files in e.g. ~/ss-lab/.

1

Orient.

kubectl config use-context orbstack
kubectl get storageclass local-path

Expect local-path present. If missing, re-run the provisioner install from lesson 0015 step 1.

2

Deploy headless Service + StatefulSet. Save as ss-lab.yaml:

apiVersion: v1
kind: Namespace
metadata:
  name: ss-lab
---
apiVersion: v1
kind: Service
metadata:
  name: db
  namespace: ss-lab
spec:
  clusterIP: None
  selector:
    app: db
  ports:
  - port: 80
    name: http
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
  namespace: ss-lab
spec:
  serviceName: db
  replicas: 1
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      containers:
      - name: app
        image: busybox:1.36
        command: ["/bin/sh", "-c", "echo ordinal-0-$(date +%s) > /data/id.txt && sleep 3600"]
        volumeMounts:
        - name: data
          mountPath: /data
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes:
      - ReadWriteOnce
      storageClassName: local-path
      resources:
        requests:
          storage: 64Mi
kubectl apply -f ss-lab.yaml
kubectl get svc db -n ss-lab
kubectl get statefulset,pod,pvc -n ss-lab

Expect Service with CLUSTER-IP None. StatefulSet db with READY 1/1. Pod named db-0 (not a random suffix). PVC data-db-0 Bound.

kubectl exec -n ss-lab db-0 -- cat /data/id.txt

Expect line like ordinal-0-1718822400. Note the timestamp.

3

Stable identity — delete the pod, not the claim.

kubectl delete pod db-0 -n ss-lab
kubectl get pod db-0 -n ss-lab -w

Expect a new pod still named db-0 (watch until Running). Same PVC data-db-0 — not recreated.

kubectl exec -n ss-lab db-0 -- cat /data/id.txt

Expect the same timestamp as step 2. Contrast with a Deployment: deleted pod would return as db-<new-hash>.

4

Ordered scale-up — one PVC per ordinal.

kubectl scale statefulset db --replicas=2 -n ss-lab
kubectl get pod -n ss-lab -w

Expect db-1 appears only after db-0 is Ready — ordered rollout. Two PVCs: data-db-0 and data-db-1, each Bound.

kubectl exec -n ss-lab db-1 -- sh -c 'echo ordinal-1-$(date +%s) > /data/id.txt'
kubectl exec -n ss-lab db-1 -- cat /data/id.txt

Expect ordinal-1-… on db-1 only — separate disks per ordinal.

5

Break — delete a StatefulSet PVC. The controller does not recreate claims you delete manually:

kubectl delete pvc data-db-1 -n ss-lab
kubectl get pod db-1 -n ss-lab
kubectl describe pod db-1 -n ss-lab | tail -n 12

Expect pod db-1 failing or stuck — events mention missing volume or failed mount. Pod db-0 and PVC data-db-0 are fine. This is why ops runbooks say: never kubectl delete pvc on StatefulSet storage unless you mean permanent data loss.

6

Fix and clean up. Simplest recovery — tear down and redeploy:

kubectl delete statefulset db -n ss-lab
kubectl delete pvc --all -n ss-lab
kubectl delete svc db -n ss-lab
kubectl delete namespace ss-lab

Expect all pods, PVCs, and namespace gone. Re-applying ss-lab.yaml would start fresh with new PVCs.

StatefulSet storage rule: PVCs created from volumeClaimTemplates survive StatefulSet deletion by default — data outlives the controller. Scale-down removes pods but keeps their PVCs too. Plan cleanup explicitly; do not assume delete statefulset wipes disks.
