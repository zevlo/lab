Lesson 0005 · Kubernetes Fundamentals

Probes: Catching the Quiet Failures

Teaching the control loop what "healthy" actually means.

Lesson 0004 ended with a warning: the stuck rollout was contained only because the failure was loud — the image wouldn't even pull. A version that starts cleanly but serves garbage sails straight through, and Kubernetes happily sends it your users. The fix is to give the system a definition of healthy it can check for itself. At work, that's the difference between a bad deploy being a non-event and a pager going off. In the homelab, it's services that heal themselves at 3 a.m. — the same promise as lesson 0001, extended from "running" to "actually working."

The Idea

Out of the box, Kubernetes has one health signal: is the process running? Probes let the kubelet ask better questions, on a schedule, per container [docs]. The two main ones ask different questions and trigger very different consequences — confusing them causes real outages:

ProbeQuestionOn failure
Readiness"Can this pod take traffic right now?"Quarantine. Pod is pulled from the Service's EndpointSlice. Nothing is restarted. When the probe passes again, it rejoins.
Liveness"Is this container beyond saving?"Restart. The kubelet kills and restarts the container.

Two consequences worth internalizing before the lab:

  • Readiness is what closes lesson 0004's gap. During a rollout, the controller only continues once new pods are Ready. Give your pods a real readiness check, and a version that starts-but-doesn't-work stalls the rollout with old pods still serving — the same containment you saw with the bad image tag, now extended to quiet failures.
  • Liveness must never check dependencies. A readiness probe may reasonably check "can I reach my database?" — backing out of traffic while a dependency is down is correct. Put that same check in a liveness probe and a ten-minute database outage becomes every one of your pods restart-looping: an external problem converted into a self-inflicted storm [docs]. Liveness checks the container itself, nothing else.

Mechanically, a probe is one of three checks — httpGet (2xx/3xx passes), tcpSocket (connection passes), exec (exit 0 passes) — run every periodSeconds, acting after failureThreshold consecutive failures [docs]. (There's a third probe type, startup, for slow-booting apps — know it exists; we won't lab it today.)

The mental model in one line: readiness controls membership (am I in the Service?), liveness controls existence (do I get restarted?) — quarantine vs. defibrillator.

Lab — Quarantine, Stall, Self-Heal (~25 min)

Against OrbStack, two terminals. You'll write one manifest and evolve it through three stages.

1

Create web.yaml — a Deployment and its Service in one file (the --- separates documents; this is how related resources usually travel together):

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.29
        readinessProbe:
          httpGet:
            path: /
            port: 80
          periodSeconds: 2
          failureThreshold: 2
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
  - port: 80

Read it first — you should recognize every line by now. Note the Deployment's selector/template.labels pair (what kubectl create deployment was generating for you all along) and the readiness probe: HTTP GET on /, every 2 seconds, two strikes and you're out. Apply and verify:

kubectl config use-context orbstack
kubectl apply -f web.yaml
kubectl get pods
kubectl get endpointslices -l kubernetes.io/service-name=web -o wide

Expect: three pods 1/1 Running, three IPs in the EndpointSlice. The 1/1 means 1 of 1 containers Ready — that column is the readiness probe talking.

2

In terminal 2, keep watch for the whole lab:

kubectl get pods -w
3

Quarantine. Quietly break one pod — make nginx unable to serve / without touching the process (pick any pod name):

kubectl exec <pod-name> -- mv /usr/share/nginx/html/index.html /tmp/

Within ~4 seconds, terminal 2 shows that pod drop to 0/1 — Running, but not Ready. Now check the damage and the containment:

kubectl get endpointslices -l kubernetes.io/service-name=web -o wide
kubectl describe pod <pod-name>   # events: "Readiness probe failed: ... 403"

Expect: the EndpointSlice marks that pod's IP not-ready — traffic flows only to the two healthy pods. RESTARTS is still 0: readiness quarantines, it never restarts. The process is fine; it's just benched. Now heal it:

kubectl exec <pod-name> -- mv /tmp/index.html /usr/share/nginx/html/

Back to 1/1 within seconds, IP back in rotation. Quarantine, release.

4

The quiet failure that 0004 couldn't catch. Ship a version that starts cleanly but serves nothing. In web.yaml, add a command to the container that replaces nginx with an idle process:

      containers:
      - name: nginx
        image: nginx:1.29
        command: ["sleep", "infinity"]   # <-- add this line
        readinessProbe: ...
kubectl apply -f web.yaml
kubectl rollout status deployment/web   # let it hang a moment, then Ctrl-C

Terminal 2: one new pod appears, Running… and stays 0/1 forever. The container is alive (sleep runs fine — a loud check would pass!) but nothing listens on port 80, so readiness never passes, so the rollout stalls with all three old pods still serving. Confirm with kubectl get replicasets: new RS stuck at 1 not-ready pod, old RS still at 3. This is the lesson-0004 caveat, closed. Roll it back and remove the command line from web.yaml:

kubectl rollout undo deployment/web
5

Self-healing. Now add a liveness probe — note it gets a higher threshold than readiness, so quarantine happens before the defibrillator comes out:

        readinessProbe:
          httpGet: { path: /, port: 80 }
          periodSeconds: 2
          failureThreshold: 2
        livenessProbe:            # <-- add this block
          httpGet: { path: /, port: 80 }
          periodSeconds: 2
          failureThreshold: 5
kubectl apply -f web.yaml   # a rollout, of course — watch terminal 2

Once all pods are 1/1 again, break one the same way as before:

kubectl exec <pod-name> -- mv /usr/share/nginx/html/index.html /tmp/

Watch terminal 2 closely. The sequence: 0/1 (readiness quarantines it first) … ~10 seconds later, RESTARTS ticks to 1 (liveness gave up and restarted the container) … then back to 1/1 — because the fresh container has its index.html back. The pod broke, got benched, got restarted, and rejoined — zero humans involved. Verify with kubectl describe pod: events show the readiness failures, the liveness failures, then the kill and re-pull.

6

Clean up:

kubectl delete -f web.yaml
Why this self-heal worked — and when it wouldn't: restarting fixed the problem because the damage was inside the container's filesystem, which a restart resets. A liveness restart fixes wedged processes, deadlocks, leaked memory. It does not fix bad config, bad code, or a down database — that's why liveness must only test the container itself, and why it gets a generous failureThreshold. When in doubt, readiness only.

Quiz — Harder This Time

Four perfect scores means the training wheels come off: these are scenarios, and the wrong answers are things people actually do.

1. A pod's readiness probe starts failing while its liveness probe keeps passing. What does the system do?

2. Your API's liveness probe checks its database connection. The database goes down for ten minutes. What happens to your API pods?

3. You ship a version that starts cleanly but serves only errors on its readiness path. What's the result?

4. Your app needs two minutes of warm-up before it can serve anything. Cleanest way to handle that?

5. kubectl get pods shows 1/1 Running but RESTARTS climbs every few minutes. Which probe is acting, and what's your first diagnostic move?
