Horizontal Pod Autoscaler: Scale on Signals

Let a controller chase load — but only if metrics and requests are wired.

Lesson 0004 taught you to change replica counts through a Deployment. Lesson 0009 taught CPU requests as scheduling promises. The Horizontal Pod Autoscaler (HPA) connects both: a control loop that reads utilization metrics and patches spec.replicas on your workload. At work, this is how a service survives a traffic spike without someone watching Grafana at 3am. In the homelab, it is how a hobby app scales up for a demo and back down so your single OrbStack node breathes again.

The Idea

HPA is another controller [docs]. You declare a target (usually a Deployment), a metric (usually CPU utilization), and bounds (minReplicas / maxReplicas). Every ~15 seconds it:

  1. Asks metrics-server for current pod CPU usage
  2. Compares usage against each pod's CPU request to compute utilization %
  3. Calculates a desired replica count and writes it to the Deployment's spec.replicas

The Deployment and ReplicaSet machinery from lesson 0004 does the rest — create pods, run rollouts, respect readiness. HPA never talks to pods directly.

PieceRole
metrics-serverCluster add-on you install on OrbStack. Aggregates usage from kubelets; powers kubectl top and HPA resource metrics. Requires kubelet feature gate PodAndContainerStatsFromCRI on OrbStack for pod metrics.
CPU requestThe denominator in utilization math. No request → utilization is <unknown> → HPA cannot scale on CPU.
HPAOwns replica count while it exists. Manual kubectl scale is temporary — HPA reconciles back toward its bounds.
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: php-apache
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: php-apache
  minReplicas: 1
  maxReplicas: 5
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50

Three constraints HPA does not override:

  • Scheduler / node capacity. HPA can ask for five pods; if requests exceed allocatable CPU on your one homelab node, extras stay Pending.
  • ResourceQuota. From lesson 0011: HPA may desire more replicas than quota allows — ReplicaSet Events show FailedCreate, not HPA errors.
  • maxReplicas. Load can exceed the target forever; HPA stops at the ceiling.
The mental model in one line: HPA adjusts the Deployment's desired replica count from metrics; everything downstream is the same control loop you already know.

Scale-down is deliberately slower than scale-up (stabilization windows) so a brief lull does not flap replicas. Expect a few minutes after load stops before counts drop — that is policy, not a broken lab.

Lab — Load, Scale Up, Break Requests (~30 min)

OrbStack, namespace hpa-lab. Uses the upstream hpa-example image and a synthetic load generator. Copy manifests from yaml/php-apache.yaml and yaml/load-generator.yaml in this repo, or type them from the steps.

1

Orient and wire metrics. OrbStack does not ship metrics-server — you install it once. HPA and kubectl top both depend on it.

kubectl config use-context orbstack
kubectl cluster-info

Must show https://127.0.0.1:26443 (OrbStack). If you see 6443 and connection refused, your shell is on the old rancher-desktop context — switch with the command above, or start Rancher Desktop if you intentionally use that cluster.

kubectl create namespace hpa-lab --dry-run=client -o yaml | kubectl apply -f -
kubectl config set-context --current --namespace=hpa-lab
kubectl get apiservice v1beta1.metrics.k8s.io

If that returns NotFound, install metrics-server:

helm repo add metrics-server https://kubernetes-sigs.github.io/metrics-server/
helm upgrade --install metrics-server metrics-server/metrics-server \
  --namespace kube-system --create-namespace
kubectl rollout status deployment/metrics-server -n kube-system

No Helm? Use the upstream manifest instead:

kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
kubectl rollout status deployment/metrics-server -n kube-system

OrbStack kubelet gate. Pod-level metrics need CRI stats, not cAdvisor. In OrbStack → Settings → Kubernetes → Kubelet Configuration, paste exactly:

apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
featureGates:
  PodAndContainerStatsFromCRI: true

PodAndContainerStatsFromCRI must sit under featureGates: — a bare top-level line is ignored. After changing this, restart Kubernetes in OrbStack (Settings → Kubernetes → Restart). OrbStack v2.1.1+ may not need the gate; older versions do.

Verify the pipeline:

kubectl get apiservice v1beta1.metrics.k8s.io
kubectl top nodes
kubectl top pod -A

Expect: APIService Available=True; both top commands print CPU/memory columns (values vary). If top nodes works but top pod fails with NotFound, the feature gate is missing or the cluster was not restarted after editing it.

2

Deploy the target workload. Create php-apache.yaml (Deployment + Service) — note the resources.requests.cpu: 200m:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: php-apache
  labels:
    app: php-apache
spec:
  replicas: 1
  selector:
    matchLabels:
      app: php-apache
  template:
    metadata:
      labels:
        app: php-apache
    spec:
      containers:
      - name: php-apache
        image: registry.k8s.io/hpa-example
        ports:
        - containerPort: 80
        resources:
          requests:
            cpu: 200m
---
apiVersion: v1
kind: Service
metadata:
  name: php-apache
spec:
  ports:
  - port: 80
  selector:
    app: php-apache
kubectl apply -f php-apache.yaml
kubectl rollout status deployment/php-apache
kubectl top pod -l app=php-apache

Expect: one Running pod; top shows low CPU at idle (often single-digit millicores).

3

Attach HPA.

kubectl autoscale deployment php-apache --cpu-percent=50 --min=1 --max=5
kubectl get hpa
watch -n2 kubectl get hpa,deploy,pods

Expect: HPA row shows TARGETS like 3%/50% or similar — not <unknown>/50%. REPLICAS 1/1. Press Ctrl+C to leave watch.

4

Generate load and watch scale-up. Apply a load generator (hammers the Service by DNS name):

apiVersion: apps/v1
kind: Deployment
metadata:
  name: load-generator
spec:
  replicas: 3
  selector:
    matchLabels:
      app: load-generator
  template:
    metadata:
      labels:
        app: load-generator
    spec:
      containers:
      - name: busybox
        image: busybox:1.36
        command: ["/bin/sh", "-c", "while true; do wget -q -O- http://php-apache; done"]
kubectl apply -f load-generator.yaml
kubectl get hpa -w

Expect: over 1–3 minutes, TARGETS CPU rises above 50%, REPLICAS climbs toward 5 (or stops lower if the node runs out of allocatable CPU — check kubectl describe node if stuck below 5). Press Ctrl+C when replicas have increased at least once.

5

Stop load and watch scale-down.

kubectl scale deployment load-generator --replicas=0
kubectl get hpa -w

Expect: CPU target drops; replica count falls back toward 1, possibly after several minutes (scale-down stabilization). Do not assume instant shrink.

6

Break — remove CPU requests. Patch the Deployment template so containers have limits but no requests:

kubectl patch deployment php-apache --type=json -p='[
  {"op": "replace", "path": "/spec/template/spec/containers/0/resources",
   "value": {"limits": {"cpu": "500m"}}}
]'
kubectl rollout status deployment/php-apache
kubectl get hpa
kubectl describe hpa php-apache | tail -20

Expect: after new pods roll out, HPA TARGETS shows <unknown>/50%. Replica count stops responding to load — HPA has no denominator for utilization. describe hpa may warn about missing resource metrics. This is the most common production HPA misconfiguration.

7

Fix and clean up. Restore requests, confirm metrics return, then tear down:

kubectl patch deployment php-apache --type=json -p='[
  {"op": "replace", "path": "/spec/template/spec/containers/0/resources",
   "value": {"requests": {"cpu": "200m"}, "limits": {"cpu": "500m"}}}
]'
kubectl rollout status deployment/php-apache
kubectl get hpa
kubectl delete -f load-generator.yaml -f php-apache.yaml
kubectl delete hpa php-apache
kubectl delete namespace hpa-lab
kubectl config set-context --current --namespace=default

Expect: TARGETS numeric again before delete. Namespace gone.

Three different "stuck" signals: <unknown> TARGETS — missing CPU requests or metrics-server down. REPLICAS below DESIRED with Pending pods — node allocatable exhausted. REPLICAS below DESIRED with FailedCreate on ReplicaSet — ResourceQuota cap. Read the right object.

Quiz

1. Deployment pods have no resources.requests.cpu. HPA targets 50% CPU utilization. What does kubectl get hpa show in TARGETS?

2. HPA maxReplicas is 8. Namespace ResourceQuota caps pods at 6 and six are running. Heavy load continues. Result?

3. You run kubectl scale deployment app --replicas=10. An HPA on the same Deployment has minReplicas=2 and maxReplicas=5. A few minutes later?

4. metrics-server is down. kubectl top pod fails. HPA on CPU utilization is active. Effect?

5. HPA scales a Deployment from 2 to 4 replicas during load. A ClusterIP Service selects app=web. How do new pods receive traffic?
