RBAC & ServiceAccounts

Who the Pod is — and what the API will let it do.

NetworkPolicies (0021) control which pods may talk to which pods. They say nothing about talking to the Kubernetes API. At work, a controller, CI Job, or sidecar that lists Secrets needs an identity and a permission grant — not your admin kubeconfig. In the homelab, the same pattern keeps a broken chart from owning the whole cluster. This lesson is the identity half of production safety: ServiceAccount + Role + RoleBinding.

The Idea

Kubernetes separates authentication (who are you?) from authorization (what may you do?). For workloads, the answer to “who” is a ServiceAccount — a namespaced API object, not a human user. Every namespace gets a default ServiceAccount; Pods that omit spec.serviceAccountName use it. By design, that default account has almost no powers beyond API discovery [docs].

Permissions come from RBAC — four object kinds:

ObjectMeaning
RoleRules in one namespace: which resources and verbs (get, list, create, …)
ClusterRoleSame rule shape, but cluster-scoped (or reusable across namespaces when bound carefully)
RoleBindingGrants a Role or ClusterRole to subjects — only inside the binding’s namespace
ClusterRoleBindingGrants a ClusterRole cluster-wide
# Least privilege for a workload that only reads Secrets in its namespace
ServiceAccount  secret-reader
Role            secret-reader   →  get/list/watch on secrets
RoleBinding     read-secrets    →  subject: SA secret-reader
Pod             serviceAccountName: secret-reader
The binding-scope trap. A RoleBinding that references a ClusterRole still grants access only in the RoleBinding’s namespace. Cluster-wide power requires a ClusterRoleBinding. Permissions are additive — there are no deny rules [docs].

Diagnosis tool for this lesson (and for production): kubectl auth can-i with --as=system:serviceaccount:<ns>:<sa>. Your OrbStack admin user can usually do everything — that proves nothing about the Pod [docs].

kubectl auth can-i list secrets \
  --as=system:serviceaccount:rbac-lab:secret-reader \
  -n rbac-lab

Lab — Grant, break, fix (~25 min)

OrbStack, context orbstack. Lab files in yaml/rbac-lab/:

cd ~/projects/teach/kubernetes/yaml/rbac-lab
ls

Expect namespace.yaml, stack.yaml, role/binding/deploy break+fix pairs.

0

SCOPE — lab namespace on context.

kubectl config use-context orbstack
kubectl apply -f namespace.yaml
kubectl config set-context --current --namespace=rbac-lab
1

Baseline — default SA cannot list Secrets. Namespace auto-created default SA; no RoleBinding yet for our custom account.

kubectl get serviceaccount
kubectl auth can-i list secrets \
  --as=system:serviceaccount:rbac-lab:default

default ServiceAccount exists. auth can-i prints no (or a denial). Your admin user without --as may still say yes — that is you, not the Pod.

kubectl auth can-i list secrets

Likely yes as OrbStack admin. Never confuse the two checks.

2

Ship least privilege — SA + Role + RoleBinding + a reader Pod.

kubectl apply -f stack.yaml
kubectl get sa,role,rolebinding,secret,deploy
kubectl rollout status deployment/reader --timeout=60s
kubectl auth can-i list secrets \
  --as=system:serviceaccount:rbac-lab:secret-reader
kubectl auth can-i get pods \
  --as=system:serviceaccount:rbac-lab:secret-reader

Objects present. Deployment Ready. list secrets → yes. get pods → no — Role did not grant pods. Confirm the Pod’s identity:

kubectl get pod -l app=reader -o yaml | grep serviceAccountName

serviceAccountName: secret-reader (not default).

3

Break A — Role grants get but not list.

kubectl apply -f role-bad-verbs.yaml
kubectl auth can-i list secrets \
  --as=system:serviceaccount:rbac-lab:secret-reader
kubectl auth can-i get secret/app-config \
  --as=system:serviceaccount:rbac-lab:secret-reader

list → no. Named get on secret/app-config → yes. Collection list and named get are different verbs [docs].

Your turn: kubectl get role secret-reader -o yaml — confirm verbs is only get.

Fix:

kubectl apply -f role-fixed.yaml
kubectl auth can-i list secrets \
  --as=system:serviceaccount:rbac-lab:secret-reader

yes again.

4

Break B — RoleBinding subject typo. Role is fine; binding points at a non-existent SA name.

kubectl apply -f binding-bad-subject.yaml
kubectl auth can-i list secrets \
  --as=system:serviceaccount:rbac-lab:secret-reader
kubectl get rolebinding read-secrets -o yaml | grep -A5 subjects

can-i → no. Subject shows secret-reedr. The Role still looks correct — the grant never reached the real SA.

Fix:

kubectl apply -f binding-fixed.yaml
kubectl auth can-i list secrets \
  --as=system:serviceaccount:rbac-lab:secret-reader

yes.

5

Break C — Pod references a missing ServiceAccount.

kubectl apply -f deploy-bad-sa.yaml
kubectl get pods -l app=reader
kubectl describe deploy/reader | tail -n 20
kubectl get events --field-selector reason=FailedCreate --sort-by=.lastTimestamp | tail -n 5

New ReplicaSet cannot create pods (or pods never become Ready). Events mention ServiceAccount secret-reedr not found. RBAC Role is irrelevant until the identity exists.

Fix:

kubectl apply -f deploy-fixed.yaml
kubectl rollout status deployment/reader --timeout=60s
kubectl get pod -l app=reader -o yaml | grep serviceAccountName

Rollout succeeds. serviceAccountName: secret-reader.

6

Optional — short-lived token (TokenRequest). Prefer this over long-lived SA token Secrets [docs]:

kubectl create token secret-reader --duration=10m | head -c 40; echo "…"

A JWT prefix prints. Do not paste full tokens into chat logs. Pods normally get projected tokens mounted automatically — you rarely create them by hand.

7

Clean up.

kubectl delete namespace rbac-lab
kubectl config set-context --current --namespace=default
Production note: give each controller / Job its own ServiceAccount and the smallest Role that works. Prefer Role + RoleBinding in the app namespace over ClusterRoleBinding. Never mount long-lived SA token Secrets when a projected token will do.

Quiz

1. A Pod omits serviceAccountName. Which identity does it use?

2. RoleBinding in apps references ClusterRole secret-reader. Where can that subject list Secrets?

3. auth can-i list secrets (no --as) says yes; the app still gets Forbidden. Best next check?

4. Role allows get on secrets only. kubectl get secrets as that SA fails. Why?

5. Deployment sets serviceAccountName: helper but SA helper was never created. Likely result?
