Lesson 0044 · Missing Semester: Code Quality

Code Quality

Format the surface. Lint the antipatterns. Test the behavior. Run the same checks on every commit and every push.

Why this matters

Lesson 0028 gave you checkers you run beside vim: py_compile, mypy, gofmt. Lesson 0042 made those the agent feedback loop. The remaining failure mode is drift. One laptop uses single quotes. A pull request introduces a nested if. A function works on the author’s input and breaks on yours. Nobody reruns the checks after the last “tiny” edit.

Missing Semester’s stack for that: a formatter so the team stops arguing about spaces, a linter so antipatterns fail before review, tests so behavior has a tripwire, and hooks plus CI so the gate runs when you are not watching. Regex is the bonus: it shows up in test selection, search-replace, and log scraping. Learn the building blocks, look up the rest, and reach for a parser when the language is not regular.

Knowledge 1: Format and lint

A formatter rewrites surface syntax: quotes, spaces around operators, import layout, line wrapping. The point is a shared style, so review time goes to the change. Some tools (Prettier) have many knobs: check the config file into git. Some (Black, gofmt) have almost none, on purpose. Ruff’s formatter is Black-compatible with a small config surface. Tonight it is the Python floor. gofmt stays the Go floor from lesson 0028.

A linter runs static analysis: it reads the code without running it, and flags antipatterns the formatter will not touch. Rules come in presets. A good rule page says what it matches, why that is a problem, and what to write instead. Missing Semester’s example is Ruff SIM102: nested if that can be one if with and. Some rules auto-fix. Some false-positive: disable per line (# noqa: SIM102) or in project config after you have read the rule.

JobTonight
rewrite styleruff format
check styleruff format --check (exit 1 if it would rewrite)
flag issuesruff check
apply safe fixesruff check --fix
types / syntaxmypy / py_compile (lesson 0028)

An EditorConfig file records indent size and charset for the repo. IDEs honor it. This mission’s vim stays plugin-free, so the file is still worth committing: it documents the project for everyone else.

semgrep is a “semantic grep”: it matches the parse tree, not characters. That is how you ban subprocess.Popen(..., shell=True) even when the call is split across lines. Character grep is still the drill. semgrep is optional in the scratch venv.

Knowledge 2: Tests, hooks, and CI

A test is code that exercises other code and fails when behavior is wrong. Granularity:

KindScope
unitone function
integrationmodules or services together
functionalan end-to-end scenario

You will mix them. Test-driven development writes the test first. A regression test locks a bug you already paid for. Property-based tests (QuickCheck, Hypothesis for Python) check invariants across many inputs. Mock a database or HTTP API so the suite does not depend on a live third party.

Coverage reports which lines ran during the tests. Use it as a map of untested paths. A high percentage with weak assertions still ships bugs. Services such as Codecov plot that map over time. Tonight: python3 -m coverage run -m pytest, then report -m and html.

A Git pre-commit hook runs before git commit records the snapshot. Nonzero status blocks the commit (lesson 0023). Projects hang formatters and linters here, and sometimes tests. .git/hooks/ is local: it is not committed. The pre-commit framework exists so a YAML file in the repo can install the same hooks for everyone. Tonight the floor is a raw hook that calls a script you do commit.

Hook PATH. A hook does not source your bashrc. It will not see venv/bin just because you activated the venv in Ghostty. Point the hook at "$root/venv/bin" with git rev-parse --show-toplevel, or it will fail with ruff: command not found (or, worse, run some other python3).

Continuous integration runs the same checks on a machine that is not yours: on every push (main does not rot), on every pull request (contributor submissions), and on a schedule (a dependency that claimed SemVer-compatible and was not: lesson 0041). A matrix repeats the job across OS and language versions. The job runs check-only: ruff format --check, not ruff format. CI should fail when the tree is dirty, not rewrite it. Status badges in a README show that result. Continuous deployment uses the same machinery to publish: the class site rebuilds GitHub Pages on push; you can also build wheels or images (lesson 0041).

Study a project like yours: pyproject.toml, .github/workflows/, DEVELOPMENT.md. The class-site build.yml is push + pull_request + a Saturday cron, then a Jekyll build.

A command runner is one name for “run the project’s quality tools.” Missing Semester names just (just lint). npm scripts and Hatch do the same inside the language’s manifest. Tonight: scripts/check, which the hook and CI both call. Skip installing just.

Knowledge 3: Regular expressions

A regex names a set of strings. This lecture uses Python syntax. Flavors differ: grep -E, vim’s :s, and Python re are not the same language. regex101 (flavor: Python) is a good scratchpad. Learn the blocks below, then look the rest up.

PatternMatches
abcthe literal abc
.any one character
[abc] / [^abc]one of / none of
a|beither
\d \w \bdigit, word char, word boundary
? * + {N}0–1, 0+, 1+, exactly N
^ $start / end of line
\. \\a literal dot / backslash
(...)a group you can extract

\d{4}-\d{2}-\d{2} matches 2026-01-14 and also 2026-01-99: shape, not a real date. .+@.+ is a weak email check. Groups: re.match(r"\d{4}-(\d{2})-\d{2}", s).group(1) is the month. In vim’s replace side, that group is \1 (lesson 0003’s :%s, with \( \) on the search side under default magic). VS Code uses $1.

* and + are greedy: they take as much as they can while the rest of the pattern still matches. .* on a JSON line will run to the last quote. .*? is the non-greedy twin. Even then, escaped quotes and nested structure outgrow a regex. HTML is not a regular language. Use the language’s parser (json in the stdlib; pyparsing named for harder grammars).

An LLM can draft a pattern from an example log line. You still test it against cases it should miss.

1. Formatter, linter, hook

Missing Semester: configure a formatter, linter, and pre-commit hooks on a project. Autoformat first. For leftover linter errors, let an agent run the linter, edit, and re-run until status 0. Read the diff.

cd /tmp/ms-quality
source venv/bin/activate
cat > clamp.py <<'EOF'
import os
def clamp(n,lo,hi):
    if n>=lo:
        if n<=hi:
            return n
    if n<lo:
        return lo
    return hi
EOF
cat > pyproject.toml <<'EOF'
[project]
name = "ms-quality"
version = "0.1.0"
requires-python = ">=3.11"

[tool.ruff.lint]
select = ["E", "F", "SIM"]
EOF
cat > .editorconfig <<'EOF'
root = true

[*.py]
indent_style = space
indent_size = 4
EOF
cat > .gitignore <<'EOF'
venv/
htmlcov/
.coverage
__pycache__/
.pytest_cache/
EOF
ruff format --check clamp.py; echo "status=$?"
ruff format clamp.py
ruff check clamp.py; echo "status=$?"
ruff check --fix clamp.py
ruff check clamp.py

Expect format --check to exit 1 (it would add spaces and a blank line). After ruff format and ruff check --fix, the unused import os is gone. SIM102 remains: nested if. Ask this agent: “In /tmp/ms-quality, run ruff check, fix SIM102, re-run until status 0. Do not touch other files.” Confirm the tool calls. Then read clamp.py in vim. Then:

mkdir -p scripts
cat > scripts/check <<'EOF'
#!/bin/sh
set -e
root=$(git rev-parse --show-toplevel)
export PATH="$root/venv/bin:$PATH"
cd "$root"
ruff format --check .
ruff check .
python3 -m pytest
EOF
chmod +x scripts/check
git init -b main
git add clamp.py pyproject.toml .editorconfig .gitignore scripts/check
git config user.email drill@example.com
git config user.name Drill
# hook: same PATH trick, tests optional here so a missing test file is not a blocker yet
cat > .git/hooks/pre-commit <<'EOF'
#!/bin/sh
set -e
root=$(git rev-parse --show-toplevel)
export PATH="$root/venv/bin:$PATH"
cd "$root"
ruff format --check .
ruff check .
EOF
chmod +x .git/hooks/pre-commit
# dirty the format, try to commit, then restore
printf '\n' >> clamp.py
ruff format --check clamp.py; echo "dirty=$?"
git add clamp.py
git commit -m "add clamp"    # hook should block
ruff format clamp.py
git add clamp.py
git commit -m "Add clamp with ruff-clean style."
show answer

ruff format --check exits 1 on the cramped def clamp(n,lo,hi). ruff format rewrites it and exits 0 (a successful rewrite is still 0 unless you pass extra flags). ruff check then reports F401 (os unused, auto-fixable) and SIM102 (nested if; fix is unsafe by default, so --fix leaves it). Combining into if n >= lo and n <= hi is the SIM102 page. The hook blocks a commit whose file would be reformatted. After ruff format, the commit goes through. scripts/check is the command you will hang on CI. The hook must put venv/bin on PATH: it does not inherit your activated shell.

2. Tests and coverage

Missing Semester: learn a testing library, write a unit test, generate an HTML coverage report, then improve coverage by hand and with an agent. Ask whether the agent’s tests are actually good.

cd /tmp/ms-quality
source venv/bin/activate
cat > test_clamp.py <<'EOF'
from clamp import clamp

def test_inside():
    assert clamp(5, 0, 10) == 5
EOF
python3 -m coverage run -m pytest -q
python3 -m coverage report -m
python3 -m coverage html
# open htmlcov/index.html in a browser; the below-lo and above-hi paths should be uncovered

Write two more tests: below lo, above hi. Re-run coverage. Then restore to only test_inside and ask this agent to raise coverage while running python3 -m coverage run -m pytest and report -m. Read the tests: would they fail if clamp always returned n?

show answer

With one inside-path test, the n < lo branch and the final return hi stay red (about 62% on the nested-if shape; similar after SIM102 collapses). assert clamp(-1, 0, 10) == 0 and assert clamp(99, 0, 10) == 10 cover those paths. HTML: red lines are the map. An agent that only asserts clamp(x, x, x) == x can paint the file green and still miss a broken bounds check. A test is good when a wrong return would fail it. pytest collects test_* functions; assert is the API. unittest is stdlib if you ever want zero extra packages.

3. CI, check-only

Missing Semester: set up CI on every push to run format, lint, and tests. Break the tree on purpose and confirm CI catches it.

Write the workflow. Run the same commands locally (that is the job). Inspect the class-site file. Skip a GitHub push unless you want a throwaway repo.

cd /tmp/ms-quality
mkdir -p .github/workflows
cat > .github/workflows/ci.yml <<'EOF'
name: ci
on:
  push:
  pull_request:
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: python -m pip install ruff pytest
      - run: ruff format --check .
      - run: ruff check .
      - run: python -m pytest
EOF

# needs test_clamp.py from exercise 2 (pytest exits 5 on an empty suite)
./scripts/check; echo "clean=$?"
# break format, same check-only command CI will run:
python3 -c 'open("clamp.py","a").write("x=1+2\n")'
ruff format --check .; echo "broken=$?"
ruff format clamp.py   # restore
# class-site: push + pull_request + Saturday cron, then Jekyll (check-only build)
SITE=/tmp/ms-git/class-site
sed -n '1,20p' "$SITE/.github/workflows/build.yml"
show answer

Local ./scripts/check is the CI job: format check, lint, tests. After appending x=1+2, ruff format --check exits 1. That is the catch. A job that ran ruff format (rewrite) would green-pass a dirty PR and hide the drift. Class-site build.yml (verified on current master): on.push, on.pull_request, schedule cron 0 8 * * 6, then bundle exec jekyll build. A failed Jekyll build fails the job. Their link checker is a second workflow; it often fails on third-party sites and still earns its keep. A real GitHub push is optional. If you do it, use a throwaway repo, not a spam PR on the class site.

4. grep versus the parse tree

Missing Semester: write a regex and grep for subprocess.Popen(..., shell=True). Break the regex. See whether semgrep still matches.

cd /tmp/ms-quality
cat > dangerous.py <<'EOF'
import subprocess
subprocess.Popen("true", shell=True)
subprocess.Popen(
    "true",
    shell=True,
)
subprocess.Popen("true", shell = True)
EOF
grep -n 'Popen.*shell=True' dangerous.py
grep -n 'shell=True' dangerous.py
grep -n 'shell = True' dangerous.py

Optional: python3 -m pip install semgrep then semgrep -l python -e 'subprocess.Popen(..., shell=True, ...)' dangerous.py. Otherwise skip the install: the point is already on the screen.

show answer

Popen.*shell=True hits only the one-line call. The split call still has shell=True on its own line; a same-line pattern misses it. shell = True (spaces) misses both tight patterns. An AST tool matches the call and the keyword regardless of whitespace and wrapping. semgrep’s -e "subprocess.Popen(..., shell=True, ...)" is that tool. A tiny stdlib stand-in if you skip the install:

python3 - <<'PY'
import ast
src = open("dangerous.py").read()
for node in ast.walk(ast.parse(src)):
    if isinstance(node, ast.Call) and ast.unparse(node.func).endswith("Popen"):
        for kw in node.keywords:
            if kw.arg == "shell":
                print(f"line {node.lineno}: shell={ast.unparse(kw.value)}")
PY

All three calls print. Character grep cannot do that reliably.

5. Bullet markers in vim

Missing Semester: replace Markdown - bullets with * in these lecture notes. A replace-all of every hyphen is wrong. Lesson 0042 did this with sed. Tonight: vim (lesson 0003).

cd /tmp/ms-quality
curl -sL https://raw.githubusercontent.com/missing-semester/missing-semester/master/_2026/code-quality.md -o notes.md
# in vim:  vim notes.md
#   :%s/^\(\s*\)- /\1* /
#   :wq
grep -nE '^\s*[-*] |2026-01-23|--fix|pre-commit' notes.md | head
show answer

:%s/^\(\s*\)- /\1* / only rewrites a hyphen that starts a list item (optional indent, then - ). Dates (2026-01-23), flags (--fix), and words (pre-commit) stay. \( \) is vim’s group under default magic; \1 is that indent on the replace side. :%s/-/*/g would smash all of those. Same rule as the sed -E in lesson 0042: s/^([[:space:]]*)- /\1* /.

6. Greedy JSON, then a parser

Missing Semester: capture the name from {"name": "Alyssa P. Hacker", "college": "MIT"}. Your first regex may swallow the rest of the line. Read greedy quantifiers. Then handle an escaped quote. Then use the JSON parser instead: stdin in, name out.

cd /tmp/ms-quality
source venv/bin/activate
python3 <<'PY'
import re
s = '{"name": "Alyssa P. Hacker", "college": "MIT"}'
print("greedy:   ", re.search(r'"name": "(.*)"', s).group(1))
print("nongreedy:", re.search(r'"name": "(.*?)"', s).group(1))
PY
# 6a. escaped quote inside the name
python3 <<'PY'
import re, json
s = '{"name": "Alyssa \\"P\\" Hacker", "college": "MIT"}'
print("json:    ", json.loads(s)["name"])
m = re.search(r'"name": "((?:\\.|[^"\\])*)"', s)
print("regex:   ", m.group(1) if m else None)
PY
# 6b. the tool you actually ship
cat > name_from_json.py <<'EOF'
import json, sys
print(json.load(sys.stdin)["name"])
EOF
printf '%s\n' '{"name": "Alyssa P. Hacker", "college": "MIT"}' | python3 name_from_json.py
printf '%s\n' '{"name": "Alyssa \"P\" Hacker", "college": "MIT"}' | python3 name_from_json.py
show answer

Greedy .* runs to the last quote: Alyssa P. Hacker", "college": "MIT. .*? stops at the first close-quote: Alyssa P. Hacker. Escaped quotes: the ugly ((?:\\.|[^"\\])*) captures Alyssa \"P\" Hacker still with backslashes. json.loads / json.load(sys.stdin)["name"] returns Alyssa "P" Hacker for both inputs. One line past the import. That is the production tool. Regex is for shape checks and editor replace, not for nested structured data.

  3. What does a coverage report measure, and how should you use it?
  4. Why does a pre-commit hook need venv/bin on PATH?
  5. Why does grep 'Popen.*shell=True' miss a split call?

show answer

(a) Formatter: surface syntax (quotes, spaces, wrapping) so the team shares a style. Linter: static analysis of antipatterns the formatter will not rewrite (SIM102, unused imports).
(b) Check-only fails the job when the tree would be rewritten. A rewrite in CI hides drift and surprises the author.
(c) Which lines executed. Use it as a map of untested paths. A high percentage is not the same as tests that would fail on a broken return.
(d) The hook does not source bashrc or inherit your activated venv. Without venv/bin, it cannot see ruff, or it runs the wrong interpreter.
(e) . does not match a newline, so a Popen whose shell=True sits on the next line misses a same-line pattern. An AST search still sees the keyword.
(f) Greedy .* eats through later quotes. json.load handles escapes and structure. Ship the parser.

Check your understanding

Four questions. Answers shuffle on each page load.

Q1A formatter versus a linter:

  • A formatter rewrites surface syntax so the team shares a style; a linter analyzes without running and flags antipatterns
  • A formatter proves the program is correct on every input; a linter rewrites quotes and spaces until the file is pretty
  • A formatter runs the test suite on every save; a linter deploys the wheel to the package index for you
  • A formatter records why a constant is 1492; a linter writes the README funnel for a later stranger

Q2A CI job should run formatters, linters, and tests:

  • In check-only mode, so a drift fails the job instead of rewriting the tree on the CI machine
  • In fix mode, so CI commits a cleaned tree back to the branch the author just pushed
  • Only on the author’s laptop, because those tools already ran before the last commit
  • Only as a coverage percentage, because a green badge means the tests would catch a break

Q3A coverage report tells you:

  • Which lines executed while the tests ran, as a map of untested paths, not a score to maximize
  • How many assertions each test contains, as a proof that a wrong return would fail the suite
  • How fast the suite runs on CI, as a budget you must stay under before you merge
  • How many linter rules fired, as a count of antipatterns the formatter already rewrote

Q4To pull a name out of a JSON object, you:

  • Use the language’s JSON parser; greedy .* swallows later keys, and escaped quotes outgrow a regex
  • Use greedy .* as the production parser, because it is faster than the stdlib and never over-matches
  • Use non-greedy .*? for HTML and JSON with no false positives, so you can skip the stdlib
  • Use vim \1 alone to validate dates, emails, and nested JSON objects in one substitute
