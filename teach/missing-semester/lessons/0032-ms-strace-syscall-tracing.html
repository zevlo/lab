Lesson 0032 · Missing Semester — Debugging & Profiling

System-call tracing

strace: watch every request a program makes of the kernel — files it opens, sockets it takes, why it waits. The Lecture-4 slice for the bug that lives at the program↔OS boundary, where L0031’s pdb can’t see.

Why this matters

L0031’s toolkit works inside a program you can edit and re-run: prints and pdb watch your own variables. Plenty of real triage isn’t like that. The program is a binary you didn’t compile, a service already running, a tool that hangs with no error at all. System-call tracing moves the observation point to the boundary: every request the program makes of the kernel — opening files, allocating memory, creating processes, accepting connections. MS calls this family (with bpftrace) the highest-leverage DevOps debugging tool in the lecture. And it answers the question L0023 left open: a nonzero exit status tells you it failed; the trace shows you where — the openat() that came back -1 ENOENT.

Read first (≈10 min): MS Debugging and Profiling — the “System Call Tracing” section, strace/dtruss subsection. Skim the bpftrace paragraphs; they are named later, not drilled.

Knowledge 1 — the program↔kernel boundary

Everything a program wants from the outside world — files, memory, network, other processes — it asks the kernel for via a system call. User code runs unprivileged; the syscall is the guarded door. strace sits at that door and logs every crossing:

execve("/bin/ls", ["ls", "/"], 0x... /* 25 vars */) = 0
openat(AT_FDCWD, "/", O_RDONLY|O_DIRECTORY)     = 3
getdents64(3, 0x... /* 20 entries */, 32768)    = 616
close(3)                                         = 0
write(1, "bin\nboot\ndev\n...", 49)              = 49
exit_group(0)                                    = ?

Read each line as syscall(arguments) = result. Three things to recognize on sight:

LineMeansRecall hook
execve firstthe kernel loads and runs the program — the traced command itself“the load verb”
write(1, …)a write to fd 1 = stdout — the program’s output IS this syscallL0009 streams
= -1 ENOENTa failed open — the file it wanted does not exist (there)the smoking gun

File descriptors 0/1/2 are stdin/stdout/stderr (L0009). And note the last line: exit_group(0) — the exit status you have read as $? since L0023 is literally a syscall argument. The trace also lands on stderr, so strace ls / > /dev/null shows the trace alone and strace ls / 2>/dev/null shows the clean run — L0009 redirect skill, reused.

Knowledge 2 — the five strace shapes

MS lists five invocations. They compose: pick what to trace, whether to follow children, live or from birth, timed or not.

InvocationAnswersRecall hook
strace ./progeverything, from the first execve“all of it”
strace -e trace=file ./progonly file-related calls — cut the noise“what files?”
strace -f ./progfollow children too — MS: “important for programs that start other programs”f = family
strace -p <PID>attach to a process already running; Ctrl-C detaches“it’s alive — observe in place”
strace -T ./progtime spent in each call (<0.000123>)“where does it wait?”
Where to run it. strace is Linux — same posture as ss in L0010. Drill it in the L0030 dev container (a disposable Linux box) or over SSH on a Linux remote. On macOS/BSD the equivalent is dtruss, which wraps dtrace: it needs sudo, and SIP-protected system binaries resist it — named, not drilled, same posture as gdb in L0031. On a shared remote, attaching with -p generally needs sudo too; in your own container you are root.

Knowledge 3 — triage patterns

Four shapes cover most real use:

SymptomMoveWhat you see
fails silently, no message-e trace=filethe openat(… config …) = -1 ENOENT it died on
spawns helpers, pipeline-shaped-fpipe2 + clone + a child execve per stage
service already runningpgrep (L0008) → -p PIDtraffic arriving (accept4) or not; no restart needed
hangs / slow for no reason-Tthe one call with a multi-second <…> — the wait made visible

The common thread is the L0031 cardinal rule, one level down: don’t assume what the program did with the OS — watch the actual calls. A debugger inspects state inside the program; a syscall trace inspects its behavior at the boundary. Each sees what the other can’t. One honest caveat, straight from MS’s bpftrace paragraphs: tracing this way traps every syscall, so it slows the target — fine for triage, wrong for load. The low-overhead kernel-depth version is bpftrace, named below.

Drill — at the door

Ghostty + bash + vim, tmux for panes. The trace runs on Linux: the L0030 container posture (nothing lands on the Mac; --rm cleans up). An SSH Linux remote works identically — add sudo for installs and -p attaches.

  1. Cold-name the slice: what is a system call, and what can a syscall trace show that L0031’s pdb cannot?
    show answer

    A syscall is a program’s request for a kernel service (open a file, allocate memory, spawn a process, accept a connection). The trace shows behavior at the program↔kernel boundary — for binaries you can’t step through, services already running, and waits that never appear as a variable value. pdb inspects state inside a program you can re-run and edit; strace inspects what any program does to the OS.

  2. Boot the Linux box and first trace. On the Mac: 
    docker run --rm -it -p 4444:4444 --name ms-trace debian bash
# inside the container:
apt-get update && apt-get install -y strace python3
strace ls /
    Scroll to the top. Three cold reads: (a) which syscall is line 1 and why, (b) which call carries the directory listing itself, (c) find the write(1, …) lines and say what fd 1 is. Then prove the trace lives on stderr, L0009-style: strace ls / > /dev/null vs strace ls / 2>/dev/null.
    show answer

    (a) execve("/bin/ls", …) — the kernel loading the traced command itself. (b) openat on the directory, then getdents64 reads the entries, close when done. (c) fd 1 = stdout; the listing you normally see is exactly that write(1, "bin\nboot\n…"). Redirects: > /dev/null discards stdout → only the trace remains; 2>/dev/null discards the trace → only the listing remains. Trace = stderr, listing = stdout.

  3. Cut the noise. -e trace=file shows only file-related calls: 
    strace -e trace=file ls -l /
    Look at what appears before ls even starts (hints: /etc/ld.so.cache, locale files). One sentence: what is that pre-show, and what does -e trace=file buy you?
    show answer

    The dynamic linker and libc startup run first — hunting shared libraries (ld.so.cache) and locale data before main() ever executes. -e trace=file filters to file-related calls only, so “what files does it touch” stays readable instead of drowning in mmap/read/housekeeping noise.

  4. A pipeline from the kernel’s side. L0016 composed ls | wc -l in the shell; here is what the kernel saw: 
    strace -f bash -c 'ls | wc -l' 2>&1 | grep -E 'execve|pipe|clone'
    Name the three acts you spot, and one sentence on why -f was mandatory.
    show answer

    Three acts: pipe2([3, 4]) creates the pipe; clone (or clone3) forks each stage; each child gets its own execve (ls, wc). Without -f, strace follows only the parent (bash) and you’d see the pipe built but never the children that do the work — MS’s “important for programs that start other programs.”

  5. Attach to a live service (L0008 + L0031 callback). Pane A in the container: 
    python3 -m http.server 4444
    Pane B in the container (a second docker exec -it ms-trace bash from the Mac, or a tmux split): 
    pgrep -f http.server          # L0008
strace -p <PID> -T
    Then from the Mac: curl -i http://localhost:4444/ >/dev/null. Watch pane B: an accept4 arrives, a socket is read, and — L0031 callback — the access-log line you read there is itself a write(1, "127.0.0.1 - - …"). Detach with Ctrl-C; the server keeps running. One sentence: why attach rather than restart-and-trace?
    show answer

    Same logic as L0031’s debugger-vs-print call: attaching observes the real process — its state, its traffic, its waits — without paying a restart (lost in-memory state, dropped connections) and without owning the code. For “is the service even receiving requests / where is it stuck,” pgrep → strace -p is the whole loop, and Ctrl-C detaches without killing it. Cleanup when done: kill <PID> (L0008), exit the container, --rm already took care of the rest.

  6. Cold rebuilds (no peeking):
    1. All five strace shapes from memory, with the question each answers.
    2. Why is execve always line 1 — whose syscall is it?
    3. One sentence: pdb vs strace observation point.
    4. Name the macOS equivalent, and the one-line reason it isn’t drilled tonight.
    show answer

    (a) plain = everything; -e trace=file = what files; -f = follow children; -p PID = attach to a running process; -T = time per call.
    (b) It’s the kernel loading the traced command itself — the door you walked in through.
    (c) pdb watches state inside a program you can edit/re-run; strace watches its behavior at the kernel boundary — any binary, running or fresh.
    (d) dtruss (wraps dtrace) — needs sudo and fights SIP on system binaries, so the drill runs on a Linux box instead.

Later. bpftrace/eBPF — MS’s lower-overhead, kernel-depth sibling: aggregations (syscall counts), filtering by comm/PID, runs as root and watches the whole kernel; reach for it when plain tracing is too slow or you need counts, not lines. Still open in Lecture 4: network debugging (tcpdump/Wireshark — pairs with L0010), memory debugging (ASan/Valgrind), record-replay (rr, named L0031), AI-for-debugging, and the whole Profiling half. Check your understanding

Four questions. Shuffled answers.

Q1What does strace actually show you?

  • every system call the program makes to the kernel
  • every function call made inside your own code
  • every packet crossing the machine’s network card
  • every line of source the interpreter executes

Q2Why does MS call -f “important for programs that start other programs”?

  • children are traced too — without it you only follow the parent
  • it makes strace run noticeably faster on large binaries
  • it filters the trace down to file-related calls only
  • it forces strace to follow the system’s font cache

Q3A binary fails with no error message. You want the files it tried to open. Which move?

  • strace -e trace=file ./prog
  • strace -T ./prog
  • strace -p ./prog
  • strace -f -T ./prog

Q4A service is already running and you suspect it’s stuck. How do you see its syscalls without restarting it?

  • pgrep for the PID, then strace -p <PID> to attach
  • run strace ./service — it attaches to the live copy
  • run strace -f ./service so children are included
  • send kill -9, then trace the core dump it leaves

Ask the teacher. Did the boundary framing land — pdb inside the program, strace at the kernel door? Did execve-first, write(1, …), and the -p attach loop click in the container? Any surprise that the trace itself rides stderr?
