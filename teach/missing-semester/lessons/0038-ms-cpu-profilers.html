Lesson 0038 · Missing Semester — Debugging & Profiling

CPU profilers

time says the program is slow. A profiler names the function. Sample in production; trace when you need exact call counts.

Why this matters

L0036 gave you three numbers for the whole command. L0037 gave you a series. Neither names which function is on the CPU. MS: people say “profiler” and usually mean a CPU profiler — the tool that turns “it’s slow” into a stack. Premature optimization is still the root of all evil; today is how you find the hot spot before you rewrite anything.

Read first (≈8 min): MS Debugging and Profiling — “CPU Profilers” (stop before “Memory Profilers”). Skim the slow.c exercise so the drill looks familiar.

Knowledge 1 — two kinds of profiler

KindWhat it doesCost
samplingwakes up on a timer (often ~1 ms), records the current stack, goes back to sleeplow — the default for production
tracingrecords every function callhigh — exact call counts, caller/callee

A sample is a vote: “this stack was on-CPU just now.” Ten thousand votes later, the wide frames are the hot path. You miss a function that ran for 50 µs between ticks; you do not miss the one that ate 80% of the run. Tracing never misses a call — and pays for it (Valgrind-class slowdown, L0034).

Knowledge 2 — perf, then a flame graph

perf is the standard Linux sampler. No recompile. Two invocations from MS:

perf stat ./slow_program          # counters for the whole run
perf record -g ./my_program       # stack samples → perf.data
perf report                       # read them

perf-record(1): -g means record a call graph. Default unwind is fp (frame pointers). gcc -O2 omits those unless you pass -fno-omit-frame-pointer — that is why L0035 treated frame pointers as a profiling habit, not a debugger nicety. Without them the stacks come out truncated; --call-graph dwarf is the fallback that uses -g debug info instead.

perf stat’s hardware lines (cycles, instructions, branches) need a PMU. This Docker-on-Mac VM does not expose one — same gap as rr (L0034). Those lines print <not supported>. Software events still work: task-clock, context-switches, page-faults. For recording stacks, pick the software timer Gregg uses in VMs:

perf record -e cpu-clock -g ./slow

A flame graph (Brendan Gregg) turns those stacks into a picture:

AxisMeans
ystack depth — bottom is main’s ancestors, top edge is what is on-CPU
widthhow often that frame appeared in the samples (∝ time on CPU)
left → rightnot a timeline — stacks are sorted alphabetically

MS’s “time taken proportional to the X axis” is the width claim. The gotcha operators miss: a frame on the right is not “later.” Click-to-zoom is why the SVG is interactive. MS’s pipeline:

perf script | stackcollapse-perf.pl | flamegraph.pl > flamegraph.svg

Speedscope and Perfetto are named viewers for the same data (not drilled). Language-specific cousins — Python cProfile / py-spy, Go pprof, Rust cargo-flamegraph — named only.

This box needs two extra flags MS does not write. (1) -e cpu-clock — default cycles is hardware and will fail here. (2) docker run --privileged — perf_event is blocked otherwise. Not a production posture; callgrind does not need it. If perf complains it cannot find a binary for this kernel, Debian’s /usr/bin/perf is a wrapper: run the versioned binary it names (perf_* under /usr/bin or /usr/lib/linux-tools-*).

Knowledge 3 — callgrind, the tracing profiler

L0034’s forward pointer: Valgrind is “a really powerful controlled execution environment.” callgrind is the CPU tool in that suite. It traces every instruction, so you get exact call counts and caller/callee — and a large slowdown. MS:

valgrind --tool=callgrind ./my_program
callgrind_annotate callgrind.out.<pid>

callgrind_annotate lists functions by self cost (instructions in that function, not its children). Pass --inclusive=yes to fold callees in — main should sit near 100%. --cache-sim=yes optionally simulates the cache (named, not run). kcachegrind is the GUI (named, like gnuplot’s window in L0037).

Sampling vs tracing on the same program: perf is the one you attach to a live service; callgrind is the one you run overnight on a short test when you need “sin was called N times.”

Drill — name the hot function

Ghostty + bash + vim. Scratch on the Mac at /tmp/ms-cpu/ is the container’s /work (L0030 -v/-w), so the SVG is waiting for open. perf and callgrind are Linux — apt in the box, nothing on the Mac. An SSH Linux remote works identically (and there the PMU may actually work — try perf stat without -e and see).

  1. Cold-name the slice: sampling vs tracing; why production prefers sampling; the three flame-graph facts (y, width, not a timeline).
    show answer

    Sampling: periodic stack snapshots, low overhead. Tracing: every call, exact counts, slow. Production → sampling, you can afford it on the live box. Flame graph: y = stack depth (top = on-CPU); width ∝ samples; left-to-right is alphabetical, not time.

  2. Boot a privileged box with the scratch dir mounted. On the Mac: 
    mkdir -p /tmp/ms-cpu
docker run --rm -it --privileged -v /tmp/ms-cpu:/work -w /work --name ms-cpu debian bash
# inside:
apt-get update && apt-get install -y gcc valgrind linux-perf git ca-certificates
    If perf stat -- sleep 0.1 says it cannot find a kernel-matched binary, run the versioned one the message names. Confirm software events live and hardware does not: 
    perf stat -- sleep 0.1
    show answer

    task-clock / context-switches / page-faults have numbers. cycles / instructions / branches are <not supported> — no PMU in this VM, same class as rr. If even software events fail, you forgot --privileged.

  3. MS’s slow.c (CC BY-NC-SA), with two knobs so callgrind can finish. In /work: 
    cat > slow.c <<'EOF'
#include <math.h>
#include <stdio.h>

#ifndef OUTER
#define OUTER 100
#endif
#ifndef WORK
#define WORK 1000
#endif

double slow_computation(int n) {
    double result = 0;
    for (int i = 0; i < n; i++) {
        for (int j = 0; j < WORK; j++) {
            result += sin(i * j) * cos(i + j);
        }
    }
    return result;
}

int main(void) {
    double r = 0;
    for (int i = 0; i < OUTER; i++) {
        r += slow_computation(WORK);
    }
    printf("Result: %f\n", r);
    return 0;
}
EOF
gcc -g -O2 -fno-omit-frame-pointer slow.c -o slow -lm
time ./slow
    MS compiled -g -O2 -lm; the extra flag is L0035, so perf record -g can walk frames. time prints three numbers (L0036). One sentence: what does it not name?
    show answer

    real ≈ user (this is CPU work, not wait). It does not name slow_computation, sin, or cos. That is the gap this slice fills.

  4. perf stat, then record. Still the full binary: 
    perf stat ./slow
perf record -e cpu-clock -g ./slow
perf report --stdio | head -n 40
    Where is the time? Then the flame graph (MS’s pipeline; scripts from Gregg’s repo): 
    git clone --depth 1 https://github.com/brendangregg/FlameGraph.git
perf script | FlameGraph/stackcollapse-perf.pl | FlameGraph/flamegraph.pl > flame.svg
    On the Mac (another pane): open /tmp/ms-cpu/flame.svg. Click the wide leaf. What is on-CPU, and who called it?
    show answer

    perf stat: task-clock near 100% of one CPU; hardware lines unsupported. perf report / the SVG: wide top frames are sin and cos (libm); under them slow_computation, then main. Width is samples, not a timeline — the two trig leaves sit side by side because they both ran a lot, not because one happened “after” the other.

  5. callgrind — exact counts, smaller run. Full OUTER=100 / WORK=1000 is ~20–50× slower under Valgrind; shrink it: 
    gcc -g -O2 -fno-omit-frame-pointer -DOUTER=4 -DWORK=50 slow.c -o tiny -lm
valgrind --tool=callgrind ./tiny
callgrind_annotate --auto=no --inclusive=yes --show-percs=yes callgrind.out.*
    Self vs inclusive: which function has the instructions, and which one includes them? One sentence on when you would pick this over perf.
    show answer

    Self cost piles up in sin / cos (or inlined trig). Inclusive: slow_computation and main near the top of the run — they called the leaves. Pick callgrind when you need exact call counts or a caller/callee graph on a short test; pick perf on anything live. --cache-sim=yes and kcachegrind stay named.

  6. Cold rebuilds (no peeking):
    1. Sampling vs tracing, and which one production uses.
    2. The two perf invocations, plus the extra event this box needs.
    3. Why -fno-omit-frame-pointer sits next to -g for perf record -g.
    4. Flame graph: y, width, and the timeline mistake.
    5. callgrind: the two commands, self vs inclusive.
    show answer

    (a) Periodic stacks vs every call; production → sampling.
    (b) perf stat ./prog; perf record -g ./prog then perf report. Here: -e cpu-clock (and --privileged).
    (c) Default unwind is frame pointers; -O2 drops them unless you keep them. -g names the frames; pointers let -g (the perf flag) walk them.
    (d) y = depth, top = on-CPU; width ∝ samples; left-to-right is not time.
    (e) valgrind --tool=callgrind ./prog; callgrind_annotate callgrind.out.*. Self = instructions in that function; inclusive = self + callees.

Check your understanding

Four questions. Shuffled answers.

Q1A sampling profiler vs a tracing profiler — what is the difference that matters in production?

  • Sampling records periodic stacks (low overhead); tracing records every call (exact, slow)
  • Sampling needs a recompile; tracing attaches to any binary with no flags
  • Sampling only works on Python; tracing is the C/C++/Rust tool
  • Sampling prints time’s three numbers; tracing is just perf stat with more rows

Q2On a flame graph, a wide frame on the right means:

  • That stack appeared in many samples — width ∝ on-CPU time; left-to-right is not a timeline
  • That function ran last, because X is wall-clock from start to exit
  • That function allocated the most heap; CPU flame graphs plot RSS
  • gnuplot sorted the CSV by the second column again

Q3perf record -g on a -O2 binary: why also compile with -fno-omit-frame-pointer?

  • Default unwind is frame pointers; -O2 drops them, so stacks come out truncated
  • Frame pointers are how gcc writes the perf.data file format
  • Without them callgrind cannot count instructions at all
  • -g (the compiler flag) is illegal unless frame pointers are on

Q4In this Docker-on-Mac box, perf stat prints <not supported> for cycles. What still works, and why?

  • Software events (task-clock, cpu-clock) — the VM has no PMU, same gap as rr
  • Nothing — perf cannot run in any container, only on bare metal
  • Hardware events still work if you pass -g; software events never do
  • cycles is a callgrind counter; perf stat is the wrong tool

Ask the teacher. Did sin/cos show as the wide leaves? Did <not supported> on cycles make the PMU gap click? Prefer the SVG or perf report’s text?
