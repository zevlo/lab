Debugging fundamentals

The golden rule, print-vs-log discipline, and a debugger (pdb) for when prints run out. The first slice of MS lecture 4 — what reaches for after the L0028 checkers pass and the program is still wrong.

Why this matters

L0030 closed MS lecture 3 (Dev Environment). Lecture 4 opens with the line every bug fixes back to: code does not do what you expect it to do, but what you tell it to do. Debugging is the work of closing that gap. The lecture is dense — it splits, the way Lectures 1–3 did. This slice is the foundational debugging half: the golden rule, printf debugging vs logging, and one debugger driven by hand. It targets the bug class the L0028 checkers can’t touch: a program that is syntactically valid, type-clean, and still wrong — a logic bug.

Read first (≈10 min): MS Debugging and Profiling — the “Printf Debugging and Logging” and “Debuggers” sections only. Skim the rest; it is later slices.

Knowledge 1 — the golden rule + printf vs logging

Once py_compile / mypy / gofmt (L0028) pass — 0 exit status (L0023) — syntax and type errors are off the table. What remains is a logic bug: the code runs, and does the wrong thing. MS names two escalating approaches:

ApproachWhat it isReach for it when
printfad-hoc print() around the suspected region; iterate until the cause is visibleyou know roughly where the bug is and re-running is cheap
logging“printing with care” — a framework with severity levels, routable output, structured fieldsthe diagnostic should survive the fix; for services / long-running code

MS’s durable advice: once a print finds the bug, convert it into a proper log statement instead of deleting it — next time a similar bug appears, the diagnostic is already there. Severity levels (DEBUG / INFO / WARNING / ERROR) let you filter after the fact.

Third-party logs. Many programs take -v / --verbose (repeatable on some) to print more. Services write logs under /var/log/ on Linux; systemd services show theirs via journalctl -u <service>. That is the ops-triage counterpart to in-code prints, and it pairs with the L0008 ops loop (pgrep → curl -i → kill).

Knowledge 2 — the debugger concept + pdb

Prints work when you know what to print and re-running is cheap. A debugger wins when you don’t yet know what to print, when the bug only shows under hard-to-reproduce conditions, or when a restart is expensive (long startup, complex state). It lets you interact with execution as it happens: halt at a line, step one instruction at a time, inspect variable values, halt conditionally, read the call stack.

Launch Python’s pdb three ways:

python3 -m pdb script.py            # from the start
python3 -m pdb -c continue script.py # run until a breakpoint/error
# or inline in the source (Python 3.7+):
breakpoint()                         # drops into pdb here
CommandDoesRecall hook
b / breakset a breakpoint (function or file:line)“stop here”
c / continuerun to next breakpoint / error“go”
n / nextstep over a line (no descent)same line, next

Mission framing. The hands-on debugger here is pdb — Python is the primary language track. MS’s de-facto debugger for C/C++/Rust is gdb, whose command shapes mirror pdb (run/break/step/next/print/bt) — named so you recognize it on a compiled-language remote, not drilled tonight.

Knowledge 3 — the debug loop + tidy logs

The loop, stated as a discipline:

reproduce  →  isolate  →  inspect  →  fix  →  gate
   make it      narrow       look at      change      re-run the
   happen       the blast    the ACTUAL   the code    L0028 checkers
   on demand    radius       value                      + the bug case

The cardinal rule sits in inspect: look at the value the program actually holds, not the one you assumed. An init-to-zero bug is invisible until you p biggest and see 0 where a negative number should be. Most “I don’t understand the bug” moments are really “I haven’t looked at the actual value” moments.

Tidy logs. MS’s profiling half makes the same point, and it matters here too: when you add diagnostic output, shape it so it can be graphed later. A line like 1705012345,42.5 (timestamp,value) is trivial to plot; a prose sentence is not. Prints you add to chase a slow path today become the dataset you profile tomorrow — that sets up the later Lecture-4 profiling slice.

Drill — print, step, gate

Ghostty + bash + vim. Scratch: /tmp/ms-debug/. Reuses the Python track (functions, lists, loops) and the L0028 checkers.

  1. Cold-name the golden rule, and the printf-vs-logging distinction — one sentence each.
    show answer

    Golden rule: code does what you tell it, not what you expect — debugging closes that gap. Printf = ad-hoc print() around the suspected region when re-running is cheap; logging = a framework with severity levels and routable, structured output, kept after the fix so the diagnostic survives.

  2. Reproduce with a print. Write a buggy running_max, run it, watch it return wrong output, then add a print to isolate: 
    mkdir -p /tmp/ms-debug && cd /tmp/ms-debug
cat > running_max.py <<'EOF'
def running_max(numbers: list[int]) -> list[int]:
    result = []
    biggest = 0            # BUG: fails for all-negative input
    for n in numbers:
        if n > biggest:
            biggest = n
        result.append(biggest)
    return result

print(running_max([-5, -2, -9]))   # expect [-5, -2, -2]
EOF
python3 running_max.py
    Output is [0, 0, 0]. Now add print(n, biggest) inside the loop and re-run. One sentence: what does the print show, and what is the fix?
    show answer

    The print shows biggest stuck at 0 across every iteration — the negatives never beat it. Fix: initialize biggest to the first element (biggest = numbers[0]) instead of 0, so a negative first value can become the running max. (Empty-input is a separate edge — out of scope here.)

  3. Re-do it in pdb. Remove the print, drop a breakpoint() on the loop body, and step: 
    cat > running_max.py <<'EOF'
def running_max(numbers: list[int]) -> list[int]:
    result = []
    biggest = 0
    for n in numbers:
        breakpoint()        # <-- drops into pdb here each iteration
        if n > biggest:
            biggest = n
        result.append(biggest)
    return result

print(running_max([-5, -2, -9]))
EOF
python3 running_max.py
    In pdb: type p n, p biggest, then n to step, c to continue to the next iteration. Watch biggest never move off 0. Quit with q. One sentence: what did the debugger show that the print did, without editing the source twice?
    show answer

    Same fact (biggest pinned at 0), but the debugger inspected every variable live without re-editing/re-running for each new value — one p biggest per stop, c to advance. The bug is the init; the debugger just let you stare at the actual value on demand.

  4. Fix, then gate (L0028/L0023 callback). Apply the fix (biggest = numbers[0]) and drop the breakpoint() — write the clean fixed file, then run the L0028 checkers against it: 
    cat > running_max.py <<'EOF'
def running_max(numbers: list[int]) -> list[int]:
    result = []
    biggest = numbers[0]   # FIXED: was 0 — failed for all-negative input
    for n in numbers:
        if n > biggest:
            biggest = n
        result.append(biggest)
    return result

print(running_max([-5, -2, -9]))
EOF
python3 -m py_compile running_max.py && \
  { command -v mypy >/dev/null && mypy running_max.py || true; }; \
  echo "status=$?"
python3 running_max.py   # now prints [-5, -2, -2]
    Expect status=0 and [-5, -2, -2]. One sentence: why was this bug invisible to the L0028 checkers in the first place?
    show answer

    Syntax (py_compile) and types (mypy) were already valid — biggest = 0 is legal, well-typed Python. The bug is a logic bug (a wrong initial value), which checkers cannot see; only running the code or stepping it reveals it. That is exactly the bug class this slice targets after L0028 passes.

  5. Third-party logs (L0008 callback). In one pane, start the stdlib server; in another, hit it and read the request log lines it prints: 
    # pane A
python3 -m http.server 4444
# pane B
curl -i http://localhost:4444/ >/dev/null
    Pane A logs a line like 127.0.0.1 - - [...] "GET / HTTP/1.1" 200 -. One sentence: how is this the same idea as an in-code print, and where would you look on a systemd Linux remote instead?
    show answer

    Both expose runtime behavior as text you can read after the fact — the server’s access log is a built-in, routable version of a print. On a systemd Linux remote the equivalent lives in the journal: journalctl -u <service> (or under /var/log/); macOS has no direct journalctl equivalent, same posture as the ss-vs-lsof and BSD-vs-GNU caveats from earlier lessons.

  6. Cold rebuilds (no peeking):
    1. State MS’s golden rule from memory.
    2. Name the one circumstance where a debugger clearly beats a print.
    3. One sentence: why won’t py_compile / mypy catch the biggest = 0 bug?
    show answer

    (a) Code does what you tell it to do, not what you expect it to do.
    (b) When you don’t yet know what to print, the bug is hard to reproduce, or re-running is expensive.
    (c) The code is syntactically valid and type-clean — it’s a logic bug (wrong initial value), which only execution or stepping reveals. Checkers raise the floor; they don’t catch wrong intent.
