Lesson 0036 · Missing Semester — Debugging & Profiling

Timing and resource monitoring

Correct is not the same as fast enough. Read time’s three numbers, then ask which resource is scarce — CPU, memory, open files, or a port — before you optimize anything.

Why this matters

The debugging half of Lecture 4 asked “is it wrong?” The profiling half asks “is it too expensive even when it’s right?” MS: algorithms classes teach big-O, not how to find the hot spot in this program on this box. And: premature optimization is the root of all evil — measure first. Today is the first measurement: wall-clock vs CPU, then a live look at what the process is actually consuming. The tools that name a function (profilers, flame graphs) wait until you know which resource is the constraint.

Read first (≈5 min): MS Debugging and Profiling — the opening of “Profiling,” then “Timing” and “Resource Monitoring” (stop before “Visualizing Performance Data”).

Knowledge 1 — time: real, user, sys

The simplest measurement is how long a command took. Wall-clock alone misleads: the box may be busy with other work, or the program may be waiting (disk, network, a sleep). bash’s time keyword splits that:

NumberMeans
realwall clock, start to finish — includes waiting
userCPU time in user code
sysCPU time in kernel code

MS’s example:

$ time curl https://missing.csail.mit.edu &> /dev/null
real    0m0.272s
user    0m0.079s
sys     0m0.028s

real ≈ 272 ms; user+sys ≈ 107 ms. The rest was waiting for the network. Confirm you have the keyword, not the other time:

type time          # shell keyword
help time          # real / user / sys; -p for POSIX

/usr/bin/time is a different program (BSD on this Mac, GNU on Linux) with a different default layout. Stay with the keyword — it times a whole pipeline, which is what you want.

Three shapes, one read:

ShapeWhat you seeVerdict
time sleep 1real ≈ 1s; user and sys ≈ 0almost all waiting
a tight Python loopreal ≈ user + sysCPU-bound
the curl abovereal ≫ user + syswaiting on I/O or the network

user+sys can exceed real on a multi-core machine (several CPUs working at once). That is still CPU-bound — just parallel.

Knowledge 2 — the monitoring map

MS: programs often run slowly because they are resource constrained. Before you profile a function, name the scarce thing:

QuestionToolWhere
which process is burning CPU / RAM right now?htopLinux box (apt); improved top
how much memory is left for new work?free -hLinux only
which process has this file (or socket) open?lsofMac and Linux
what is listening on this port?ss -tlnpLinux (L0010); Mac: lsof

htop is MS’s process viewer. Keys from man htop (the ones you will actually press today):

KeyDoes
P / Msort by CPU / by memory
ttree view (parent → children)
Hhide user threads (toggle)
lopen files for the selected process (calls lsof)
qquit

free -h prints a memory table. The column that answers “can I start something new without swapping?” is available, not free. Linux uses idle RAM as cache, so free looks small on a healthy box; available already counts reclaimable cache. That is man free, not folklore.

lsof’s original job is files, not just sockets. Two shapes: lsof /path (who holds this file) and lsof -p PID (what this process has open). The listen-sockets form from L0010 still stands on the Mac: lsof -nP -iTCP -sTCP:LISTEN.

h is help, not threads. MS’s key list is abbreviated; man htop is the source of truth. h / F1 / ? open help. User threads are H. top ships on the Mac with different keys — named, not drilled. btop, iotop, nethogs, iftop wait.

Knowledge 3 — affinity: N workers ≠ N CPUs

A process is only allowed to run on the CPUs in its affinity mask. taskset sets that mask. MS’s exercise: start more workers than CPUs you have granted, watch them fail to fill the machine.

nproc                              # how many CPUs this box sees
taskset --cpu-list 0 stress -c 2   # two CPU-spinners, both pinned to CPU 0

In htop you will not see two cores at 100%. Both stress workers share CPU 0. That is the whole point: the scheduler will not put them elsewhere. (MS writes taskset --cpu-list 0,2 stress -c 3 — three workers, two listed CPUs. Same idea; pinning to CPU 0 alone does not require CPU 2 to exist.)

Linux-only. You are root in the drill box, so no sudo.

Drill — measure, then watch

Ghostty + bash + vim, tmux for panes. time runs on the Mac. htop / free / taskset / ss need Linux: the L0030 disposable box, nothing lands on the Mac, --rm cleans up. An SSH Linux remote works identically (add sudo for installs).

  1. Cold-name the slice: the three time numbers, one phrase each. Then the four-tool map: CPU/RAM now, memory left, who holds a file, who holds a port.
    show answer

    real = wall clock including waits; user = CPU in user code; sys = CPU in the kernel. Map: htop (which process is hot), free -h (memory left — read available), lsof (who has this file), ss -tlnp (who is listening — L0010; Mac: lsof).

  2. Three time shapes, on the Mac. 
    type time
time sleep 1
time python3 -c "print(sum(range(10**7)))"
time curl https://missing.csail.mit.edu &> /dev/null
    For each: is real ≈ user+sys, or is most of real waiting? One sentence on the curl gap.
    show answer

    sleep 1: real ≈ 1s, user and sys near 0 — waiting. Python: real close to user+sys — CPU-bound (a little leftover is startup and whatever else the Mac is doing). curl: real much larger than user+sys — the gap is network wait, same as MS’s 272 ms vs 107 ms. type time should say shell keyword.

  3. Boot the box and watch CPU. On the Mac: 
    docker run --rm -it -p 4444:4444 --name ms-prof debian bash
# inside:
apt-get update && apt-get install -y htop python3 procps iproute2 lsof stress
nproc
htop
    Second pane (Mac: docker exec -it ms-prof bash, or a tmux split after apt-get): 
    stress -c 2
    In htop: P to sort by CPU, find the stress rows. How many cores are pegged? t for tree — stress is a parent with worker children. Stop the workers with Ctrl-C (L0019) in that pane.
    show answer

    Unconstrained, stress -c 2 wants two full CPUs. If nproc ≥ 2 you should see two cores near 100% and two hot stress rows after P. Tree view shows the parent plus children. If the VM only has one CPU, both workers already share it — the next task still names the constraint.

  4. Pin them. Same second pane: 
    taskset --cpu-list 0 stress -c 2
    Watch htop again. Why don’t you get two cores at 100%? Stop with Ctrl-C.
    show answer

    Affinity is CPU 0 only — the scheduler must run both workers there. They share one core (each well under 100%, or one at 100% and one waiting). N workers is a request; the mask is the ceiling. That is MS’s taskset / stress exercise, pinned to a CPU that always exists.

  5. free and lsof. Still in the box: 
    free -h
python3 -m http.server 4444 &
pgrep -f http.server          # L0008
lsof -p <PID> | head
# in htop: highlight that python, press l — same list, via htop
    On the free line: which column is “room for a new program”? Then the occupied-port loop (MS’s own exercise, L0010 retrieval): 
    python3 -m http.server 4444
# Address already in use — good.
ss -tlnp | grep 4444
kill <PID>                    # the PID ss named
    show answer

    available, not free — cache makes free look poorer than it is. lsof -p lists cwd, the Python binary, libs, and a TCP listen on *:4444. htop l is that list without leaving the viewer. Second http.server fails because the port is taken; ss -tlnp names the process (L0010); kill frees it. On the Mac the same question is lsof -nP -iTCP -sTCP:LISTEN.

  6. Cold rebuilds (no peeking):
    1. real / user / sys, one phrase each.
    2. The curl gap: what is the missing time?
    3. The four-tool map.
    4. free -h: available vs free.
    5. Why taskset --cpu-list 0 stress -c 2 does not fill two cores.

    show answer

    (a) Wall clock including wait; CPU in user code; CPU in the kernel.
    (b) Waiting on the network — real includes it, user+sys do not.
    (c) htop / free -h / lsof / ss -tlnp.

Check your understanding

Four questions. Shuffled answers.

Q1A timed curl shows real 0.272s, user 0.079s, sys 0.028s. Where did the rest of the real time go?

  • Waiting — real includes network/I/O wait; user+sys is only CPU time
  • The kernel hid the CPU time so it would not appear in user or sys
  • curl always reports wall time as three times the CPU time by design
  • The missing time is memory used, which time prints on the real line

Q2You need to know which process has a given file open. Which tool?

  • lsof — it lists open files and which process holds each one
  • free — it lists files that are sitting in the page cache
  • time — it reports how long the file has been open
  • htop’s P key — it sorts processes by how many files they hold

Q3python3 -m http.server 4444 fails: address already in use. First move on Linux?

  • ss -tlnp | grep 4444 — then kill the PID it names (L0010)
  • time python3 -m http.server 4444 — a slow bind is a timing bug
  • free -h — the port is exhausted because RAM is full
  • strace -e trace=file — ports are files, so openat will name it

Q4taskset --cpu-list 0 stress -c 2. Why don’t you see two cores at 100%?

  • Affinity pins both workers to CPU 0, so they share one core
  • stress -c 2 always uses one core; the 2 is a delay in seconds
  • taskset starts two copies of htop, which do not burn CPU
  • CPU 0 is reserved for the kernel, so both workers sit idle

Ask the teacher. Did the curl gap land (waiting vs CPU)? Did pinning with taskset make the “N workers ≠ N CPUs” point obvious in htop? Any surprise that free is the wrong column?
