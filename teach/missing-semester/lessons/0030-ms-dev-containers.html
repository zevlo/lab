Dev containers

A container, defined as code, that runs your dev tools the same way on any machine. MS names them under IDE extensions for portability and isolation — this slice teaches the terminal-native core so a vim/SSH stack gets the same win without an IDE.

Why this matters

L0029 finished MS lecture 3’s named slices (editing, language servers, AI form factors). One item MS lists under “Extensions and other IDE functionality” is still open: development containers — “use a container to run development tools … helpful for portability or isolation.” The lecture defers container depth to its own Packaging and Shipping Code lecture, so this slice stays at the dev-environment level: what a dev container is, the terminal-native verbs that drive it, and how it reunites the L0028 checkers with a versioned, reproducible environment.

Read first (≈10 min): MS Development Environment and Tools — the “Extensions and other IDE functionality” bullet on development containers, plus the containers.dev spec introduction. Skim only; do not install an IDE tonight.

Knowledge 1 — image, container, dev container

Three nouns, layered. MS frames dev containers as a portability/isolation win; the nouns explain how:

TermWhat it isOne-line shape
imagelayered filesystem + metadata; the blueprintbuilt from a Dockerfile; immutable, tagged
containera running instance of an imagedocker run starts one; docker ps lists them
dev containera container + a config that encodes the full dev environment.devcontainer/devcontainer.json (editor-agnostic spec)

The dev container spec (containers.dev) is editor-agnostic: VS Code, Cursor, GitHub Codespaces, JetBrains, and the standalone devcontainer CLI all read the same devcontainer.json. That is the key decoupling — the environment is defined as code, not locked inside one IDE.

Knowledge 2 — the docker CLI core (terminal-native)

The daily verbs. These run identically on macOS (via Docker Desktop or colima, which provide the Linux VM) and on a Linux remote — same posture as the ss-vs-lsof and BSD-vs-GNU caveats from earlier lessons.

VerbDoesRecall hook
docker build -t tag .build an image from the Dockerfile in cwdtag = name; . = build context
docker imageslist imagesthe blueprints
docker runstart a container from an imagesee flags below
docker ps / -alist running / all containersthe instances
docker exec -it NAME bashopen a shell in a running container“SSH into the box”
docker stop / docker rm NAMEstop / remove a containerinstance cleanup
docker rmi IMAGEremove an imageblueprint cleanup
docker logs NAMEcontainer stdout/stderrlike tail on the box

The docker run flags that matter most for dev work:

docker run -it --rm \
  -v "$PWD":/work \      # mount your source live (host → container)
  -w /work \             # working dir inside the container
  -p 8000:8000 \         # forward a port (host:container)
  --name ms-box \        # name the instance
  ms-dev bash            # image + command

-i keeps stdin open, -t allocates a TTY — together they give an interactive shell. --rm removes the container on exit (disposable). -v is the live mount: you edit on the host in vim, the change is instantly visible inside the container. This is the whole dev-container loop in one line.

Knowledge 3 — devcontainer.json + the L0028 callback

A bare docker run works, but you retype the flags every time. A dev container captures them as code. Minimal shape:

.devcontainer/devcontainer.json
{
  "name": "ms-dev",
  "build": { "dockerfile": "../Dockerfile" },
  "workspaceFolder": "/work",
  "mounts": [ "source=${localWorkspaceFolder},target=/work,type=bind,consistency=cached" ],
  "forwardPorts": [8000],
  "postCreateCommand": "mypy --version"
}

Each key is something you would otherwise pass to docker run or do by hand: the build context, the workspace mount, port forwards, and a hook that runs once after creation. An IDE (or the devcontainer CLI) reads this file and runs the equivalent docker commands for you — but the file itself is plain text, versioned like the L0025 dotfiles.

L0028 callback. The image bakes in the checkers — py_compile, mypy, gofmt — so they exist identically on every machine that runs the image. The gate is still the L0028 checkers under the L0023 exit-status rule (0 clean, nonzero reject/fix); the container just guarantees the gate is runnable anywhere. The L0029 AI agent can run inside this same container, and its output gets gated by the same checkers — the environment and the gate travel together.

Mission framing. MS lists dev containers as an IDE extension. Under this mission the IDE path is named, not expanded (same posture as Zed in L0029, kitty/starship in L0025) — the terminal-native docker verbs are the curriculum. The optional devcontainer CLI (npm install -g @devcontainers/cli) is a one-off install like jq (L0020) or mypy (L0028), not a dependency.

Drill — build, run, exec, gate

Ghostty + bash + vim. Scratch: /tmp/ms-devcontainer/. Requires a working Docker daemon — on macOS that means Docker Desktop or colima running.

  1. Cold-name the three nouns, no peeking: image, container, dev container — one sentence each.
    show answer

    Image = layered filesystem + metadata, the blueprint, built from a Dockerfile. Container = a running instance of an image. Dev container = a container plus a devcontainer.json config that encodes the full dev environment (build, mounts, ports, post-create hooks) as editor-agnostic code.

  2. Write a minimal Dockerfile that bakes in the L0028 checker, build it, run a one-shot: 
    mkdir -p /tmp/ms-devcontainer && cd /tmp/ms-devcontainer
cat > Dockerfile <<'EOF'
FROM python:3.12-slim
RUN pip install --no-cache-dir mypy
WORKDIR /work
EOF
docker build -t ms-dev .
docker run --rm ms-dev mypy --version
    Confirm mypy prints a version. One sentence: where does mypy live, and what would be different on a fresh machine without this image?
    show answer

    mypy is installed inside the image at build time (RUN pip install). On a fresh machine you would have to pip install mypy again — or just docker run ms-dev and it is already there. That gap is the portability win MS names.

  3. Mount your source, gate inside the container. Reuse L0029’s extract.py shape and run the L0028 checkers against it from inside the image: 
    cat > extract.py <<'EOF'
def extract(content: str) -> list[str]:
    # extract all Markdown links from the content
    import re
    pattern = r'\[.*?\]\((.*?)\)'
    return re.findall(pattern, content)
EOF
docker run --rm -v "$PWD":/work -w /work ms-dev \
  bash -lc 'python3 -m py_compile extract.py && mypy extract.py; echo status=$?'
    Expect status=0 — same as L0029. The point: the checkers ran inside the container against your live-mounted source; the host never needed mypy installed.
    show answer

    status=0: syntactically valid and mypy-clean, identical to L0029’s host run. The difference is the environment: the container guarantees mypy + py_compile exist; the host is irrelevant. The L0023 exit-status gate still rules; the container just makes the gate portable.

  4. Long-running container + exec — the “container as a remote box” model (callback to L0024): 
    docker run -d --name ms-box -v "$PWD":/work -w /work ms-dev sleep 600
docker exec -it ms-box bash
# inside the container:
python3 -m py_compile extract.py
exit
docker stop ms-box && docker rm ms-box
    One sentence: why is this different from drill 3’s --rm one-shot, and what in L0024 does it replace?
    show answer

    Drill 3 ran a fresh disposable container per command (--rm, exits and vanishes). Here the container stays alive (-d, detached) so you can exec into it repeatedly — closer to SSH-ing into a persistent remote box (L0024), except the “box” is local, disposable, and defined by the Dockerfile.

  5. Read devcontainer.json, map to docker run. Create the file from Knowledge 3, then — without running anything — predict the bare docker run equivalent of each key (build, workspaceFolder, mounts, forwardPorts, postCreateCommand). Optional, only if you ran npm install -g @devcontainers/cli: devcontainer up --workspace-folder . then devcontainer exec --workspace-folder . bash.
    show answer

    build → docker build -t … .; workspaceFolder → -w /work; mounts → -v "$PWD":/work; forwardPorts → -p 8000:8000; postCreateCommand → a one-shot docker run … mypy --version after first create. The file is just those flags, versioned.

  6. Cold rebuilds (no peeking):
    1. Image vs container — define each in one sentence.
    2. Which two docker run flags give an interactive shell with a TTY, and which removes the container on exit?
    3. One sentence: what does devcontainer.json add over a bare Dockerfile, and why bake the L0028 checkers into the image?
    show answer

    (a) Image = immutable layered blueprint built from a Dockerfile; container = a running instance of an image.
    (b) -i -t (often written -it) for interactive + TTY; --rm removes on exit.
    (c) devcontainer.json captures the full dev environment as code (build, workspace mount, ports, post-create hook) so it is reproducible across machines/IDEs; baking the checkers in means the L0028/L0023 gate is runnable anywhere the image runs — no per-host install.

  • image; container
  • container; image

Q2Which flags give an interactive shell inside a container with a TTY?

  • -i -t (-it)
  • -d --rm
  • -v -w
  • -p -a

Q3What does a dev container (devcontainer.json) add over a bare Dockerfile?

  • a versioned, reproducible dev environment as code — mounts, ports, post-create hooks
  • a faster container runtime than docker
  • an AI autocomplete model bundled in
  • a replacement for SSH

Q4Why bake the L0028 checkers (mypy, py_compile) into the image?

  • so the gate is runnable identically on any machine; no per-host install
  • to make the image smaller
  • to skip the exit-status check (L0023)
  • to enable vim plugins inside the container
