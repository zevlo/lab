Lesson 0043 · Missing Semester: Beyond the Code

Beyond the Code

Write the why. Respect maintainer time. Review the code, not the person. Disclose AI.

Why this matters

On a bare box you already have the tools: vim for the edit, git for the snapshot (lesson 0040), an agent you confirm and gate (lesson 0042). The remaining failure mode is silent. Six months from now, you (or a teammate, or a maintainer) will open a file and have no idea why that timeout is 1492, why the obvious approach was skipped, or what a git blame line was trying to fix.

Missing Semester’s hinge for all of this writing: capture the why. The diff already shows the what. That is also how you file a bug, open a pull request, review someone else’s, and ask a question that someone can actually answer. On an incident, the same habit is the difference between a useful page and a pile of “me too.”

Read first (about 20 minutes): Missing Semester: Beyond the Code, including the Exercises section. Then Julia Evans, How to ask good questions (short).

This file covers the whole lecture: comments, READMEs, commit messages, contributing, review, questions, and AI etiquette. Spread the work across sittings if you want. Knowledge 1: One-way writing

You write for someone who lacks your current context: a teammate, a maintainer, or you in six months. Scale the length with the complexity. A typo fix needs a subject line. A race that took hours deserves a paragraph. Over-explaining the how trains people to skip the comment.

Comments that are almost always worth keeping:

KindWhat it records
TODOWhat is unfinished, and why it was deferred. “TODO: this O(n²) loop is fine for n<100; index it if we scale.”
ReferenceA permalink to a paper, RFC, or borrowed code, plus any divergence.
CorrectnessWhy the steps work. The code already shows the steps.
Hard-learnedA non-obvious incantation that cost 30+ minutes.
ConstantWhy 1492, or 16 bits. “Chosen arbitrarily” still helps.
Load-bearingA detail that looks innocent and is required. “Must be a BTreeSet: iteration order matters below.”
Why notWhy you skipped the obvious approach, so the next person does not “fix” it.

A README answers four questions, in this order: what does this do, why should I care, how do I use it, how do I install it. Funnel: a one-liner (and maybe a demo) so a stranger can decide in seconds, then more depth. Show usage before install.

A commit message is the historical record of why the tree changed. git blame (lesson 0040) is only as good as those messages. The body, when the change is non-trivial, answers:

  • What problem forced this change?
  • What alternatives did you consider?
  • What are the trade-offs?
  • What might surprise a later reader?

For a complex change, Missing Semester’s shape is Problem → Solution → Implications. The last section is the one people skip, and it is the one that stops a later “fix” of an intentional trade-off.

If you ask an LLM to write the message from the diff alone, it sees the what. If you used the agent to make the change, ask for the commit in that same session: the chat already has the why. Otherwise tell it to ask you for missing context. You are the tool that can read the why.

Keep each commit one coherent change. Split a refactor from a feature. git add -p stages hunks: y yes, n no, s split, q quit. That is also what makes git bisect later able to name one cause.

Knowledge 2: Collaboration

Users outnumber contributors. Contributors outnumber maintainers. Maintainer time is oversubscribed. High signal-to-noise is how a contribution gets anywhere.

A bug report that a maintainer can act on includes: environment (OS, versions, relevant config), expected versus actual, specific reproduction steps, and what you already tried. Search existing issues first and add to those. A minimal reproducible example is the gold: the smallest case that still shows the bug. Isolating it often shows you the fix. A “me too” or a paste of a whole terminal is noise.

Security. If you find a vulnerability, contact the maintainers privately first and give them time to fix it. Many projects have a SECURITY.md. curl’s README points at a private disclosure page. Public GitHub issues are the wrong channel.

Before you send code: read CONTRIBUTING.md. Start small (a typo or a doc fix learns the process). Check the license. Code you contribute uses the project’s license. Copyleft (GPL family, AGPL) requires derivatives to stay open, which can matter for an employer. choosealicense.com is the map. curl is MIT-like. Redis today is RSALv2 / SSPL / AGPLv3. The class site is CC BY-NC-SA.

A pull request isolates the change you want accepted. Explain why it is needed and why this is a good way. Call out the parts that need extra review. Contribute upstream first. Fork when the change is out of scope, and credit the original. If you used an agent (lesson 0042), you still have to understand the patch. Maintainers inherit the code after you leave. A fluent-looking PR you cannot explain is their burden.

Review the code, not the person. Fresh eyes catch things veterans skip, including undocumented assumptions. Tips that pay off immediately:

DoExample
Name the code“This function is confusing.”
Make it actionable“Can you replace these globals with a config dataclass?”
Ask, then decide“What happens if X is null here?”
Give the why“A constant here lets us retune the timeout per environment.”
Mark blocking vs nitMust-change versus preference. Prefix nits so they can wait.
Name what worksSo the author keeps doing it.
StopFocus on the big things. You can tidy nits yourself after.

An LLM first pass can catch some issues. It misses product context and can be confidently wrong. Human review stays the gate. Your code is not you. If you disagree with a comment, ask a clarifying question.

Knowledge 3: Questions and AI etiquette

Asking well is how you learn from people who are not perfect explainers. Julia Evans (and the follow-up on getting useful answers) is the primary extra reading. The moves:

  • State what you think is true, then ask “is that right?”
  • Ask yes/no questions. They stay on the rails, and people still elaborate.
  • Be specific. “Does a LEFT JOIN include rows where the right table has no match?” is answerable. “How do SQL joins work?” is not.
  • Stop on an unfamiliar term. “I don’t know” plus “but I think…” or “I can find out” is confidence.
  • Keep asking until you understand. Interrupt a tangent with a tighter question.
  • Do enough research to aim. Casual questions among colleagues are still fine.

The same moves work with an LLM. A well-crafted public question also helps the next person.

When AI meaningfully contributed, disclose it, and say which parts. “This whole thing is vibecoded” and “I wrote the tool and used an LLM on the CSS” are different review loads. Missing Semester used LLMs on these notes for proofreading, brainstorming, and first drafts of snippets. Follow the project’s policy (compliance, data residency). If you are trying to learn the task, having the agent do the whole thing teaches prompting, not the skill. In an assessment, ask whether AI is in scope. If the rules say no external tools, leave them off.

1. Comment types in the wild

Missing Semester: browse Redis or curl and find a useful TODO, a reference, a “why not,” or a hard-learned lesson. What would be lost without that comment?

Start here (verified on current master / unstable; search if a line moved):

  • curl lib/http.c: search RFC2616 forbids (why not + RFC), zlib cannot handle compress (hard-learned), RFC 9112, ch. 6.1 (correctness), and the comment above Expect: 100-continue (why a size threshold skips the header).
  • Redis src/sds.h: search sdshdr5 is never used (load-bearing layout that looks unused).

Write one sentence per find: the kind, and what a later “cleanup” would break. Optional local clone: git clone --depth 1 https://github.com/curl/curl.git /tmp/ms-beyond/curl then grep -n 'RFC2616 forbids' lib/http.c.

show answer

Without the RFC2616 comment, the next person adds both Content-Length and chunked Transfer-Encoding, which the RFC forbids. Without the zlib note, someone enables compress and gets a mystery decode failure. Without the RFC 9112 note, a HEAD or 304 response gets a transfer decoder it should not. Without the SDS comment, someone deletes sdshdr5 as dead code and the layout documentation disappears. curl also deleted stale inline TODOs on purpose (94c596b): a TODO without context becomes a lie. Their backlog lives in docs/TODO. Actionable TODOs still match Missing Semester; lingering “FIXME” noise is why curl removed them.

2. Commit messages: why versus what

Missing Semester: in a project you care about, find one commit whose message explains why, and one that only names what. For the weak one, read git show HASH and rewrite it as Problem → Solution → Implications. Notice how much context you have to reconstruct.

Two ways. Do at least the local rewrite. The class-site pass is the Missing Semester shape.

# A. class-site (full clone from lesson 0040; skip if missing)
SITE=/tmp/ms-git/class-site
cd "$SITE" && git log --oneline -20
# pick a short subject that only names a file or "fix typo"
git show --stat HASH
git show HASH   # then write a better body on paper / in /tmp

# B. toy repo: one good commit, one weak one, then add -p
cd /tmp/ms-beyond
rm -rf commits && mkdir commits && cd commits
git init -b main
git config user.email drill@example.com
git config user.name Drill
cat > serve.py <<'EOF'
from http.server import BaseHTTPRequestHandler, HTTPServer
class H(BaseHTTPRequestHandler):
    def do_GET(self):
        body = b"ok\n"
        self.send_response(200)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)
HTTPServer(("127.0.0.1", 8080), H).serve_forever()
EOF
git add serve.py
git commit -m "$(cat <<'EOF'
Bind the drill server to loopback only.

Problem: a default bind to 0.0.0.0 would expose the handler on every
interface the moment someone copies the snippet onto a laptop on coffee-shop
Wi-Fi.

Solution: HTTPServer(("127.0.0.1", 8080), ...).

Implications: curl from another machine fails. That is intended. Change the
bind only behind a documented flag if we ever need a demo from a phone.
EOF
)"
# now a weak commit: two unrelated edits in one snapshot
printf '%s\n' 'TIMEOUT = 30' >> serve.py
echo "# notes" > README.md
git add -A
git commit -m "updates"
git log
git show HEAD

Rewrite updates as two messages (timeout rationale vs adding a README). Then make two fresh unstaged edits and stage only one hunk:

# edit serve.py: change TIMEOUT, and add a comment on do_GET
git add -p    # y for the timeout hunk, n for the comment
git diff --cached
git diff      # leftover hunk stays unstaged
show answer

The first commit already has a forcing function (accidental bind), a decision (loopback), and a consequence (remote curl fails). updates names nothing. A rewrite that still mixes the timeout and the README leaves git bisect unable to separate them. Split: (1) Problem: magic 30 with no unit or reason. Solution: named TIMEOUT. Implications: callers can retune without hunting a literal. (2) Problem: a stranger cannot tell what the tree is. Solution: a one-line README. git add -p: staged diff is only the hunks you accepted. Class-site: “Redo lectures as a collection” (from the lesson 0040 blame drill) is a why. A one-word “typo” subject is a what: the diff shows the character, the message does not say why it mattered.

3. Three READMEs

Missing Semester: compare READMEs of three GitHub projects with 1000+ stars. Are they equally useful? What reads as noise that you would skip in your own?

Use these three, then add a project you actually use if you want a fourth:

  1. curl/curl
  2. missing-semester/missing-semester
  3. nvm-sh/nvm

For each: does the first screen answer what / why care / how to use / how to install, in that order? Score the noise (badges, every install method, sponsor blocks).

show answer

curl: one-sentence what, then the man page (use) before INSTALL. License, contact, and private security disclosure are easy to find. That is the funnel. Class site: title and website link are the what; CI badges and “run Jekyll / Compose” land before you see a lecture list in the README itself. nvm: a usage demo appears early (good), then a very long file of install variants, Docker, and edge cases. The length is the noise. For your own README: one-liner, one demo, use, then install. Put the long tail behind a link.

4. Evaluate an issue

Missing Semester: find an open issue on a project you use (try “good first issue” or “help wanted”). Does it give the maintainer enough to debug, or will they need several rounds of questions?

Score it against Knowledge 2: environment, expected versus actual, steps, what they tried, existing-issue search, MRE. Write four bullets. Do not comment on the issue.

Fallback if you have no favorite tracker: open curl issues, pick one labeled and one unlabeled, and score both.

show answer

A high-signal issue names versions, the command, expected versus actual output, and a small repro. A low-signal issue is “it doesn’t work” plus a 200-line paste, or a “me too.” “Good first issue” is about scope, not about report quality: some are still underspecified. If you cannot reproduce from the text alone, the maintainer cannot either.

5. Minimal reproducible example

Missing Semester: take a bug and strip everything unrelated until the smallest case still shows it. Write down what you removed and why. Seed (the bug is real; the extra files are camouflage):

cd /tmp/ms-beyond
rm -rf mre && mkdir -p mre/data mre/vendor
cat > mre/config.yaml <<'EOF'
timeout: 30
features: [a, b, c]
EOF
cat > mre/helpers.py <<'EOF'
def greet(name: str) -> str:
    return f"Hello, {name}!"
EOF
cat > mre/vendor/unused.py <<'EOF'
VALUE = 99
EOF
printf 'x\n' > mre/data/log.txt
cat > mre/app.py <<'EOF'
from helpers import greet
# show just the name: slice off the greeting
print(greet("Ada")[1:])
EOF
cd mre
python3 app.py

You should see ello, Ada! instead of the full greeting. Reduce this to the smallest script that still prints the wrong string. List every file you dropped.

show answer

print("Hello, Ada!"[1:]) is enough. It prints ello, Ada!. The slice drops one character. It does not skip the greeting. config.yaml, vendor/, data/, and even helpers.py are unrelated. What you removed: config, unused vendor, a log file, and an import that only wrapped a literal. A maintainer can act on the one-liner. The original tree hides the slice in ceremony.

6. Read a real review

Missing Semester: find a merged pull request with substantive review comments (more than “LGTM”). Were all comments equally useful? How would it feel to receive that review?

GitHub → a repo you use → Pull requests → Closed. Open one with a long Conversation tab. Fallback: curl PRs with review comments, plus How to code review in curl. Do not comment.

Write: one blocking comment that earned its keep, one nit that could have been a follow-up, and one sentence on tone (code versus person).

show answer

Useful comments ask a question, name a failure mode, or explain a why. Nits about wrapping or a local name are cheaper for the merger to fix (curl’s own review doc says experienced maintainers often do that for newcomers). “You wrote confusing code” is the person. “This function is confusing because X is nullable here” is the code. A wall of equally-weighted comments is exhausting; marking blocking versus nit is the kindness.

7. Questions that get answers

Missing Semester: on Stack Overflow, find a highly voted question in a technology you know, and one that was closed or heavily downvoted. Compare them to Knowledge 3. Was the outcome predictable?

On-mission pair to start from, then find your own second example:

  • High-signal (bash redirects, lesson 0015/0009): What does 2>&1 mean?
  • Search [bash] closed:yes and open one closed as too broad or “needs details.”

Also skim How to ask and How to create a minimal reproducible example.

show answer

The 2>&1 question is specific, names the construct, and is answerable with a fact. A closed “How do I learn bash?” is a topic, not a question. “My script doesn’t work” with no OS, no script, and no error is the issue-tracker failure mode on another site. Predictable: stated understanding + a yes/no or factual target gets an answer. The same test applies when you prompt this agent.

Check your understanding

Four questions. Answers shuffle on each page load.

Q1A comment worth keeping records:

  • Why this code path exists, including constants, load-bearing details, and avoided approaches
  • How this code path works, restating each following line in ordinary English
  • Who last edited this file, including the hour they committed it locally
  • Which Python wheel tag matches this machine, including OS and CPU architecture

Q2A non-trivial commit body should record:

  • What problem forced this change, alternatives considered, trade-offs, and any surprising implications
  • Which files the patch touched, plus the added and deleted line counts
  • Which language model wrote the diff, plus prompt hash and model name
  • Which branch and remote you used, plus the ticket from the tracker

Q3A bug report a maintainer can act on includes:

  • The environment, expected versus actual, reproduction steps, and what you already tried
  • A screenshot, a core dump, and a demand for a same-day hotfix
  • Your distro name, a stack screenshot, and paste of the whole log
  • A me-too comment, a screenshot, and a paste of the entire terminal

Q4When AI meaningfully contributed to the work, you:

  • Disclose the use, name which parts, and follow the project's AI policy
  • Delete the chat log so reviewers cannot tell an LLM was involved
  • Ship the patch as-is, because the model's fluency means it is correct
  • Ask the model to hide itself, then claim you typed every line

Ask the teacher. Did the curl “why not” comments change what you would leave in a config file? Was rewriting updates harder than you expected? Did the nvm README feel useful or noisy past the first screen? Anything unclear: ask here. The agent is the teacher for this course.
