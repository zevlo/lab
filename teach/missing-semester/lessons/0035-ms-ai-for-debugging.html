AI for debugging

Feed last week’s ASan report — and a wall of C++ errors — to an LLM, then verify the suggestion with the tool that produced it. Distinct from L0029: diagnosing, not authoring.

Why this matters

The Lecture-4 ladder now produces artifacts: a pdb backtrace (L0031), a strace line (L0032), a tcpdump flag (L0033), an ASan three-stack (L0034). MS’s next section: large language models as debugging assistants that read those artifacts. This is not L0029. That slice named how AI writes code (autocomplete / inline chat / agent). This slice is how an LLM reads a diagnosis you already know how to produce — and why you still run the tool after it speaks.

Read first (≈5 min): MS Debugging and Profiling — the “AI for Debugging” section (short: four shine areas, the debug-symbols note, four limitations). MS’s own exercise is today’s drill spine: paste a compiler error, and some strace or ASan output.

Knowledge 1 — four shine areas

MS: LLMs “excel at certain debugging tasks that complement traditional tools.” The four:

Shine areaWhat you pasteWhat you hope back
cryptic errorsa compiler wall — C++ templates, Rust’s borrow checkerplain English + a suggested fix
language boundariesa Python traceback that names a C library, an FFI / build errorwhich layer is actually wrong
symptom ↔ causea vague report (“works, uses 10× the memory”)likely causes and what to measure next
crash dumps / stacksan ASan report, a bt, a core dump excerpta story that connects the frames

The habit: paste the tool output, not a paraphrase. “It crashed after I freed something” is a vibe. The ASan report that names uaf.c:12 / :10 / :6 is evidence. The model is a reader of last week’s artifacts.

Knowledge 2 — limitations, then verify

MS lists four limits. Treat them as first-class, not a footnote:

  • The model can hallucinate a fluent, wrong explanation.
  • It may suggest a fix that masks the bug instead of fixing it.
  • Always verify the suggestion with the debugging tool that produced the artifact.
  • It is a complement, not a replacement, for understanding the code.

Same gate as L0028 / L0029: the explanation is a draft, not a verdict. Re-run ASan, recompile, re-trace. Exit status is still the verdict (L0023). A suggestion that makes uaf “work” by deleting the free has traded a use-after-free for a leak — LeakSanitizer and Valgrind (L0034) would say so. That is a mask.

One sentence against L0029: form factors = how the model touches your code; this slice = how the model reads a tool’s output.

Knowledge 3 — debug symbols: why the paste is readable

MS puts this note here, not under sanitizers, because it is about the artifact you are about to paste. For native binaries (C / C++ / Rust), compile with debug symbols:

gcc -g -fno-omit-frame-pointer …

-g writes DWARF debug info so stacks name file:line instead of bare addresses. -fno-omit-frame-pointer keeps a frame-pointer chain the unwinder can walk — stacks stay complete, which also matters for the profilers still to come. Without these, you paste a list of hex addresses; neither you nor the model can pin the act. Python and Java already ship symbolic traces — this is a compiled-language habit. You used -g in L0034 so the ASan report said uaf.c:12. That is why that paste is worth making.

You do not need to know C++ for today’s compiler wall. The point of the shine area is that the error is unreadable on purpose. Paste the wall; apply a suggested fix; let g++’s exit status decide. If the model says “delete the free” on the ASan report, reject it and say why.

    Recreate L0034’s uaf.c (heredoc, not vim-paste): 
    cat > uaf.c <<'EOF'
#include <stdlib.h>
#include <string.h>
#include <stdio.h>

int main() {
    char *greeting = malloc(32);
    strcpy(greeting, "Hello, world!");
    printf("%s\n", greeting);

    free(greeting);

    greeting[0] = 'J';
    printf("%s\n", greeting);

    return 0;
}
EOF
gcc -fsanitize=address -g uaf.c -o uaf
./uaf 2> asan.txt; echo $?
    Paste asan.txt into an LLM. Ask it what happened. Compare its story to the three-stack read you already know (access ← freed by ← allocated by). Did it name uaf.c:12 / :10 / :6?
    show answer

    A competent read: heap-use-after-free — a 1-byte write at line 12 through a pointer freed at line 10, block allocated at line 6. Exit nonzero (typically 134). If the model invents a data race or a double-free, that is a hallucination — you already have the report. If it suggests deleting the free, that is a mask (leak). The fix you already know: move free below the last use.

  3. The cryptic compiler wall (MS: “especially from C++ templates”). You do not need to know C++. 
    cat > sort_widgets.cpp <<'EOF'
#include <vector>
#include <algorithm>

struct Widget {
    int id;
};

int main() {
    std::vector<Widget> w = {{3}, {1}, {2}};
    std::sort(w.begin(), w.end());
    return 0;
}
EOF
g++ sort_widgets.cpp -o sort_widgets 2> cxx.txt; echo $?
    Open cxx.txt — a wall. The first useful line is usually no match for 'operator<' (g++) or invalid operands to binary expression ('const Widget' and 'const Widget') (clang), then a long instantiation chain that ends at your std::sort call. Paste the wall. Apply a suggested fix (an operator< on Widget, or a comparator passed to sort — either is fine). Rebuild and run: 
    g++ sort_widgets.cpp -o sort_widgets && ./sort_widgets; echo $?
    Expect status=0. If not, the suggestion was wrong — that is the point of verifying.
    show answer

    std::sort needs a way to compare two Widgets. The struct has only an id — no operator< — so the template instantiation fails deep inside the standard library, which is why the wall is long. A typical fix: bool operator<(const Widget& o) const { return id < o.id; } inside the struct, or std::sort(w.begin(), w.end(), [](const Widget& a, const Widget& b){ return a.id < b.id; }). Clean compile, run, exit 0. You did not have to learn C++; g++ certified the translation.

  4. A trace you can already read. 
    strace -e trace=file cat /no/such/file 2> trace.txt; echo $?
    Paste trace.txt. The model should name the missing path and ENOENT. You already know this line from L0032 — the check is whether the LLM’s story matches the syscall, not whether you needed help.
    show answer

    openat(…, "/no/such/file", …) = -1 ENOENT (No such file or directory), then cat writes an error to stderr and exits nonzero. If the model blames permissions or a missing shared library, that is a hallucination — the trace already named the path and the errno.

    show answer

    (b) L0029 = how AI writes code; this slice = how an LLM reads tool output to diagnose.
    (c) Hallucinate; mask the bug; always verify with the real tool; complement, not replacement.

Check your understanding

Four questions. Shuffled answers.

Q1How does this slice differ from L0029 (AI form factors)?

  • Form factors = how AI writes code; this slice = how an LLM reads tool output to diagnose
  • Form factors = how AI reads traces; this slice = how an LLM writes new features
  • Both slices teach the same three form factors — autocomplete, inline chat, agent
  • L0029 was sanitizers; this slice is the Profiling half of lecture 4

Q2You want an LLM’s help on a crash. What do you paste?

  • The ASan / compiler / strace output itself — the artifact, not a paraphrase
  • A one-line summary of how the program felt when it crashed
  • The source file only, with no error or report attached
  • A request to rewrite the program from scratch in another language

Q3An LLM says fix the use-after-free by deleting the free(). Why reject that?

  • It masks the bug with a leak — verify with ASan/Valgrind; the suggestion is not a verdict
  • Deleting free() is always correct because leaks never matter in short programs
  • ASan cannot see leaks, so the suggestion cannot be checked at all
  • You should accept it, then run tcpdump to confirm the heap is fine

Q4Why compile with -g before you paste a native crash stack to an LLM?

  • Debug symbols turn addresses into file:line — that is what makes the paste readable
  • The -g flag makes the program faster, so the crash is easier to reproduce
  • Python and Java refuse to print any stack trace unless you pass -g
  • Without -g the sanitizer refuses to run and you get no report at all
