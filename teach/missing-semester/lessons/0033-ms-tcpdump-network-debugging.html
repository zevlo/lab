Lesson 0033 · Missing Semester — Debugging & Profiling

Network debugging — tcpdump

tcpdump: read the packets themselves as they cross an interface. The Lecture-4 slice for when the question is “is this even leaving the machine — and what comes back?” — one observation point past L0032’s kernel boundary.

Why this matters

The triage ladder so far: curl -i (L0008) showed the HTTP conversation; ss -tlnp (L0010) showed the sockets a box owns; strace (L0032) showed the syscalls at the kernel door. When two machines disagree — “works for me,” connection refused versus a silent timeout — every one of those views is a claim by one side. The packet is the only neutral witness. MS: “For network issues, tcpdump and Wireshark let you capture and analyze network packets.” This slice drills tcpdump — the CLI one, present on every Linux box you will ever SSH into.

Read first (≈5 min): MS Debugging and Profiling — the “Network Debugging” subsection (short: two commands, one honest caveat about HTTPS).

Knowledge 1 — the fourth observation point

tcpdump copies packets that match a filter as they cross a network interface — loopback included — and prints one summary line per packet, or saves them raw to a file. Put it at the end of the ladder:

ToolObservation pointSees
curl -ithe client (L0008)the conversation — request, status, headers
ss -tlnpthe box (L0010)the sockets — who is listening, owning process
stracethe boundary (L0032)the syscalls — socket, bind, accept4
tcpdumpthe wirethe packets themselves — both directions, both sides of the story

Capturing needs raw access to the interface — hence sudo on any shared box (MS writes it that way too); in your own L0030 container you are already root. Unlike strace, this one is not Linux-only: macOS ships tcpdump (same libpcap filters; interfaces are named lo0/en0, and -i any works on recent macOS). The drill still runs in the disposable container — quiet network, no Mac traffic noise, --rm cleanup.

Knowledge 2 — the command shapes

MS gives two invocations; the man page adds the habits that make output readable:

InvocationAnswersRecall hook
sudo tcpdump -i any port 80packets to/from port 80, on every interface (MS)“web traffic”
sudo tcpdump -i any -w capture.pcapsave raw packets to a file for later / Wireshark (MS)“keep the evidence”
-ndon’t resolve addresses to names — output stays numbers (man: “often best to pass -n”)no DNS detours
-c 20stop after 20 packets — scriptable, no Ctrl-C wait“just twenty”
-r file.pcapread a capture back (pair of -w)replay
-A / -Xpayload as ASCII / hex+ASCII — “handy for capturing web pages” (man)see the bytes

The tail of the command is a filter in the libpcap language — the same one Wireshark uses. It compiles to BPF and runs in the kernel, so packets you don’t want never even reach userspace. The working vocabulary is small:

PrimitiveMatchesMan-page example
host 192.0.2.1any packet to or from that addresstcpdump -n 'host 192.0.2.1'
port 53any packet with that source or dest porttcpdump -n 'port 8080'
src / dstone direction onlytcpdump -n 'src host … and port 53'
tcp / udp / icmpprotocoltcpdump -n icmp
and / or / notcombine any of the abovehost … and not port 22

Knowledge 3 — reading a capture

One line per packet: timestamp interface dir IP src.port > dst.port: Flags […], seq …, ack …, length N. A curl against a local server reads like this (modern tcpdump prints the interface and In/Out on -i any):

11:04:07.113501 lo In IP 127.0.0.1.51732 > 127.0.0.1.4444: Flags [S],  seq 3847561023, win 65495, options [mss 65495,…], length 0
11:04:07.113544 lo In IP 127.0.0.1.4444 > 127.0.0.1.51732: Flags [S.], seq 2309310903, ack 1, win 65483, options […], length 0
11:04:07.113568 lo In IP 127.0.0.1.51732 > 127.0.0.1.4444: Flags [.],  ack 1, win 65495, length 0
11:04:07.113701 lo In IP 127.0.0.1.51732 > 127.0.0.1.4444: Flags [P.], seq 1:79, ack 1, win 65495, length 78: HTTP: GET / HTTP/1.1

The first three lines are the TCP three-way handshake — a connection being born, recognizable on sight as S → S. → . with length 0. What L0032 showed as one accept4 syscall is, on the wire, exactly these packets. Flags to know:

FlagMeansSeen when
[S] / [S.]SYN — open a connection; SYN+ACK — the answerhandshake lines 1–2
[.]ACK — receipt confirmation, no datahandshake line 3, and between bursts
[P.]PSH+ACK — carries payloadthe GET, the response body
[F.]FIN — orderly close, one per sideteardown
[R.]RST — abort: nothing listening hererefused connections

Now the triage shapes — the two failures that look identical in a client log and are unmistakable in a capture:

SymptomCapture showsVerdict / next move
fails fast, “connection refused”your [S] answered by [R.]host alive, port closed — cross-check ss -tlnp (L0010)
hangs, then timeout[S] out, silence backdropped, not refused — firewall or wrong host
“server receives nothing”run the capture on the server while curlingpackets present = network fine, app-layer problem
need it later, or for someone else-w file.pcap, read with -r, open in Wiresharkthe evidence file — MS’s second invocation
which process is that?—tcpdump can’t say; that’s ss -tlnp’s job (L0010). They compose.
The HTTPS caveat, straight from MS. Encryption makes tcpdump “less useful” for HTTPS: you still see the connection shape — handshake, sizes, resets — but the payload is ciphertext. For content, MS points at browser dev tools (Network tab) and mitmproxy as an intercepting proxy — named, not drilled. The counterpoint: this slice’s plaintext HTTP drills are fully readable with -A — that’s the whole point of the flag.

Drill — on the wire

Ghostty + bash + vim, tmux for panes. Same posture as L0032: the L0030 disposable Linux box, nothing lands on the Mac, --rm cleans up. You are root inside, so no sudo. An SSH Linux remote works identically (add sudo).

  1. Cold-name the slice: the four observation points in the ladder, and what each one sees. One sentence: why is the packet the “neutral witness”?
    show answer

    curl -i — the client’s view of the conversation (L0008). ss -tlnp — the box’s sockets, with owning process (L0010). strace — the program↔kernel boundary, e.g. accept4 (L0032). tcpdump — the packets crossing an interface, both directions. Neutral because every other view is reported by one side; the packet is the raw fact both sides actually put on the wire.

  2. Boot the box and watch a connection be born. On the Mac: 
    docker run --rm -it -p 4444:4444 --name ms-net debian bash
# inside the container:
apt-get update && apt-get install -y tcpdump python3 curl
python3 -m http.server 4444
    Second shell (docker exec -it ms-net bash from the Mac, or a tmux split): 
    tcpdump -ni any port 4444
    Then from the Mac: curl -i http://localhost:4444/. Cold reads: (a) the first three packet lines — name the ceremony; (b) which line carries GET /, and which flag marks it; (c) where did the Mac’s address go — whose 172.17.0.1 is that?
    show answer

    (a) [S] → [S.] → [.] — the TCP three-way handshake, all length 0; L0032’s single accept4 syscall unpacked into packets. (b) The [P.] line — PSH+ACK is the “carries data” flag; length 78 matches the request size, and tcpdump annotates HTTP: GET / HTTP/1.1. (c) Docker’s port publish does NAT: your curl arrives at the container as the bridge gateway 172.17.0.1, not your Mac’s LAN address — the rewrite is visible because -n keeps everything as numbers.

  3. Work the filter. Still capturing on any, narrow three ways and one sentence each on what changed: 
    tcpdump -ni any host 127.0.0.1
tcpdump -ni any src port 4444
tcpdump -ni any not port 4444
    Then the L0010 callback, from the wire’s side: 
    tcpdump -ni any udp port 53
getent hosts example.com
    show answer

    host 127.0.0.1: only loopback traffic — the eth0 lines from task 2 vanish. src port 4444: one direction only — just the server’s replies. not port 4444: everything except your own drill traffic — how you watch a box without watching yourself. DNS: two UDP lines to port 53 (A? example.com. out, answer back) — in a container that resolver is Docker’s embedded DNS at 127.0.0.11; same question dig answered in L0010, now seen as packets.

  4. The two failures (the money drill). Capture on the dead port: 
    tcpdump -ni any port 9999
curl -v http://127.0.0.1:9999/   # in the other shell
    Read the two lines, then cross-check: ss -tlnp | grep 9999 versus ss -tlnp | grep 4444 (L0010). Now the other shape — curl -m 3 http://10.255.255.1/ with tcpdump -ni any port 80 running. One sentence: same client symptom class, different wire truth.
    show answer

    Refused: your [S] is answered [R.] within the millisecond — the kernel itself saying “nothing listens on 9999.” Confirmed: ss -tlnp shows no 9999 listener but a live 4444 one. Timeout: [S] out, nothing back — dropped (firewall / unroutable host), not refused. “Connection refused” means the host answered; silence means the packet never made a round trip. That distinction exists only at this observation point — curl prints two vaguely similar errors.

  5. Keep the evidence. MS’s second invocation, bounded: 
    tcpdump -ni any port 4444 -w /tmp/hi.pcap -c 12
curl -s http://127.0.0.1:4444/ > /dev/null   # refill
tcpdump -r /tmp/hi.pcap | head -4
tcpdump -A -r /tmp/hi.pcap | less
    Note what changed in the readback without -n; then find the GET in the -A output. One sentence: why is the plaintext visible here and never on an HTTPS capture?
    show answer

    -w writes raw packets (the .pcap Wireshark also opens); -r replays them through the same printer — and without -n it now resolves addresses to names, so the readback looks different from the live capture; add -n to keep numbers. -A prints the payload as ASCII — the GET / HTTP/1.1 line sits there in plain sight because HTTP is plaintext; on HTTPS those bytes are ciphertext and no flag decodes them (MS’s caveat — that’s browser dev tools / mitmproxy territory, named only).

  6. Cold rebuilds (no peeking):
    1. The observation-point ladder — four tools, four views.
    2. The handshake as three flag-lines, plus what [P.], [F.], [R.] each mean.
    3. Refused vs. dropped: the two capture shapes, and which tool names the owning process.
    4. Both MS invocations from memory; the one-line HTTPS caveat.
    show answer

    (a) curl -i conversation / ss -tlnp sockets / strace syscalls / tcpdump packets.
    (b) [S] → [S.] → [.], length 0 — a connection opening; [P.] carries data; [F.] orderly close; [R.] abort — nothing listening.
    (c) Refused = SYN answered by RST, fast; dropped = SYN out, silence, timeout. Process names come from ss -tlnp (L0010), never tcpdump.
    (d) sudo tcpdump -i any port 80; sudo tcpdump -i any -w capture.pcap. HTTPS: shape visible, payload encrypted — dev tools / mitmproxy for content.

Later. Wireshark — the GUI analyst for those .pcap files: same filter language, “follow TCP stream,” protocol decodes; named, not part of a defaults-only terminal stack. mitmproxy — the intercepting proxy for encrypted-traffic content (MS-linked). Check your understanding

Four questions. Shuffled answers.

Q1What does tcpdump actually show you?

  • the packets crossing an interface, both directions, filtered as asked
  • the system calls a program makes to the kernel
  • the sockets a box has open, with owning processes
  • the HTTP conversation exactly as the client saw it

Q2You see [S], then [S.], then [.] — three lines, length 0. What just happened?

  • a TCP connection was established — the three-way handshake
  • a connection was refused and torn down at once
  • three packets of application data were delivered
  • the kernel logged a malformed packet it dropped

Q3MS’s invocation for capturing web traffic on port 80, all interfaces:

  • sudo tcpdump -i any port 80
  • sudo tcpdump -i any -w 80
  • sudo tcpdump -c any -i 80
  • sudo tcpdump -i any host 80

Q4Your [S] comes back as [R.] within a millisecond; curl says “connection refused.” What does that mean, and what confirms it?

  • the host answered “nothing listening” — ss -tlnp shows no listener on that port
  • a firewall silently dropped the packet on its way out
  • DNS resolved the name to the wrong address
  • the server accepted the connection and then crashed

Ask the teacher. Did the ladder land — curl conversation, ss sockets, strace syscalls, tcpdump packets? Did refused-RST vs. dropped-silence click once ss -tlnp confirmed it? Any surprise that -A reads the plaintext GET in full, while HTTPS stays opaque?
