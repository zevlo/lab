Lesson 0028 · Missing Semester — Dev Environment

Language servers & CLI checkers

How IDEs get “smart” features via LSP — and how your terminal stack covers format, lint, and typecheck with programs you run beside vim.

Why this matters

L0026 named two development-environment shapes. Missing Semester’s next slice is code intelligence: completion, jump-to-definition, find-references, formatting, linting, and type checking. In an IDE those often arrive through a language server speaking Language Server Protocol (LSP). On a terminal workflow, the same quality jobs — format, lint, typecheck — usually run as CLI checkers you invoke from bash (and later in CI). You keep editing in vim; you do not need a vim plugin for that floor.

Read first (10–15 min): MS Development Environment and Tools — “Code intelligence and language servers” (through configuring language servers). Skim AI / Extensions for later. Skip installing VS Code extensions and vim plugin managers.

Knowledge 1 — what a language server is

A language server is a program that understands a language semantically (symbols, types, imports — not just text). An editor starts it and talks over LSP. MS examples: Pylance for Python in VS Code, gopls for Go. Features people mean by “the IDE is smart”:

FeatureWhat you get
completionsuggest fields/methods after obj.
hover docsdocs at the cursor
jump-to-definitionfrom use → definition
find referencesall uses of a symbol
importsorganize / flag missing imports
code qualityformat, lint, type diagnostics (often as-you-type)

MS notes that some of those quality tools also run standalone. That standalone path is the terminal floor for this mission.

No vim LSP client tonight. Jump-to-definition and rich in-buffer completion need an editor plugin or an IDE. Mission constraint: no vim plugin managers. You still get format / lint / typecheck by running CLIs. (Cursor already gives you IDE-side intelligence when you want it — this lesson is the SSH-box / defaults vim path.)

Knowledge 2 — CLI checkers map to the terminal stack

MS’s terminal example pairs vim/tmux/shell with language CLIs (they name Ruff and Mypy for Python). Jobs and stock tools you already have:

JobTool in this lesson
Python syntaxpython3 -m py_compile file.py
Go formatgofmt -w file.go
Go static checksgo vet ./…
Python typesmypy (one install — MS-named; like the jq exception)

Same exit-status rule as L0023: success → 0, problems → nonzero. So python3 -m py_compile x.py && echo ok only prints ok when syntax is clean.

python3 -m py_compile broken.py; echo "status=$?"
# fix in vim, re-run until status=0

gofmt -w main.go          # rewrite file to gofmt style
go vet ./...              # report suspicious code; nonzero if issues
Environment still matters. MS says IDEs need the right Python env so the language server sees packages. For CLIs: the python3 / mypy on your PATH is the one that runs. Wrong interpreter → wrong or missing packages. Virtualenvs and packaging depth wait for a later lecture.

Knowledge 3 — mypy as the type-check CLI

Syntax can be fine while types are wrong. mypy reads annotations and reports mismatches without running the program:

python3 -m pip install --user mypy
mypy typed.py; echo "status=$?"

Ruff (format + lint) is the other MS-named Python CLI — optional later. Tonight’s install is mypy only.

Drill — catch, fix, re-check

Ghostty + bash + vim. Scratch: /tmp/ms-lsp/.

  1. Seed a syntax error and prove the checker: 
    mkdir -p /tmp/ms-lsp && cd /tmp/ms-lsp
cat > broken.py <<'EOF'
def greet(name):
    print("hello", name
EOF
python3 -m py_compile broken.py; echo "status=$?"
    Expect nonzero status and a traceback pointing near the missing ).
    show answer

    status is not 0. Message mentions a syntax error (often “'(' was never closed” / unexpected EOF). File is not executed — only compiled.

  2. Fix in vim (compose — e.g. add the closing )), save, re-run until: 
    python3 -m py_compile broken.py && echo ok
    show answer

    Closing paren on the print line. ok prints only when status is 0.

  3. Go format + vet (stock toolchain — no extra install): 
    cat > main.go <<'EOF'
package main
import "fmt"
func main() {
fmt.Println( "hi" )
}
EOF
gofmt -w main.go
cat main.go
go vet ./...; echo "vet=$?"
    Confirm gofmt rewrote spacing/layout; vet should be clean (0) on this tiny file.
    show answer

    gofmt aligns braces/spacing to Go style. vet=0. (If you later introduce real vet findings — e.g. unreachable code — status goes nonzero.)

  4. Install and run mypy (one-time): 
    python3 -m pip install --user mypy
cat > typed.py <<'EOF'
def add(a: int, b: int) -> int:
    return a + b

print(add("1", 2))
EOF
mypy typed.py; echo "status=$?"
    Expect a type error and nonzero status. Fix the call to pass two ints (vim), re-run until Success: no issues found (or equivalent) and status 0.
    show answer

    mypy flags argument 1 as str where int expected. Change to add(1, 2). Re-run mypy typed.py; echo status=$?.

  5. One sentence out loud: what does a language server do for an IDE that mypy / gofmt do not replace by themselves?
    show answer

    Interactive editor features — completion, jump-to-definition, find-references, hover — while you type. CLIs cover the quality checks on demand (and in CI).

  6. Cold rebuilds (no peeking):
    1. Command to syntax-check x.py with the stdlib.
    2. Commands to format then vet a Go module in the current directory.
    3. Why might mypy fail while python3 -m py_compile succeeds?
    show answer

    (a) python3 -m py_compile x.py
    (b) gofmt -w . (or named files) then go vet ./...
    (c) Syntax is valid but types/annotations disagree — compile does not enforce annotations.
