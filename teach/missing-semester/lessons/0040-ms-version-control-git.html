Version Control and Git

Git’s interface is leaky. The data model is not. Once you see blobs, trees, commits, and refs, the commands stop being spells.

Why this matters

A VCS is a history of snapshots of a folder, plus who/when/why. Alone, that is “what did this look like last Tuesday.” With others, it is how you combine parallel work without rm -rf; git clone. Git is the default. MS’s bet: learn the model first, then the CLI is just how you edit the graph.

Read first (≈20 min): MS Version Control and Git — the whole lecture, including Exercises. You already use git; read for the data model, not for “how to commit.”

This is the whole lecture — model, command map, and the exercise set. Spread across sittings if you want. Scratch lives under /tmp/ms-git/. History-rewrite (exercise 4) never runs in /Users/za/lab.

Knowledge 1 — the data model

A file is a blob (bytes). A directory is a tree (names → blobs or trees). A snapshot is the top-level tree. A commit is that snapshot plus parents, author, and message. History is a DAG: each commit points at one parent, or two when you merge. Commits are immutable; fixing a mistake means new objects and moving a pointer.

type blob   = array<byte>
type tree   = map<string, tree | blob>
type commit = struct {
    parents:  array<commit>
    author:   string
    message:  string
    snapshot: tree
}

On disk, blob / tree / commit are all objects, stored by SHA-1 hash. They point at each other by hash, not by embedding. Humans cannot remember 40 hex chars, so references are mutable names for hashes (main, salty, origin/main). HEAD is “where we are” — usually a pointer to a branch, which points at a commit. A repository is objects + references. That is the whole model. Every command adds objects and/or moves refs.

See it: git cat-file -p HEAD prints the commit; git cat-file -p HEAD^{tree} prints the tree (mode, type, hash, name). MS’s example tree is exactly that listing.

Knowledge 2 — the staging area

Git does not snapshot the working directory blindly. The staging area (index) is the proposed next commit. git add copies chosen changes into it; git commit freezes the index as a new commit and advances the current branch. That is how you commit a bugfix without the debug prints, or two features as two commits.

PlaceRole
working directorywhat you edit
indexwhat the next snapshot will contain
HEADlast snapshot on this branch

git status and git diff (working vs index) / git diff --staged (index vs HEAD) are how you read those three states.

Knowledge 3 — commands as graph edits

MS does not re-teach every flag — Pro Git and git help <cmd> do. Map the verbs to the model:

CommandWhat it does to the graph
git initempty .git (objects + refs)
git add / commitnew commit; move current branch
git log --all --graph --decoratedraw the DAG
git branch / switchcreate a ref / point HEAD at it
git mergecommit with two parents, or fast-forward
git fetchdownload objects + remote-tracking refs
git pullfetch then merge
git pushsend objects; update the remote’s ref
git reset FILEunstage (MS)
git restorethrow away working-tree changes
git stashpark uncommitted work; clean the tree
git blame / showwho last touched a line; show that commit

MS notes say master. Use main here (git init -b main) — same ref role. git switch for branches; git restore for files. git checkout still does both; the split is clearer. Git is not GitHub. A pull request is a GitHub workflow on top of fetch/merge. Named advanced: rebase -i, add -p, bisect, revert, worktree, clone --depth=1 (do not shallow-clone for blame/log drills).

1 — Relate commands to the model

MS: if you are new to git, read Pro Git ch. 1–2 or play Learn Git Branching, and relate each command to the DAG. You already commit daily — skip the game unless you want it. Instead, build MS’s tiny tree and look at the objects:

cd /tmp/ms-git
mkdir -p model/foo && cd model
git init -b main
printf 'hello world\n' > foo/bar.txt
printf 'git is wonderful\n' > baz.txt
git add foo/bar.txt baz.txt
git commit -m 'initial snapshot'
git cat-file -p HEAD
git cat-file -p HEAD^{tree}
git log --all --graph --decorate --oneline

One sentence: what in that cat-file output is a hash pointer vs a name?

show answer

The commit object lists a tree hash and a parent if any — pointers. The tree listing is blob <hash> baz.txt and tree <hash> foo — the name is the key; the hash is the object. main and HEAD are refs sitting on that commit. The files in the working tree are not the objects; they are a checkout of them.

4 — Delete a file from history

A later git rm only adds a new commit. The blob is still in old snapshots. Do this on a throwaway repo.

cd /tmp/ms-git
mkdir hist && cd hist && git init -b main
printf 'ok\n' > keep.txt && git add keep.txt && git commit -m 'keep'
printf 'whsec_fake\n' > secret.txt && git add secret.txt && git commit -m 'oops secret'
printf 'more\n' >> keep.txt && git add keep.txt && git commit -m 'more work'
git log --all --full-history -- secret.txt
# secret still there. Now drop the commit that added it:
git rebase -i --root

In vim: on the oops secret line, change pick to drop, save, quit. Then prove the file is gone from history. (MS points at GitHub’s “removing sensitive data” guide if you ever have to do this on a repo you already pushed — assume leaked, rotate the secret, and coordinate with anyone who cloned.)

show answer

After drop, git log --all --full-history -- secret.txt is empty. git log --oneline shows keep then more work — two commits, new hashes (rebase rewrote the “more work” commit because its parent changed). ls has no secret.txt. Never run this in a shared repo that others have fetched; you would have to force-push and they would have to reset.

5 — stash

In the class-site clone, dirty one existing file, then:

cd /tmp/ms-git/class-site
# edit a line in README.md (vim), leave it uncommitted
git status
git stash
git status
git log --all --oneline | head
git stash pop

What did stash do to the working tree? What extra line did log --all show? When is this useful?

show answer

Working tree is clean; the edit is gone from the file. git log --all --oneline shows a WIP on main: … (or similar) under refs/stash — a commit that is not on any branch. stash pop reapplies it and drops the stash. Useful: you need a clean tree to switch / pull / bisect, and the work is not ready to commit.

6 — git graph alias

MS wants git graph → git log --all --graph --decorate --oneline. Do it in the toy repo first (does not touch ~/.gitconfig):

cd /tmp/ms-git/model
git config alias.graph 'log --all --graph --decorate --oneline'
git graph

Optional later: the same with git config --global, or an [alias] block in your existing gitconfig. Owned dotfile — your call, not required tonight.

show answer

Repo-local config lives in .git/config. git config --get alias.graph prints the command. git graph is git log with those flags. Global equivalent: git config --global alias.graph 'log --all --graph --decorate --oneline'.

7 — ignore junk

In the toy repo, ignore editor/OS crumbs so they never get staged:

cd /tmp/ms-git/model
printf '.DS_Store\n*.swp\n' > .gitignore
git add .gitignore && git commit -m 'ignore DS_Store and vim swaps'
touch .DS_Store foo/.DS_Store
git status

MS’s global version: git config --global core.excludesfile ~/.gitignore_global, then create that file. Same posture as exercise 6 — optional on the real machine. The idea is one ignore list for every repo.

show answer

git status should not list .DS_Store. A tracked file is not ignored — gitignore only applies to untracked paths. Global excludesfile is the same patterns, applied everywhere, without committing a .gitignore.

9 — merge conflict

MS’s recipe drill, on main:

cd /tmp/ms-git
mkdir recipe && cd recipe
git init -b main
cat > recipe.txt <<'EOF'
Pancakes
1 cup flour
1 cup sugar
1 cup milk
EOF
git add recipe.txt && git commit -m 'base recipe'
git branch salty
git branch sweet
git switch salty
vim recipe.txt   # 1 cup sugar → 1 cup salt
git add recipe.txt && git commit -m 'salty'
git switch sweet
vim recipe.txt   # 1 cup sugar → 2 cups sugar
git add recipe.txt && git commit -m 'sweet'
git switch main
git merge salty
git merge sweet

What happens on the second merge? What do <<<<<<< / ======= / >>>>>>> mean? Resolve in vim (keep what you want, delete the markers), then finish the merge. Visualize with git log --graph --oneline.

show answer

git merge salty fast-forwards (or merges cleanly) — main has salt. git merge sweet conflicts: both sides edited the same line. Markers: current branch (HEAD / main) above =======, incoming (sweet) below. After editing, git add recipe.txt && git commit (or git merge --continue). git log --graph --oneline shows a merge commit with two parents. git mergetool is named; vim is enough.

Check your understanding

Four questions. Shuffled answers.

Q1A Git commit object contains:

  • Parent hash(es), author, message, and a pointer to a tree
  • A diff against the previous commit, stored as a patch
  • The full working tree including untracked files and the index
  • Only the files from git add, zipped under .git/commits/

Q2The staging area exists so that:

  • The next snapshot can include a chosen subset of working-tree changes
  • Blobs can be stored before they have a SHA-1 hash
  • Remotes can receive files without creating a commit
  • Merge conflicts have a place to live besides the working tree

Q3HEAD is:

  • “Where we are” — usually the current branch ref, which points at a commit
  • The SHA-1 of the first commit in the repository (the root)
  • GitHub’s name for the default remote, same as origin
  • The staging area’s other name; git add updates HEAD

Q4git pull is:

  • git fetch plus git merge — download objects/refs, then merge into the current branch
  • Only a download; it never moves your branch or creates a merge
  • The same as cloning a subdirectory of a remote repository
  • git push in reverse: it sends your commits to origin
