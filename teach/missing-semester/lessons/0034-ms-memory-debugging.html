Lesson 0034 · Missing Semester — Debugging & Profiling

Memory debugging — sanitizers & Valgrind

The bug class that appears to work: buffer overflows, use-after-free, leaks. Two tools, one question apart — AddressSanitizer if you can recompile, Valgrind if you can’t. The Lecture-4 slice where the crash is far from the cause.

Why this matters

The debugging ladder so far: pdb (L0031) watches variables in a program you can edit; strace (L0032) watches the kernel boundary; tcpdump (L0033) watches the wire. None of them can see the heap — a program that writes one byte past its malloc, or touches a block after free, looks fine at every one of those observation points. MS: memory bugs “often don’t crash immediately but corrupt memory in ways that cause problems much later.” This slice adds the two tools that make the invisible visible.

Read first (≈5 min): MS Debugging and Profiling — the “Memory Debugging” subsection (short: sanitizers, the sanitizer family, Valgrind).

Knowledge 1 — the problem class

Three bugs, one shared property — the symptom lands far from the act:

BugThe actThe symptom, later
buffer overflowwrite past the end of an array or allocationneighbor’s data quietly changes; crash in unrelated code
use-after-freewrite (or read) through a pointer after free()often nothing — until the allocator reuses the block
memory leakmalloc without a matching freeno crash at all — memory climbs until the OOM killer (L0019)

Every earlier tool has a blind spot here. pdb shows your variables, not your heap neighborhood. strace -e trace=memory shows the mmap/brk calls — it cannot see what you do inside the block you got. And the L0028 checkers pass happily: the code is logically exactly what you wrote. Undefined behavior means the run “works” today — which is not evidence of anything.

Knowledge 2 — sanitizers: catch it at the moment it happens

A sanitizer is a compiler feature: add a flag, and the compiler instruments your code so that every memory access is checked at runtime. AddressSanitizer (ASan) pads each allocation with guard bytes (redzones) and quarantines freed blocks — so the first bad touch is caught when it happens, with the exact line:

gcc -fsanitize=address -g program.c -o program
./program

ASan detects (per MS): stack, heap, and global buffer overflows; use-after-free; use-after-return; and memory leaks. A report reads as three connected stacks — the bad access, the free that made it bad, the malloc that created it:

==36==ERROR: AddressSanitizer: heap-use-after-free on address 0x602000000010
WRITE of size 1 at 0x602000000010 thread T0
    #0 0x55… in main /root/uaf.c:12      ← the bad write
freed by thread T0 here:
    #0 0x7f… in free
    #1 0x55… in main /root/uaf.c:10      ← the free
previously allocated by thread T0 here:
    #0 0x7f… in malloc
    #1 0x55… in main /root/uaf.c:6       ← the origin
SUMMARY: AddressSanitizer: heap-use-after-free /root/uaf.c:12 in main

Same stack-reading skill as L0031’s bt: start at frame #0 of the first stack. The process aborts with a nonzero exit (L0023 — typically 134, SIGABRT, L0019). MS’s deployment point: sanitizers require recompilation, “but are fast enough to use in CI pipelines and during regular development” — the L0028 checkers-as-gate pattern, one flag deeper. The habit: always compile with -g so reports name files and lines (frame pointers — -fno-omit-frame-pointer — make stacks more reliable still).

The family, one flag each:

SanitizerFlagCatches
AddressSanitizer-fsanitize=addressoverflows, use-after-free, leaks
ThreadSanitizer-fsanitize=threaddata races in multithreaded code
MemorySanitizer-fsanitize=memoryreads of uninitialized memory
UBSan-fsanitize=undefinedundefined behavior (integer overflow, …)

Knowledge 3 — Valgrind: when you can’t recompile

Valgrind runs your existing binary “in something akin to a virtual machine” (MS) — every instruction is supervised, no recompilation, noticeably slower. The invocation MS gives:

valgrind --leak-check=full ./my_program

Use it when — per MS — you don’t have the source, can’t recompile (third-party binary or library), or need a tool the sanitizers don’t ship. At exit it prints a leak summary with verdicts worth knowing cold:

VerdictMeans
definitely lostno pointer to the block survives — a true leak
indirectly lostreachable only from a definitely-lost block
still reachablea pointer still exists at exit — often benign

It also catches the live errors — an invalid write after free shows as Invalid write of size 1 on a block “that was freed,” with the stacks. Where ASan dies at the first bad access with the exact line, Valgrind keeps running and tallies contexts (ERROR SUMMARY: 1 errors from 1 contexts). MS’s forward pointer: Valgrind is “a really powerful controlled execution environment” — its callgrind and massif tools are part of the Profiling half still to come. The decision table:

SituationReach for
you have the source, can rebuildASan — default choice: fast, precise, first-error abort
no source / can’t recompilevalgrind --leak-check=full
suspect a data raceTSan (-fsanitize=thread)
flaky, timing-dependent heisenbugrr — named below, not drilled here
The write ASan can’t see. MS’s rr exercise is a loop that writes scores[0..3] into a 3-slot array — clobbering the neighboring struct’s id. That write lands inside the same allocated object, so it breaks nothing ASan guards: redzones guard object borders, not wrong slots within. Wrong-place-but-legal writes are watchpoint territory (gdb/rr, L0031) — the honest limit of this slice’s tools.

Drill — make it confess

Ghostty + bash + vim, tmux for panes. Same posture as L0032/L0033: the L0030 disposable Linux box, nothing lands on the Mac, --rm cleans up. You are root inside, so no sudo. An SSH Linux remote works identically.

  1. Cold-name the slice: the three memory-bug classes and, one sentence each, why print-debugging (L0031) can’t see them. Then the decision: which tool when you can recompile, and which when you can’t?
    show answer

    Overflow (write past an allocation), use-after-free (touch after free), leak (allocate, never release). Prints show variables you thought to print — the heap neighborhood and allocator state are invisible; the symptom lands far from the act. Can recompile → ASan; can’t → valgrind --leak-check=full.

  2. Boot the box and meet “appears to work.” On the Mac: 
    docker run --rm -it --name ms-mem debian bash
# inside:
apt-get update && apt-get install -y gcc valgrind vim
    Now type MS’s exercise program in vim as uaf.c (use-after-free): 
    #include <stdlib.h>
#include <string.h>
#include <stdio.h>

int main() {
    char *greeting = malloc(32);
    strcpy(greeting, "Hello, world!");
    printf("%s\n", greeting);

    free(greeting);

    greeting[0] = 'J';
    printf("%s\n", greeting);

    return 0;
}
    Plain build and run: gcc uaf.c -o uaf && ./uaf; echo $?. Cold reads: (a) what printed — and is that correct? (b) what exit status, and what does that prove?
    show answer

    (a) Both lines print — likely Hello, world! then Jello, world!. MS: “It may appear to work.” It is undefined behavior, not correctness: the write landed in freed-but-not-yet-reused memory. (b) 0 — nobody told the kernel anything went wrong (L0023). Exit 0 means “terminated normally,” never “bug-free.”

  3. The sanitizer moment. Rebuild instrumented, run: 
    gcc -fsanitize=address -g uaf.c -o uaf
./uaf; echo $?
    Read the report as three stacks: connect uaf.c:6 (malloc), uaf.c:10 (free), uaf.c:12 (the write). Then fix it — MS: “Fix the issue it identifies” — and rerun until clean.
    show answer

    heap-use-after-free: a WRITE of size 1 at line 12, on a 32-byte block freed at line 10, allocated at line 6 — the pointer’s story in one report. Exit is nonzero: 134 = 128 + SIGABRT (L0019) — the sanitizer aborts at the first bad touch, by design. Fix: don’t touch memory after free — move the free(greeting) below the last use. Clean run: both lines print, exit 0, no report.

  4. The leak verdicts. In vim, comment out the free line. (a) Plain build, run — what do you observe? (b) ASan build, run — where does the leak show, and what names it? (c) Now the no-recompile path: plain build, valgrind --leak-check=full ./uaf — read the verdict. One sentence: what makes a leak definitely lost?
    show answer

    (a) Silence — correct output, exit 0; leaks never announce themselves (until the OOM killer, L0019). (b) At exit: ERROR: LeakSanitizer: detected memory leaks — Direct leak of 32 byte(s) in 1 object(s) allocated from: the uaf.c:6 stack (LeakSanitizer ships inside ASan on Linux). (c) definitely lost: 32 bytes in 1 blocks — same 32 bytes, same stack, no recompile. “Definitely” = no pointer to the block survives anywhere — unreachable by construction; still reachable would mean a live pointer remains at exit (often benign).

  5. Valgrind on the live error. Restore the free and the after-free write (task-2 state), plain build, then: 
    valgrind --leak-check=full ./uaf
    Find the use-after-free in Valgrind’s idiom. One sentence comparing the two tools’ styles on the same bug.
    show answer

    Invalid write of size 1 … Address … is 0 bytes inside a 32-byte block that was freed — with the free and malloc stacks; then ERROR SUMMARY: 1 errors from 1 contexts. Style: ASan aborts instantly at the exact line, Valgrind keeps running and tallies — first-error abort vs. a full supervised run; recompile vs. none; ~2× slowdown vs. substantially more (MS: “slower than sanitizers”).

  6. Cold rebuilds (no peeking):
    1. The three memory-bug classes, and the two-tool decision table.
    2. Both ASan invocations from memory — compile and run.
    3. ASan report anatomy: the three stacks and what each one pins down.
    4. The leak verdicts, and which leak report requires no recompile.
    5. The sanitizer family map: race, uninitialized read, overflow/UAF/leak, UB.
    6. rr in one line — and the one-sentence reason it’s not drilled here.
    show answer

    (a) Overflow / use-after-free / leak; recompile → ASan, can’t → Valgrind.
    (b) gcc -fsanitize=address -g prog.c -o prog; ./prog.
    (c) Bad access (line of the write) ← freed by (the free) ← previously allocated by (the malloc).
    (d) Definitely lost / indirectly lost / still reachable; Valgrind’s — no recompile.
    (e) TSan races, MSan uninitialized reads, ASan overflow/UAF/leak, UBSan undefined behavior.
    (f) rr record ./prog; rr replay — deterministic replay with reverse debugging; needs Linux + hardware performance counters, which VMs (incl. the Docker box) don’t expose.

Later. rr — record once, replay deterministically, debug backwards (reverse-continue finds where corruption began); Linux-only, hardware counters, fails in most VMs (MS says so — that’s why it’s named, not drilled). bpftrace/eBPF — kernel-wide syscall tracing and aggregation; strace’s lower-overhead, root-only cousin. TSan/MSan/UBSan hands-on (the family map is today’s floor). callgrind/massif — Valgrind’s profiling tools, waiting in the Profiling half. Still open in Lecture 4: AI-for-debugging (feeding reports like today’s to an LLM) and that Profiling half (time/htop/perf/hyperfine).

Check your understanding

Four questions. Shuffled answers.

Q1You have a third-party binary and no source. Suspected memory bug — which tool, and why?

  • Valgrind — it supervises the existing binary, no recompilation needed
  • ASan — it checks every access without touching the source
  • tcpdump — capture what the process sends while it crashes
  • strace -f — memory bugs show up as failed write syscalls

Q2The plain-built uaf prints both lines and exits 0. Why is that not evidence the program is correct?

  • Use-after-free is undefined behavior — the write may silently “work” until the allocator reuses that block
  • Exit 0 only means the program was small enough to finish quickly
  • It is evidence — sanitizers flag hypothetical risks, not real ones
  • printf flushes the buffer, so the corruption was already undone

Q3An ASan report says heap-use-after-free, with WRITE of size 1 at uaf.c:12, freed by a stack ending at uaf.c:10. What happened?

  • The program wrote through a pointer at line 12 to a block it had already freed at line 10
  • The program allocated a block at line 12 that was too small for one byte
  • Two threads wrote the same address at lines 10 and 12 — a data race
  • The program freed the same block twice, at lines 10 and 12

Q4Your multithreaded server has intermittent corrupted state — races suspected. Which sanitizer flag?

  • -fsanitize=thread (TSan — detects data races)
  • -fsanitize=address (ASan — races and leaks together)
  • -fsanitize=memory (MSan — uninitialized reads)
  • valgrind --leak-check=full (races show as leaks)
