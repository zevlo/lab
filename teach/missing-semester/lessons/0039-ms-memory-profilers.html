Memory profilers

Memcheck tells you a pointer was lost. Massif tells you when the heap grew, and which call owned the peak. A live pointer to unused memory is still a leak of space.

Withdrawn — skip this page. Lecture 4 is closed. Massif is in the notes, not the exercise set. Next lesson is 0040 — Version Control and Git.

Why this matters

L0034’s Memcheck answers one question at exit: was a pointer lost? L0036’s free -h / htop answer a different one: how big is the box right now? Neither draws the heap over the run, and neither names the malloc site that owned the high-water mark. MS: a memory profiler is how you find leaks and excessive allocation as a series — same move as L0037, for bytes instead of latency.

Read first (≈5 min): MS Debugging and Profiling — “Memory Profilers” (stop before “Benchmarking”).

Knowledge 1 — three heap questions

ToolQuestion it answers
MemcheckAt exit: definitely / indirectly / possibly lost, or still reachable (L0034)
free / htopWhole-process RSS this second — no function names, no history (L0036)
MassifHeap size over the run, plus an allocation tree at the peak

Valgrind’s own Massif manual names a class Memcheck is built to miss: the pointer is still live, so nothing is “lost,” but the memory is unused and the heap never comes down. That is a space leak. Massif’s graph is the tell — the line that should have fallen, didn’t.

CPU profilers (L0038) name who is on the CPU. Massif names who asked for heap. Same Valgrind VM as callgrind / Memcheck; different --tool.

Knowledge 2 — massif, then ms_print

MS’s two commands:

valgrind --tool=massif ./my_program
ms_print massif.out.<pid>

Nothing useful prints to the commentary. The profile is the file. ms_print turns it into (a) an ASCII graph of heap over “time” and (b) snapshot tables, with an allocation tree on detailed snapshots. Compile with -g so those trees name file:line. Optimisation level barely matters for heap.

Read the graph as three glyphs:

BarKind of snapshot
:normal — totals only
@detailed — includes the allocation tree (default: every 10th)
#peak — also detailed; the greatest recorded heap

Each snapshot row has useful-heap (bytes the program asked for) and extra-heap (allocator admin + alignment — Massif’s default admin guess is 8 bytes per block). stacks stays 0 unless you pass --stacks=yes (slow; leave it off).

Short programs look empty. Default time unit is instructions executed (i). Loading and dynamic linking dominate a tiny C program, so the graph is flat until the last columns. Pass --time-unit=B — time becomes bytes allocated and freed — and the climb shows up. Other units: ms (wall clock). Peak bars are taken after a free; a program that never deallocates may show no #.

No --privileged tonight. That flag was perf_event (L0038). Massif is ordinary Valgrind.

Knowledge 3 — the peak tree, and what the number is not

Start at the # snapshot. The tree under it is every live heap block, collated by stack: malloc at the root, then the call sites that asked for the bytes. Percentages are of total memory at that instant. Entries under ~1% get aggregated (both Massif and ms_print have --threshold).

By default Massif measures malloc / new and friends — not mmap, not the binary’s code/data/BSS, not the stack. htop RSS can be much larger; that is not a Massif bug. --pages-as-heap=yes switches to page-level accounting (named, not run). massif-visualizer is the GUI for the same file (named, like kcachegrind). Python’s memory-profiler is MS’s language-specific cousin — named only.

Drill — heap over time

Ghostty + bash + vim. Scratch on the Mac at /tmp/ms-massif/ is the container’s /work. Valgrind is Linux — apt in the box, nothing on the Mac. An SSH Linux remote works identically. No --privileged.

  3. A program with three heap shapes. In /work: 
    cat > heap.c <<'EOF'
#include <stdlib.h>
#include <string.h>

#define UNIT 1000

static char *kept;

void leak(void) {
    malloc(4 * UNIT);          /* pointer dropped */
}

void hold(void) {
    kept = malloc(8 * UNIT);   /* still reachable at exit */
    memset(kept, 0, 8 * UNIT);
}

void burst(void) {
    char *p = malloc(16 * UNIT);
    memset(p, 0, 16 * UNIT);
    free(p);
}

int main(void) {
    char *bufs[10];
    for (int i = 0; i < 10; i++) {
        bufs[i] = malloc(UNIT);
        memset(bufs[i], 0, UNIT);
    }
    burst();
    hold();
    leak();
    for (int i = 0; i < 10; i++)
        free(bufs[i]);
    return 0;
}
EOF
gcc -g heap.c -o heap
./heap; echo $?
    Exit 0. One sentence: what does that not prove about the heap? (L0034 callback.)
    show answer

    Exit 0 means the process finished. It does not mean the heap came back down, and it does not mean every malloc still had a pointer. “Appears to work” is not a heap profile.

  4. The empty-graph gotcha. 
    valgrind --tool=massif --massif-out-file=massif-i.out ./heap
ms_print massif-i.out
    Where is the climb? Why? Do not hunt for a bug in heap.c.
    show answer

    Most of the graph is empty; the bars pile up at the right. Default time unit is instructions executed. A tiny program spends almost all of those in load/link; main’s mallocs are a blip at the end. That is why the next step passes --time-unit=B.

  5. Bytes as time, then read the peak. 
    valgrind --tool=massif --time-unit=B --massif-out-file=massif.out ./heap
ms_print massif.out
    Find the # bar. Does the graph climb, spike, and fail to return to zero? In the peak tree, which function asked for the 16 KiB? After the final free loop, what is still on the heap — and which two functions own it?
    show answer

    With B, the climb is visible. Peak (#) is during burst while the ten bufs are still live (~10 KiB + 16 KiB useful, plus extra-heap). burst then frees, so the graph drops; hold + leak push it back up; freeing bufs drops it again — but not to zero. Leftover useful heap ≈ 8 KiB (hold / kept) + 4 KiB (leak). Extra-heap is a few dozen bytes of admin, not the story. Exact byte counts include rounding; the shape and the names are the floor.

  6. Same binary, Memcheck. 
    valgrind --leak-check=full ./heap
    Match the leftover Massif heap to the two verdicts. One sentence: what did Massif see as one leftover that Memcheck split?
    show answer

    Definitely lost ≈ 4 KiB in leak (pointer dropped). Still reachable ≈ 8 KiB in hold (kept still points at it). Massif does not care about that split — both are live heap until process exit, so both sit on the graph after the last drop. The still-reachable 8 KiB is the space leak Memcheck will not call “lost.”

  7. Cold rebuilds (no peeking):
    1. Memcheck vs Massif vs htop — one question each.
    2. The two MS commands, plus the extra flag a short program needs.
    3. Graph glyphs: : @ #.
    4. Why Massif’s number can be much smaller than htop RSS.
    5. What a space leak looks like on each tool.
    show answer

    (a) Lost pointer at exit / heap over time + peak tree / RSS right now.
    (b) valgrind --tool=massif ./prog; ms_print massif.out.*. Short: --time-unit=B.
    (c) normal / detailed / peak.
    (d) Default is malloc-heap only — not mmap, code, BSS, or stack.
    (e) Graph never returns to zero; Memcheck says still reachable if the pointer is kept, definitely lost if it was dropped.

Check your understanding

Four questions. Shuffled answers.

Q1Memcheck vs Massif — what split actually matters?

  • Memcheck: lost-pointer verdict at exit. Massif: heap over time + who allocated at the peak
  • Memcheck: heap over time and peak trees. Massif: lost-pointer verdicts like ASan
  • Memcheck: sampling stacks every 1 ms. Massif: tracing every call like callgrind
  • Memcheck: RSS as shown in htop. Massif: stack frames only, never malloc

Q2On an ms_print graph, a # bar means:

  • The peak snapshot — greatest recorded heap; also detailed (allocation tree)
  • A normal snapshot — totals only, no tree; every tenth bar is a peak
  • CPU on fire — Massif plots task-clock the way perf stat does
  • The first snapshot — Massif always treats startup as the peak

Q3A 20-line C program under Massif: the graph is empty until the last columns. Why, and the fix?

  • Default time unit is instructions executed (load/link dominate); pass --time-unit=B
  • Massif cannot profile programs that exit in under a second; use perf instead
  • You forgot --privileged; Massif needs a PMU the way perf record does
  • Default time unit is wall-clock ms; pass --time-unit=i to see mallocs

Q4A pointer is kept in a global, the memory is unused, the process exits 0. Memcheck vs Massif?

  • Memcheck: still reachable. Massif: leftover heap on the graph — a space leak, not “lost”
  • Both print definitely lost; Massif is just Memcheck with an ASCII sparkline
  • Memcheck: invalid write. Massif: the # bar sits at zero because globals are not heap
  • Neither sees it — only --pages-as-heap=yes can count malloc of a global

Ask the teacher. Did --time-unit=B flip the graph from empty-right to a real climb? Did the leftover heap match Memcheck’s lost + reachable split? ASCII ms_print enough, or would you want the GUI later?
