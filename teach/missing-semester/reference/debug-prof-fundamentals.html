Debugging fundamentals

Lecture 4 debugging slice — the golden rule, print-vs-log discipline, and a debugger (pdb) for when prints run out. Grounded in Debugging and Profiling.

The golden rule

MS opens the lecture with it: code does not do what you expect it to do, but what you tell it to do. Debugging is the work of closing that gap. The checkers from L0028 (py_compile, mypy, gofmt/go vet) catch syntax and type errors before you have to reason about logic — once those gates pass, what remains is a logic bug: the program is valid, and wrong. That is the bug class this slice targets.

Printf debugging vs logging

ApproachWhat it isReach for it when
printfad-hoc print() around the suspected region; iterate until the cause is visibleyou know roughly where the bug is and can re-run cheaply
logging“printing with care” via a framework — severity levels, routable output, structured fieldsthe diagnostic should survive after the fix; for services / long-running code

MS’s advice: once a print finds the bug, convert it into a proper log statement rather than deleting it. The next time a similar bug appears, the diagnostic data is already there. Severity levels let you filter later:

LevelMeaning
DEBUGfine-grained detail; off by default
INFOroutine progress (“server started on :8000”)
WARNINGunexpected but recoverable
ERRORa failure; usually needs attention
Third-party logs. Many programs take -v / --verbose (repeatable on some) to print more. Services (databases, web servers) write logs under /var/log/ on Linux; systemd services show theirs via journalctl -u <service> (Linux/systemd only — no direct macOS equivalent). This is the ops-triage counterpart to in-code prints, and pairs with the L0008 ops loop.

The debugger concept

Prints work when you know what to print and re-running is cheap. A debugger wins when (a) you don’t yet know what to print, (b) the bug only shows under hard-to-reproduce conditions, or (c) restart is expensive (long startup, complex state). It lets you interact with execution as it happens:

  • halt at a line (breakpoint),
  • step one instruction at a time,
  • inspect variable values,
  • halt conditionally,
  • read the call stack (backtrace).

pdb — Python’s debugger

Launch three ways:

python3 -m pdb script.py          # from the start
python3 -m pdb -c continue script.py   # run until a breakpoint/error
# or, inline in the source (Python 3.7+):
breakpoint()                     # program drops into pdb here
CommandDoes
b / break funcset a breakpoint (function or file:line)
c / continuerun until the next breakpoint / error
n / nextstep over the current line (no descent)
s / stepstep into a called function
p exprprint an expression / variable
l / listshow source around the current line
w / wherebacktrace (call stack)
q / quitexit pdb
Reproduce → isolate → inspect → fix → gate. The cardinal rule of inspecting: look at the actual value, not the one you assumed. An init-to-zero bug is invisible until you p biggest and see 0 where a negative number should be.

gdb — named, for compiled languages

MS’s de-facto debugger for C, C++, and Rust. The command shapes mirror pdb (debuggers share a vocabulary), so knowing one transfers:

gdbpdb equivalentAction

Under this mission the hands-on debugger is pdb (Python is the primary language track); gdb is named so you recognize it on a compiled-language remote. gdb -tui (or Ctrl-x a) gives a split source view.

Tidy logs — debugging data doubles as profiling data

MS’s profiling half makes the same point: when you add diagnostic output, shape it so it can be graphed later. A line like 1705012345,42.5 (timestamp,value) is trivial to plot; a prose sentence is not. Logging in a tidy, parseable shape means the prints you add to debug a slow path today become the dataset you profile tomorrow. That sets up the later Lecture-4 profiling slice.

Beyond this slice

These remain for later Lecture-4 slices (the lecture is dense; it gets split, like Lectures 1–3 were):

  • Record-replay debugging — rr records a run and replays it deterministically with reverse commands (reverse-continue, reverse-step) for Heisenbugs and hard-to-reproduce races. Linux only.
  • System-call tracing — strace (Linux) / dtruss (macOS) shows every syscall; bpftrace/eBPF does it at kernel depth with aggregation. The highest-leverage DevOps debug tool on the list.
  • Network debugging — tcpdump / Wireshark packet capture; relates to L0010 (dig/ss).
  • Memory debugging — sanitizers (ASan/TSan/MSan/UBSan) and Valgrind; mostly C/C++/Rust.
  • AI for debugging — LLMs explaining stack traces and cryptic errors; distinct from the L0029 AI form factors (which are about authoring code).
  • The Profiling half — time (real/user/sys), htop, perf + flame graphs, Valgrind’s callgrind/massif, hyperfine benchmarking.
