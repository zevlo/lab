Dev containers

Lecture 3 dev-environment slice — a container, defined as code, that runs your dev tools the same way on any machine. Grounded in Development Environment and Tools and the containers.dev spec.

The three nouns

TermWhat it isShape
imagelayered filesystem + metadata; the blueprintbuilt from a Dockerfile; immutable, tagged
containera running instance of an imagedocker run starts one; docker ps lists them
dev containera container + a config encoding the full dev environment.devcontainer/devcontainer.json
MS names dev containers under “Extensions and other IDE functionality” — “use a container to run development tools … helpful for portability or isolation.” The spec is editor-agnostic: VS Code, Cursor, Codespaces, JetBrains, and the devcontainer CLI all read the same devcontainer.json. The environment is code, not locked inside one IDE.

The docker CLI core (terminal-native)

These run identically on macOS (Docker Desktop or colima provides the Linux VM) and on a Linux remote.

VerbDoes
docker build -t tag .build an image from Dockerfile in cwd
docker imageslist images
docker run -it --rm …start a container (interactive + TTY + auto-remove)
docker ps / -alist running / all containers
docker exec -it NAME bashshell into a running container
docker stop / rm NAMEstop / remove a container
docker rmi IMAGEremove an image
docker logs NAMEcontainer stdout/stderr
 
docker run -it --rm \
  -v "$PWD":/work \      # live mount: edit on host, see it in the container
  -w /work \             # working dir inside
  -p 8000:8000 \         # forward a port (host:container)
  --name ms-box \        # name the instance
  ms-dev bash            # image + command
-i keeps stdin open; -t allocates a TTY (together = interactive shell). --rm removes on exit. -v is the dev loop: edit in vim on the host, the change is instantly visible inside. That mount is what makes a container feel like a local dev box rather than a one-shot command.

devcontainer.json — the flags, versioned

{
  "name": "ms-dev",
  "build": { "dockerfile": "../Dockerfile" },
  "workspaceFolder": "/work",
  "mounts": [ "source=${localWorkspaceFolder},target=/work,type=bind,consistency=cached" ],
  "forwardPorts": [8000],
  "postCreateCommand": "mypy --version"
}

Each key is a docker run flag or a manual post-create step, captured as text. An IDE or the devcontainer CLI (npm install -g @devcontainers/cli) reads it and runs the equivalent docker commands.

Gate inside the container — L0028 callback

The image bakes in the checkers (py_compile, mypy, gofmt). The gate is still L0028 checkers under the L0023 exit-status rule (0 clean, nonzero reject/fix) — the container only guarantees the gate is runnable anywhere the image runs. No per-host install; the environment and the gate travel together.

docker run --rm -v "$PWD":/work -w /work ms-dev \
  bash -lc 'python3 -m py_compile extract.py && mypy extract.py; echo status=$?'
The L0029 agent can run inside this same container; its output is gated by the same checkers. Container = portable environment; checkers = portable gate; exit status = portable verdict.
Mission posture. MS lists dev containers as an IDE extension. Here the IDE path is named, not expanded (same as Zed in L0029, kitty/starship in L0025). The docker verbs are the curriculum; the devcontainer CLI is a one-off install like jq (L0020) or mypy (L0028).
