The code already shows the what. Scale length with complexity. Trust the reader with the how.

README funnel

What does this do → why should I care → how do I use it → how do I install it. One-liner (and maybe a demo) first. Usage before install.

Commit body

Problem → Solution → Implications. Also: alternatives, trade-offs, surprises. A typo needs only a subject. Split refactors from features.

git add -p    # y yes  n no  s split  q quit
git blame FILE
git show HASH

An LLM looking only at the diff sees the what. Ask for the message in the same agent session that made the change, or tell it to query you for the why.

Search existing issues first. Vulnerabilities go through SECURITY.md / private disclosure, not a public issue. Copyleft (GPL / AGPL) applies to your contribution: choosealicense.com. Read CONTRIBUTING.md. Start small. Upstream before a fork.

Review

Name the code, not the person. Actionable. Ask a question. Give the why. Mark blocking versus nit. Name what works. Stop. LLM first pass is not a substitute.

Questions

State your understanding, then “is that right?” Yes/no. Specific. Stop on unknown terms. Keep going until you understand. Same moves with an LLM. Julia Evans.

AI etiquette

Disclose that AI contributed, and which parts. Follow the project’s policy. If the point is learning the task, doing the task is the point. Assessments: ask; if they forbid tools, leave them off.
