Memory debugging — sanitizers & Valgrind

Lecture 4 slice — the bug class that appears to work: overflows, use-after-free, leaks. ASan if you can recompile, Valgrind if you can’t. Grounded in Debugging and Profiling.

The problem class

Memory bugs corrupt quietly and confess late — the symptom lands far from the act. Earlier observation points are blind to them: pdb shows variables, not the heap neighborhood (L0031); strace shows the mmap/brk calls, not what happens inside the block (L0032); checkers pass because the code says what you meant (L0028).

BugThe actThe symptom, later
buffer overflowwrite past the end of an array / allocationneighbor’s data changes; crash in unrelated code
use-after-freetouch memory after free()often nothing — until the allocator reuses the block
memory leakmalloc with no matching freeno crash — memory climbs until the OOM killer (L0019)

Sanitizers (recompile)

Compiler instrumentation: redzones around every allocation, freed blocks quarantined — the first bad touch is caught at the moment it happens, with the exact line. MS: fast enough for CI and regular development (the L0028 gate, one flag deeper).

gcc -fsanitize=address -g program.c -o program
./program

Report anatomy — three connected stacks (same #0-first reading as bt, L0031):

==36==ERROR: AddressSanitizer: heap-use-after-free on address 0x602000000010
WRITE of size 1 at 0x602000000010 thread T0
    #0 … in main uaf.c:12          ← the bad access
freed by thread T0 here:
    #1 … in main uaf.c:10          ← the free that made it bad
previously allocated by thread T0 here:
    #1 … in main uaf.c:6           ← the origin
SUMMARY: AddressSanitizer: heap-use-after-free uaf.c:12 in main

The process aborts nonzero (typically 134 = 128 + SIGABRT). At exit, ASan’s LeakSanitizer reports blocks never freed — Direct leak of 32 byte(s) in 1 object(s) — on Linux, no extra flag. Family map:

FlagToolCatches
-fsanitize=addressASanstack/heap/global overflows, use-after-free, use-after-return, leaks
-fsanitize=threadTSandata races
-fsanitize=memoryMSanreads of uninitialized memory
-fsanitize=undefinedUBSanundefined behavior (integer overflow, …)
Habits. Always -g so reports name files and lines; -fno-omit-frame-pointer makes stacks more reliable (matters for profiling too — MS).

Valgrind (no recompile)

Runs the existing binary in a supervised, VM-like harness — no source, no rebuild, noticeably slower than sanitizers. MS’s invocation:

valgrind --leak-check=full ./my_program

Use when: no source; can’t recompile (third-party); or for tools the sanitizers lack. Live errors print as Invalid write of size 1 on a block “that was freed,” then ERROR SUMMARY: N errors from M contexts — it tallies rather than aborts. At exit, leak verdicts:

VerdictMeans
definitely lostno surviving pointer — a true leak
indirectly lostreachable only from a definitely-lost block
possibly lostonly an interior pointer survives — suspicious
still reachablea live pointer exists at exit — often benign

Decision table

SituationReach for
have source, can rebuildASan — default: fast, precise, first-error abort
no source / can’t recompilevalgrind --leak-check=full
suspected data raceTSan (-fsanitize=thread)
flaky heisenbugrr (named — see beyond)

Where to run it

Sanitizers compile fine anywhere gcc/clang lives, macOS included. Valgrind is Linux (unusable on modern macOS) — the lesson drill keeps everything in the L0030 container posture regardless: docker run --rm -it --name ms-mem debian bash, apt-get install -y gcc valgrind vim, nothing lands on the Mac. MS’s exercise 3 (uaf.c) is the drill spine: plain build “appears to work,” ASan names the use-after-free, the fix is to move free below the last use, the leak variant comments the free out.

Beyond this slice

  • rr — record once (rr record ./prog), replay deterministically (rr replay, opens gdb), debug backwards: reverse-continue runs to the last moment a watchpoint changed. For Heisenbugs and MS’s corruption.c exercise — a write to the wrong slot inside a valid object, which ASan/Valgrind cannot see (redzones guard borders, not wrong addresses within). Linux-only, needs hardware performance counters — fails in most VMs, including Docker-on-Mac; macOS → Warpspeed (named).
  • bpftrace/eBPF — kernel-wide syscall tracing with aggregation, root-only: strace’s lower-overhead cousin for system-level questions (MS, System Call Tracing).
  • callgrind / massif — Valgrind’s CPU and heap profilers (--tool=callgrind, --tool=massif): the Profiling half of Lecture 4.
  • LeakSanitizer standalone — ASAN_OPTIONS=detect_leaks=1 toggles leak detection where it isn’t default (e.g. some platforms/CI setups).
