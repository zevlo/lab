System-call tracing

Lecture 4 slice — strace at the program↔kernel boundary: the five shapes, how to read a trace line, and the triage patterns. Grounded in Debugging and Profiling.

The boundary

Everything a program wants from the outside world — files, memory, network, processes — it requests from the kernel via a system call. MS: tracing these calls “can reveal why a program is hanging, what files it’s trying to access, or where it’s spending time waiting.” The observation point differs from L0031: a debugger inspects state inside a program you can edit and re-run; a syscall trace watches behavior at the boundary — any binary, running or fresh, no source needed.

The five strace shapes

InvocationAnswersRecall hook
strace ./progevery syscall, from the first execve“all of it”
strace -e trace=file ./progfile-related calls only — cut the noise“what files?”
strace -f ./progfollow child processes too (MS: “important for programs that start other programs”)f = family
strace -p <PID>attach to a running process; Ctrl-C detaches without killing“observe in place”
strace -T ./progduration of each call, in <…>“where does it wait?”

Reading a trace

execve("/bin/ls", ["ls", "/"], 0x… /* 25 vars */) = 0
openat(AT_FDCWD, "/", O_RDONLY|O_DIRECTORY)   = 3
getdents64(3, 0x… /* 20 entries */, 32768)    = 616
close(3)                                       = 0
write(1, "bin\nboot\ndev\n…", 49)              = 49
exit_group(0)                                  = ?

Each line is syscall(args) = result. On-sight reads:

PatternMeaning
execve line 1kernel loads the traced command itself — every trace opens with it
write(1, …)a write to stdout (fd 1) — program output is this syscall (L0009)
= 3, = 4…successful open/socket returns a new file descriptor
= -1 ENOENTa failed open — file not there; the silent-failure smoking gun
exit_group(N)the exit status — the same N read as $? since L0023
The trace rides stderr. strace ls > /dev/null → trace only; strace ls 2>/dev/null → clean run only (L0009 skill). Redirect deliberately before grepping: strace -f sh -c '…' 2>&1 | grep -E 'execve|pipe|clone'.

Where to run it

strace is Linux-only — the L0010 ss posture: drill it in the L0030 dev container (docker run --rm -it debian bash, then apt-get update && apt-get install -y strace) or over SSH on a Linux remote (add sudo for installs and for -p attaches on shared boxes; in your own container you are root). macOS/BSD equivalent: dtruss, which wraps dtrace — needs sudo, and SIP-protected system binaries resist it. Named, not drilled (same posture as gdb in L0031).

Triage patterns

SymptomMoveWhat you see
fails silently-e trace=filethe openat(…) = -1 ENOENT it died on
spawns helpers-fpipe2 + clone + a child execve per stage
service already runningpgrep (L0008) → -p PIDtraffic arriving (accept4) or not; no restart, no code access
hangs / unexplained slowness-Tthe one call with a multi-second <…>
Overhead is real. Trapping every syscall slows the target — fine for triage, wrong for loaded production. That is MS’s bridge to bpftrace: lower overhead, kernel depth, aggregations — at the cost of root, an awk-ish syntax, and whole-kernel scope.

Beyond this slice

  • bpftrace / eBPF — sandboxed kernel programs; syscall counting and latency aggregation, filtered by comm or PID, tracing from process start via -c 'cmd'. Root required.
  • strace -c — summary table (calls, errors, time) instead of a line-by-line trace; the cheap cousin of bpftrace aggregation.
  • ltrace — library-call tracing (the boundary with libc, not the kernel).
  • ptrace scope — /proc/sys/kernel/yama/ptrace_scope governs who may attach on modern Linux; the reason sudo shows up on shared remotes.
  • Network debugging — tcpdump/Wireshark; the packet-level sibling of this slice, pairs with L0010. Later Lecture-4 slice.
