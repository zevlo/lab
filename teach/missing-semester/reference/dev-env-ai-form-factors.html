Three form factors (MS taxonomy)

The boundary that matters is how much existing code the model can touch.

Form factorWhat it doesKey limit
autocompletesuggests at the cursor as you type; steered by commentsonly completes beyond the cursor — cannot rearrange existing code
inline chatselect a block, prompt in plain language, model proposes an edityou review & accept the proposed diff
agentmulti-step task; edits across files, may run commandsmost autonomous — needs the most verification (own MS lecture)
MS’s canonical AI mistake: asked to “extract Markdown links,” autocomplete returns valid code but places import re inside the function. Plausible, runnable, wrong-shaped. py_compile passes; review or a linter catches it.

opencode is a terminal-native coding agent — the most autonomous MS form factor, inside the bash / tmux / ssh stack this mission masters. The agent form factor is not locked in an IDE here.

Zed is an IDE the user already owns (like kitty / starship) — present, not curriculum to expand. Vim stays the no-AI editing floor: remote / SSH / surgical speed, and the neutral surface to review AI output. Exact Zed panel / mode names: zed.dev/docs.

Gate AI output — checkers as the floor

AI output is a draft, not a verdict. Run the L0028 checkers on it; exit status (L0023) is the gate — 0 clean, nonzero reject/fix.

python3 -m py_compile ai_output.py   # syntax
mypy ai_output.py                    # types
gofmt -w ai_output.go && go vet ./... # format + static
Checkers catch syntax / type errors. They do not catch placement, naming, or design issues (the import-inside-function class). Those need review or a linter — the later Code Quality lecture. Checkers raise the floor; they do not ceiling the work.
