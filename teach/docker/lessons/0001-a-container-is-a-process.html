A Container Is Just a Process

The image-vs-container mental model that turns copy-paste commands into understanding.

§1Two objects, not one

Everything confusing about Docker gets unconfusing once you separate two things that the word "Docker" blurs together:

An image is a frozen, read-only template: a filesystem plus some metadata (what to run, what ports, what env). It sits on disk doing nothing. It cannot run — it's not alive.

A container is what you get when Docker takes an image and launches it: an ordinary Linux process, running in isolation, with a private copy-on-write filesystem made from the image's layers. Containers run; images sit there.

IMAGEtemplate · immutable · stored
─ docker run →
CONTAINERprocess · live · disposable

One image → many containers. Like a class and its instances.

sourceDocker's own definition: "containers are isolated processes." What is a container? — Docker docs. On images: What is an image?

Two consequences worth tattooing somewhere:

1. Containers are disposable; images are the durable artifact. You delete containers freely and re-run from the image any time. Anything a container wrote inside its own filesystem dies with it — by design.

2. Containers share the host kernel. A container is not a small computer with its own OS — it's a process the kernel has deceived into thinking it's alone. That's why they start in milliseconds and why they're Linux (more on that trick in Module 2).

macOSYou're on a Mac, so where's "the host kernel"? Inside OrbStack: a small Linux VM that Docker actually runs containers in. Your containers are invisible to macOS ps — they live in that VM. On Linux servers, they'd be plain processes on the host. Details in Module 2.

§2The lifecycle loop

docker pull nginx     # fetch image from registry → stored locally
docker run nginx       # create container from image, start it
docker ps              # list running containers (add -a for stopped)
docker stop web        # graceful shutdown — container still exists
docker rm web          # destroy container + its private filesystem

The word to internalize: stopped ≠ gone. A stopped container still exists on disk, keeps its name, keeps its writable files — until rm. Full command reference: Docker Core Commands (reference).

§3Lab — prove it to yourself (≈10 min, in your terminal)

OrbStack is running on your machine. Each step shows the expected output — if yours matches, you're on track. Immediate feedback, no waiting for me.

  1. Run your first named container:

    docker run -d --name web -p 8080:80 nginx
    a1f7a4bb3a27... (64-character id, no error)

    What happened: Docker pulled nginx (image), created a container named web, started it in the background (-d), and forwarded host port 8080 → container port 80. Open http://localhost:8080 — that page is served from inside the container.

  2. See it as what it is — one row in a process table:

    docker ps
    CONTAINER ID IMAGE PORTS NAMES a1f7a4bb3a27 nginx 0.0.0.0:8080->80/tcp web

    What happened: ps = process status. One image (nginx), one running container (web). The id you see is the container's id — not the image's.

  3. Go inside it:

    docker exec -it web sh
hostname
cat /etc/os-release | head -2
ls /etc/nginx
    a1f7a4bb3a27 (its own hostname = container id) PRETTY_NAME="Debian GNU/Linux 12 ..." conf.d fastcgi_params mime.types ...

    What happened: exec started a second process (a shell) inside the running container. You're now looking at the container's private filesystem — Debian, nginx config, none of your Mac's files. It has its own hostname. A process with its own filesystem view and identity: that's the whole trick.

  4. Write a file inside, then leave:

    touch /I_WAS_HERE
ls /
exit
    bin boot dev etc ... I_WAS_HERE ... usr var

    What happened: the file lives in web's private writable layer. Remember it — we're about to kill it.

  5. The decisive experiment. Destroy the container, re-create it from the same image:

    docker rm -f web
docker run -d --name web -p 8080:80 nginx
docker exec web ls /
    bin boot dev etc ... usr var (no I_WAS_HERE)

    What happened: rm destroyed the old container's writable layer — the file is gone forever. The new container started clean from the untouched image. This ephemerality is a feature: containers can be killed and replaced at will, which is the entire basis of how production systems stay healthy. (Check docker ps — still one image, fresh container, new id.)

  6. Clean up after yourself — a good habit from day one:

    docker rm -f web
docker ps -a && docker images
    CONTAINER ID ... (empty list) REPOSITORY TAG IMAGE ID ... nginx latest ...

    What happened: no containers left; the image is still on disk. Templates survive their instances.
