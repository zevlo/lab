Lesson 0007 · Module 3 of 5 · Image Building · Mini-Project I

Two Stages, One Image

Ship the program, not the compiler — and this time the program is yours.

§1The workshop and the product

Your mission says: take a real application and ship it end-to-end. Starting now, the real application is count_errors — your Rust tool that walks a directory and counts lines containing ERROR in .log files. One real dependency (walkdir). One binary. Perfect cargo for this lesson.

Think about what that binary needs from the world. To build it, you need the whole Rust workshop: cargo, the compiler, headers, a registry download. The official rust:1-alpine image carrying that workshop unpacks to well over a gigabyte. To run it, you need: one file. A compiled Rust binary asks the kernel for syscalls and nothing else.

Lesson 0006 gave you the recipe. Followed naively, it welds the factory to the product: compiler, build cache, source, and binary all frozen into one image. Every server that pulls your image drags a gigabyte of workshop it will never use. That is the problem this lesson deletes.

§2Two stages

A Dockerfile may contain more than one FROM. Each FROM starts a stage — its own image, its own layers, its own cache chain. Stages build in order. When the build ends, only the last stage becomes your image. The earlier stages are scaffolding. They are kept out of the shipping product.

One instruction moves things between stages: COPY --from=build copies files out of an earlier stage. It is the only door. Anything not carried through that door stays behind with the compiler.

The final stage below is FROM scratch — the empty image. No base at all. Your files are the entire filesystem. That works only because the builder is Alpine: Alpine's Rust compiles against musl, which produces a static binary — every library it needs is inside itself. A binary built on Debian asks the system for shared libraries at startup, and on scratch there is no system to ask.

FROM rust:1-alpine AS build      # the workshop
WORKDIR /src
COPY Cargo.toml Cargo.lock ./
RUN mkdir src && echo 'fn main() {}' > src/main.rs && cargo fetch --locked
COPY src ./src
RUN cargo build --release --locked

FROM scratch                       # the product — this ships
COPY --from=build /src/target/release/count_errors /count_errors
ENTRYPOINT ["/count_errors"]
CMD ["/logs"]

Two new instructions share the last line's job:

ENTRYPOINTCMD
roleThe fixed programDefault arguments
docker run img /datastaysreplaced by /data
suitsCLI tool imagesserver images (Lesson 0006)

And note the ordering, because it is Lesson 0006's rule wearing work clothes. The manifests (Cargo.toml, Cargo.lock) are copied before the source. So the dependency download sits in its own layer, above your daily edits. Change main.rs, rebuild: the fetch layer stays cached. You will watch it happen in the lab.

The recipe met reality. This Dockerfile's dependency line was first written as plain cargo fetch --locked. It failed, live: "no targets specified in the manifest — either src/main.rs … must be present." Cargo refuses to read a project with no source. The standard fix is the placeholder: create a one-line dummy main.rs, fetch dependencies, then overwrite it with your real src. Failures like this are why lessons get verified before they get taught.

§3Lab — your code, two stages (≈25 min, in your terminal)

Everything below was built and run on this machine before you read it. First, one disclosure: identical layers from that verification may still sit in your build cache. If a "first" build shows CACHED, that is why. To feel the true cold build, run docker builder prune -f first — it empties the build cache (Lesson 0006's little app rebuilds in seconds, so nothing is lost).

  1. Arrive at your project, and measure what must never enter an image:

    cd ~/lab/rust/count_errors
du -sh target
    300M target ← your number will differ; all of it is macOS build output

    That folder is your Mac's compiled output. It is useless inside a Linux image, and COPY . . would ship every byte of it. Keep it out, plus the test logs you are about to make:

    cat > .dockerignore <<'EOF'
target/
testlogs/
.git/
EOF

  2. The honest first attempt — one stage, everything in. Write Dockerfile.fat:

    FROM rust:1-alpine
WORKDIR /src
COPY . .
RUN cargo build --release
CMD ["./target/release/count_errors", "/logs"]

    Build it:

    docker build -f Dockerfile.fat -t count-errors:fat .
    #4 [1/4] FROM docker.io/library/rust:1-alpine@sha256:0cce0a5e0e8b… #4 DONE 391.0s ← the one long wait: pulling the workshop (~280 MB) #5 [2/4] WORKDIR /src #5 DONE 0.4s #7 [3/4] COPY . . #7 DONE 0.0s ← tiny, because .dockerignore kept target/ out #8 [4/4] RUN cargo build --release #8 DONE 1.2s #9 naming to docker.io/library/count-errors:fat done

    What happened: the base pull dominates (first time only — Lesson 0005's image store remembers it). The compile itself took seconds: walkdir is small. Note the tag resolved to a digest again — Lesson 0002, every time, forever.

  3. The bill:

    docker images
    IMAGE ID DISK USAGE CONTENT SIZE count-errors:fat 7587a4eb923a 1.35GB 352MB first-app:latest 33c3f4ac29a8 201MB 43.5MB

    What happened: one point three five gigabytes, for a tool that reads text files. The workshop, the product, and cargo's download cache — welded into one layer stack. Every pull of your image moves all of it.

  4. It works, though. Make test data and run the giant:

    mkdir -p testlogs
printf 'INFO started\nERROR db timeout\nERROR retry failed\nINFO done\n' > testlogs/app.log
printf 'ERROR conn refused\nINFO ok\nERROR bad crc\nERROR disk full\n' > testlogs/web.log
printf 'ERROR i am not a .log file\n' > testlogs/notes.txt
docker run --rm -v "$(pwd)/testlogs":/logs:ro count-errors:fat
    5 errors found

    What happened: five — two from app.log, three from web.log, and notes.txt correctly ignored (not a .log). Same count your Mac's build gives you: same code, same kernel syscalls, different filesystem view. Two flags did new work: --rm deletes the container the moment it exits (CLI containers exit at once — no point keeping corpses), and -v "$(pwd)/testlogs":/logs:ro lends a Mac folder into the container, read-only. That is a bind mount — Module 4's subject, previewed today because your tool needs data to chew on.

  5. Now the real Dockerfile. Name it Dockerfile (the default name, so builds need no -f):

    FROM rust:1-alpine AS build
WORKDIR /src
COPY Cargo.toml Cargo.lock ./
RUN mkdir src && echo 'fn main() {}' > src/main.rs && cargo fetch --locked
COPY src ./src
RUN cargo build --release --locked

FROM scratch
COPY --from=build /src/target/release/count_errors /count_errors
ENTRYPOINT ["/count_errors"]
CMD ["/logs"]

  6. Build and read the log closely — BuildKit names your stages:

    docker build -t count-errors .
    #4 [build 1/6] FROM docker.io/library/rust:1-alpine@sha256:0cce0a5e… #4 CACHED #8 [build 4/6] RUN mkdir src && echo 'fn main() {}' … && cargo fetch --locked #8 0.855 Downloaded walkdir v2.5.0 #8 0.962 Downloaded rustix v1.1.4 #8 3.996 Downloaded windows-sys v0.61.2 ← yes, Windows — the lockfile lists every platform #8 DONE 4.2s #9 [build 5/6] COPY src ./src #9 DONE 0.0s #10 [build 6/6] RUN cargo build --release --locked #10 0.400 Compiling walkdir v2.5.0 #10 0.575 Finished `release` profile [optimized] in 0.49s #11 [stage-1 1/1] COPY --from=build /src/target/release/count_errors /count_errors #11 DONE 0.0s #13 naming to docker.io/library/count-errors:latest done

    What happened: rows say [build n/6] for the workshop and [stage-1 1/1] for the product. The final stage has exactly one instruction: copy the binary across the only door. From rust:1-alpine pulled nothing this time — and notice it never appears in docker images either: BuildKit keeps build bases in its cache, not the image list.

  7. The new bill:

    docker images
docker image history count-errors
    IMAGE ID DISK USAGE CONTENT SIZE count-errors:latest 4ef836a1c54c 921kB 274kB count-errors:fat 7587a4eb923a 1.35GB 352MB first-app:latest 33c3f4ac29a8 201MB 43.5MB IMAGE CREATED BY SIZE 4ef836a1c54c CMD ["/logs"] 0B <missing> ENTRYPOINT ["/count_errors"] 0B <missing> COPY /src/target/release/count_errors /count… 647kB ⋮ nothing below — scratch has no base

    What happened: 921 kilobytes against 1.35 gigabytes — about 1,470 times lighter, and the binary is 647 kB of it. And the birth certificate from Lesson 0002 has just three rows with nothing underneath: the first image you have built that stands on no base at all. Delete the fat one — it served its purpose as the before-picture:

    docker rmi count-errors:fat

  8. Run yours, then argue with it. First, no arguments — the defaults drive:

    docker run --rm -v "$(pwd)/testlogs":/logs:ro count-errors
    5 errors found

    Now mount the same folder somewhere else and say so:

    docker run --rm -v "$(pwd)/testlogs":/data:ro count-errors /data
    5 errors found

    What happened: same five, two ways. Bare docker run used the defaults: ENTRYPOINT ran /count_errors, CMD handed it /logs. The second time, /data replaced CMD's default — ENTRYPOINT never moved. That split is what makes a CLI tool usable as an image.

  9. The cache dance, with real dependencies. Edit src/main.rs — change one line:

    println!("{} errors found (v2)", total);

    Rebuild and watch which layers flinch:

    docker build -t count-errors .
    #8 [build 4/6] RUN mkdir src && echo 'fn main() {}' … && cargo fetch --locked #8 CACHED ← your edit did not touch this #9 [build 5/6] COPY src ./src #9 DONE 0.0s ← content changed (Lesson 0006) #10 [build 6/6] RUN cargo build --release --locked #10 DONE 0.6s ← recompiled, against already-downloaded deps #11 [stage-1 1/1] COPY --from=build … #11 DONE 0.0s
    docker run --rm -v "$(pwd)/testlogs":/logs:ro count-errors
    5 errors found (v2)

    What happened: Lesson 0006's rule, now carrying a real dependency graph. The fetch layer — the slow one on a big project — stayed cached, because Cargo.toml and Cargo.lock did not change. Only the copy, the compile, and the final image rebuilt. Revert the edit if you like; the image you keep is yours either way.
