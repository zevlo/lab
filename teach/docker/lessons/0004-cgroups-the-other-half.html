Cgroups: The Other Half

Namespaces hide the world. Cgroups cap the damage.

§1Two mechanisms, two jobs

Last lesson you saw the first half of container isolation. Namespaces hide things from a process. A container believes it is alone.

A container can still believe it is alone and eat all the memory on the machine. Namespaces do nothing about that. This is the second half.

A cgroup (control group) is a kernel feature. It groups processes. The kernel measures what the group uses. You set caps on the group. When the group hits a cap, the kernel acts.

Docker gives each container its own cgroup. Your docker run flags become the caps.

CONTAINERa set of processes
belongs to

Namespaces change what a process sees. Cgroups cap how much it can use.

§2The caps you will use

flagcapsat the cap, the kernel…
--memory=256mRAMkills the process (OOM killer)
--cpus=1.5CPUslows the process (throttle)
--pids-limit=100process countblocks new processes
--memory-swap=256mRAM + swapset equal to --memory to turn swap off

Remember one pair: memory kills, CPU slows.

A killed container exits with code 137. The math: 128 means "killed by a signal", and 9 is signal 9 (SIGKILL). So 137 means the kernel ended the process by force. You will meet 137 again in every production incident involving memory.

sourceThe kernel's own manual on cgroups: Control Group v2 — kernel.org. Docker's flags map onto it directly.

§3Lab — prove it to yourself (≈10 min, in your terminal)

You will set a memory cap, break it, and read the kernel's receipt. Then you will see a CPU cap do the opposite: slow, not kill.

  1. Give a container 100 MB of memory. Then fill it up:

    docker run --name oomtest --memory=100m --tmpfs /tmp:size=300m busybox dd if=/dev/zero of=/tmp/blob bs=1M count=250
echo $?
    137

    What happened: /tmp here is a tmpfs — a filesystem stored in RAM. Writing files to it uses memory. dd wrote zeros until the blob passed 100 MB. The container hit its cap. The kernel's OOM killer killed dd. The command printed no output because dd died before finishing. $? holds the exit code: 137 = 128 + 9, a forced kill.

  2. Read the receipt:

    docker inspect --format '{{.State.OOMKilled}} {{.State.ExitCode}}' oomtest
    true 137

    What happened: Docker records what the kernel did. OOMKilled: true is proof. Your app did not crash. The kernel killed it for the cap. When a container dies in production, check this flag before blaming the code.

  3. Same job, bigger cap:

    docker rm -f oomtest
docker run --rm --memory=300m --tmpfs /tmp:size=300m busybox dd if=/dev/zero of=/tmp/blob bs=1M count=250
    250+0 records in 250+0 records out

    What happened: the same dd, the same data, exit code 0. The only change was the cap: 100 MB → 300 MB. The app was never the problem. The cap was. This is the whole point of cgroups: behavior depends on the limit, not on luck.

  4. Now the opposite. Cap the CPU and watch it slow, not die:

    docker run --rm busybox dd if=/dev/zero of=/dev/null bs=1M count=4000
docker run --rm --cpus=0.25 busybox dd if=/dev/zero of=/dev/null bs=1M count=4000
    4000+0 records in / 4000+0 records out, then: 4194304000 bytes (3.9GB) copied, 0.15 seconds, 26.6GB/s ← no cap 4194304000 bytes (3.9GB) copied, 1.46 seconds, 2.7GB/s ← capped to a quarter core

    What happened: both runs copied the same 3.9 GB and exited with code 0. dd prints its own speed, and speed is the whole lesson. The capped run was about ten times slower. Pure math says four, because a quarter core does the work in four times the time. Real throttling costs a little more. Your exact numbers will differ. The outcome is what counts: same work, same result, slower. Nothing died. (If you wrap the command in time, ignore its user and sys lines — they measure the docker client on your Mac, not the container. The container works inside OrbStack's VM.)

    5. field noteAn earlier version of this step used timeout 5 to stop a program that never ends. The container ran forever. Ctrl-C did nothing. docker stop waited ten seconds, then killed by force. Only docker kill worked at once. The reason is a kernel rule: the main process in a container is PID 1, and PID 1 ignores any signal it has not registered a handler for. The busybox timer sent SIGTERM to its parent. The parent was PID 1. The kernel dropped the signal. SIGKILL is the one signal no process can refuse, and that is what docker kill sends. Docker's fix is the --init flag: a tiny signal-forwarding PID 1 in front of your program. You will meet this again in Module 4, where graceful shutdown matters.

  5. See the cap in the kernel's own files:

    docker run --rm --memory=100m busybox cat /sys/fs/cgroup/memory.max
    104857600

    What happened: 104857600 bytes = 100 MB. Cgroups live in a virtual filesystem, /sys/fs/cgroup. Docker wrote your flag into memory.max, and the kernel enforces that file. The CPU cap sits in cpu.max in the same place. There is no magic layer between your flag and the kernel.

  6. Clean up:

    docker ps -a
    CONTAINER ID ... (empty list — step 3 removed oomtest, later runs used --rm)

    What happened: nothing left running. The full flag table and exit-code decoder live here: Cgroups & Limits (reference).
