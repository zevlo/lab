Lesson 0003 · Module 2 of 5 · Architecture & Isolation

How the Kernel Lies to a Process

Namespaces — the machinery behind "isolated", one filtered view at a time.

§1The lie, named

Lesson 0001 called a container "a process the kernel has deceived into thinking it's alone." Here is the deception, named: namespaces. The kernel's own manual defines one as wrapping a global system resource "in an abstraction that makes it appear to the processes within the namespace that they have their own isolated instance" of it.

Read that twice. Nothing is copied. Nothing is virtualized. The processes, network interfaces, and mount points all exist exactly once, on one shared kernel — but each namespace filters the view a process gets of them. A container is an ordinary process looking at the kernel through a set of carefully narrowed windows.

CONTAINER Asees: pid 1 · own eth0 · hostname a1b2…
CONTAINER Bsees: pid 1 · own eth0 · hostname c3d4…
↕ namespaces narrow the view ↕
ONE SHARED KERNELevery process · every interface · every mount

Same kernel, same reality — different windows.

Linux has eight namespace types: mount, PID, network, UTS (hostname), IPC, user, cgroup, time. Docker's run creates fresh copies of the ones that matter most — mount, PID, network, UTS, IPC — per container. You've already met mount (the private Debian filesystem in Lesson 0001's lab) and UTS (the hostname that equalled the container id). Today you'll pin down PID and network with your own hands.

sourceThe kernel's own definitions, all eight types in one table: namespaces(7) — Linux man-pages.

§2Isolation is à la carte

Here's the part that interviewers love and operators live: namespaces are independent. Each dimension can be isolated — or deliberately shared with the host — on its own. Docker exposes the switch for each:

namespaceprivatizesshare it withyou met it when
UTShostname--uts=hosthostname = container id (L0001)
PIDprocess numbering--pid=hosttoday, step 3
NETinterfaces, IPs, ports--network=hosttoday, step 5 — and why -p exists
MNTfilesystem mounts(no simple flag)private Debian fs (L0001)
IPCshared memory--ipc=host—
useruid/gid mappingoff by defaultModule 5 (security)
cgroup · timerarely visible——

Two things follow. First: sharing one dimension doesn't surrender the others — --pid=host still gives the container its own network and filesystem. Second: every =host flag is a hole in the wall. Useful for debugging, dangerous by default — seeing other containers' processes is an attack surface, which is why these flags belong to the production-hardening conversation (Module 5).

macOS"Host" here means OrbStack's Linux VM — the kernel your containers have been sharing all along — not macOS itself. On a Linux server, it would be the real host. That's why --pid=host will show the VM's processes, never your Mac's.

§3Lab — prove it to yourself (≈10 min, in your terminal)

Short commands, big reveals. You'll watch one process table become many, and one network become many.

  1. Start a witness — one boring process in the background:

    docker run -d --name victim busybox sleep 1000
    e4b2c1a90f7d… (container id, no error — busybox image may pull first, ~2 MB)

    What happened: nothing fancy — sleep 1000 is an ordinary process, no different in kind from nginx. It's now running on the shared kernel, believing otherwise.

  2. Open a fresh universe and count its processes:

    docker run --rm busybox ps
    PID USER TIME COMMAND 1 root 0:00 ps

    What happened: a whole world containing exactly one process — ps itself, and it's PID 1. This container has a fresh PID namespace: its own numbering, starting at 1. There is no other process in this universe because none was started in it.

  3. The reveal. Ask for the host's numbering instead:

    docker run --rm --pid=host busybox ps
    PID USER TIME COMMAND 1 root 0:00 /sbin/init … ← the VM's pid 1 ⋮ (the VM's daemon processes — rows vary) 731 root 0:00 sleep 1000 ← victim! 742 root 0:00 ps ← you

    What happened: same kernel, wider window. Without a private PID namespace, you see the true process table: the VM's init, its daemons — and sleep 1000, which turned out to be PID 731 on the shared kernel all along. The container's "PID 1" was a renumbering, not a separate machine. This flag is also why --pid=host weakens isolation: neighbors become visible.

  4. Hostname = a private slot, not a private computer:

    docker run --rm busybox hostname
docker run --rm -h myownworld busybox hostname
    a1f7a4bb3a27 (a 12-char id — its own UTS namespace, seeded with the id) myownworld (same kind of namespace, your choice of contents)

    What happened: the UTS namespace gives each container its own hostname slot. Lesson 0001's mystery — "why did hostname equal the container id?" — is now solved: Docker simply fills that slot with the short id. -h fills it with whatever you like.

  5. Networks: one per container, or the host's one:

    docker run --rm alpine ip addr          # alpine pulls first if needed (~3 MB)
docker run --rm --network=host alpine ip addr
    # first command — its own NET namespace: lo: 127.0.0.1 eth0: 192.168.x.x (or 172.x.x.x — one private interface, one IP) # second command — the host's stack: lo, eth0, plus bridges and veths — the VM's full wiring

    What happened: every container normally gets a fresh NET namespace: its own loopback, one private interface and IP. That's why Lesson 0001 needed -p 8080:80 — a hole punched between namespaces. --network=host skips all that and shares the VM's single stack — fast, but its ports are first-come-first-served (Quiz Q3 will test this).

  6. Clean up, and notice what isolation costs to dismantle:

    docker rm -f victim
docker ps -a && docker images
    CONTAINER ID ... (empty list) REPOSITORY TAG ... nginx latest ... nginx 1.27 ...

    What happened: the victim, its namespaces, and its writable layer are gone — nothing to clean up separately, the kernel tears the views down with the process. The images (Lessons 0001–0002) never even noticed. Review the full isolation cheat sheet: Isolation & Namespaces (reference).
