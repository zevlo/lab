The Anatomy of an Image

Layers, tags, and digests — what docker pull actually moves.

§1An image is a stack of diffs

Last lesson's model: an image is a frozen template. Now open it up. An image is not one big file — it's an ordered stack of read-only layers, each one a filesystem diff: "add these files, change these, delete these." Stacked and merged, they produce the filesystem you saw when you went inside web with exec.

metadata — CMD, EXPOSE, ENV0 B
+ nginx config, entrypoint scripts4.6 kB
+ apt-get install nginx61 MB
+ Debian base filesystem74 MB
writable layer — added at run timecontainer's

Bottom-up construction. The red dashed layer is the one part that is not the image — it belongs to the container (Lesson 0001).

Three consequences worth tattooing:

1. Layers are content-addressed. Each layer's true name is sha256:… — a cryptographic fingerprint of its bytes. Identical bytes, identical digest, no matter which image claims to own them.

2. Layers are shared. Because layers are named by content, two images built on the same base store those base layers once. Twenty images on debian:bookworm-slim share its 74 MB layer twenty times over. That's also why pull sometimes skips layers: it already has those exact bytes.

3. Some history is weightless. Instructions like EXPOSE 80 or CMD change no files — they're metadata in a config blob, costing 0 B. You'll see this in the lab.

§2Names, tags, digests

What does docker pull nginx even ask for? Every image reference has hidden structure:

REGISTRYdocker.io
/
NAMESPACElibrary
/
REPOnginx
:
TAG1.27

Everything before the repo can be omitted: nginx secretly means docker.io/library/nginx:latest.

A tag (1.27, latest, 1.27-alpine) is a movable label the publisher can re-point any time. latest is only the default name — it does not promise newest, and pulling it today vs. next month can give you different bytes. A digest (nginx@sha256:9c3f…) is the content fingerprint itself: the same digest always means the same layers, forever. That is why production deployments pin by digest, or at minimum by exact version tag — "just re-pull latest" is how a Tuesday becomes an incident.

And what does pull actually do? It asks the registry for the image's manifest — a small JSON list of layer digests — then downloads each layer it doesn't already have, checked against those digests. Content-addressing is what makes sharing and integrity the same mechanism.

§3Lab — prove it to yourself (≈10 min, in your terminal)

No containers get harmed in this lab — it's all image-side. OrbStack's daemon does the work; the same commands run identically on any Linux server.

  1. What's on your disk already:

    docker images
    REPOSITORY TAG IMAGE ID CREATED SIZE nginx latest 9c8ea7f3d1b2 2 weeks ago 195MB

    What happened: the nginx:latest you pulled in Lesson 0001, still there — templates survive. Note the IMAGE ID; it becomes important in step 5.

  2. Pull a specific version and watch it arrive — layer by layer:

    docker pull nginx:1.27
    1.27: Pulling from library/nginx 5f3a6cf317de: Pull complete 3f4d0a1c8b9e: Pull complete ⋮ (a handful more) Digest: sha256:8f3a1c…(64 hex chars) Status: Downloaded newer image for nginx:1.27 docker.io/library/nginx:1.27

    What happened: that's not one download — it's one per layer. If any line says Already exists, that layer's bytes were already on your disk from another image: same digest, no re-download. The final line is the full name, unabbreviated.

  3. X-ray the stack:

    docker image history nginx:1.27
    IMAGE CREATED BY SIZE <missing> /bin/sh -c #(nop) CMD ["nginx" …] 0B <missing> /bin/sh -c #(nop) EXPOSE 80 0B <missing> /bin/sh -c #(nop) ENTRYPOINT ["/doc… 0B <missing> /bin/sh -c #(nop) COPY 30-tune-work… 4.62kB <missing> /bin/sh -c set -x nginx config… 1.11kB <missing> /bin/sh -c #(nop) ENV DPKG_IDX… 0B <missing> /bin/sh -c set -x apt-get install… 61.3MB <missing> /bin/sh -c #(nop) ADD file:ea… 74.8MB ⋮ (≈10 rows, newest first)

    What happened: every row is one build instruction, newest on top — you are reading the image's birth certificate. The 0B rows changed config, not files (§1, consequence 3). The two big rows are the Debian base and the nginx install. The IDs read <missing> because pulled layers aren't tagged images themselves. This table is the foundation of Module 3: Dockerfile order = layer order = cache behavior.

  4. See the image as the machine sees it:

    docker image inspect nginx:1.27 --format '{{.Id}}'
docker image inspect nginx:1.27 --format '{{json .RootFS.Layers}}'
    sha256:d1a4a1a3f2e6… (its ID — digest of the config blob) ["sha256:2ce52c3f…","sha256:9c6b1d4e…","sha256:8d2f7a90…", "sha256:a71f33c2…","sha256:e3d04b8a…","sha256:94d5c117…","sha256:1f29e8d4…"]

    What happened: an image literally is this: a config blob (the ID) plus an ordered list of layer digests. Count the entries — the non-zero rows of history. No magic, just checksums in a JSON list.

  5. A tag costs nothing. Make your own:

    docker tag nginx:1.27 demo/nginx:my-alias
docker images
    REPOSITORY TAG IMAGE ID CREATED SIZE demo/nginx my-alias d1a4a1a3f2e6 4 months ago 187MB nginx 1.27 d1a4a1a3f2e6 4 months ago 187MB nginx latest 9c8ea7f3d1b2 2 weeks ago 195MB

    What happened: two rows, one IMAGE ID. tag copied nothing — it pinned a second label onto the same stack of layers. (And note: 1.27 and latest have different IDs — different builds, likely sharing most layers underneath.)

  6. Find the fingerprint — the part that never moves:

    docker image inspect nginx:1.27 --format '{{index .RepoDigests 0}}'
    nginx@sha256:8f3a1c…(same 64 hex chars as the pull printed)

    What happened: this is the digest the registry recorded for the content you got. Anyone, anywhere, pulling nginx@sha256:8f3a1c… gets byte-identical layers. The tag 1.27 could be re-pointed tomorrow; the digest cannot. This is the production pinning knob — mission-critical habit for Module 5.

  7. The decisive experiment. Remove your alias:

    docker rmi demo/nginx:my-alias
    Untagged: demo/nginx:my-alias

    What happened: notice what's missing — any Deleted: line. No bytes were freed, because nginx:1.27 still references the same image. rmi removes references; layers die only when the last reference goes. A tag is a pointer, and now you've proven it in both directions.
