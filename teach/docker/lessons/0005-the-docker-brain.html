Lesson 0005 · Module 2 of 5 · Architecture & Isolation

The Docker Brain

Who talks, who works, and where your containers really live.

§1The split

You have never talked to a container. Not once. Here is what actually happens when you type docker run:

Three parts. The docker CLI is the program named docker on your Mac. It is a thin client. It holds no images and no containers. It only sends requests. The Docker daemon (dockerd) receives them and does the work: it pulls images, creates containers, manages networks and volumes. Between them sits a REST API, spoken over a Unix socket — a special file that works like a door between two programs.

docker CLIyour Mac · thin · no state
─ REST API over socket →
dockerdinside OrbStack's Linux VM
→ containerd → runc →
the kernelnamespaces + cgroups · Lessons 0003–0004

The chain behind every docker command you have ever typed.

One line on the deepest links: the daemon does not start containers itself. It delegates to containerd and runc, which set up the namespaces and cgroups you already met. That is the whole magic revealed — Docker is a manager wrapped around kernel features.

sourceDocker's own words: "The Docker client talks to the Docker daemon… using a REST API, over UNIX sockets or a network interface." — Docker overview — Docker docs.

§2Where things live

thingwherewhat it holds
docker CLIyour Macnothing — stateless
dockerd + its dataOrbStack's Linux VMall images, containers, volumes, networks (/var/lib/docker)
container processesthe VM's kernelthe actual running work (Lesson 0003)
the socket~/.orbstack/run/docker.sockthe door between client and daemon

Three consequences follow from this map.

1. All Docker state lives in the VM. Your twenty images and their 4.5 GB are files inside OrbStack's VM. Nothing important lives in the CLI.

2. The client can point anywhere. The CLI reads an address — the DOCKER_HOST variable or a saved context — and speaks HTTP to whatever daemon answers. Same laptop, daemon in another city. This is exactly how CI pipelines drive remote Docker.

3. "Cannot connect to the Docker daemon" means one thing. The door is closed. Either the daemon is not running, or the client is pointing at the wrong door. You will produce this error on purpose in the lab, and read it calmly forever after.

§3Lab — prove it to yourself (≈10 min, in your terminal)

Nothing gets created or destroyed today. You will watch the split, find the door, and speak the daemon's language by hand.

  1. One command, two worlds:

    docker version
    Client: Version: 29.4.0 OS/Arch: darwin/arm64 ← your Mac Context: orbstack Server: Docker Engine - Community Engine: Version: 29.4.0 OS/Arch: linux/arm64 ← a Linux machine containerd: Version: v2.2.2 ← the chain from §1 runc: Version: 1.5.1

    What happened: one command, two operating systems. The top half describes the CLI running on your Mac. The bottom half describes the daemon answering from inside OrbStack's Linux VM — and even lists containerd and runc from the chain. Your Mac never ran a container. It asked, and a Linux machine said yes.

  2. Find the door:

    docker context show
docker context inspect --format '{{.Endpoints.docker.Host}}'
docker context ls
    orbstack unix:///Users/…/.orbstack/run/docker.sock ← a file, inside your home NAME DESCRIPTION DOCKER ENDPOINT default Current DOCKER_HOST based con… unix:///var/run/docker.sock desktop-linux Docker Desktop unix:///Users/…/.docker/run/docker.sock orbstack * OrbStack unix:///Users/…/.orbstack/run/docker.sock

    What happened: a context is a saved door address. The star marks the one in use: orbstack, pointing at a socket file in your home directory. The list also shows the Docker Desktop door you are not using. Switching context switches which daemon hears your commands — remember this for your first remote server.

  3. Now speak to the daemon directly, no docker CLI at all:

    curl -s --unix-socket ~/.orbstack/run/docker.sock http://localhost/_ping
curl -s --unix-socket ~/.orbstack/run/docker.sock http://localhost/version | head -c 120
    OK {"Platform":{"Name":"Docker Engine - Community"},"Version":"29.4.0","ApiVersion":"1.54","Os":"linux","Arch":"arm64",…

    What happened: curl spoke plain HTTP through the socket file, and the daemon answered: OK, then JSON describing itself — note "Os":"linux". The docker CLI does exactly what you just did. It is an HTTP client with nice formatting. The REST API is public and documented — every SDK, compose, and CI system drives Docker through this same door.

  4. Read the daemon's ledger:

    docker info --format 'Root={{.DockerRootDir}} Driver={{.Driver}} Cgroup={{.CgroupVersion}}'
docker system df
    Root=/var/lib/docker Driver=overlayfs Cgroup=2 TYPE TOTAL ACTIVE SIZE RECLAIMABLE Images 20 0 4.505GB 4.717GB (104%) Containers 0 0 0B 0B Local Volumes 2 0 64B 64B (100%) Build Cache 11 0 1.329GB 29.92MB

    What happened: everything the daemon owns, in one place. /var/lib/docker is inside the VM. Driver=overlayfs is the layer-stacking filesystem from Lesson 0002. Cgroup=2 is the version whose memory.max you catted in Lesson 0004. Your images are 4.5 GB of files on the VM's disk — the CLI just asked for the numbers. (Numbers will differ on your machine.)

  5. Break the door on purpose:

    DOCKER_HOST=unix:///nonexistent.sock docker ps
echo $?
    failed to connect to the docker API at unix:///nonexistent.sock; check if the path is correct and if the daemon is running 1

    What happened: you pointed the client at a door that does not exist. The CLI did not hang, did not guess, did not fix. It reported a closed door and exited with code 1. When a CI log or a teammate's terminal shows this error, you now know: the client is fine, the address or the daemon is wrong. If OrbStack is not running, you get the same error with the real socket path.

  6. The manager is not the muscle:

    docker info --format 'Containers={{.Containers}} Running={{.ContainersRunning}}'
    Containers=0 Running=0

    What happened: the daemon's live bookkeeping — right now, nothing running. Now the key claim: if the daemon crashed this second, running containers would keep running. The kernel runs them (Lessons 0003–0004); the daemon only creates, tracks, and cleans up after them. A manager walking off the site does not stop the workers. (Quitting OrbStack stops the whole VM — that is a bigger switch, and different.)
