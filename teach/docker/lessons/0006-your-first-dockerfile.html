Lesson 0006 · Module 3 of 5 · Image Building

Your First Dockerfile

Write the recipe, build the image, and make the cache obey your ordering.

§1The recipe

You know what an image is: a stack of layers (Lesson 0002). You know who builds it: the daemon (Lesson 0005). A Dockerfile is the recipe they follow — a short file of instructions. The daemon reads it top to bottom. Each instruction produces one layer. The result is an image.

instructionwhat it does
FROM python:3.12-slimStart from a base image. Every Dockerfile begins here.
WORKDIR /appSet the working directory inside the image.
COPY file .Copy a file from your folder into a layer.
RUN commandRun a command at build time and freeze the result into a layer.
EXPOSE 8000Document the port. Humans read it; -p does the real work (Lesson 0001).
CMD ["python", "app.py"]Declare what a container of this image runs at start time.
RUN vs CMD — the classic confusion, settled now. RUN happens once, during the build. Its result is frozen into the image forever. CMD happens every time a container starts, and nothing it does is ever saved. RUN makes the image. CMD runs it. (And remember the field note from Lesson 0004: your CMD process becomes PID 1.)

One more file worth knowing: .dockerignore. A build sends your whole folder to the daemon. List junk there — .git, node_modules, secrets — and it stays out of the image. Same syntax as .gitignore.

§2The cache

Rebuilding an unchanged Dockerfile takes no time. The daemon recognizes every instruction it has already run and reuses the layers. This is the build cache.

The rule that runs your career: the cache stops at the first change. Docker walks your instructions top to bottom. It reuses every cached layer until it hits one whose inputs changed. From that line down, everything rebuilds.

So the order of your Dockerfile is a decision. Put stable things first (base image, system packages, dependencies) and changing things last (your code). Then a one-line code change rebuilds one small layer — not a ten-minute dependency install.

One refinement that surprises everyone: the cache checks file content, not timestamps. You will prove this in the lab with touch.

sourceDocker's own guidance on ordering, cache, and RUN vs CMD: Building best practices — Docker docs.

§3Lab — build your first image (≈15 min, in your terminal)

A tiny real web app: one Python file, one page. No dependencies, so the build is fast and nothing can go wrong. Next lesson you containerize a project of your own with this exact pattern.

  1. Make the project folder and three files:

    mkdir -p ~/docker-first && cd ~/docker-first

    index.html:

    <!DOCTYPE html>
<html>
<head><title>lesson 0006</title></head>
<body><h1>hello from my first image</h1></body>
</html>

    app.py — serves the page, and ok at /health:

    import pathlib
from http.server import BaseHTTPRequestHandler, HTTPServer

ROOT = pathlib.Path(__file__).parent

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/health":
            body, ctype = b"ok\n", "text/plain"
        else:
            body, ctype = (ROOT / "index.html").read_bytes(), "text/html"
        self.send_response(200)
        self.send_header("Content-Type", ctype)
        self.end_headers()
        self.wfile.write(body)

HTTPServer(("0.0.0.0", 8000), Handler).serve_forever()

    Dockerfile — five instructions, five layers:

    FROM python:3.12-slim
WORKDIR /app
COPY index.html .
COPY app.py .
EXPOSE 8000
CMD ["python", "app.py"]

    Note the order: the rarely-changing file (index.html) is copied before the often-changing one (app.py). That ordering earns its keep in step 6.

  2. Build. The dot at the end matters — it is the build context, the folder sent to the daemon (Lesson 0005):

    docker build -t first-app .
    #5 [1/4] FROM docker.io/library/python:3.12-slim@sha256:a6e34c59… #5 DONE 1.7s #6 [2/4] WORKDIR /app #6 DONE 0.2s #7 [3/4] COPY index.html . #7 DONE 0.0s #8 [4/4] COPY app.py . #8 DONE 0.0s #9 naming to docker.io/library/first-app:latest done

    What happened: the daemon pulled the base image (first time only — it is now cached locally), then ran your instructions in order. Look closely at line #5: the tag python:3.12-slim resolved to a digest — Lesson 0002 happening live in your build log.

  3. Read the birth certificate:

    docker image history first-app
    IMAGE CREATED BY SIZE a60b4fb30151 CMD ["python" "app.py"] 0B <missing> EXPOSE [8000/tcp] 0B <missing> COPY app.py . # buildkit 4.1kB <missing> COPY index.html . # buildkit 4.1kB <missing> WORKDIR /app 0B <missing> ENV PYTHON_VERSION=3.12.15 0B <missing> RUN … apt-get … 43.7MB <missing> … debian base … 109MB ⋮ (python:3.12-slim's layers below — from Lesson 0002's chart)

    What happened: your five instructions are the top five rows, sitting on the base image's layers — exactly the stack you drew in Lesson 0002. EXPOSE and CMD show 0B: they change config, not files. That was Lesson 0002's quiz prediction, now in your own image.

  4. Run it and prove it serves:

    docker run -d --name web -p 8000:8000 first-app
curl -s localhost:8000
curl -s localhost:8000/health
    <!DOCTYPE html> <html> <head><title>lesson 0006</title></head> <body><h1>hello from my first image</h1></body> </html> ok

    What happened: an image you wrote, built, and ran. Every prior lesson is inside this moment: the image layers (0002), the container as a process (0001), the daemon doing the work (0005), the port hole-punch between network namespaces (0003). -p 8000:8000 forwards your Mac's port 8000 into the container, where your CMD's Python listens.

  5. Now the cache. Change nothing and rebuild:

    docker build -t first-app .
    #6 [2/4] WORKDIR /app #6 CACHED #7 [3/4] COPY index.html . #7 CACHED #8 [4/4] COPY app.py . #8 CACHED #9 naming to docker.io/library/first-app:latest done (≈0 s total)

    What happened: every layer recognized, every layer reused. This is why ordered Dockerfiles make builds fast. In a real project, the slow steps — pip install, apt-get — sit above this cached zone and never re-run for a code change.

  6. The decisive experiment, in two acts.

    Act one — change nothing but the timestamp:

    touch app.py
docker build -t first-app .
    #6 CACHED #7 CACHED #8 CACHED ← still! touch changed nothing the cache can see

    Act two — change actual content:

    echo "# v2" >> app.py
docker build -t first-app .
    #6 [2/4] WORKDIR /app #6 CACHED #7 [3/4] COPY index.html . #7 CACHED #8 [4/4] COPY app.py . #8 DONE 0.0s ← rebuilt: content changed #9 naming … done

    What happened: the cache checks content checksums, not file timestamps — touch is invisible to it. A real edit to app.py rebuilt exactly one layer: its own. index.html stayed cached because its instruction comes before the change. Cache stops at the first change; everything below rebuilds, everything above survives. That is the whole game.

  7. Clean up. Keep the images — next lesson uses the base again:

    docker rm -f web
docker images
    CONTAINER ID ... (empty) REPOSITORY TAG IMAGE ID SIZE first-app latest a60b4fb30151 132MB nginx 1.27/latest … … python 3.12-slim … 127MB

    What happened: container gone, your first image kept. Full instruction table and cache rules: Dockerfile Basics (reference).
