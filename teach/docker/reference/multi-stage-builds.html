Multi-Stage Builds

Build in the factory, ship the product: stage selection, FROM scratch, and the linking rule that makes it legal.

01The idea in one breath

Compiling needs a workshop. Running needs an artifact. A multi-stage build puts the workshop in an early stage and ships only the last one. Earlier stages are scaffolding: BuildKit labels their steps [build 4/6]; the final stage's steps carry no prefix (or [stage-1 1/1]).

FROM rust:1-alpine AS build        # stage 1: the workshop
WORKDIR /src
COPY Cargo.toml Cargo.lock ./
RUN mkdir src && echo 'fn main() {}' > src/main.rs && cargo fetch --locked
COPY src ./src
RUN cargo build --release --locked

FROM scratch                        # stage 2: the product — this ships
COPY --from=build /src/target/release/count_errors /count_errors
ENTRYPOINT ["/count_errors"]
CMD ["/logs"]
  • Every FROM starts a new stage. Each stage is its own image with its own layers and cache chain.
  • Only the last stage becomes your image. Everything the builder downloaded, compiled, and cached stays behind.
  • COPY --from=STAGE is the only door between stages. What isn't copied doesn't cross.
  • Build a middle stage alone: docker build --target build . — handy for debugging the workshop without shipping it.
The Rust gotcha (verified the hard way). cargo fetch refuses a manifest with no targets — no src/main.rs, no parse. So the dummy mkdir src && echo 'fn main() {}' > src/main.rs line exists to satisfy cargo during the dependency step. The real COPY src ./src overwrites the dummy afterwards.

03The linking rule (why the builder was alpine)

A static binary carries every library it needs inside itself. It makes raw syscalls and nothing else — so FROM scratch is legal. A dynamic binary asks the loader for shared libraries at start (libc at minimum) — on scratch it dies instantly with not found.

  • Alpine's rust targets musl, and musl binaries are static by default → runs on scratch.
  • Debian rust builds against glibc, dynamic → final stage needs *-slim or distroless.
  • Check any binary: file BINARY says "statically linked" or "dynamically linked"; ldd BINARY lists what it will ask for.

04Dependency cache, per language

The Lesson 0006 rule — stable things first, changing things last — becomes more valuable with every real dependency. Copy the manifest, install deps, only then copy code.

languagemanifest stepdep step
RustCOPY Cargo.toml Cargo.lock ./ + dummy src/main.rscargo fetch --locked
PythonCOPY requirements.txt .pip install -r requirements.txt
NodeCOPY package.json package-lock.json .npm ci
GoCOPY go.mod go.sum ./go mod download

Then COPY the source. Edit code → the manifest layers stay CACHED → the slow dep step never re-runs.

Verified shape for a CLI tool: ENTRYPOINT ["/count_errors"] + CMD ["/logs"]. Bare docker run img scans /logs; docker run img /data scans /data. For a web service, plain CMD is enough (Lesson 0006).

06Worth taping to the wall

  • Verified payoff: same app, fat single-stage image 1.35 GB → multi-stage scratch image 921 kB. About 1,470× lighter.
  • Base images used by builds often don't appear in docker images — BuildKit keeps them in its build cache. docker system df shows both stores; docker builder prune clears the build cache.
  • Shrink further: RUN strip target/release/BIN drops symbol names — typically 30–50% off a Rust binary. Do it in the builder, before COPY --from.
  • --locked on cargo commands: use the lockfile exactly as committed; fail instead of silently upgrading deps inside the image.
  • Scratch has no shell, no ls, no anything. If you need to look inside a broken container, debug the --target build stage or use a slim final stage first, shrink later.
