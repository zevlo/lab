03Pointing the client: DOCKER_HOST and contexts

docker context ls          # saved door addresses; * marks the one in use
docker context show        # which one is active
docker context use NAME    # switch daemons
DOCKER_HOST=… docker ps    # one-off override, no switching
  • OrbStack door: unix:///Users/<you>/.orbstack/run/docker.sock (Docker Desktop's differs — check the list, don't guess)
  • Remote daemons: DOCKER_HOST=ssh://user@server — same CLI, daemon in another city. This is how CI drives Docker.
  • Speak the API by hand: curl -s --unix-socket ~/.orbstack/run/docker.sock http://localhost/_ping → OK. The CLI is just a formatted HTTP client.

04Reading the classic error

failed to connect to the docker API at unix:///…;
check if the path is correct and if the daemon is running

The client is fine. The door is closed. In order of likelihood: the daemon app is not running (start OrbStack — open -a OrbStack), the context points at the wrong socket (docker context ls), or DOCKER_HOST is set to a dead address (echo $DOCKER_HOST).

05Rules worth taping to the wall

  • The daemon manages; the kernel runs. If dockerd crashes, running containers keep running. Quitting OrbStack stops the whole VM — a different, bigger switch.
  • All state is daemon-side. docker system df is the ledger; docker info shows where it lives (/var/lib/docker in the VM).
  • One CLI, many daemons. Never assume the CLI on a machine talks to a daemon on that machine — check the context.
  • docker version is the split-o-meter. Client half describes this machine; Server half describes the machine doing the work. If Server is missing, see the classic error above.
