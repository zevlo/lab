GPU Baseline Diagnostic

Your first AI infrastructure skill is not installing a tool. It is proving where the GPU is visible, where it disappears, and what that says about the stack.

Curriculum · Glossary · Sources

The Mental Model

A GPU workload reaches hardware through four visibility gates. When a command fails, do not guess. Ask which gate failed.

1. Host Driver

The kernel driver owns the device. If nvidia-smi fails on the host, containers and Kubernetes cannot fix it.

2. User Libraries

CUDA user-space libraries must be compatible with the driver. Frameworks ride on this ABI boundary.

3. Container Runtime

The NVIDIA Container Toolkit injects devices and libraries into containers. Docker or containerd must be configured to ask for GPUs.

4. Scheduler

Kubernetes or Slurm must advertise, allocate, and constrain the GPU. This is where device plugins, GPU Operator, GRES, quotas, and jobs enter.

Why this matters: most GPU platform incidents are path problems. The GPU can exist electrically, work on the host, vanish in a container, or be invisible to the scheduler. Each state has a different owner and fix.

Diagnostic Ladder

Run these on the Dell GPU node or from a shell that can reach your K3s cluster. Paste output into the boxes to get immediate feedback. Do not paste secrets or tokens.

Gate 1: Host Driver

nvidia-smi
nvidia-smi --query-gpu=name,driver_version,memory.total,memory.free,power.draw,temperature.gpu --format=csv

Waiting for host output.

Gate 2: Container Runtime

docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

If you use containerd without Docker, this command may intentionally fail. The failure is still useful: it tells us which runtime path to inspect next.

Waiting for container output.

Gate 3: Kubernetes Visibility

kubectl get nodes -o wide
kubectl describe node <gpu-node-name>
kubectl get pods -A | rg 'nvidia|gpu|dcgm'

Waiting for Kubernetes output.

Optional Gate 4: Scheduled GPU Pod

kubectl run gpu-smoke \
  --rm -it \
  --restart=Never \
  --image=nvidia/cuda:12.4.1-base-ubuntu22.04 \
  --limits='nvidia.com/gpu=1' \
  -- nvidia-smi

Run this only after Kubernetes shows nvidia.com/gpu as allocatable. If it fails, save the event output for the next lesson.

Retrieval Check

Answer before checking. The point is to strengthen recall, not to be fast.

What To Bring Back

Ask the agent follow-up questions with the outputs from the diagnostic ladder. The next lesson should be chosen from the first failing gate:

  • Host failure: driver, kernel, PCIe, Secure Boot, or device health.
  • Container failure: NVIDIA Container Toolkit, Docker/containerd runtime config, or driver/library compatibility.
  • Kubernetes failure: device plugin, GPU Operator, node labels, runtime class, or allocatable resource path.
  • Scheduled pod failure: scheduler allocation, image/runtime, events, permissions, or cluster policy.

Exit Criteria

You can explain the four GPU visibility gates and identify the first failing gate from command output. If all gates pass, the lab is ready for GPU Operator/DCGM and small-model memory lessons.
