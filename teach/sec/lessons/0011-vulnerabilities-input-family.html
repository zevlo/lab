Vulnerabilities I: The Untrusted Input Family

One win today: recognize the five code-level weaknesses the exam names — injection, cross-site scripting, memory injection, buffer overflow, race conditions — from one sentence of scenario. One story connects them all: the software trusted input it should not have.

Why this matters to your mission

Every vulnerability report you will triage in a DoD 8140 role is a list of these names with severity scores attached. Knowing the mechanism tells you the urgency: a SQL injection on an internet-facing form outranks a theoretical race condition on an internal tool. Objective 2.3 is the vocabulary that turns a scanner's output into a prioritized work queue — and it is the half of the catalog your DevOps tooling never made you learn by hand.

Warm-up — typed recall, no choices

Type each answer, then check all three. The first is the key-direction pair's fourth spaced rep — the signing side, the last untested angle.




Part 1 — What a vulnerability is

A vulnerability is a weakness that can be exploited — a flaw in code, configuration, process, or hardware. Pair it with what you already know: the threat actor (Lesson 0008) arrives by a vector (Lesson 0010) and exploits a vulnerability to cause harm. Today is the weakness itself. This lesson covers the five that live in code; the next lesson covers the ones that live in platforms and environments.

Part 2 — The input family

WeaknessMechanism in one sentenceScenario tell
SQL injectionUntrusted input becomes part of a database query, so attacker text is query logic.A login form where typing ' OR '1'='1' -- returns every account.
Cross-site scripting (XSS)Untrusted input becomes part of a web page shown to other users, so attacker script runs in their browsers.A comment box that stores <script> and steals visitors' session cookies.
Memory injection (DLL / process injection)Code is pushed into a running process's memory, so the malicious code wears a legitimate process's name.Malware living inside a trusted process, nothing written to disk — fileless.
Buffer overflowMore input arrives than the allocated buffer holds; the overflow overwrites adjacent memory — crash, or attacker-chosen code execution.A legacy C service sent 10,000 bytes into a 512-byte field.
Race conditionTwo operations race on the same resource; the result depends on timing. The classic: time-of-check to time-of-use (TOCTOU).The app checks a file's permissions, then opens it — and the attacker swaps the file in between.

Part 3 — The direction of attack differs

SQL injection runs server-side: attacker input, server's database. Cross-site scripting runs client-side: attacker input, other users' browsers. That single distinction answers most scenario questions: the victims differ (the database versus the visitors), and so do the harms (dumped records versus stolen sessions). Memory injection and buffer overflow both target memory — the difference is that overflow breaks in by smashing a boundary, while injection moves in beside a legitimate process.

Part 4 — The mechanism-level cure

WeaknessCure at the mechanism
SQL injectionParameterized queries — code and data travel separately, so input can never become logic. (Input validation as an allow list helps too.)
Cross-site scriptingOutput encoding — render user content as text, never as markup; content security policy headers as defense in depth.
Memory injectionEndpoint detection watching for one process writing into another; least privilege limiting what injected code reaches.
Buffer overflowMemory-safe languages, compiler protections, and above all patching — overflows are found in old C code and fixed in updates.
Race conditionLocking and atomic operations — check and use happen as one indivisible step.

Practice — 8 questions, timed

Four marked MULTI-HOP combine frameworks from earlier lessons. One marked BEST ANSWER has two defensible options — pick the better. Budget: 11 minutes for 11 questions — the exam's pace. Stopwatch: 0:00

QUESTION 1

Typing ' OR '1'='1' -- into a login form returns every account in the table. Which weakness?

SQL injection. Attacker text became query logic — input treated as code, server-side, against the database.

QUESTION 2

A product-review box accepts <script> and stores it; every visitor's browser then runs it. Which weakness?

Cross-site scripting (XSS). Stored input rendered as markup in other users' browsers — client-side, visitors are the victims.

QUESTION 3 MULTI-HOP

A stored script harvests other users' session cookies and ships them to the attacker. Weakness, and which triad goal is directly harmed?

Cross-site scripting; confidentiality. Stolen sessions mean other people can now read the victim's data — the classic XSS harm. (Lesson 0002's triad applied to 2.3.)

QUESTION 4

A legacy C service expects a 512-byte field; 10,000 bytes crash it, and researchers craft the overflow into code execution. Which weakness?

Buffer overflow. Input exceeding the allocated buffer overwrites adjacent memory — crash first, attacker-chosen execution second. Old C code is the natural habitat.

QUESTION 5 MULTI-HOP

An application checks a file's permissions, then opens it; an attacker swaps in a different file between the two steps. Weakness, and which goal is harmed?

Race condition; integrity. Time-of-check to time-of-use: the check and the use raced, and the substitution made the system act on the wrong data — an integrity harm.

QUESTION 6 MULTI-HOP

Malware pushes its code into a running service's memory, wears that service's name, and never writes a file to disk. Weakness, and the malware trait it enables?

Memory injection; fileless execution. DLL/process injection runs inside a legitimate process — nothing on disk to scan, which is exactly what fileless means (full treatment in 2.4).

QUESTION 7 MULTI-HOP

The team asks what most reduces injection risk in the codebase. Which answer names the practice and its control category and type?

Parameterized queries; technical; preventive. The code-level fix is a machine doing the stopping — technical and preventive (Lesson 0001). Training helps the human surface, not the query.

QUESTION 8 BEST ANSWER

A developer asks for the single best practice against SQL injection. Which is best?

Parameterized queries throughout. Escaping input is the tempting distractor — helpful, but it must be perfect everywhere, forever, and each missed spot is a hole. Parameterization separates code from data by construction. Encryption and firewalls limit damage or exposure; they do not close the weakness.
