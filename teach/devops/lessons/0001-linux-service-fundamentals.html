DevOps fundamentals · Linux · Lesson 0001 · ~30 min

Run and inspect one Linux service

Install a real systemd service, prove each layer, break it on purpose, and locate the failure from evidence.

Tangible win: by the end, you will diagnose a failed service with systemctl, journalctl, /proc, ss, and curl—in that order, without guessing.

1 · Enter a real Linux machine

Use your existing OrbStack Ubuntu Noble machine. It runs systemd, so this is a service-management lab—not a systemd-less container simulation.

macOS terminal

orb start linux-lab
orb -m linux-lab

inside Linux

cat /etc/os-release | grep PRETTY_NAME
ps -p 1 -o comm=
cd /mnt/mac/Users/za/lab/teach/devops/labs/linux-service
pwd
ls

Expected: Ubuntu is named, PID 1 is systemd, and the lab directory contains app.py, devops-lab.service, and broken-port.conf.

Check the required commands:

command -v python3 curl systemctl journalctl ss
If a command is missing

Ubuntu:

sudo apt-get update
sudo apt-get install -y python3 curl iproute2

Arch Linux:

sudo pacman -S --needed python curl iproute2

2 · Install the service

Create a dedicated system account. The service should not need your login identity or root privileges.

if ! id devops-lab >/dev/null 2>&1; then
  sudo useradd --system --user-group \
    --home-dir /nonexistent \
    --shell "$(command -v nologin)" \
    devops-lab
fi

id devops-lab

Copy the application and unit file into standard system locations, then tell systemd to reload unit files:

sudo install -Dm755 app.py \
  /usr/local/lib/devops-lab/app.py

sudo install -Dm644 devops-lab.service \
  /etc/systemd/system/devops-lab.service

sudo systemctl daemon-reload
systemctl cat devops-lab.service

The unit has three sections:

SectionWhat this lab uses it for
[Unit]Description and startup ordering.
[Service]User, environment, command, and restart behavior.
[Install]The boot target used if you later enable the unit.

Configuration is not runtime. Installing a unit file creates no service process. daemon-reload makes systemd reread unit files; it still does not start the service.

3 · Start it; distinguish active from enabled

sudo systemctl start devops-lab.service
sleep 1

systemctl is-active devops-lab.service
systemctl is-enabled devops-lab.service
systemctl status devops-lab.service --no-pager

You should see active and disabled. Those are not contradictory:

  • active: the unit is running now.
  • enabled: systemd is configured to start it during a future boot.

start changes now. enable changes boot configuration. Combining them with systemctl enable --now … is convenient, but first retain the distinction.

4 · Inspect the process Linux is actually running

Ask systemd for its machine-readable main PID. Do not scrape the human-formatted status output.

pid=$(systemctl show \
  -p MainPID --value devops-lab.service)

printf 'main pid: %s\n' "$pid"
ps -o user,pid,ppid,stat,etime,cmd -p "$pid"

Expected: the user is devops-lab, the state includes S (sleeping while waiting for work), and the command runs app.py.

Linux exposes one numeric directory per running process under /proc. Inspect this process directly:

sudo tr '\0' ' ' < "/proc/$pid/cmdline"; echo
sudo readlink "/proc/$pid/exe"
sudo readlink "/proc/$pid/cwd"
sudo ls -l "/proc/$pid/fd"

In /proc/$pid/fd, descriptors 0, 1, and 2 are standard input, output, and error. For a normal systemd service, stdout and stderr are connected to the journal by default; they may appear as socket links rather than ordinary log files.

5 · Prove the socket, request, and logs

A PID alone does not prove the service bound its expected port.

sudo ss -ltnp 'sport = :8080'

Read the flags: -l listening, -t TCP, -n numeric addresses, -p process. Expected: Python listens on 127.0.0.1:8080 with the same PID.

Now make an application-level request:

curl -i http://127.0.0.1:8080/healthz

Expected: HTTP 200 OK and JSON containing "status": "ok", version 1.0.0, and the same PID.

Finally, inspect the service's own output:

sudo journalctl \
  -u devops-lab.service \
  -n 20 --no-pager

You should find one startup line and one request line. systemctl status shows current state plus a small recent log tail; journalctl -u is the proper unit-scoped log history.

6 · Break it, then diagnose before fixing

The supplied override replaces the valid numeric port with text. Install it, reload the unit definition, and attempt a restart:

sudo install -Dm644 broken-port.conf \
  /etc/systemd/system/devops-lab.service.d/override.conf

sudo systemctl daemon-reload
sudo systemctl restart devops-lab.service
sleep 1

The service should now be failed. With Type=simple, the restart command may return before a short-lived process exits; the one-second pause makes this lab check deterministic. Do not remove the override yet.

Diagnose from evidence

Run these in order. Before each command, predict what it will prove.

  1. systemctl status devops-lab.service --no-pager
  2. sudo journalctl -u devops-lab.service -n 20 --no-pager
  3. systemctl show -p MainPID --value devops-lab.service
  4. sudo ss -ltnp 'sport = :8080'
  5. curl -i http://127.0.0.1:8080/healthz
Show expected evidence
  • Unit state: failed.
  • Journal: Python raises ValueError while converting not-a-number to an integer.
  • Main PID: 0; no service process remains.
  • Socket: no listener on port 8080.
  • Request: connection fails because no process is listening.

The journal identifies the cause. The later checks confirm the consequences. Repeated curl attempts or blind restarts cannot correct invalid configuration.

7 · Repair and prove recovery

sudo rm \
  /etc/systemd/system/devops-lab.service.d/override.conf

sudo systemctl daemon-reload
sudo systemctl start devops-lab.service
sleep 1

systemctl is-active devops-lab.service
sudo ss -ltnp 'sport = :8080'
curl -sS http://127.0.0.1:8080/healthz
sudo journalctl -u devops-lab.service -n 10 --no-pager

Recovery is proved only when state, socket, request, and logs agree. “I ran restart” is an action, not evidence.

Leave or remove the lab

Keep it installed if you want another cold run. To remove it completely:

Show cleanup commands 
sudo systemctl disable --now devops-lab.service
sudo rm -f /etc/systemd/system/devops-lab.service
sudo rm -rf /etc/systemd/system/devops-lab.service.d
sudo rm -rf /usr/local/lib/devops-lab
sudo userdel devops-lab
sudo systemctl daemon-reload

Exit Linux, then stop the OrbStack machine from macOS if you are done:

exit
orb stop linux-lab
