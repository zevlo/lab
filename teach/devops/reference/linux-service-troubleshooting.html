Linux service troubleshooting

Prove each layer with a command: unit state, logs, process, socket, then application response.

The evidence ladder

1 · StateDid systemd start the unit?
2 · LogsWhat did the service report?
3 · ProcessWhich PID and command run?
4 · SocketIs that PID listening?
5 · RequestDoes the endpoint respond?
systemctl status devops-lab.service --no-pager
sudo journalctl -u devops-lab.service -n 30 --no-pager
pid=$(systemctl show -p MainPID --value devops-lab.service)
ps -o user,pid,ppid,stat,etime,cmd -p "$pid"
sudo ss -ltnp 'sport = :8080'
curl -i http://127.0.0.1:8080/healthz
Stop at the first failed proof. If no process exists, a socket check adds no useful information. If no socket listens, repeated HTTP requests cannot repair it.

systemctl: lifecycle and state

CommandUse
systemctl status UNITHuman-readable current state plus recent journal lines.
systemctl is-active UNITShort, script-friendly active/inactive result and exit status.
systemctl start UNITStart now; does not configure the next boot.
systemctl stop UNITStop now; does not change boot configuration.
systemctl restart UNITStop and start again. Inspect evidence before doing this during an incident.
systemctl enable UNITConfigure startup for future boots; does not start now unless combined with --now.
systemctl disable UNITRemove future-boot enablement; does not stop now unless combined with --now.
systemctl daemon-reloadReload changed unit files. It does not restart the service.
systemctl show -p MainPID --value UNITPrint the service's main PID without parsing human-oriented status output.

journalctl: unit logs

# Recent entries
sudo journalctl -u devops-lab.service -n 30 --no-pager

# Entries from this boot
sudo journalctl -u devops-lab.service -b --no-pager

# Entries since a time boundary
sudo journalctl -u devops-lab.service --since "10 minutes ago"

# Follow new entries
sudo journalctl -u devops-lab.service -f

By default, systemd connects a service's standard output and standard error to the journal. A Python traceback printed to stderr therefore appears in the unit's journal.

/proc/<PID>: the running process

PathQuestion answered
/proc/PID/statusWhat are its state, IDs, memory summary, and capabilities?
/proc/PID/cmdlineWhat argument vector started it? Fields are NUL-separated.
/proc/PID/exeWhich executable does the process use?
/proc/PID/cwdWhat is its current working directory?
/proc/PID/fd/Which files, pipes, and sockets are open? Descriptor 0 is stdin, 1 stdout, 2 stderr.
 
sudo tr '\0' ' ' < "/proc/$pid/cmdline"; echo
sudo readlink "/proc/$pid/exe"
sudo readlink "/proc/$pid/cwd"
sudo ls -l "/proc/$pid/fd"

Socket and request

# -l listening, -t TCP, -n numeric, -p process
sudo ss -ltnp 'sport = :8080'

# Application-level proof
curl -i http://127.0.0.1:8080/healthz

ss proves the kernel has a listening TCP socket and identifies its process. curl goes one layer higher: it proves the application handled an HTTP request.

Distinctions worth retaining

  • Installed unit ≠ running unit. A file under /etc/systemd/system is configuration, not proof of a process.
  • Enabled ≠ active. Enabled concerns a future boot; active concerns now.
  • Process ≠ listener. A PID can exist while startup is blocked or the expected bind failed.
  • Listener ≠ healthy application. A TCP accept can succeed while HTTP returns an error.
  • Status is a snapshot. Use journalctl -u for older invocations and fuller history.
