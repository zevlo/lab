Lesson 0001

The DevOps map of AWS

How one request travels through the nine core services, and the five questions every production stack answers.

Time to complete: 15 minutes · Last updated: 2026-09-01

Why this lesson You passed the SAA-C03 exam, so you know these services as exam topics. DevOps interviews and day-to-day operations require a different skill: tracing a live request through a production stack and identifying where it fails. This lesson turns nine separate services into one mental model. In the following lessons, you build this architecture in your own AWS account.

Before you begin

This lesson assumes the following:

  • You're familiar with the names of the nine services at SAA-C03 level: VPC, EC2, S3, IAM, RDS, Route 53, CloudWatch, ECS, and EKS.
  • To complete the billing-alarm task at the end of this lesson, you can sign in to your own AWS account.

The five questions every stack answers

Most AWS interviews include a question similar to "Walk me through how a request reaches your application." The question tests whether you can hold an entire system in mind at once. After this lesson, you can answer it in about ninety seconds.

Whatever the product, every production stack answers the same five questions:

QuestionServices that answer it
How do users reach the application?Route 53 (DNS) and the Application Load Balancer
Where does code run?EC2, ECS, EKS, and Fargate, with container images from ECR
How is the network shaped?VPC: subnets, route tables, internet gateway, NAT gateway, and security groups
Where does data live?RDS for relational data, and S3 for objects and build artifacts
Who is allowed, and who is watching?IAM for permissions, and CloudWatch for metrics, logs, and alarms

Memorize the five questions rather than the service list. The questions give each service a place to live. The AWS Well-Architected Framework is built on the same habit: name the concern first, then the mechanism that addresses it.

How a request flows through the stack

The request moves through the stack in five steps:

  1. Route 53 resolves the name. The browser requests the IP address for app.example.com. The record in the hosted zone, preferably an alias record, returns the addresses of the Application Load Balancer. For more information, see the Route 53 developer guide.
  2. The load balancer terminates TLS and selects a target. The request arrives at the Application Load Balancer in the public subnets. TLS ends here, using a certificate from ACM. Only targets that pass health checks receive traffic. For more information, see the Application Load Balancer guide.
  3. The application answers from a private subnet. Your container (ECS, EKS, or Fargate) or instance (EC2) has no public IP address and no inbound route from the internet. Its security group accepts traffic only from the load balancer's security group. Outbound traffic, such as operating system updates, leaves through the NAT gateway in a public subnet. For more information, see the NAT gateway documentation.
  4. Data lives one tier deeper. The application connects to RDS in isolated data subnets. The database security group accepts connections only from the application security group, and only on a single port. Build artifacts and static files live in S3, and container images live in ECR. For more information, see the RDS documentation.
  5. IAM authorizes each call, and CloudWatch records everything. Each step works only because a role allows it, such as the task role for a container or the instance profile for an EC2 instance. CloudWatch collects metrics and logs at every hop and can trigger an alarm. For more information, see the IAM best practices.

Two patterns recur in this architecture:

  • Defense in depth: the stack has public, private, and data tiers, and each tier accepts traffic only from the tier in front of it.
  • Duplication across Availability Zones: each tier spans two zones, so the loss of one zone doesn't remove a tier.

These patterns are the reliability and security pillars of the AWS Well-Architected Framework in miniature. Full definitions of every term are in the workspace glossary.

Set up a billing alarm

Before you create any AWS resources, protect your budget. A billing alarm sends an email when your estimated monthly charges cross a threshold. This task is a prerequisite for all hands-on lessons.

To set up a billing alarm:

  1. In the AWS Management Console, use the Region selector to choose N. Virginia (us-east-1). Billing metrics are published only in this Region.
  2. Open the CloudWatch console, and in the navigation pane choose Alarms > Billing > Create alarm.
  3. For the metric, choose the EstimatedCharges metric for your account, and then choose Select metric.
  4. For the alarm condition, choose Greater, and enter 5. Keep the default currency of USD.
  5. To receive notifications by email, choose Create new topic, enter a topic name and your email address, and then choose Create topic.
  6. Choose Next, enter an alarm name such as billing-over-5-usd, and then choose Next > Create alarm.
  7. Open the subscription confirmation email from AWS Notifications, and choose Confirm subscription.

When your estimated charges for the month exceed 5 USD, CloudWatch sends an email to the address you entered. For more information, see the CloudWatch billing metrics documentation.
