Lesson 0008 · Phase shell — ops

Find it, probe it, stop it

pgrep, curl -i, and kill — with cut woven in so last lesson’s new tool sticks.

Why this matters

Mission success includes debugging by reflex: curl -i, pgrep/kill. You mapped those in Lesson 0007 but have not drilled them. cut was brand-new — this lesson reuses it under desirable difficulty (interleaving) so storage strength grows.

Knowledge 1 — cut, one more pass

From info coreutils: cut keeps columns from each line. Fields are 1-indexed. Default delimiter is tab — for spaces you must say so.

echo 'HTTP/1.0 200 OK' | cut -d' ' -f2
# → 200

echo '10.0.0.2 GET /api' | cut -d' ' -f1
# → 10.0.0.2

Knowledge 2 — curl -i

From man curl: -i / --include prints response headers before the body. That is how you see status lines and Content-Type without a browser. -s silences the progress meter (handy in pipes).

curl -si http://127.0.0.1:8765/ | head -1
# HTTP/1.0 200 OK

Knowledge 3 — pgrep then kill

From man pgrep / man kill: find PIDs by pattern, then signal a specific PID. Default kill signal is TERM (polite). -9 / KILL is last resort — cannot be caught, no cleanup.

CommandDoes
pgrep -f PATPIDs matching full argv (portable)
pgrep -lf PATmacOS: show PID + command line
kill PIDSend TERM
kill -9 PIDForce KILL
kill -0 PIDTest “still alive?” (no signal)
macOS vs Linux display. Listing with names: Mac uses pgrep -lf; many Linux hosts use pgrep -af. PID-only pgrep -f is the portable core — use that before kill.
Kill by PID, not by name. Skip pkill for now. Over-broad patterns can hit the wrong process. Confirm with pgrep -lf, then kill the number you see.

Drill — local server lifecycle

One Ghostty window is enough. You will start a throwaway server, probe it, extract fields with cut, then stop it cleanly.

  1. Start a background HTTP server on port 8765 (stdlib — no install): 
    python3 -m http.server 8765 --bind 127.0.0.1 >/tmp/http8765.log 2>&1 &
echo "started pid $!"
    show answer

    Shell prints a PID. The & backgrounds the job. Logs go to /tmp/http8765.log so your terminal stays clean.

  2. Probe with headers included; pull the status code with cut: 
    curl -si http://127.0.0.1:8765/ | head -1
curl -si http://127.0.0.1:8765/ | head -1 | cut -d' ' -f2
    show answer

    First line looks like HTTP/1.0 200 OK. Field 2 is 200. If curl fails, the server did not start — check cat /tmp/http8765.log.

  3. Find the process. On your Mac: 
    pgrep -lf 'http.server 8765'
    Then capture just the PID (portable form) and confirm field 1 is the PID if you pipe long output through cut: 
    pgrep -f 'http.server 8765'
pgrep -lf 'http.server 8765' | cut -d' ' -f1
    show answer

    Both should print the same number (the server PID). cut -d' ' -f1 on -lf output is retrieval practice: PID is field 1.

  4. Stop it politely, then verify it is gone: 
    PID=$(pgrep -f 'http.server 8765')
echo "killing $PID"
kill "$PID"
sleep 1
kill -0 "$PID" 2>/dev/null && echo still-alive || echo gone
curl -si http://127.0.0.1:8765/ | head -1
    show answer

    Expect gone, and curl should fail (connection refused). That is the happy path: TERM worked. Only reach for kill -9 if kill -0 still succeeds after a few seconds.

  5. Optional: restart the server, send kill -9 instead, and notice it also dies — but default to TERM in real work.
    show answer

    Re-run the start command from step 1, then kill -9 "$(pgrep -f 'http.server 8765')". Same end state; worse manners.

Check your understanding

Four short questions. Answers are shuffled on each page load.

Q1Default signal from plain kill PID?

  • TERM (polite stop)
  • KILL (force stop)
  • HUP (hangup sig)
  • STOP (pause proc)

Q2Portable “match full argv” flag?

  • pgrep -f
  • pgrep -a
  • pgrep -l
  • pgrep -n

Q3Status code from HTTP/1.0 200 OK?

  • cut -d' ' -f2
  • cut -d' ' -f1
  • cut -d' ' -f3
  • cut -d' ' -f4

Q4What does curl -i add?

  • response headers too
  • request payload too
  • resolve DNS only
  • ignore TLS errors

Ask the teacher. After the drill: did TERM leave gone on the first try? Did cut -f2 on the status line feel automatic or still slow? Any surprise in pgrep -lf vs bare pgrep -f?
