Lesson 0010 · Phase shell — network

Name it, then find the bind

dig answers “where does this name go?” ss -tlnp answers “what is listening on this Linux host?” — mission network reflexes.

Why this matters

Success criteria already include curl -i, dig, and ss -tlnp. You have curl. This lesson closes the other two: resolve a name, then on a remote Linux box see which process owns a port.

Knowledge 1 — dig

From man dig (BIND on your Mac): query DNS; default record type is A (IPv4). Without @server, dig uses /etc/resolv.conf.

CommandDoes
dig nameFull output — read status: and ANSWER
dig name +shortTerse answer only
dig @1.1.1.1 nameBypass local resolver; ask Cloudflare
dig name AAAAIPv6
dig name MXMail exchangers
Status, not silence. status: NOERROR means the query worked. NXDOMAIN means the name does not exist. Empty +short with NXDOMAIN is a real answer — “no such name.”

Knowledge 2 — ss -tlnp (Linux remotes)

From man ss (iproute2). Mission mnemonic:

ss -tlnp
# -t  TCP
# -l  listening only
# -n  numeric ports/addresses
# -p  owning process (may need root for others)

Read the Local Address:Port column (0.0.0.0:22, *:443, [::]:22) and the process field when present.

Not on macOS. Your Mac has no ss. Run it over SSH on Linux. Local preview of “what is listening”: lsof -nP -iTCP -sTCP:LISTEN — different tool, same question.

Drill A — dig (local Mac)

Needs network. Use example.com (stable IANA name).

  1. Full lookup — find the status line and ANSWER section: 
    dig example.com
    show answer

    Look for status: NOERROR near the top HEADER. ANSWER SECTION should show an A record with an IPv4 address. Note the QUERY TIME at the bottom.

  2. Short form, then ask a public resolver: 
    dig example.com +short
dig @1.1.1.1 example.com +short
    show answer

    Both print one or more IPv4 addresses. They usually match; if they differ, you have a resolver/cache story to chase later — not today’s lesson.

  3. Other types: 
    dig example.com AAAA +short
dig example.com MX +short
    show answer

    AAAA may be empty or an IPv6 address. MX lines look like 0 . or priority + hostname — shape matters more than memorizing today’s values.

  4. Optional failure shape — pick a nonsense name: 
    dig this-name-should-not-exist-zz9.example +short
dig this-name-should-not-exist-zz9.example | grep status
    show answer

    Expect empty short output and status: NXDOMAIN (or similar failure status). That is how dig reports “no such name.”

Drill B — ss (SSH to Linux)

Attach to any Linux host you use for work (ssh user@host). If you have no remote tonight, do Drill A + quiz, then run Drill B next SSH session.

  1. List listening TCP sockets: 
    ss -tlnp
    show answer

    You should see rows with LISTEN and ports like :22 (ssh). Without root, -p may omit process names for services you do not own — the ports still show.

  2. Narrow to a port you care about (ssh is a safe bet): 
    ss -tlnp | grep ':22'
    show answer

    One or more listen lines for port 22. This is the triage pattern: wide list, then grep the port from an incident.

  3. Optional Mac contrast (same question, different binary): 
    lsof -nP -iTCP -sTCP:LISTEN | head
    show answer

    Local Mac only. Do not train this as your remote reflex — remotes get ss -tlnp.

Pareto cut. Not today: dig +trace, DNSSEC, ss state filters, UDP deep dives. Cheat sheet: dig and ss.

Check your understanding

Four short questions. Answers are shuffled on each page load.

Q1Default record type for bare dig name?

  • A (IPv4 addr)
  • MX (mail exch)
  • NS (name serv)
  • TXT (text data)

Q2What does dig +short strip away?

  • verbose dig chrome
  • the answer RDATA
  • the query itself
  • the DNS protocol

Q3Mission flags for listening TCP + process?

  • ss -tlnp
  • ss -uanp
  • ss -srlp
  • ss -xanp

Q4Where do you run ss for this mission?

  • Linux SSH hosts
  • macOS by default
  • inside vim only
  • inside dig only
