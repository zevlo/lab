The merge request is the unit of work

A merge request (MR) proposes one change: a branch, a review, a pipeline, and approvals, collected in one place. Team GitLab lives in MRs.

Approvals carry the control. An approval rule names required reviewers: a count, a role, or the CODEOWNERS file. GitLab's rule is absolute: without required approvals, merging is impossible. A failed pipeline blocks the merge the same way.

One setting matters in interviews: prevent approval by author. The engineer who wrote the change cannot approve it. That is separation of duties from Lesson 0004, control CM-5, as a checkbox.

Bridge. A GitHub Actions environment requiring reviewer approval is the same shape. Lesson 0004 named the human version a CCB. The MR is the CCB's smallest daily meeting.

The scanners

GitLab ships scanners as pipeline templates. Three lines of include add three jobs. No code changes.

include:
  - template: Jobs/SAST.gitlab-ci.yml
  - template: Jobs/Dependency-Scanning.gitlab-ci.yml
  - template: Jobs/Secret-Detection.gitlab-ci.yml

Definitions, one sentence each:

ScannerReadsCatches
SAST, static application security testingYour source codeInsecure patterns in the code you wrote.
Dependency scanning (the SCA class, software composition analysis)The dependency listKnown CVEs in packages you imported, transitive packages included.
Secret detectionRepository content and historyCommitted credentials.
DAST, dynamic application security testingThe running applicationFlaws visible from outside, found by simulated attacks.
Container scanningThe built imageVulnerable packages inside the image.

Secret push protection deserves its own line: it blocks the push itself when a credential is in it. Detection reports history; push protection stops the leak at the door.

Every finding carries a severity. Scanner severities are six levels, scored from CVSS: Critical, High, Medium, Low, Info, Unknown. STIG severity stops at High. Two vocabularies; keep them separate.

Bridge from Lesson 0005. GitLab's own guidance says store secrets outside the repository. Vault is where they live instead. Secret detection catches what slipped in anyway.

Findings become gates

Findings appear in the MR itself. Per GitLab's security overview: scans run in the pipeline when code is committed or an MR is created, and the findings surface in the MR, before merge.

Every finding gets a decision. Fix it now, or accept it with a documented reason. GitLab names the cycle detect, triage, analyze, remediate. Triage is the gate: an accepted finding carries a reason, an owner, and a date.

Bridge. A finding with an owner and a date is a POA&M entry. Triage decisions are the pipeline's POA&M. Controls RA-5 (vulnerability scanning) and SA-11 (developer testing), running automatically.

Two classified details. Continuous dependency scanning re-scans the dependency list whenever the advisory database updates, so a new CVE surfaces on an old build with no pipeline run. And the scanner images ship in FIPS-enabled versions, built on a FIPS 140-validated cryptographic module. The artifact gated in the MR is the artifact promoted (Lesson 0004). Scanners re-verify the same digest at every gate.

Interview traps. SAST reads the code you wrote; dependency scanning reads the code you imported. Scanner severity includes Critical; STIG severity stops at High. Secret push protection blocks a push; Vault keeps the secret out of code entirely. Pipeline scanners gate the application; oscap gates the operating system. “Shift left” means scanning in the MR, before merge, where fixing costs least.
