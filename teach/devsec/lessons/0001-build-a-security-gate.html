Lesson 0001 · Secure pipelines · Secrets and dependencies

Build a security gate for your pipeline

A security gate is a pipeline step that fails the build when it finds a risky problem. Start with leaked secrets and vulnerable dependencies.

A common opening question in DevSecOps interviews is: "How would you secure a CI/CD pipeline?" A strong answer names each check, where it runs, and what makes it fail. In this lesson you build a small gate on your Mac with two scanners. You break it on purpose, and then you fix it. Lesson 0002 runs the same gate in GitLab CI.

About 90 minutes: 20 to read, 45 for the lab, and 25 to practice answers and take the quiz. This lesson builds on the Git data model (Missing Semester 0040) and return codes (Missing Semester 0023).

1. Where security checks run

A pipeline moves a change from commit to production in stages. Each stage can run a check. A check that can stop the pipeline is a security gate.

Run each check where the person who can fix the problem will see it. The earlier you find a problem, the cheaper it is to fix. This idea is called shift left.

StageChecks that run hereExample tools
CommitSecret scanning, as a pre-commit hookGitleaks
Merge requestSecret scanning, SCA, SAST, IaC scanningGitleaks, Trivy, Semgrep
BuildContainer scanning, SBOM, signingTrivy, cosign
DeployAdmission policy, GitOps syncKyverno, Argo CD
RunRescans for new CVEs, DASTTrivy, ZAP

Two of these terms matter most today:

  • SCA (software composition analysis) checks the third-party packages you depend on for known vulnerabilities. It checks code you did not write.
  • SAST (static application security testing) checks your own source code for insecure patterns. It checks code you did write.

Which check comes first? OWASP recommends this order: secret scanning, then SCA, then branch protection with SAST. It says to start with these three because they remove the most risk for the least effort (OWASP DevSecOps Guideline). This lesson builds the first two. The pipeline security map shows the full order.

2. How a gate passes or fails

A gate uses the rule you already know from $?: exit code 0 means pass, and any other number means fail. When a step exits with a nonzero code, the CI job fails and the pipeline stops.

  • Gitleaks exits 1 when it finds a leak, and 0 when it finds none (Gitleaks README).
  • Trivy exits 0 by default, even when it finds problems. Add --exit-code 1 to make it fail (Trivy docs). A scanner that cannot fail is a report, not a gate.

Next, choose what should fail. A severity threshold sets the lowest level that blocks. For example, --severity HIGH,CRITICAL fails only on HIGH or CRITICAL findings. The severity label comes from the vulnerability's advisory, or from its CVSS score. Lower findings still need a fix, but they do not block a merge.

Two more rules keep a gate useful (OWASP):

  • Fail on new findings. Put old findings in a baseline, and fix them on a schedule.
  • Keep a documented exception process. Without one, teams switch the gate off.
SCA can check only the versions it can read. Pin exact versions, such as PyYAML==6.0.3, or commit a lock file. Trivy skips a package when it cannot tell the exact version, as with requests>=2.0 (Trivy docs).

3. A deleted secret is still in Git

Git stores each commit as a snapshot that points to its parent. If you delete a secret in a new commit, the old commit still contains it. Anyone with a copy of the repository can read it.

So deleting the secret is not the fix. The fix is rotation: revoke the secret and issue a new one. GitLab's guidance is to "always revoke and replace exposed secrets as soon as possible" (GitLab docs). Respond in this order:

  1. Revoke the secret, and issue a new one.
  2. Check the service's logs for any use of the old secret.
  3. Clean up: record an exception, or rewrite history if your team requires it.

Gitleaks can scan in two ways (Gitleaks README):

  • gitleaks git scans every commit in the repository's history.
  • gitleaks dir scans only the files on disk right now.
Use Trivy v0.74.0 or later. In March 2026, attackers published a malicious Trivy binary (v0.69.4) and malicious Docker Hub images (v0.69.5 and v0.69.6). The malware ran a normal scan, so jobs looked successful, while it stole credentials from CI/CD systems and developer machines (Trivy advisory, Microsoft). Never install those versions. A scanner is part of your supply chain, too. Lesson 0007 shows how to check a tool's signature before you run it.

4. Lab: build the gate

You build the gate in a new Git repository at ~/devsec-lab/gate-demo, outside your teaching folder. Lesson 0002 pushes it to GitLab. Steps with a red number break something on purpose. The token in this lab is fake. Never put a real secret in a lab.

0

Install the two scanners and check their versions.

brew install gitleaks trivy
gitleaks version
trivy --version

Expect 8.30.1 and Version: 0.74.0, or later versions. If Trivy shows 0.69.4, 0.69.5, or 0.69.6, stop and run brew uninstall trivy.

1

Create a small project with pinned dependencies. The versions are old on purpose.

mkdir -p ~/devsec-lab/gate-demo
cd ~/devsec-lab/gate-demo
git init -b main

cat > app.py <<'EOF'
import requests
import yaml


def load_settings(path):
    with open(path) as f:
        return yaml.safe_load(f)


def check_status(url):
    return requests.get(url, timeout=5).status_code
EOF

cat > requirements.txt <<'EOF'
PyYAML==5.3.1
requests==2.25.1
EOF

git add app.py requirements.txt
git commit -m "Add demo app"

Git prints [main (root-commit) …] Add demo app and 2 files changed.

2

Commit a fake token, then scan the history. The printf command builds a fake GitLab token from two parts. That way, this web page does not contain a whole token that other scanners would flag.

printf 'GITLAB_TOKEN = "%s%s"\n' 'glpat-' 'Xk3v9Qm2Lp7Rt5Wz8Yb1' > config.py
git add config.py
git commit -m "Add config"

gitleaks git -v --redact .
echo "exit: $?"

git scans every commit. -v prints each finding. --redact hides the secret in the output. That matters in CI logs, which many people can read.

Delete the token in a new commit, then scan twice.

cat > config.py <<'EOF'
import os

GITLAB_TOKEN = os.environ["GITLAB_TOKEN"]
EOF
git commit -am "Read the token from the environment"

gitleaks dir -v --redact .
echo "exit: $?"

gitleaks git -v --redact .
echo "exit: $?"

The dir scan passes:

5:40PM INF scanned ~275 bytes (275 bytes) in 698µs
5:40PM INF no leaks found
exit: 0

The git scan prints the same finding as step 2, from the same older commit, and fails:

5:40PM WRN leaks found: 1

Your turn. Before you read on, say out loud why the two scans disagree. Then prove it: git show HEAD~1:config.py prints the token from the older commit.
4

Respond: rotate the token, then record an exception. With a real token, you would now revoke it in GitLab, create a new one, and check for use. Pretend you have done that. Then record an exception, so that the gate passes for this one finding only.

echo "# Revoked and rotated on $(date +%F)" > .gitleaksignore
gitleaks git -v --redact . 2>/dev/null | awk '/Fingerprint:/ {print $2}' >> .gitleaksignore
cat .gitleaksignore

gitleaks git -v --redact .
echo "exit: $?"

git add .gitleaksignore
git commit -m "Record exception for the rotated token"

The first line writes a comment that says why the exception exists. In the second line, 2>/dev/null hides the log lines, and awk keeps only the fingerprint.

The file holds the comment and one fingerprint. The scan then passes:

# Revoked and rotated on 2026-09-30
8ceca5477a1a113035efb2007dbb8b4abd98bd82:config.py:gitlab-pat:1
…
5:40PM INF no leaks found
exit: 0

A fingerprint names one commit, one file, one rule, and one line. You test in step 9 whether it hides anything else.

5

Scan the dependencies. The first run downloads Trivy's vulnerability database, which is about 120 MB. It can take a few minutes.

trivy fs --scanners vuln .
echo "exit: $?"

fs scans a folder. --scanners vuln looks only for known vulnerabilities, because Gitleaks already covers secrets.

Expect this, trimmed. Counts can change as new CVEs are published.

requirements.txt (pip)
======================
Total: 5 (UNKNOWN: 0, LOW: 0, MEDIUM: 4, HIGH: 0, CRITICAL: 1)

│ Library  │ Vulnerability  │ Severity │ Status │ Installed Version │ Fixed Version │
│ PyYAML   │ CVE-2020-14343 │ CRITICAL │ fixed  │ 5.3.1             │ 5.4           │
│ requests │ CVE-2023-32681 │ MEDIUM   │        │ 2.25.1            │ 2.31.0        │
│          │ CVE-2024-35195 │          │        │                   │ 2.32.0        │
│          │ CVE-2024-47081 │          │        │                   │ 2.32.4        │
│          │ CVE-2026-25645 │          │        │                   │ 2.33.0        │
exit: 0

Trivy found five problems and still exited 0. This command can report, but it cannot block anything. Now make it a gate:

trivy fs --scanners vuln --severity HIGH,CRITICAL --exit-code 1 .
echo "exit: $?"
Total: 1 (HIGH: 0, CRITICAL: 1)

│ PyYAML  │ CVE-2020-14343 │ CRITICAL │ fixed  │ 5.3.1             │ 5.4           │
exit: 1

The threshold kept the four MEDIUM findings out of the gate. They still need a fix, but they do not block the merge. You may also see a WARN line about Python license detection. It does not change the vulnerability results.

6

Fix it: upgrade the pins.

cat > requirements.txt <<'EOF'
PyYAML==6.0.3
requests==2.34.2
EOF

trivy fs --scanners vuln --severity HIGH,CRITICAL --exit-code 1 .
echo "exit: $?"

git commit -am "Upgrade vulnerable dependencies"

The report summary shows 0 vulnerabilities for requirements.txt, and the exit code is 0:

│ requirements.txt │ pip  │        0        │
…
exit: 0

These were the newest releases on 2026-09-30. If a new CVE appears later, Trivy's "Fixed Version" column shows the version to move to.

7

Build the gate script. Lesson 0002 runs this same script in GitLab CI.

mkdir -p scripts
cat > scripts/gate.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail

echo "== Secrets (Gitleaks) =="
gitleaks git --redact --no-banner .

echo "== Dependencies (Trivy) =="
trivy fs --scanners vuln --severity HIGH,CRITICAL --exit-code 1 --quiet .

echo "Gate passed."
EOF
chmod +x scripts/gate.sh

./scripts/gate.sh
echo "exit: $?"

git add scripts/gate.sh
git commit -m "Add security gate script"

set -e stops the script at the first command that fails, and the script exits with that command's code. So one failing scanner fails the whole gate. --no-banner hides the Gitleaks logo, and --quiet hides Trivy's progress lines.

== Secrets (Gitleaks) ==
5:44PM INF 5 commits scanned.
5:44PM INF scanned ~450 bytes (450 bytes) in 78.7ms
5:44PM INF no leaks found
== Dependencies (Trivy) ==
…
│ requirements.txt │ pip  │        0        │
…
Gate passed.
exit: 0
8

Prove that the gate can fail. Put the vulnerable PyYAML version back, run the gate, and then restore the file.

printf 'PyYAML==5.3.1\nrequests==2.34.2\n' > requirements.txt
./scripts/gate.sh
echo "exit: $?"

git restore requirements.txt
./scripts/gate.sh
echo "exit: $?"

The first run passes the secrets check, lists CVE-2020-14343, never prints Gate passed., and ends with exit: 1. After git restore, the gate prints Gate passed. and exit: 0.

A gate that you have never seen fail is not yet a gate.

9

Does the exception hide a new leak? Commit a second fake token on a separate branch. Predict each result before you run it.

git switch -c try-leak
printf 'DEPLOY_TOKEN = "%s%s"\n' 'glpat-' 'Hq7Tz2Nw5Kc8Vb3Mx6Pd' > deploy.py
git add deploy.py
git commit -m "Add deploy helper"
./scripts/gate.sh
echo "exit: $?"

Now go back to main, which has no deploy.py. Predict again, then run the gate:

git switch main
./scripts/gate.sh
echo "exit: $?"

git branch -D try-leak
./scripts/gate.sh
echo "exit: $?"
Show the results

On try-leak: the gate fails with WRN leaks found: 1 and exit: 1. The fingerprint covers only the old token, so the new one is caught.

Back on main: the gate still fails. gitleaks git scans every branch in the repository, not only the one you are on.

After deleting the branch: Gate passed. and exit: 0. In CI, a job usually scans only the new commits in a merge request. Lesson 0002 sets that up.

Keep this repository. Lesson 0002 pushes it to GitLab and runs scripts/gate.sh in a pipeline.

5. Explain it out loud

An interview tests whether you can explain the work, not only do it. Answer each question out loud, in under two minutes. Then open the model answer and compare. The interview kit keeps short versions for review.

"How would you add security to a CI/CD pipeline?"

Show a model answer

"I add controls in the order that removes the most risk for the least effort. First, secret scanning, as a pre-commit hook and again in CI, because hooks can be skipped. Second, SCA on every merge request, to catch known CVEs in our dependencies. Third, branch protection with SAST, so nothing merges without a review and a passing pipeline. Later I add IaC and container scanning, SBOMs and signing, and admission policy at deploy time.

Each control is a gate: it exits nonzero on findings above a threshold, and a merge needs a passing pipeline. I fail on new HIGH or CRITICAL findings that have a fix, baseline the old ones with due dates, and keep a documented exception process. I also protect the pipeline itself: short-lived credentials, pinned images, least-privilege jobs, and tools that I verify before I run them. The 2026 Trivy compromise showed why that last part matters."

"A developer pushed an API key and deleted it in the next commit. What do you do?"

Show a model answer

"I treat the key as exposed, because the old commit still holds it, and anyone who cloned the repository has a copy. First, I revoke the key and issue a new one. That is the real fix. Then I check the provider's logs for any use of the old key between the push and the revocation, and I escalate if I find any.

Next, I scan the whole history, for example with gitleaks git, in case there are other leaks. Rewriting history disrupts everyone and does not reach existing clones, so after rotation I usually record a documented exception for that one finding. Finally, I close the gap: a pre-commit hook, a CI gate, and the value moved into a CI variable or a secrets manager."

"Your scanner reports 200 findings. What should fail the build?"

Show a model answer

"Not the count. A gate that fails on everything gets switched off. I fail the merge request on new findings that are HIGH or CRITICAL and have a fix available, because the developer can act on those now. The existing findings go into a baseline, with due dates by severity: for example, 7 days for critical and 30 for high.

I rank that backlog with context, not only the CVSS score: is it being exploited, how likely is an attack, and is the vulnerable code reachable and exposed? If we cannot fix something yet, it gets a documented exception with a reason, an owner, and an expiry date. Then I track the trend: new risk blocked, backlog size, and time to fix."

6. Add a story

Most behavioral questions follow the STAR pattern: Situation, Task, Action, Result. Draft one story for this prompt:

"Tell me about a time you automated a manual check, or caught a problem before it reached production."
  1. Open ~/devsec-lab/star-stories.md, or create it. Keep it out of any Git repository, because it describes real work.
  2. Copy the template from the interview kit.
  3. Use a real example from your work, such as an Ansible, Terraform, Argo CD, or Trivy task.
  4. Spend 60% of the story on what you did. End with a result, and give a number if you can.
