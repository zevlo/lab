SDLC Promotion Across Classified Boundaries

Why this lesson. The postings require “SDLC promotion across classified boundaries.” In an interview, you must narrate the path from one commit on an unclassified network to one deployment on a classified network. Nothing else on your resume is specific to classified work. This is.

The path software walks

Four terms carry this whole lesson. Definitions first.

An environment is one copy of the system reserved for one purpose. The standard three: dev, test, prod. In classified work, each environment sits at a classification level. Dev and test usually sit on unclassified networks — the low side. Prod often sits on classified networks — the high side.

An artifact is the immutable output of one build. A container image digest or a signed package. Immutable means the bits never change after the build finishes. A new build makes a new artifact, never a modified old one.

Promotion is moving an artifact from one environment to the next. The rule is absolute: build once, promote everywhere. You never rebuild per environment. The artifact that passed the gates in test is bit-for-bit the artifact that runs in prod. What was tested is what flies.

Bridge from your floor. You already live this pattern. A GitHub Actions environment with protection rules is a gate. An image digest pinned in a manifest is an immutable artifact. Multi-environment deploys are promotions. Today you only add the words and the boundary.

Gates and approvals

A gate is a check that must pass before promotion. Typical gates: the test suite, SAST scanning, secrets scanning, an oscap STIG scan — your Lesson 0003 one-liner, now placed in the pipeline — and human approval.

The human gate has a name. The change control board (CCB) is the group that approves changes to the baseline. This is control CM-3, Configuration Change Control, in SP 800-53. Before approval, the security impact of the change is analyzed — control CM-4.

Separation of duties: the developer who builds may not be the operator who deploys to prod. Nobody both writes and ships. This is why the CCB exists, and control CM-5 (access restrictions for change) is how it is enforced.

Bridge. A GitHub Actions environment requiring reviewer approval is the same shape: a protected environment, a named approver, an audited yes. CCB is that, with a charter.

The classification boundary

The classification boundary is the line between networks at different classification levels. There is no direct network path across it. No VPN. No shared Git remote. No container registry that both sides pull from.

Data crosses only through an accredited mechanism. A cross-domain solution (CDS) is the accredited mechanism that moves data across the boundary. Two kinds matter in interviews: a guard — two-way transfer, every byte inspected against policy — and a data diode — one-way transfer, no return path. The office that accredits CDS for DoD is the Unified Cross Domain Management Office (UCDMO; its site is unreachable from this network — browse it another time).

The fallback is manual media, under the two-person rule: two cleared people witness every transfer.

Direction matters. Artifacts flow up: built on the low side, promoted to the high side. Vulnerability data often flows down: advisories and scanner feeds shipped from high-side sources to low-side developers. Promotion within one side — dev to test, both unclassified — needs no CDS at all.

Integrity across the boundary

Every crossing needs proof the bits survived it. A checksum proves the content. A signature proves the source. Both are recorded on the low side and re-verified on the high side before deploy. Control SI-7, Software, Firmware, and Information Integrity, demands exactly this. NIST SP 800-218 (the Secure Software Development Framework) makes verification a standing practice, not an event.

Bridge. Same instinct as pinning an image digest in Kubernetes manifests instead of a mutable tag. The digest is the checksum. You have been verifying integrity all along.

From ATO to cATO

Lesson 0001 gave you the point-in-time ATO: a package — SysSP, SAP, SAR, POA&M — reviewed once, signed by the AO. That rhythm cannot ship weekly releases. SP 800-37 already contains the answer: the Monitor step, run as a continuous program (SP 800-137).

A cATO — continuous ATO — attaches the authorization to the pipeline instead of one release package. The deal: the pipeline itself is hardened, every change passes the gates automatically, and continuous monitoring reports to the AO. The RMF Monitor step becomes infrastructure. DoD's cATO guidance lives on the DoD CIO site (bot-blocked; reach it in a browser). The DoD name for this whole apparatus — containerized pipeline plus artifact repository — is the software factory.

Interview traps, collected. “Critical” is not a STIG severity — High, Medium, Low. You never rebuild per environment. Nothing crosses a classification boundary except through the CDS or accredited media. The AO accepts risk; the AO never deploys.
