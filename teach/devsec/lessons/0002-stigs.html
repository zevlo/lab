DevSec Engineering · Lesson 0002

STIGs: How Controls Become Settings

Why this lesson. Your postings require “Linux (RHEL, RockyOS) administration and hardening” and “RMF within classified environments.” The STIG is where those two bullets meet. Every classified RHEL, Windows, and Kubernetes deployment you support will be measured against a STIG.

One win. By the end you can name what a STIG is, read a STIG requirement, place STIGs inside the RMF, and say how a scan runs.

What a STIG is

A STIG — Security Technical Implementation Guide is a published checklist of security requirements for one technology. DISA — the Defense Information Systems Agency — writes and publishes STIGs at cyber.mil/stigs. There is a STIG for RHEL 9, a STIG for Windows Server 2022, a STIG for Kubernetes, a STIG for network gear.

Each line of a STIG is a rule. A rule states one requirement. A rule carries a severity, a check, and a fix. A parent document — the SRG, Security Requirements Guide — holds requirements that apply broadly. A STIG instantiates the SRG for one product.

Where the STIG sits in the RMF

You learned the seven steps in Lesson 0001. The STIG lives in step 4, Implement. A control in SP 800-53 says what must be true. A STIG rule says which setting makes it true. Scan results then feed step 5, Assess. Findings you cannot fix become POA&M entries in step 6. Re-scans feed step 7, Monitor.

Bridge to what you know. You already run checks in GitHub Actions. A SCAP scan is the same pattern: a test that fails the build on a security finding. Same feedback loop, different domain.

Anatomy of a rule

Every STIG rule carries the same fields. Below is one rule, with the shape you will see in every STIG. Values are illustrative. The banner rule is a classic first example.

SV-000000r000000_ruleRHEL-09-000000 · Severity: Medium
Statement
The operating system must display the approved use notification before granting logon access.
Discussion
Without a use notification, users may not know the system is restricted — and consent is unprovable.
Check
sudo grep -i banner /etc/ssh/sshd_config — if the banner path is unset or the file is empty, this is a finding.
Fix
Configure sshd to present the approved banner text before authentication.
CCI
CCI-000048 — maps to control AC-8, System Use Notification, in SP 800-53.

The CCI — Control Correlation Identifier is the bridge. One CCI maps one STIG rule to one 800-53 control. When an assessor asks “which control does this satisfy,” the CCI is your answer.

Severity

SeverityLegacy nameMeans
HighCAT ICatastrophic. Fix immediately, or do not operate.
MediumCAT IISerious. Fix on a schedule. Most rules live here.
LowCAT IIIMinor. Fix when convenient, or document an exception.

You will hear both scales in interviews. Know both. Speak in High/Medium/Low; translate CAT I/II/III when asked.

How a STIG is applied

The workflow has five moves:

#MoveHow
1ObtainDownload the STIG package from cyber.mil/stigs. The package holds XML (machine-readable) and a checklist (readable).
2ReadOpen the checklist in DISA's STIG Viewer tool, published on the same site. The community mirror stigviewer.com works in a browser — convenience only, never a citation.
3CheckScan with OpenSCAP, or check by hand where automation is absent.
4FixApply the fix procedure — manually, scripted, or through Ansible. Re-scan to verify.
5DocumentRecord results. Rules that cannot apply or cannot be fixed become exceptions and POA&M entries.

The scanner: OpenSCAP on Rocky

Rocky Linux ships the SCAP Security Guide — the machine-readable STIG content maintained by the ComplianceAsCode project. The oscap tool evaluates it. The Red Hat security hardening guide documents the same commands for RHEL.

# install scanner and content
dnf install -y openscap-scanner scap-security-guide

# list available profiles in the content
oscap info /usr/share/xml/scap/ssg/content/ssg-rocky9-ds.xml

# scan against the DISA STIG profile
oscap xccdf eval \
  --profile xccdf_org.ssgproject.content_profile_stig \
  --results results.xml --report report.html \
  /usr/share/xml/scap/ssg/content/ssg-rocky9-ds.xml

Open report.html. Every rule shows pass or fail. The same content can generate Ansible remediations — that is your Terraform instinct speaking: infrastructure declared, not clicked.

Say it in an interview

A STIG is the concrete settings layer of the RMF: the control says what must be true in 800-53, and the STIG rule says which setting makes it true.
I would run oscap as a pipeline gate: fail the build on High findings, and route the rest to the POA&M with owners and dates.
Primary source. Browse cyber.mil/stigs. Download the RHEL 9 STIG, Volume 1. Open it in STIG Viewer. Read ten rules and note the repeated shape: statement, check, fix, CCI. Then skim the Red Hat security hardening guide chapter on compliance scanning.
