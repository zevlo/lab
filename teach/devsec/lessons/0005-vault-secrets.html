The problem

A secret is sensitive information an attacker needs and an application uses: a password, an API key, an encryption key, a certificate. Vault's own definition adds the shape of the problem: secrets are “sensitive, discrete pieces of information.” They are small, numerous, and scattered.

Without a secrets manager, secrets live in environment variables, config files, and CI variables. Each copy is one more place to leak from. Each copy lives forever. No log records who read one.

Vault is HashiCorp's server for secrets. One definition, used everywhere in this workspace: Vault stores secrets, generates credentials on demand, performs encryption, and audits every request. Its own words: “centralized, well-audited privileged access and secret management.”

One request, four steps

Everything in Vault hangs off one flow, documented by HashiCorp:

StepNameWhat happens
1AuthenticateThe client proves an identity to an auth method: Kubernetes service account token, LDAP, AppRole for machines.
2TokenVault issues a token carrying the client's policies. The token has a lifetime.
3RequestThe client reads or writes a path, like database/creds/app-reader. All access is path-based.
4AuditEvery request is logged, granted or denied. An audit device writes the log.

An auth method verifies identity. Vault delegates the check — to LDAP, to the Kubernetes API — and keeps no copy of the directory. A policy grants capabilities on paths. Policies are deny by default: an empty policy grants nothing. This is SP 800-53 control AC-6, Least Privilege, expressed as configuration.

path "secret/data/payments/*" {
  capabilities = ["read"]
}
path "secret/data/payments/admin" {
  capabilities = ["deny"]   # explicit deny beats any wider grant
}

Bridge from your floor. You already authenticate machines without long-lived keys: GitHub Actions OIDC to AWS. Same shape — a platform vouches for a workload, no stored password. Vault's Kubernetes auth does this with the pod's service account token.

Static secrets, dynamic secrets

A static secret is one a human writes and later replaces. The KV secrets engine stores static secrets as key-value pairs, with version history in v2. A static secret has no expiry.

A dynamic secret is one Vault generates on request, for one caller, for a limited time. The database engine creates a real database username and password per request. Every dynamic secret carries a lease: metadata with a time to live (TTL). Per the lease model: Vault promises validity for the TTL; when the lease expires, Vault revokes the secret automatically; a revoke command kills it immediately — the database account is disabled the moment the lease is revoked.

Revocation scales by prefix: vault lease revoke -prefix database/ kills every credential the engine issued. That command is your answer to “a credential leaked.” This is control IA-5, Authenticator Management, automated.

Bridge. Your env-var credentials today have no TTL and no kill switch. Dynamic secrets turn “rotate the password this quarter” into “every password is minutes old.”

Sealed, unsealed, and the key chain

A Vault server starts sealed. Sealed, it can reach its storage but cannot decrypt anything in it — the barrier is closed. The chain: an encryption key protects the data; the root key protects the encryption key; the unseal key protects the root key.

Vault never hands one person the unseal key. It splits the key with Shamir's Secret Sharing into shares — say five — and a threshold — say three — must be presented, in any order, to unseal. vault operator init mints the shares once. A restart seals the server again; the threshold must be presented again.

On the high side, this maps to the two-person rule from Lesson 0004. No single cleared person holds enough shares to unseal Vault alone. Splitting the shares across roles is separation of duties, applied to a key. Auto-unseal — delegating to an HSM or cloud KMS — exists for operations; a classified environment often prefers Shamir precisely because it keeps humans in the loop.

Vault at the boundary

Lesson 0004: artifacts flow up through the CDS. Secrets do not flow at all. Each side runs its own Vault. The low-side Vault holds dev and test secrets. The high-side Vault holds prod secrets. A high-side secret never crosses the boundary, because nothing on the low side needs it. What crosses is the artifact; the secret is fetched, on its own side, by the workload that earned it with its identity.

This is why interviewers pair the two bullets: promotion solves delivery, Vault solves delivery of the one thing that must never be delivered.

Vault on Kubernetes

You run Kubernetes; the postings mention it. Vault's Kubernetes integrations consume secrets without code changes:

IntegrationMechanism
Agent InjectorA webhook edits the pod spec; an injected agent authenticates with the service account and writes secrets to a file the pod mounts.
Secrets Store CSIA CSI driver mounts secrets as a volume at pod start.
Vault Secrets OperatorA controller syncs Vault secrets into native Kubernetes Secret objects.

A Kubernetes Secret is base64 in etcd. Base64 is encoding, not encryption. No lease, no per-path policy, no read audit. Vault adds all three. The comparison page names the trade-offs.

Interview traps, collected. The root token is revoked after setup — policies do the daily work. The KV engine issues no leases; only dynamic secrets expire. A VPN is not an answer to anything on the boundary. And “we encrypt Kubernetes Secrets with base64” is a sentence you correct, not repeat.
