DevSecOps Glossary

Reference — the working vocabulary for this workspace. Each lesson adds the terms it introduces.

Each entry gives the term to use, a short definition, and the words to avoid. Terms are grouped by where you meet them: the pipeline, the scanners, and the vulnerabilities that scanners report.

The pipeline

Security gate
A pipeline step that runs a security check and fails the pipeline when the check finds risk above an agreed limit. It signals through its exit code: 0 passes, and any other number fails. Avoid: "security check" when you mean a blocking step. A check can report problems without blocking anything. [OWASP] · [lesson 0001]
Shift left
Moving security feedback as close as possible to the moment code is written, when problems are cheapest to fix. Mature teams also keep checking later, through build, deploy, and runtime. OWASP calls this "shift everywhere". Avoid: reading it as "check only early". Later checks still matter. [OWASP]
Baseline
The set of findings that existed before a gate was turned on. The gate fails only on new findings, so each team answers for the risk it adds. Old findings are still tracked and fixed over time. Avoid: "allowlist". An allowlist accepts a finding for good. A baseline is debt that you pay down. [OWASP]
Exception
A recorded decision to let one specific finding pass a gate, with the reason written down. Gitleaks stores exceptions as fingerprints in .gitleaksignore. Trivy stores vulnerability IDs in .trivyignore. Avoid: "false positive" as a synonym. An exception can cover a real finding whose risk is gone, such as a secret that was already rotated. [Gitleaks] · [Trivy]

Scanning

Secret scanning
Searching code and its Git history for credentials, such as tokens, passwords, and private keys. Scan every commit, not only the current files, because Git keeps every old version. Avoid: "credential scanning". GitLab calls this feature secret detection. [Gitleaks] · [GitLab]
Secret rotation
Replacing a credential with a new one and revoking the old one, so the leaked value stops working. After a leak, rotation is the fix. Deleting the secret from the code is not, because the old value still works and stays in Git history. Avoid: "removing the secret" as the response to a leak. [GitLab]
SCA (software composition analysis)
Scanning the third-party packages that a project depends on. The scanner matches each package version against databases of known vulnerabilities and licenses. SCA checks code you did not write. Avoid: "dependency scanning" outside GitLab. That is the name of GitLab's paid SCA feature. [OWASP]
SAST (static application security testing)
Analyzing your own source code, without running it, for insecure patterns. An example is an SQL query built by joining strings. SAST checks code you did write. Avoid: "linting" as a synonym. A linter looks for style problems and bugs. SAST looks for security flaws. [OWASP] · [GitLab]
SBOM (software bill of materials)
A machine-readable list of the components in a piece of software, with their versions and producers. Common formats are CycloneDX and SPDX. When a new CVE appears, an SBOM answers "which of our releases contain it?" Avoid: "dependency list". An SBOM also covers indirect components and records who made each one. [CISA 2026]

Vulnerabilities

CVE (Common Vulnerabilities and Exposures)
A unique ID and record for one publicly disclosed vulnerability, such as CVE-2020-14343. Scanners report findings by CVE ID, so people and tools know they mean the same issue. Avoid: "CVE score". The CVE Program does not assign severity. CVSS does. [CVE Program]
CVSS (Common Vulnerability Scoring System)
A score from 0.0 to 10.0 for how severe a vulnerability is. The ratings are Low (0.1–3.9), Medium (4.0–6.9), High (7.0–8.9), and Critical (9.0–10.0). Version 4.0 is current. Trivy takes its severity label from the advisory source first, and falls back to the CVSS score. Avoid: "risk score". CVSS measures severity, not the risk to your system. Lesson 0004 adds exploit likelihood and exposure. [FIRST] · [Trivy]
Severity threshold
The lowest severity that fails a gate. For example, --severity HIGH,CRITICAL --exit-code 1 makes Trivy fail only on HIGH or CRITICAL findings. Lower findings are still tracked, but they do not block a merge. Avoid: "risk threshold". Severity is one input to risk, not the whole of it. [Trivy]
