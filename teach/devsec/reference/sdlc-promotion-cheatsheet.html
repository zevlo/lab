SDLC Promotion Cheat Sheet

Companion to Lesson 0004. Sources: NIST SP 800-218 (SSDF), NIST SP 800-53 Rev. 5 (browse in the CPRT catalog), NIST SP 800-37 Rev. 2.

What is what

TermDefinition
SDLCSoftware development life cycle. The path from a code change to running software.
EnvironmentOne copy of the system reserved for one purpose: dev, test, prod. Each sits at a classification level.
ArtifactThe immutable output of one build. A container image digest or a signed package.
PromotionMoving an artifact to the next environment. Build once, promote everywhere. Never rebuild per environment.
GateA check that must pass before promotion: tests, SAST, oscap STIG scan, human approval.
CCBChange control board. The group that approves changes to the baseline (control CM-3).
Separation of dutiesThe developer builds. Operations deploys. Nobody both writes and ships.
Classification boundaryThe line between networks at different classification levels. Low side = unclassified. High side = classified.
CDSCross-domain solution. The accredited mechanism that moves data across the boundary. Guard = two-way, inspected. Data diode = one-way.
Two-person ruleTwo cleared people witness any manual media transfer across the boundary.
Checksum / signatureProof the bits survived the crossing unchanged (control SI-7). Verified on both sides.
cATOContinuous ATO. Authorization attached to a monitored pipeline instead of one release package.
Software factoryThe DoD term for the containerized pipeline plus artifact repository where this all runs.

The promotion flow

Side#StepWhat happens
Low (unclassified)1BuildOne artifact built in dev; digest recorded
2GateTests, SAST, oscap STIG scan; a failure blocks promotion
3SignArtifact signed; checksum recorded
4TestSame artifact promoted to the test environment
5ApproveCCB approves the release
Boundary6TransferThrough the CDS (guard or data diode), or two-person media
High (classified)7Verify, deployChecksum re-verified; operations deploys — not the developer
8MonitorContinuous monitoring feeds the cATO

Artifacts flow up (dev on the low side → prod on the high side). Vulnerability data often flows down (advisories, feeds). Promotion within one side needs no CDS.

Interview traps

If you hearThe truth
“We rebuild in prod”Build once, promote the same bits. Rebuilds destroy the tested-bits guarantee.
“A critical STIG finding”STIG severities are High, Medium, Low. “Critical” is not one.
“A VPN across the boundary”Only the CDS or accredited media crosses a classification boundary.
“The AO approved the deploy”The AO accepts residual risk. Operations deploys.
“cATO means no authorization”Authorization is continuous, attached to a monitored pipeline.

Interview one-liners

We build once, gate hard — scan, test, review — then promote the same signed artifact through the accredited CDS to the high side.
What was tested is what flies: checksums verified on both sides of the boundary.
Separation of duties: I build it, operations ships it, the AO owns the risk.
A cATO works when the pipeline itself is hardened and continuously monitored — the RMF Monitor step turned into infrastructure.
