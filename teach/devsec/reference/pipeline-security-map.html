Pipeline Security Map

Reference — where each security control runs, the question it answers, and when it should block a change.

Key message. Add controls in order of risk reduction per unit of effort. Start with secret scanning, dependency scanning (SCA), and branch protection with SAST. Make each control a gate that fails on new, high-risk findings, not on the total count.

Add controls in this order

OWASP recommends this order, and says to start with controls 1–3. [OWASP DevSecOps Guideline]

  1. Secret scanning (pre-commit and CI). It stops the most common and damaging pipeline leak, with almost no false positives.
  2. SCA in CI. It finds known CVEs in dependencies, which are often the largest immediate risk.
  3. Branch protection and SAST in the merge request. It gates new code where developers can fix it at the lowest cost.
  4. IaC scanning. It catches cloud misconfigurations before anything is provisioned.
  5. Container scanning. It stops vulnerable base images from reaching production.
  6. DAST and IAST. They test the running application, so they need a test environment.
  7. SBOM and signing. They establish supply chain trust and meet new regulatory requirements.

The gate contract

  • A scanner reports its result through its exit code. 0 means pass. Any other number means fail. CI marks the job as failed on a nonzero exit code and stops the pipeline. [OWASP]
  • Some scanners print findings and still exit 0. Trivy does this unless you pass --exit-code 1. Always test that your gate can fail. [Trivy]
  • Gitleaks exits 0 when it finds no leaks, and 1 when it finds leaks or hits an error. [Gitleaks]
  • Save a machine-readable report as well, in SARIF, JSON, or CycloneDX, so that dashboards and ticket systems can use the results. [OWASP]

Gate policy: block risk, not noise

A gate that blocks every build on every finding loses developers' trust. OWASP gives these rules. [OWASP]

  • Gate on risk (severity, exploitability, and reachability), not on the raw count.
  • Baseline the existing findings, so each team answers only for the new risk it adds.
  • Show results where developers already work, such as a merge request comment, not only in a CI log.
  • Keep a documented exception process, so that teams do not switch gates off as a workaround.
  • Track everything else with due dates. OWASP's example: critical CVEs within 7 days, high within 30.

Protect the pipeline itself

Runners, registries, plugins, and long-lived tokens are targets too. [OWASP]

  • Use short-lived OIDC credentials instead of long-lived cloud keys stored as CI secrets.
  • Pin third-party CI components and container images to immutable SHA digests, not to tags that can move.
  • Give each job only the permissions it needs.
  • Run jobs on short-lived, isolated runners, and limit their network access.
  • Treat updates to third-party plugins and tools as supply chain risk. Verify what you download.
Why this matters. In March 2026, attackers published a malicious Trivy release (v0.69.4) and malicious Docker Hub images (v0.69.5 and v0.69.6). They also moved 76 of the 77 version tags of the trivy-action GitHub Action to malicious commits. Every pipeline that referenced the action by tag ran the attacker's code on its next run. A pin to a commit SHA does not move when a tag moves. Use Trivy v0.74.0 or later. [Trivy advisory] · [Microsoft]
